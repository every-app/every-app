> Internal notes for tracking the prototype as it grows — not polished user docs. Verified against code on 2026-10-13.

**Deployment in one sentence:** Cloudflare's own CLI, `cf`, does everything in the Cloudflare account with your Cloudflare login; the `eak_` deploy token registers apps with the gateway's registry, which names their Workers and resources; and binding an app is a redeploy of the live gateway release with the registry's full list of apps.

Two independent credentials — neither substitutes for the other:

| Credential                                                      | Lives                                                                            | Authorizes                                              |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Cloudflare login (`cf auth login`) or `CLOUDFLARE_API_TOKEN`    | cf's own encrypted credential store, or the environment (the CLI never reads it) | D1/KV, Worker uploads, D1 queries and migrations, zones |
| `eak_` deploy token (from admin UI, stored by `everyapp login`) | `~/.everyapp/credentials.json` (0600)                                            | the gateway's `/api/deploy/*` registry endpoints        |

All `cf` calls go through `packages/cli/src/lib/cf`: the CLI's pinned `cf` (or the app's own for local commands), run with this Node and with this Node first on its PATH (cf starts `pnpm vite …`, which would otherwise run on whatever `node` a directory's nvm or volta pin finds), account-plane calls in an empty directory with `CLOUDFLARE_ACCOUNT_ID` set, SQL in private body files (`cf d1 query --body @file`), secrets only in `cf deploy --secrets-file` (a 0600 temp file, removed afterwards).

cf runs the first `cloudflare.config.ts` it finds in its working directory or any parent, up to `/`, even for API commands. So the CLI never runs it in the shared temp directory, where any local user could plant one: the empty directory (`~/.everyapp/cf/neutral`) and every temp file or tree cf reads (`~/.everyapp/cf/tmp`, including the patched gateway release it deploys from) are 0700 directories the CLI owns, checked with `lstat` and recreated when they aren't. The CLI also refuses to run when a directory above them is writable by another user or already holds a `cloudflare.config.ts`.

Piped `cf` calls run in their own process groups, so Ctrl+C reaches only the CLI. On SIGINT or SIGTERM it forwards the signal to them, waits for them to exit, removes its temp files (secrets files, release copies) and `.everyapp/deploy.json`, frees any deploy lease it holds, and exits with 130 (143 for SIGTERM). A second Ctrl+C exits at once.

## `everyapp setup`

A resumable state machine over the commands below (`commands/setup/runSetup.ts`); each step looks before it acts, so a re-run resumes, and does nothing once everything is there: toolchain (pnpm for the starter) → `cf auth whoami`, then `cf auth login` (inherited at a terminal; piped `--no-browser` under `--json`, its link and code re-emitted as a waited-for `action_required`) → account → Workers Paid (`cf accounts subscriptions get`; a warning, never a stop) → domain (`--domain`, the install row's, or a zone picked at the terminal; none: `action_required add_domain`) → `gateway deploy`/`upgrade` (skipped when the install runs this release or a newer one) → owner link (shown at a terminal or in the `--json` events; in CI only with `--printSetupLink`, else `action_required claim_owner` without it) → automatic login → starter (the template bundled in the npm package, copied to `./simple-todo` as app `simple-todo`, then `app deploy`).

**Automatic login.** The setup link is minted with a second secret, `ecs_…`, that only the CLI keeps (`~/.everyapp/pending-claims/<host>.json`, 0600): its SHA-256 goes into `owner_setup_tokens.cli_secret_hash` with the link's. The CLI polls `POST /api/setup/deploy-token {cliSecret}` every 2 s for 10 minutes: 202 until the link is claimed, then 200 with an `eak_` deploy token for the owner's organization and the email of whoever claimed the link (the CLI prints `Logged in to … as <email> (owner of <organization>)`, so the operator can tell it was them), issued once (guarded `deploy_token_issued_at`) within 30 minutes of the claim, then 404 for everything (the link's own `est_` secret included). Whoever sees the link can't do the same. `everyapp login --resume` finishes an interrupted poll. A resumed setup (or `login --resume`) asks once before it shows the link it kept, and on a 404 with no owner yet (the link expired, or a newer one replaced it) setup mints a new one; a 404 during the wait stops it with `claim_owner` instead, leaving the newer link to whoever has it.

## `everyapp gateway deploy` / `upgrade` / `reconcile`

The gateway ships prebuilt inside the npm package (`gateway/every-app-gateway-release.tar.gz`, built by `apps/every-app-gateway/scripts/build-release.ts`): the production Build Output from `cf build`, the drizzle migrations, and a `release.json` with the toolchain versions, the migration journal and a SHA-256 of the files, which the CLI checks. Nothing is installed or built at deploy time.

1. `cf auth whoami`; pick the account (flag, `CLOUDFLARE_ACCOUNT_ID`, the remembered install, the only one). Find the zone for `--domain`: the longest of the hostname and its parents that is a zone in the account (`cf zones list --name` for each). That zone must be active: a pending one (nameservers not pointed at Cloudflare yet) is refused with `ZONE_NOT_ACTIVE`, never passed over for an active parent zone. A new install serves at `--domain`, with `APP_BASE_DOMAIN` the same, and apps one label below it; an install keeps the host and routing its row records. A database drizzle-kit migrated with no install row (wrangler-era) is refused until `gateway adopt`.
2. Get-or-create by name: D1 `every-app-gateway`, KV `every-app-gateway-OAUTH_KV`, KV `every-app-gateway-deploy` (the release cache). The old `every-app-gateway` KV namespace is no longer bound.
3. Take the `gateway` lease: a row in the gateway's own D1 (`_everyapp_deploy_lease`, created by the CLI, 10-minute TTL with a heartbeat).
4. Check what could stop the upload (the release patches into a valid Build Output; the gateway serving is the version the install row recorded, or a person at the terminal agrees to replace it), then bookmark the database (`cf d1 time-travel get-bookmark`), carry drizzle-kit's `__drizzle_migrations` history over to cf's `d1_migrations` once, then `cf d1 migrations apply`. **Migrations run before the code**, and gateway migrations must be expand-only (a test refuses drops and renames).
5. Cache the release tarball in the deploy KV under `release/<sha256>`.
6. Read the desired bindings from the registry: apps that are `binding`, `active` or `disabled`, whose Worker name follows the naming rule and whose Worker exists (binding a missing one would fail the whole deploy, so a stale row is skipped with a warning).
7. Patch a private copy of the Build Output: D1/KV ids, `APP__<worker>` service bindings, `EVERYAPP_RELEASE`, source maps, and the routing: per-app Custom Domains (`domains` = the gateway host, then every bound app's host one label below `APP_BASE_DOMAIN`, the full list each time since cf replaces the set; `APP_BASE_DOMAIN` set; no route), or for an install still on its wildcard route its host as the one Custom Domain plus the `*.<host>/*` route, with `APP_BASE_DOMAIN` removed. Validate with `@cloudflare/config`'s output schema. Before an upload that adds a hostname (and before migrating, for the hosts a migrated registry lists): no A/AAAA/CNAME/NS record at it (`cf dns records list -z … --name-exact`; `--force-dns` overrides), and a warning when it has none but a `*.<parent>` wildcard answers it, CAA over DNS-over-HTTPS from the closest name that exists up to the top-level domain (RFC 8659's climb, past the zone apex too), allowing only the CAs Cloudflare issues Advanced Certificates from (Let's Encrypt, Google Trust Services, SSL.com; not Sectigo, which only issues its backup certificates), and only warning when they are allowed with `accounturi` or `validationmethods`, and at most 100 Custom Domains in the zone. Unattended cf would replace a record, or take a hostname from another Worker, without asking.
8. `cf deploy --prebuilt --mode production`; a first deploy sends the generated secrets (`GATEWAY_URL`, `BETTER_AUTH_SECRET`, the RSA-2048 identity keypair, `GATEWAY_DEPLOYMENT_MODE`, `CLOUDFLARE_ACCOUNT_ID`) in the secrets file, so the first version has them.
9. Record the install in `_everyapp_install` (gateway D1) and `~/.everyapp/installs.json` right after the upload: the version, its release and bindings, and the `routing` and domains once cf has published them. cf puts the version live first and publishes the Custom Domains after it; when it stops part-way (a move from another Worker declined at its prompt, the zone's limit, an API error, Ctrl+C) only the version is recorded, so the next deploy checks those hostnames again and a switch to per-app domains runs again. Then poll `/api/deploy/status` until it reports the new release and a digest of the expected bindings. If apps registered meanwhile, deploy again (up to three times). Once the lease is free, wait up to 10 minutes for each new hostname's certificate (a warning, never a failure).
10. If this machine has a deploy token for the gateway, **sync each active app's agent tools** in the token's organization: one `/api/deploy/apps/<appId>/tools/sync` request per app (a request may make at most 32 Worker invocations). Best effort: it never fails the deploy, and an app it misses syncs on its next deploy or its first `/mcp` request.
11. If D1 has no owner membership, mint a one-time setup link (the SHA-256 of a fresh `est_` secret into `owner_setup_tokens`, earlier unused links expired, in one `cf d1 query`). An unattended deploy (CI, piped output) mints nothing and only says to run `everyapp gateway claim-link`, unless `--printSetupLink` is passed.

`reconcile` skips 2, 4, 5, 10 and 11: it redeploys the release that is live (from the KV cache, checked against its SHA-256; the bundled release only if it is the same), so binding an app never upgrades or downgrades the gateway. It picks that release after taking the lease, when no upgrade can be running: the one the install record names, when the Worker serves the version the record names (`cf workers deployments list`). Otherwise something deployed since: the release the live `/api/deploy/status` reports is reconciled when it is newer and cached (an upgrade stopped before recording itself), but only when the status answers from the very version Cloudflare says serves (an edge that lags a deploy still answers from the version before). Anything else (older, unknown, no answer from that version) stops unattended or asks at a terminal, so a reconcile never puts an older release back unless a person says so. Releases are ordered by their newest migration, then their build time, not by the gateway's version, which builds share; `deploy` and `upgrade` refuse an older one under the lease too, against the install record and, when the Worker serves a version the record doesn't name, against the live release whenever the live gateway can say which it is, unless `--allow-downgrade`. When the account has no workers.dev subdomain, or the Worker serves a version everyapp didn't record (see below), the command stops with `action_required` (exit 2) and says what to do.

## `everyapp app create`

Not scaffold-only — it **production-deploys as part of create**. Clone template (`templates/simple-todo` from the monorepo) → rewrite ids/deps → run the full `deployApp()` pipeline below → local setup (`.env.local`, Worker types, local migrations; failures warn, don't abort) → `git init` + first commit.

## `everyapp app deploy` — the interesting one

`everyapp.config.ts` is the source of truth; the app's `cloudflare.config.ts` turns it into the Worker with `everyAppWorker()` from `@every-app/sdk/cloudflare`, reading deploy-time values from a short-lived, gitignored `.everyapp/deploy.json` that the CLI writes for the production build (and the helper throws without it, so a bare `cf deploy` can't ship an identity-less Worker).

```
 laptop (cf login)                      gateway (eak_ token)
──────────────────────                 ───────────────────────
 1 whoami: org, account ◄────────────── /api/deploy/whoami
 2 register             ─────────────► /api/deploy/register
                                        → names: every-<orgKey>-<appId>, its
                                          D1/KV, <appId>[-<orgKey>].<base>
                                          (<appId>-<orgSlug>.<host> on a
                                          wildcard-route install);
                                          new apps start `pending` (unbound)
   a new hostname is checked now (DNS, CAA, zone room), before anything else
 3 app lease, then: its Worker, D1 and KV, used only if recorded as the
   app's own (else created and recorded)
 4 cf build with deploy.json → policy check of the built Worker → source maps
   → its Workflows' names must be free or already its own
   → unattended, the serving version must be the one everyapp recorded
 5 bookmark + backfill + cf d1 migrations apply
 6 cf deploy --prebuilt — PRIVATE worker, secrets file: GATEWAY_URL,
   EVERY_APP_ORG_ID; cf creates or updates its Workflows
 7 deployed             ─────────────► /api/deploy/apps/:id/deployed
                                        → manifest snapshot, version;
                                          pending → binding
 8 reconcile the gateway, only if it doesn't bind the Worker or publish
   its hostname yet
 9 activate (retried)   ─────────────► /api/deploy/apps/:id/activate
                                        → probes APP__<worker>; binding → active
10 sync agent tools     ─────────────► /api/deploy/apps/:id/tools/sync
                                        → gateway fetches the defineTools()
                                          catalog over the binding and
                                          snapshots it in D1 (503 while the
                                          binding rolls out: retried ≤ 60 s)
11 wait for a new hostname's certificate; the app is live at its host
```

Details worth remembering:

- **Identity is baked in at deploy**: `EVERYAPP_IDENTITY_PUBLIC_KEYS` + `EVERYAPP_IDENTITY_ISSUER` + `EVERYAPP_APP_ID` go into the worker config; there's no runtime key fetch.
- **Migrations before code** for apps and the gateway alike: a failed migration leaves the version that is serving untouched. And nothing is migrated until everything else that could stop the upload has passed: the build and policy check (apps), the patch of the release (gateway), and, unattended, cf's strict mode. cf won't replace a Worker last changed in the dashboard or through the API without a person confirming, and offers no way to ask first, so a deploy goes on only when the version serving is one everyapp recorded uploading (the registry's `version_id`, the app's Worker record, the install row's `live_version_id`, each written right after its upload). Otherwise it stops unattended with `rerun_interactive` before touching the database, and at a terminal asks before migrating (cf may ask again before uploading); a Worker deployed before everyapp used cf needs that one deploy from a terminal. A deploy stopped with Ctrl+C while cf uploads still records what cf got live, on its way out.
- **The policy check** refuses a built Worker that has another name, workers.dev or preview URLs, domains, any trigger but cron schedules (routes, queue consumers, email), missing identity keys, `EVERYAPP_DEV`, a service binding other than the gateway's `AppGateway`, another Worker's Durable Object or Workflow, D1/KV ids the deploy didn't provision, a bucket or Workflow not named after the Worker, or any binding type outside text, JSON, secret, version metadata, assets, D1, KV, R2, Durable Object, Workflow and the gateway binding (queues, Hyperdrive, dispatch namespaces, private networks, secrets stores, rate limits, Workers AI and the rest reach things outside the app). Its `exports` may delete a Durable Object class only when the deploy dropped it with `--allow-delete-durable-object-data`, and never transfer one's data to or from another Worker.
- Only **one D1 binding is migrated** per deploy (`migrations.binding` or the first one); `drizzle` (default) and `d1-sql` both run `cf d1 migrations apply`.
- **Names**: apps registered before org-scoped names (`legacy_names`) keep `every-<appId>`; names starting with `every-app-gateway` are refused. A binding other than `DB`/`KV` gets `every-<orgKey>-<appId>--<binding>` (legacy apps: `every-<appId>-<binding>`); since new app ids can't contain `--`, one app's resource can never be named like another app's. A Workflow is always `<worker>--<binding>`, lowercased with `_` as `-` (`RANK_CHECK` → `every-acme-seo--rank-check`). Removing a Durable Object class needs `--allow-delete-durable-object-data`, and removing a Workflow (or renaming its binding) `--allow-delete-workflows`, with which the deploy deletes it and its instances once the new version is live.
- **Ownership**: a name proves nothing, so the CLI records each Worker, database and namespace an app creates in `_everyapp_app_resources` (gateway D1), before creating it. A deploy uses an existing resource only when it is recorded as the app's, and refuses anything else under the app's names on every attempt, including a retry after a failed first deploy. A legacy app's first deploy with this CLI records the Worker, `DB`/`KV` and the bindings its last manifest declared, never a resource named after another app's Worker (`notes`' `every-notes-archive` is app `notes-archive`'s database). Workflows aren't recorded: Cloudflare says which Worker runs each one, and cf's deploy would hand a Workflow to whichever Worker deploys its name, so a deploy refuses a name another Worker runs before anything is migrated or uploaded, and `everyapp app workflows` touches only a Workflow the app's Worker runs. `app delete --purge` deletes only recorded resources, never one named after another app's Worker (with `--force`, after you type the app id), and the Workflows that run on the app's recorded Worker; its last message lists what it deleted and what it kept.
- A code-only redeploy of a bound app never touches the gateway.
- **The tools sync (step 10) never fails a deploy.** The gateway serves `<app-host>/mcp` from that snapshot; if the sync didn't happen, it syncs on the first `/mcp` request, and a tool call that reports a newer catalog re-syncs it.

## `everyapp dev`

No production gateway involved: the CLI builds a Node **gateway-lite** from `packages/perimeter/src/dev/devGateway.ts` — the _real_ perimeter (CSRF, public routes, header stripping, JWT minting) in front of the app's `cf dev`, with a local RSA keypair (`.everyapp/dev-keys.json`, gitignored, 0600) and an in-memory one-app registry.

|                | Stub mode (default)                             | Mirror mode                                                                      |
| -------------- | ----------------------------------------------- | -------------------------------------------------------------------------------- |
| Identity       | hardcoded `dev-user` / `dev-org` / role `owner` | your real session, resolved by a locally running gateway via `/api/dev/identity` |
| Gateway needed | none                                            | `pnpm dev` (`cf dev`) in `apps/every-app-gateway`                                |
| JWT minting    | gateway-lite, dev keypair, dev `kid`            | same (the real gateway only _resolves_ the session; gateway-lite mints)          |
| Access checks  | n/a                                             | currently always-allow (`hasAppAccess` returns true)                             |

The dev `kid` is accepted by the SDK when `EVERYAPP_DEV` is any non-empty value (or an app opts in with `allowDevIdentities: true`); `/api/dev/identity` hard-404s in production builds, though the route itself still ships. Anonymous behavior is testable via `x-everyapp-dev-anon: 1`.

`http://<appId>.localhost:8787/mcp` is served by a local ToolBus from the app's live `defineTools()` catalog, with the gateway's tool policy. In stub mode an MCP client sends any bearer and acts as the dev user; in mirror mode it sends a personal access token, which the local gateway verifies.

## What does NOT exist (despite appearing in the v2 plan docs)

- **No dispatch namespaces / Workers for Platforms** — `tier: "dispatch"` exists in types and throws in `getAppFetcher()`. Everything is service bindings.
- **No device-code login to the gateway** — `everyapp login` = paste a token an owner created in the admin UI; only `everyapp setup` logs in by itself, once, through its setup link's CLI secret.
- **No domain moves** — an install keeps the host it was installed at; `APP_BASE_DOMAIN` is always that host (the mobile shell scopes its cookie copy to it, and apps find home by dropping their first label).
- **No `everyapp doctor`** — `everyapp gateway status` shows release and binding drift, but nothing repairs it automatically.
- **No hosted-tier tenancy machinery** — no per-tenant resources, KEKs, or egress/outbound worker. (Org scoping — registry rows, Worker and resource names, tokens, access checks — does exist.)
