Every app touches the platform in two places: a one-line server wrapper (`everyApp()`) and a manifest file (`everyapp.config.ts`), plus a short `cloudflare.config.ts` that turns the manifest into the Worker definition. There is no client-side SDK. Your frontend makes normal same-origin `fetch()` calls; the Gateway handles identity before your server ever sees the request.

## `everyApp()` — the server wrapper

Your worker entry exports the app wrapped in `everyApp()`:

```ts
// src/entry.worker.ts
import { everyApp } from "@every-app/sdk/server";

export default everyApp(async (request, env, ctx, user) => {
  // `user` is the verified user (or null on a declared public route)
  return handleRequest(request, user);
});
```

That's the entire auth surface. The wrapper checks that each identity was issued for this app, using the app id the Worker config sets as `EVERYAPP_APP_ID`, so the Worker never imports `everyapp.config.ts` itself. The wrapper verifies the Gateway's signed identity header on every request, fail-closed: no valid identity means a 401 before your code runs. It also wraps anything with a `.fetch` (a Hono app, another worker export) the same way.

<Callout type="warn">
  Never read user identity from headers, cookies, or request bodies yourself.
  The verified user from the SDK is the only trustworthy source. Anything else
  can be spoofed.
</Callout>

## Users & auth in your app

The Gateway handles signup, login, and sessions; there is no client-side auth code in an app — no login page, no token storage. Your frontend calls server functions with plain `fetch()`, and identity arrives server-side. Anywhere you have the request, ask the SDK for the verified user:

```ts
import { getRequest } from "@tanstack/react-start/server";
import { requireEveryAppUser } from "@every-app/sdk/server";
import { env } from "cloudflare:workers";

const user = await requireEveryAppUser(getRequest(), env); // throws a 401 Response if absent
```

Most apps pair this with a tiny middleware that creates a local user row on first visit, so there's somewhere to hang the user's data:

```ts
// src/middleware/ensureUser.ts
export const ensureUserMiddleware = createMiddleware({
  type: "function",
}).server(async ({ next }) => {
  const identityUser = await requireEveryAppUser(getRequest(), env);

  // upsert the local row, keyed by the Gateway's user id
  const user = await db.query.users.findFirst({
    where: eq(users.id, identityUser.id),
  });
  if (!user) {
    await db.insert(users).values({
      id: identityUser.id,
      email: identityUser.email,
    });
  }

  return next({ context: { userId: identityUser.id, user: identityUser } });
});
```

Two rules keep this safe: the user id always comes from the SDK (never from client input), and every user-scoped query filters by that id.

## Agent tools — `defineTools()`

To let AI clients (Claude, Cursor, any MCP client) act in your app, describe the actions with `defineTools()` and pass them to `everyApp()`. Your app never speaks MCP: the Gateway snapshots the tools when you deploy and serves them at `https://<app-host>/mcp`, and each call reaches your handler with the verified user.

```ts
import { defineTools, everyApp, ToolError } from "@every-app/sdk/server";
import { z } from "zod"; // zod >= 4.2, or any Standard JSON Schema validator

export const tools = defineTools({
  list_todos: {
    description: "List the user's todos.",
    risk: "read", // read | write | destructive
    input: z.object({}).strict(),
    handler: async (_input, { user }) => listTodos(user.id),
  },
});

export default everyApp(handler, manifest, { tools });
```

Destructive tools stay hidden from AI clients until approvals exist, and write tools are hidden from read-only tokens. Throw `ToolError` for messages the model may read; any other error is reported only as an internal error with a reference. MCP clients connect with a personal access token; your app's own pages can also call `/mcp` with the user's session (same-origin only).

## `everyapp.config.ts` — the manifest

One file declares everything the platform needs to know about your app. The CLI reads it to provision resources, deploy, and run local dev; the gateway reads it to route requests and decide which routes are public.

```ts
export default {
  id: "todo", // kebab-case; becomes todo.apps.your-domain.dev
  name: "Todos",
  description: "Minimal todo list with real-time sync.",
  resources: {
    d1: ["DB"], // SQL databases, by binding name
    kv: ["KV"], // key-value namespaces
    durableObjects: [{ name: "USER_SYNC", className: "UserSyncDO" }],
  },
  build: "pnpm run build:prod", // optional; replaces `cf build` at deploy
  dev: "pnpm exec vite dev --port $PORT --host 127.0.0.1",
  // optional; replaces `cf dev` in everyapp dev; custom commands read PORT
  install: "pnpm install", // optional; false skips install, omitted auto-detects
  migrations: { engine: "drizzle" },
  // optional; use { engine: "d1-sql", dir: "migrations" }
  // for plain SQL migration files
  public: [], // no public routes — fully private app
} as const;
```

## `cloudflare.config.ts` — the Worker

The Cloudflare CLI (`cf`) and its Vite plugin read the Worker definition from `cloudflare.config.ts` at the app root. In an Every App app it is a few lines that build the Worker from the manifest:

```ts
// cloudflare.config.ts
import { defineConfig } from "cf/config";
import { everyAppWorker } from "@every-app/sdk/cloudflare";
import * as entrypoint from "./src/entry.worker.ts" with { type: "cf-worker" };
import manifest from "./everyapp.config.ts";

export default defineConfig((ctx) => ({
  worker: everyAppWorker({ manifest, entrypoint, ctx }),
}));
```

`everyAppWorker()` always produces a private Worker (no routes, no `workers.dev` URL, no preview URLs) with the manifest's D1 databases, KV namespaces and Durable Objects, logs, traces and Workers Issues turned on, and the identity settings the SDK checks. `cf` infers the Worker's `Env` type from it. In local dev the identity keys come from `.dev.vars`, which `everyapp dev` writes. A production build needs deploy inputs that only `everyapp app deploy` provides, so `cf build` and `cf deploy` refuse to build for production on their own — deploy with `everyapp app deploy`.

To add a binding the manifest doesn't model, spread the result. Don't import anything here that the Worker also imports: in dev, the Vite plugin hides this file's imports from the Worker.

```ts
import { bindings, defineConfig } from "cf/config";
// …the other imports above

export default defineConfig((ctx) => {
  const worker = everyAppWorker({ manifest, entrypoint, ctx });
  return {
    worker: {
      ...worker,
      env: { ...worker.env, IMAGES: bindings.r2({ name: worker.name }) },
    },
  };
});
```

A bucket must be named after the Worker: `worker.name`, or `` `${worker.name}--<suffix>` `` for more than one. The deploy refuses any other R2 bucket, so an app can't bind another app's.

### Public routes

Everything is private unless listed in `public`. Each entry is a narrow, explicit exception:

```ts
public: [
  { path: "/share/*", methods: ["GET"] },   // public share links
  { path: "/health" },
],
```

On a public route, requests skip login and your handler receives `user: null`. The manifest validator rejects anything that would blow the surface open: `/*` and other catch-alls are hard errors, as is anything touching the platform's reserved `/__everyapp` namespace.
