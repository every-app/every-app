Find your error message below. Most failures are safe to fix and re-run — `setup`, `gateway deploy` and `app deploy` are all idempotent, so running them again after fixing the cause picks up where you left off.

## Before anything else

Four things cause most failures. Check them in order:

```bash
node --version          # must be 22.18 or newer
npx cf auth whoami      # must show the account you expect
```

Then confirm your domain is **active** on that Cloudflare account (dashboard → your domain shows "Active", not "Pending Nameserver Update"), that the account is on **Workers Paid**, and that you're running the command from the right directory — `app deploy` must run from inside the app folder, next to `everyapp.config.ts`.

`npx everyapp gateway status` shows what your Gateway runs and whether it serves every app it should.

## Setting up and deploying the Gateway

### "Log in to Cloudflare first"

The CLI uses Cloudflare's own CLI, `cf`, and it isn't logged in. Run it in your terminal:

```bash
npx cf auth login
```

It prints a link and a one-time code (so it works over SSH too); open the link, check the code and approve. Run in a terminal, `everyapp` offers this login itself, and `everyapp setup --json` hands an agent the same link and code. In CI, create an API token at [dash.cloudflare.com/profile/api-tokens](https://dash.cloudflare.com/profile/api-tokens) from the **Edit Cloudflare Workers** template plus **Account → D1 → Edit**, **Zone → Zone → Read** and **Zone → DNS → Read** (and **Zone → SSL and Certificates → Edit** for `app delete` to remove certificates), then export **both**:

```bash
export CLOUDFLARE_API_TOKEN=...
export CLOUDFLARE_ACCOUNT_ID=...
```

### "cf can't authenticate with CLOUDFLARE_API_TOKEN"

The token in your environment is invalid or expired. Recreate it as above, or unset it to use your `cf auth login` session.

### The deploy targets the wrong Cloudflare account

`npx cf auth whoami` lists the accounts your login can use. Pass `--account-id <id>` or set `CLOUDFLARE_ACCOUNT_ID`. After the first deploy the CLI remembers the account.

### "No zone in this Cloudflare account holds …" / "Every App needs a domain on Cloudflare"

No domain in the account you're deploying to holds the address you gave (`apps.your-domain.dev` needs `your-domain.dev`, or `apps.your-domain.dev` itself, as a zone there). Either it was never [added to Cloudflare](https://developers.cloudflare.com/fundamentals/manage-domains/add-site/), or it lives in another account — `npx cf auth whoami` shows which ones you can use.

No domain at all? Buy one in the Cloudflare dashboard: **Domains → Buy a domain** (about $10 a year for a `.com`; it's ready in minutes). Then run `npx everyapp setup` again.

### "The Cloudflare zone … is pending"

Cloudflare doesn't serve DNS for the domain yet: point its nameservers at Cloudflare at your registrar (the dashboard's domain overview shows the two names), wait for it to show **Active**, and re-run. This can take a few hours.

### "Couldn't confirm this account is on Workers Paid"

Every App needs the Workers Paid plan ($5 a month): on the Free plan D1 stops answering for the rest of the day once the account reaches its daily limits, and the Gateway reads D1 on every request. Subscribe under **Workers & Pages → Plans**, then re-run. If the account is on Workers Paid already, the check couldn't read its subscription: go on (at a terminal, answer yes; `--allow-free-plan` skips the check).

### "…already has a DNS record" / "already have DNS records"

The Gateway's address, or a new app's, already has an A, AAAA, CNAME or NS record. Publishing the Gateway there would replace it, and whatever it served (a website, another service), so nothing was deployed. Pick another address, delete the record in the Cloudflare dashboard (your domain → DNS), or, if the record should go, pass `--force-dns`. Mail and TXT records at the same name are fine.

### "… answered now by a wildcard record"

A warning, not a stop: the new address has no DNS record of its own, but a wildcard record above it (`*.apps.your-domain.dev`, say) answers it today. Publishing the address gives it its own record, so that one name stops getting the wildcard's answer, and whatever the wildcard serves keeps every other name. On a Gateway moving off its wildcard route (`gateway use-per-app-domains`) that is the point; otherwise, if something was meant to answer at that name, pick another one.

### "Cloudflare can't issue a certificate for …"

Your domain has CAA records (they say which certificate authorities may issue its certificates), and none of them is one Cloudflare issues these certificates from: Let's Encrypt, Google Trust Services or SSL.com. (Sectigo only issues Cloudflare's backup certificates, so a record for Sectigo alone doesn't do.) Records at a parent domain count too, above your zone as well: the closest name that has any decides. Add one, for example `0 issue "letsencrypt.org"` or `0 issue "pki.goog"`, at the name the message gives, then re-run. `--force-dns` publishes the address anyway, but it gets no certificate until the records allow one.

### "Cloudflare may not get a certificate for …"

A warning, not a stop: your CAA records allow one of Cloudflare's certificate authorities only with `accounturi` (one ACME account) or `validationmethods` (some ways of proving control), and those may not be the account or method Cloudflare uses. If the certificate doesn't arrive (`npx everyapp gateway status` shows it), add a record for one of them without those parameters at the name the message gives, for example `0 issue "letsencrypt.org"`.

### "Can't read …'s DNS records with this Cloudflare login"

The deploy checks that a new address won't replace a DNS record, and the API token in use can't read DNS. Give it **Zone → DNS → Read**, or pass `--force-dns` to publish without checking.

### "This would put … Workers Custom Domains in …"

Cloudflare allows 100 Workers Custom Domains in a zone, the Gateway's own address and other Workers' included. Delete apps you no longer use (`npx everyapp app delete <app-id>`), or set up a second Gateway on another domain.

### "This account already runs a gateway deployed before everyapp used cf"

The account's Gateway was deployed with the wrangler-era CLI. Adopt it as it is (same domain, same app addresses), then upgrade it from a terminal: [Upgrading an existing install](/docs/reference/manage-your-gateway#upgrading-an-existing-install).

### "This gateway was adopted but not upgraded yet"

Run `npx everyapp gateway upgrade` once, from a terminal. Until then the account has no copy of a release everyapp deployed, so nothing can redeploy it.

### "This Cloudflare account has no workers.dev subdomain yet"

Cloudflare wants a workers.dev subdomain on the account before its first Worker upload. Open the link the CLI prints (Workers & Pages → your subdomain), pick one, and run the same command again. Your apps never use it: they stay private behind the Gateway.

### "…is serving a version everyapp didn't record deploying"

The Worker serves a version everyapp didn't record uploading: it was last changed in the Cloudflare dashboard or through the API, deployed before everyapp used `cf` (every app and Gateway deployed with the old CLI, once), or uploaded by a deploy killed before it could record it. `cf` won't replace a Worker changed in the dashboard unattended, and can't be asked first, so the command stops before it migrates anything. Run the same command in a terminal: everyapp asks before it migrates, and `cf` may ask again before it uploads. everyapp records the versions it uploads (also when a deploy is stopped with Ctrl+C, or fails after the upload), so later runs can be unattended again.

### "…was last changed outside everyapp"

`cf` itself refused, at the upload, to replace the Worker unattended: Cloudflare says it was last changed in the dashboard or through the API. If the run migrated a database, it stays migrated. Run the same command in a terminal and confirm `cf`'s prompt.

### "Another deploy holds the gateway lease"

Deploys of the Gateway (and of each app) never overlap. If another deploy is running, wait for it. If it died, its lease expires within 10 minutes, or take it over with `--break-lease`: it shows who holds the lease and asks first (unattended, it also needs `--yes`). A deploy stopped with Ctrl+C frees its lease on the way out.

`app deploy --break-lease` takes over only the app's own lease. When binding a new app waits for the Gateway's lease, its upload is kept: run `app deploy` again once the Gateway deploy finishes. If that deploy died, `npx everyapp gateway reconcile --break-lease` takes the Gateway's lease over and binds the app; then run `app deploy` once more to make it live.

### "Migrating the database failed"

Nothing was uploaded: the Gateway that was serving keeps running. Before migrating, the CLI bookmarked the database and printed the command that restores it (`cf d1 time-travel restore … --force`, in PowerShell syntax on Windows outside Git Bash; `--force` answers cf's own confirmation, which it otherwise declines wherever no one can type). Fix the cause and re-run.

### "cf finished without uploading a new version"

`cf` asked a question in the terminal (a Worker changed in the dashboard, a DNS record or Custom Domain held by something else) and it was answered no, so `cf` exited without deploying. The version that was serving still is. If the run had migrated the database, it stays migrated: run the command again and answer yes, or roll the database back with the restore command printed before the migration.

### The deploy printed DNS instructions

Only a Gateway installed before per-app addresses does this: its apps reach it through one wildcard DNS record, which you add once:

> **your domain → DNS → Add record**: Type **CNAME**, Name **`*`**, Target **your domain**, Proxy **ON** (orange cloud).

Without it the Gateway works but apps don't load. `npx everyapp gateway use-per-app-domains` gives each app its own address instead, which needs no wildcard record.

### "… has no certificate after …" / the address doesn't load yet

**The certificate isn't issued yet.** Every new address (the Gateway's, and each app's) gets its own certificate from Cloudflare, usually within a minute or two and almost always within five. The CLI waits up to ten minutes, then says so and carries on: the address works as soon as the certificate arrives. `npx everyapp gateway status` shows which addresses have theirs. If one never arrives, check your domain's CAA records (above).

**Nameservers haven't propagated.** If your domain shows "Pending Nameserver Update" in the Cloudflare dashboard, Cloudflare doesn't control DNS for it yet and nothing will resolve. This can take a few hours after you change nameservers at your registrar.

### "The live gateway release isn't cached in this account"

`gateway reconcile` redeploys exactly the release your Gateway runs, from a copy the deploy keeps in your account. A Gateway deployed by an older CLI has none: run `npx everyapp gateway upgrade` once.

### "The gateway serves version …, not the … its install record names"

A reconcile (run by `gateway reconcile`, `gateway secret set`, or an app deploy or delete that binds or unbinds an app) redeploys the release your Gateway's install record names, but only while the Gateway serves the version that record names. Here something else was deployed since (a rollback in the dashboard, a deploy by hand), and it isn't a newer release this account caches, so redeploying the recorded one could put an older release back. Nothing has changed. Check `npx everyapp gateway status`, then run the command in a terminal: it asks whether to redeploy the recorded release anyway.

### I lost the setup link, or it expired

A new Gateway has no owner and accepts no sign-ups until someone opens the one-time setup link that `setup` (or `gateway deploy`) showed. Each link works once and expires after 24 hours. Running `npx everyapp setup` again shows the same link while the Gateway still waits on it, and a new one once it doesn't (it expired, or a newer link replaced it). To get a new one yourself, run this on a machine logged in to the Gateway's Cloudflare account:

```bash
npx everyapp gateway claim-link
```

Any earlier unused link stops working. Once the Gateway has an owner, `claim-link` refuses: sign in instead, or ask an owner or admin to invite you.

### "Nobody has finished the setup link yet"

`setup` waits ten minutes for the owner account to be created with the link, then stops (exit 2). The link keeps working: open it, create the account, then run `npx everyapp setup` again, or `npx everyapp login --resume` to only finish logging this terminal in.

### "The setup link stopped working before anyone used it"

A newer link replaced it (`gateway claim-link`, `setup` or `gateway deploy` on another machine: each new link stops earlier unused ones working), or it expired. If someone has the newer link, create the owner account with it. Otherwise run `npx everyapp setup` again for a new link. A `setup` that is waiting doesn't mint one by itself, so it never takes the link away from whoever has the newer one.

### "The setup link's login was used already, or expired"

The terminal that minted a setup link can fetch the owner's first deploy token once, within 30 minutes of the account being created. After that, sign in to your Gateway, create a deploy token under **Admin → Tokens**, and run `npx everyapp login`.

## Deploying an app

### "The gateway is too old for this everyapp"

Upgrade the Gateway first, then deploy the app again:

```bash
npx everyapp gateway upgrade
```

### The CLI asks you to log in

You need a deploy token. `everyapp setup` gets one by itself for the machine that set the Gateway up. On any other machine: on your Gateway, **Admin → Tokens → Deploy token**, copy it (shown once), then:

```bash
npx everyapp login
```

Enter your Gateway URL, then paste the token when prompted. It's stored at `~/.everyapp/credentials.json` with `0600` permissions, scoped per Gateway URL.

### "The gateway runs in Cloudflare account …, which cf can't use"

App deploys run in the Gateway's own Cloudflare account. Log in to that account with `npx cf auth login`.

### "A D1 database / KV namespace / Worker named … already exists"

The Gateway just registered this app, but a resource with the name it assigned already exists in your account, perhaps from another project. Deploying would take it over, so the CLI stops. Delete or rename that resource, then deploy again.

An app registered before organization-scoped names gets `every-<app>-<binding>` for a binding other than `DB` and `KV`, which can be another app's Worker name, and so that app's database (`notes`' `ARCHIVE` and the app `notes-archive`). The CLI never uses such a resource for the first app (`…is app notes-archive's`): give the binding another name, so the app gets its own.

### "… is a … binding, which Every App apps can't use"

An app may bind only text, JSON and secret values, version metadata, its assets, D1, KV, R2 (a bucket named after its Worker), its own Durable Objects and the Gateway's `EVERY_APP_GATEWAY`. Other types (Workers AI, `send_email`, queues, Hyperdrive, workflows, rate limits, …) reach things outside the app, or capabilities the Gateway brokers, so the deploy stops before it changes anything; there is no flag to allow them. For an AI model, call it through the Gateway's AI proxy (`everyapp gateway secret set OPENAI_API_KEY`). Apps deployed with the wrangler-era CLI could carry such bindings: remove them from `cloudflare.config.ts` before their first deploy with this CLI.

### "…no longer declares the Durable Object class …"

Removing a Durable Object class from `everyapp.config.ts` deletes its data for good. If that's what you want, deploy with `--allow-delete-durable-object-data`.

### The app's address doesn't resolve yet

A new app's address is a Custom Domain the deploy creates, with its own DNS record and certificate: give it a few minutes (`npx everyapp gateway status` shows its certificate). To check the record yourself:

```bash
dig +short todo.apps.your-domain.dev
```

You want an answer, not an empty response. On a Gateway installed before per-app addresses, the deploy warns when `<app>-<org>.your-domain.dev` doesn't resolve: its wildcard DNS record is missing (see above).

### "Not inside an Every App project" / "No everyapp.config.ts found"

`app deploy` must run from inside the app folder, next to `everyapp.config.ts`. `cd` into the app directory and re-run.

### The app deployed but shows 401 or a blank screen

Reach the app through your Gateway at the URL the deploy printed (`https://todo.apps.your-domain.dev`), not through any direct worker URL. Apps are private by design: they're only reachable through the perimeter, which is what attaches your identity. A direct hit returning 401 is the security model working. Right after a first deploy the app may answer "deploying" for a few seconds while the Gateway starts serving it.

## Creating an app

### "Could not find an id field in everyapp.config.ts"

Thrown by `app create` when the fetched template's `everyapp.config.ts` doesn't declare an `id`. Re-fetch the starter — if it persists, the template itself is broken; report it.

## Local development

### "pnpm is required but not installed"

The CLI uses pnpm to install and run app projects. Install it from https://pnpm.io/installation and re-run.

### "pnpm runs this project's tools on Node.js …"

`cf build` and `cf dev` run Vite through your package manager, and everyapp makes them use its own Node. A Volta pin (`"volta": { "node": … }` in `package.json`) or pnpm's `use-node-version` puts another Node first again, and below 22.18 it can't load `cloudflare.config.ts`. Raise the pin (`volta pin node@22`), then run the command again.

### "everyapp won't run cf below …"

`cf` runs any `cloudflare.config.ts` it finds in its working directory or a parent, so everyapp runs it only in `~/.everyapp/cf`, whose every parent must be writable by you alone (and hold no `cloudflare.config.ts`). Fix the directory the message names (`chmod go-w <dir>`), or run everyapp with a `HOME` that is. A `~/.everyapp` an older CLI left group-writable is made private again by itself.

### The first page load crashes with a database error

Your local database has no tables yet. `everyapp dev` applies pending migrations on startup; if you're on an older CLI, or you passed `--skip-migrations`, run them manually:

```bash
pnpm run db:migrate:local
```

### Hitting the Vite port directly returns 401

Expected. Use the URL `everyapp dev` prints (`http://your-app-id.localhost:8787`), not the raw Vite port. The local Gateway in front of Vite is what signs you in as the seeded dev user.

### `pnpm install` fails in a copied app

If you copied a directory out of the monorepo, its dependencies may point at workspace packages that only resolve inside it. Use the published starter instead:

```bash
npx everyapp app create
```

### Schema changes don't show up

Generate the migration first, then restart:

```bash
pnpm run db:generate
```

`db:generate` writes the migration file; it doesn't apply it. Restarting `everyapp dev` applies it locally, and `everyapp app deploy` applies it in production.

## Still stuck

Collect these before asking for help — they identify almost any problem on sight:

```bash
node --version
npx everyapp --version
npx cf auth whoami
npx everyapp gateway status
dig +short apps.your-domain.dev
```

Plus the full command you ran and its complete output (with `--verbose`), and whether your domain shows **Active** in the Cloudflare dashboard.

<Callout type="info">
  Re-running a failed deploy is safe. Resources are created get-or-create,
  migrations run once each, and app registration is an upsert.
</Callout>
