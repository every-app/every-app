While publishing is paused, everyapp runs from a checkout of the repository as `pnpm everyapp …`, and its output names the next command that way. Global help: `pnpm everyapp --help`, and `pnpm everyapp <command> --help` for each command. The CLI needs Node.js 22.18 or newer and drives Cloudflare's own CLI, `cf`: log in with `npx cf auth login` (the CLI offers it when you're logged out), or set `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. That login is the only credential, on every machine and in CI: there is no token to create, paste or renew, and the CLI keeps nothing on your machine. It finds your Gateway through the login: every account the login sees is asked for the Gateway's database (`every-app-gateway`), and the install record in it says where the Gateway lives. The Gateway's code comes from the checkout you run the CLI in: `setup`, and the rebind a `deploy` or `delete` does, build it from there (once per change to its sources; the build is kept under the checkout's `node_modules/.cache/everyapp`).

| Command                                                                            | What it does                                                                                                                           |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| [`setup [--domain D]`](#everyapp-setup)                                            | Installs the Gateway, upgrades it to what this checkout builds, or repairs it; creates its owner the first time. Safe to run any time. |
| [`status`](#everyapp-status)                                                       | One screen: the Gateway, its owner, apps, certificates, running deploys, and what to run if something is off.                          |
| [`create <id>`](#everyapp-create-id)                                               | A new app from the starter template, ready for `dev`. Doesn't contact the Gateway.                                                     |
| [`dev`](#everyapp-dev)                                                             | Runs the app in this directory behind a local gateway with the real perimeter.                                                         |
| [`deploy`](#everyapp-deploy)                                                       | Deploys the app in this directory. With no Gateway yet, offers to install one first.                                                   |
| [`register <id>`](#everyapp-register-id)                                           | Registers a Worker deployed by other means as a shared app of a hosted Gateway.                                                        |
| [`delete [id]`](#everyapp-delete-id)                                               | Removes an app from the Gateway; `--purge` deletes its Worker and data too.                                                            |
| [`secret set\|unset\|list`](#everyapp-secret-setunsetlist)                         | The app's secrets, or the Gateway's settings with `--for gateway`. `set` and `unset` redeploy.                                         |
| [`db migrate`, `db query "<sql>"`](#everyapp-db-migrate-and-everyapp-db-query-sql) | Local migrations for `dev`; SQL against the app's production database, or `--local`.                                                   |
| [`workflows …`](#everyapp-workflows)                                               | The deployed app's Workflows.                                                                                                          |

**Which Gateway.** One Gateway in the login's accounts: that one. Several: `--account-id`, `CLOUDFLARE_ACCOUNT_ID`, the address you name (`--gateway`, or `setup --domain`), or a choice at a terminal; under `--json` the command stops with `action_required choose_account`, its `data.choices` listing each account, its Gateway and the command to run. None: `setup` installs one, and `deploy` offers to (below); any other command stops with `GATEWAY_NOT_FOUND`, naming the accounts it asked. An `--account-id` that names an account without a Gateway is `GATEWAY_NOT_FOUND` too, saying where the Gateway is.

## Output, `--json`, `--verbose` and `--yes`

At a terminal a command shows a few lines: its milestones, short ones joined on one line (`Built · 2 migrations applied · uploaded 3f9c1a2e`), a spinner while a step runs, the waits a person should know about (another deploy holding the lease, a certificate on its way, the Gateway's build), and warnings and errors on stderr, each ending with the command to run next. Piped, the same lines without the spinner. `--verbose` adds every step and progress line, and streams build and install output to stderr.

What a command runs writes to a log file, never to the screen: pnpm, the manifest's install and build commands, git and the Gateway's build go to `$TMPDIR/everyapp/<command>-<time>.log`, and a failure shows the last 20 lines and the log's path. `cf`'s output is kept in memory the same way (its last lines on failure). The one exception is `cf deploy` at a terminal: it runs attached, so it can ask its own questions.

With `--json`, stdout carries NDJSON events and nothing else, one per line. A command exits with 0 when done, 2 when a person has to do something first (log in, open a setup link, buy a domain, pick the Gateway's account, install the Gateway, run it once in a terminal) and 1 on an error, whatever came before it. After an exit 2, run `data.rerun`: the same command, unless it names another (`install_gateway` names `setup`). An `action_required` event with `data.waiting: true` is one the command waits for: show its `data.url` (and `data.code`) to a person and keep reading. Logged out, every command that needs the login (`setup`, `status`, `deploy`, `delete`, `secret`, `db query`, `workflows`) starts Cloudflare's device login that way and waits for it, up to 15 minutes. An error whose rerun adds a flag that takes something over (`--force-dns`, `setup --allow-downgrade`, `--allow-delete-durable-object-data`, `--allow-delete-workflows`, `--yes` where a confirmation was needed) carries `data.authorize: true`: show it to a person and ask before running it. An error after a database migration repeats the command that rolls the database back, as `data.rollbackCommand`; the migration's own `step … ok` event has it too.

The `action_required` actions: `cloudflare_login`, `choose_account`, `add_domain`, `register_workers_subdomain`, `upgrade_workers_paid`, `claim_owner`, `install_gateway` and `rerun_interactive`.

Nothing asks before it acts: a command's first line says what happens (`todo → https://todo.apps.example.com (Acme), first deploy`; `Redeploying todo with GITHUB_TOKEN (code and pending migrations from this directory)`), and the Workers Paid check is a warning. What still asks, at a terminal only: which Cloudflare account when the login has several; where the Gateway goes when `setup` has no `--domain`; whether `deploy` should install a Gateway when there is none; `cf`'s own questions at the upload (a Worker changed in the dashboard or through the API, a Custom Domain or DNS record held by something else); replacing a Worker everyapp didn't record deploying, before anything is migrated; a secret's value, hidden; and `delete` (with `--purge`, typing the app id). `--yes` skips everyapp's own confirmations (`delete`'s, including `--purge`'s typed id; `workflows terminate`'s; `deploy`'s offer to install the Gateway), never `cf`'s questions, the replace check or the secret's value.

## The Gateway

### `everyapp setup`

Installs the Gateway, upgrades it, or repairs it: one command from an empty Cloudflare account to a working Gateway and its owner, and the one to run after a `git pull` or when `status` says something is off. Each step looks at what is there before it acts, so running it again picks up where it stopped, and changes nothing once everything is there:

1. logs in to Cloudflare: `cf auth login` at a terminal (a link and a code), the same link and code as a waited-for `action_required` under `--json`, or `CLOUDFLARE_API_TOKEN` with `CLOUDFLARE_ACCOUNT_ID`;
2. finds the Gateway in the login's accounts (see **Which Gateway** above), or with none picks the account to install it in, and warns when it can't confirm Workers Paid;
3. picks where the Gateway lives: `--domain`, the installed Gateway's address (also one an install recorded before it stopped), or (at a terminal) one of the account's domains, suggesting `apps.<domain>`; with no domain on Cloudflare, it says how to buy one and stops (exit 2);
4. installs the Gateway, or upgrades it to the release this checkout builds (migrations first, after a restore point it prints), and waits for its certificate. When the Gateway already runs what this checkout's sources build (the install record's tree hash says so, before anything is built), it checks that the live Gateway binds and publishes exactly the apps its registry lists and serves the version the record names; if so it says `Gateway 0.4.0 at https://apps.example.com is up to date.`, and otherwise redeploys it with them. A checkout behind the live Gateway stops with `DOWNGRADE_REFUSED`: run `git pull`, then `setup` again;
5. sends one plain request to the Gateway (so a certificate still on its way, or Cloudflare Access in front, shows up as a warning here), then opens a one-time setup link for the owner account (at a terminal; with `--json` it is in the event, except in CI, where setup stops with `claim_owner` and says to run `setup` at a terminal on any machine with the login), and waits up to 15 minutes for someone to use it, reading the link's own row in the Gateway's database every 5 seconds. Then it says whose account that is (`Owner created: <email>`). A setup run again before anyone used the link shows a new one, and the earlier one stops working.

The owner is for people, who sign in with that account; apps deploy without one, from any machine or CI with the Cloudflare login. Apps deployed before the owner exists go to the organization the owner's account takes over, and the owner gets access to them. A Gateway whose database has no install record (an install that stopped before it wrote one) is installed again at `--domain`, and gets its owner link then.

```

```

`setup --json` in CI with no owner yet stops with exit 2 and never prints the link into the log; deploys from CI work regardless:

```
{"v":1,"type":"action_required","action":"claim_owner","message":"The Gateway has no owner yet. Run `pnpm everyapp setup` at a terminal on any machine with this Cloudflare login to create the owner account; apps deploy without one.","data":{"rerun":"pnpm everyapp setup"}}
```

| Flag                  | Meaning                                                                                                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--domain <hostname>` | Where the Gateway lives: any hostname in a zone the account has, e.g. `apps.your-domain.dev`. Asked at a terminal otherwise; the install record keeps it.                                          |
| `--mode <mode>`       | What a new Gateway is: `self_hosted` (your own, the default) or `hosted` (the hosted Gateway's rules). Set with its first upload; a live Gateway's mode never changes (`MODE_CHANGE_UNSUPPORTED`). |
| `--account-id <id>`   | The Gateway's Cloudflare account, when your login sees several; with no Gateway yet, the one to install it in.                                                                                     |
| `--force-dns`         | Publish an address even where a DNS record answers it (one at the address is replaced).                                                                                                            |
| `-y`, `--yes`         | Skip everyapp's own confirmations; setup asks for none.                                                                                                                                            |
| `--json`, `--verbose` | Only NDJSON events on stdout; every step and progress line, and the Gateway's build output on stderr.                                                                                              |

Two hidden flags:

- `--allow-downgrade` deploys this checkout's Gateway even though it is older than the live one: a deliberate rollback. Only `setup` takes it, and its `DOWNGRADE_REFUSED` offers it as the rerun with `data.authorize: true`, so an agent asks first.
- `--redeploy` uploads the Gateway even when it is up to date, for a change made outside everyapp, such as replacing its key pair (the repository's `docs/runbooks/key-rotation.md`). At a terminal `cf` asks before it replaces a Worker changed in the dashboard.

**How the Gateway deploys.** The release this checkout builds (once per change to the Gateway's, the SDK's, perimeter's or toolbus's sources, kept by their tree hash under `node_modules/.cache/everyapp`): setup creates or links its D1 database and OAuth KV namespace, records the install in the Gateway's database before anything can stop it (so a run that stops before its first upload resumes without `--domain`), migrates the database (after a Time Travel bookmark it prints with the restore command), binds every deployed app, publishes the Gateway's address and each app's as [Workers Custom Domains](/docs/reference/manage-your-gateway#where-apps-live), uploads the Worker with `cf deploy`, and records what went live. A first install generates the Gateway's secrets and sends them with the upload; the CLI keeps none of them, but writes the public half of the Gateway's identity key into the install record, where the apps' deploys read it. Nothing is asked of the Gateway over HTTPS: what `cf deploy` reports and the install record are the record. Before it adds an address, it checks for a DNS record that answers it (one at the address, or a wildcard above it) and room in the zone (100 Custom Domains), then waits for the new certificate.

**Deploys never overlap.** Each takes a lease in the Gateway's database, renewed every 30 seconds while it runs and expiring 3 minutes after its last renewal, so a deploy that died frees it within 3 minutes, however long a live one takes. Nothing takes a live lease over; `status` shows who holds it. A deploy that can't renew its lease (another took it, or renewals kept failing for 90 seconds) stops with `LEASE_LOST` before it migrates or uploads.

### `everyapp status`

Everything from the Gateway's database, `cf` and this checkout, nothing over HTTPS and nothing built:

```
$ pnpm everyapp status
Gateway:  https://apps.example.com (Example Inc)
Mode:     self_hosted
Release:  0.4.0 (e43cbca3a6aa) · built from this checkout's sources
Owner:    ben@example.com (Example Inc)
Apps:     chef (binding, not bound), todo (active)
TLS:      ready (3 hostnames)
Deploys:  none running
To do:    The live gateway doesn't bind or publish exactly the apps its registry lists. Run: pnpm everyapp setup
```

It shows the Gateway's deployment mode (`self_hosted` or `hosted`, as its first upload recorded it; `data.mode`, `null` and no `Mode:` line when the install record doesn't have it), the release the install record names and whether the Worker serves that version, whether that release was built from this checkout's Gateway sources (`upToDate`: their tree hash against the install record's, `null` when either is unknown; `data.checkout` has the checkout's version and tree), its owner, each registered app (`id`, `hostname`, `workerName`, `status`, whether the live version binds it, and who deployed it last), whether the Gateway binds and publishes exactly the registered apps, each address and whether Cloudflare lists an active certificate for it, and every deploy in progress (the Gateway's or an app's): who holds its lease, since when, and when the lease expires unless that deploy renews it.

`data.fixes` (and `To do:` at a terminal) says what to run about anything off: no owner, sources changed since the live release was built, bindings that differ from the registry, a Gateway changed outside everyapp, or an install that stopped before its first upload (all `setup`); a checkout behind the live Gateway (`git pull`); an app whose Worker is gone or that never finished a deploy (`deploy` from its directory, or `delete <id>`); and what settles by itself, with `run: null` (an app that goes live on its first visit, a certificate on its way, a running deploy). With `--json`, the `done` event's data has all of it: the one state query an agent needs. With no Gateway in the login's accounts it stops with `GATEWAY_NOT_FOUND`. Flags: `--account-id`, `--json`, `--verbose`.

## Apps

App commands find your Gateway through your Cloudflare login (see **Which Gateway** above), and the install record in its database. Any machine with the login and the checkout can deploy, with nothing to set up first. `--account-id <id>` picks the Gateway's account when the login sees several. `--gateway <url>` or `EVERYAPP_GATEWAY_URL` (meant for the hosted tier) picks among several too, and otherwise only checks you reach the Gateway you mean: one that names another address stops with `GATEWAY_URL_MISMATCH`. `deploy` and `delete` refuse to run from a checkout behind the live Gateway, before they change anything: `DOWNGRADE_REFUSED`, run `git pull`, then the same command. When they rebind the Gateway, they deploy the one this checkout builds, which upgrades it when the checkout is newer.

**The registry.** An app's registration lives in the Gateway's own D1 database, and the CLI writes it there itself, with your Cloudflare login and the same rules the Gateway ships (`@every-app/perimeter/registry`): the app's names, who can open a new app, and on every deploy the version uploaded and who deployed it (your Cloudflare login's email, or `api-token:<account id>` with an API token), shown in **Admin → Apps** and `status`. Write access to that database is what makes you the Gateway's operator. Apps register before the Gateway has an owner too: they go to an organization named after your Cloudflare account, which the owner's account takes over.

### `everyapp create <id>`

Scaffolds a new app from the starter template (kebab-case id): copies it to `apps/<id>` inside the checkout or `./<id>` anywhere else, names it in `package.json` and `everyapp.config.ts`, puts the [everyapp skill](#the-everyapp-skill) in `.claude/skills/everyapp` and `.agents/skills/everyapp`, installs its dependencies, generates the Worker's types, applies its migrations to the local database, and outside the checkout starts a git repository for it. It doesn't contact your Gateway, so `dev` works at once:

```
$ pnpm everyapp create my-app
Created my-app in ./my-app.
Next: cd ./my-app
      pnpm dev
```

With no id it asks for one at a terminal; `--json` and `-y` never ask. `--deploy` deploys the new app afterwards, as `deploy` does, offer to install the Gateway included (`--gateway` and `--account-id` pick the Gateway). Flags: `--deploy`, `--gateway`, `--account-id`, `--json`, `-y`, `--verbose`.

**The everyapp skill.** One page for coding agents, shipped with the CLI (`packages/cli/skills/everyapp/SKILL.md`): how to read `--json`, and which command does what. `create` copies it into each new app, where Claude Code and other agents look for skills; the template's `AGENTS.md` points at it. A copy rather than a link, so it survives cloning the app on its own (and git on Windows). In an app whose `AGENTS.md` doesn't mention it, `create` asks at a terminal before adding a line, and never touches it under `--json` or `-y`.

### `everyapp dev`

Runs your app under `cf dev` behind a local gateway with the real security perimeter — real identity verification, real public-route policy, hot reload intact. App at `http://<app-id>.localhost:8787`. Identities are signed with the SDK's well-known dev keypair, which a development build trusts on its own, so nothing is written into your app. Before starting it generates the Worker's types when `.cloudflare/types` is missing and applies local D1 migrations. The gateway listens on `127.0.0.1` unless `--host`: the dev key is public, so anyone who can reach the port gets a dev identity. It runs until you stop it, and prints the app's URL; it has no `--json`.

| Flag                  | Meaning                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `--port <n>`          | Gateway port (defaults to `$PORT`, then 8787).                                                                    |
| `--host <address>`    | Address the gateway listens on (default `127.0.0.1`; `0.0.0.0` lets other machines in, each as a dev identity).   |
| `--mode stub\|mirror` | `stub` (default): a seeded dev user, zero setup. `mirror`: real login against a separately running local gateway. |
| `--gateway <url>`     | Mirror mode: the local gateway's URL (default `http://localhost:3000`).                                           |
| `--baseHost <host>`   | Mirror mode: two-label base host for the session cookie (default `everyapp.localhost`).                           |
| `--skip-migrations`   | Skip the local migration preflight that normally runs before the dev server starts.                               |

### `everyapp deploy`

Run from an app directory. Registers the app in your Gateway's registry, which names its Worker and resources (`every-<org>-<app-id>`) and its address (`<app-id>.apps.your-domain.dev` for your own organization's apps, `<app-id>-<org>.apps.your-domain.dev` for another's); checks a new address (a DNS record that answers it, room in the zone) before it creates or uploads anything; creates or links the D1/KV resources in `everyapp.config.ts`, and its Hyperdrive configs (`<worker>--<binding>`, created from the database URL in the app's `.everyapp/secrets.env`, which it never uploads or prints, or adopted when one of that name connects to the same database); builds the Worker that `cloudflare.config.ts` defines (`cf build`), with the Gateway's public identity key from its install record, and checks it (private, its own identity keys, no other Workers or resources, and Workflows named after it that no other Worker runs); checks that the app's drizzle migrations still describe its schema (below); migrates its D1 database, or its Postgres database with the app's own `drizzle-kit migrate` against `POSTGRES_DATABASE_URL` from the secrets file (`migrations.dialect: "postgresql"`; Postgres has no restore point, so its own backups are the way back); uploads it with `cf deploy`, which creates or updates its Workflows, after its helper Workers (the manifest's `workers`, each `<worker>--<name>`, checked the same way and bound only by the app's Worker); records the version in the registry; redeploys the Gateway to bind it and publish its address as a Custom Domain; and waits for it to go live (below). Redeploying an app's code doesn't touch the Gateway; the Gateway takes the new code's agent tools itself when it sees the new version. Safe to run again.

At a terminal a first deploy reads:

```
$ pnpm everyapp deploy
todo → https://todo.apps.example.com (Example Inc), first deploy
Registered todo: private to you, owners and admins (change it in Admin → Apps)
Built · schema in sync · 2 migrations applied · uploaded 3f9c1a2e
  restore point: CLOUDFLARE_ACCOUNT_ID=… npx cf@1.0.0-beta.14 d1 time-travel restore <db> --bookmark <b> --force
Binding to the Gateway · uploaded 7d20c4e1
Live: https://todo.apps.example.com
```

(`private to owners and admins` when your Cloudflare login's email isn't a verified account on the Gateway: only a verified account with the same email gets the app as its deployer. `Binding to the Gateway` is a redeploy of the Gateway this checkout builds: a few seconds from the build cache, or a minute or two the first time after its sources change.) A redeploy:

```
$ pnpm everyapp deploy
todo → https://todo.apps.example.com (Example Inc)
Built · schema in sync · database up to date · uploaded 8a01d4f7
Live: https://todo.apps.example.com
```

From a checkout behind the live Gateway, nothing happens:

```
✗ This checkout's Gateway (0.3.0) is older than the one live at https://apps.example.com (0.4.0). Run git pull, then: pnpm everyapp deploy
  Then run: pnpm everyapp deploy
```

**No Gateway yet.** When no account the login sees has a Gateway, a deploy at a terminal offers to install one at `apps.<domain>` in the account `setup` would pick (asking which domain when the account has several), runs `setup` right there, owner link included, then deploys:

```
$ pnpm everyapp deploy
? No Gateway in Example Inc yet. Install one at apps.example.com? (y/N) y
Cloudflare: ben@example.com · Example Inc
Installing the Gateway at https://apps.example.com · 1 migration applied · uploaded 9c2e1b0d
  …
Owner created: ben@example.com
todo → https://todo.apps.example.com (Example Inc), first deploy
…
Live: https://todo.apps.example.com
```

`-y` installs it at `apps.<domain>` without asking. Declined, nothing happens (`GATEWAY_NOT_FOUND`, with `setup --domain` as the rerun: install it where you want it, then deploy). Under `--json`, in CI or with piped output, it never installs on its own: it stops with `action_required install_gateway` (exit 2), whose `data.rerun` is the setup command, `pnpm everyapp setup --domain apps.example.com`; run it, then deploy again.

**The live wait.** The Gateway makes a newly bound app live itself, on the first request that reaches it over its new binding. So the deploy requests `https://<app-id>.apps.your-domain.dev/` (every 3 seconds, for up to ten minutes) until the registry says the app is active: the request makes it so, the database says it happened, and no answer by itself counts as live. A new address's certificate (usually a minute or two) and the Gateway version with the binding reaching every edge (seconds) are what it waits for. With Cloudflare Access in front of the Gateway, the request never reaches it: once the address answers, the deploy warns that the app goes live on its first visit through Access, and ends successfully. So does a certificate that hasn't come after ten minutes; the Gateway answering for ten minutes without making the app live is an error (`APP_NOT_LIVE`; deploy again, the upload is kept). `--no-wait` skips the whole wait.

**The schema check.** For an app on the drizzle migrations engine (the default), the deploy runs `drizzle-kit generate` with the app's own `drizzle.config.ts` against a copy of its migrations, after the build and before anything is migrated or uploaded. If that would write a new migration, the schema has changes no migration carries, and the deploy stops with `SCHEMA_DRIFT`: run `pnpm db:generate`, then deploy again. Otherwise it reports `schema in sync`. When drizzle-kit can't tell (it asks about a renamed column or table only at a terminal), the deploy stops with `SCHEMA_CHECK_FAILED`. An app without drizzle-kit installed or a drizzle config gets a `SCHEMA_CHECK_SKIPPED` warning and deploys anyway. Apps on `migrations.engine: "d1-sql"` aren't checked.

A deploy holds the app's own lease from creating its resources to its upload, then the Gateway's while it binds a new app, with the same 3-minute expiry and no way to take a live one over. Who can open a new app comes from `access` in `everyapp.config.ts` (default: the deployer, owners and admins); after the first deploy it is managed in **Admin → Apps**.

| Flag                                 | Meaning                                                                                                    |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `--allow-delete-durable-object-data` | Deploy even though Durable Object classes were removed, deleting their data.                               |
| `--allow-delete-workflows`           | Deploy even though Workflows were removed, deleting them and their instances once the new version is live. |
| `--force-dns`                        | Publish a new address even where a DNS record answers it (one at the address is replaced).                 |
| `--no-wait`                          | Don't wait for the app to go live; it goes live on its first visit, once its certificate comes.            |
| `--shared`                           | A shared app of a hosted Gateway (below). Redeploys keep a shared app shared without it.                   |
| `--gateway <url>`                    | The Gateway you mean, checked against the one in your Cloudflare account.                                  |
| `--account-id <id>`                  | The Gateway's Cloudflare account, when your login sees several (default: `CLOUDFLARE_ACCOUNT_ID`).         |
| `-y`, `--yes`                        | With no Gateway yet, install one at `apps.<domain>` without asking. A deploy asks nothing else.            |
| `--json`, `--verbose`                | Only NDJSON events on stdout; every step, and build output on stderr.                                      |

**Shared apps.** On a hosted Gateway (`setup --mode hosted`), `deploy --shared` registers the app as a shared app: one Worker that the members of every organization can open, owned by the platform organization, at `<app-id>.<base>`. Nobody is granted it and nobody manages its access; each member's identity carries their own organization, and the app scopes its data by it. Its Worker gets no `EVERY_APP_ORG_ID`. Only owners and admins of the platform organization deploy one (your Cloudflare login's email must be one of them, verified on the Gateway; an API token is the account's own authority), and a self-hosted Gateway refuses it (`SHARED_APPS_UNAVAILABLE`). An app keeps the scope it was registered with: a redeploy or `secret set|unset` without `--shared` keeps a shared app shared (and still needs a platform owner or admin), and only `--shared` on an organization's app stops, with `APP_SCOPE_MISMATCH`. Deleting a shared app (`everyapp delete`) cuts every organization off from it, so it too needs a platform owner or admin (`SHARED_APP_FORBIDDEN`).

### `everyapp register <id>`

Registers a Worker deployed some other way (an Alchemy stage, wrangler, another pipeline) as a shared app of a hosted Gateway, and makes it live as `deploy` would, without building, uploading or changing it:

```sh
pnpm everyapp register openseo --worker every-everyapp-openseo --shared --manifest ../open-seo/everyapp.config.ts
```

It checks that the Gateway is hosted, loads and validates the manifest as `deploy` does (its `id` must be `<id>`), and checks the Worker exists in the Gateway's account (`WORKER_NOT_FOUND`). It registers the app under the Worker name the Gateway gives it, `every-<org>-<id>` for the platform organization; `--worker` must be that name (`WORKER_NAME_MISMATCH` says which). Then it records the Worker's live version, redeploys the Gateway to bind it and publish its address, and waits for it to go live. Run it again after the Worker's own pipeline ships a version. The `app.register` event's `data.worker` lists what that pipeline must give the Worker: the identity keys and issuer, and the `AppGateway` service binding's props. `delete --purge` never deletes a registered Worker. `--shared` is required: `register` makes shared apps only. Flags: `--worker`, `--manifest`, `--shared`, `--force-dns`, `--no-wait`, `--gateway`, `--account-id`, `--json`, `--verbose`.

### `everyapp delete [id]`

Removes the app from your Gateway's registry (its name and address stay reserved to your organization; everyone's access to it, the personal access tokens bound to it, its agent tools and its place in AI connections go), drops the Gateway's binding to it and its address, and deletes the certificate Cloudflare keeps for that address. With no id, the app in this directory. Its Worker and data, and any cron schedules and Workflows the Worker runs, are kept unless `--purge`, which asks you to type the app id and deletes only the Worker (and helper Workers), databases, namespaces and Hyperdrive configs (never the Postgres database behind one) its deploys recorded creating, with the Workflows that run on those Workers; anything else with its names is kept and listed. At a terminal it asks first; unattended it needs `-y`, which also skips typing the id for `--purge` (an agent asks before adding it). Flags: `-y`, `--purge`, `--gateway`, `--account-id`, `--json`, `--verbose`.

### `everyapp secret set|unset|list`

Run from an app directory. `secret set NAME` sets one of the app's own secrets (an API key its Worker calls out with, say) from a hidden prompt or `--from-env <VAR>`, never the command line, and redeploys the app with the secret in the same version, as `deploy` does: its code and pending migrations go too, which its first line says. Later deploys keep it. Setting a secret with `cf` directly makes a version everyapp didn't upload, which the next unattended deploy stops on; this doesn't.

```
$ pnpm everyapp secret set GITHUB_TOKEN
Value for GITHUB_TOKEN: ••••••••
Redeploying repolens with GITHUB_TOKEN (code and pending migrations from this directory)
Built · schema in sync · database up to date · uploaded 5c2a9e10
Live: https://repolens.apps.example.com
```

`secret unset NAME` deletes the secret from the app's Worker (`cf workers secrets delete`, which makes a new version without it), then redeploys the same way (`Redeploying repolens without GITHUB_TOKEN …`), so the version that serves is one everyapp uploaded; a secret that is gone already only redeploys. `secret list` prints the names of the Worker's secrets, everyapp's own (`GATEWAY_URL`, `EVERY_APP_ORG_ID`) included, never their values. Names everyapp sets itself are refused for `set` and `unset` (`GATEWAY_URL`, and the `EVERYAPP_*`, `EVERY_APP_*` and `APP__*` names), as are the app's own binding names for `set`.

With `--for gateway`, the same three act on the Gateway's optional settings instead, from any directory, and `set` and `unset` redeploy the Gateway this checkout builds: `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `AI_PROXY_EXTRA_ROUTES`, the capability keys `DATAFORSEO_API_KEY` and `CONTEXT_API_KEY`, `EMAIL_REST_API_TOKEN`, `EMAIL_FROM`, `EMAIL_FROM_NAME`, the MCP connector's `MCP_OAUTH_ENABLED`, `MCP_DCR_ENABLED`, `MCP_ALLOWED_ORIGINS` and `MCP_AUDIT_RETENTION_DAYS`, [Cloudflare Access sign-in](/docs/reference/cloudflare-access)'s `CLOUDFLARE_ACCESS_*` and `EMAIL_PASSWORD_SIGN_IN`, or the hosted Gateway's `HOSTED_OPEN_SIGNUP` (any other name lists them).

| Flag                  | Meaning                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `--for gateway`       | The Gateway's settings instead of the app's secrets.                                                         |
| `--from-env <VAR>`    | `set` only: read the value from this environment variable instead of a hidden prompt (unattended, required). |
| `--gateway <url>`     | The Gateway you mean, checked against the one in your Cloudflare account (the hosted tier's).                |
| `--account-id <id>`   | The Gateway's Cloudflare account, when your login sees several.                                              |
| `-y`, `--yes`         | Skip everyapp's own confirmations; `secret` asks for none (its first line says what is redeployed).          |
| `--json`, `--verbose` | Only NDJSON events on stdout; every step, and build output on stderr.                                        |

### `everyapp db migrate` and `everyapp db query "<sql>"`

`db migrate` applies the app's D1 migrations (`migrations.dir`, default `drizzle/`) to the local database in `.cloudflare/state` that `dev` serves, with `cf d1 migrations apply --local` (`--local` is the default and the only database it migrates). `dev` runs it on every start, and the `db:migrate:local` package script runs it; production migrations run inside `deploy`, after a restore point, and nowhere else. `--json` prints NDJSON events, ending `done` or `error` like every other command.

`db query "<sql>"` runs SQL against the app's production D1 database through `cf`, with your Cloudflare login in the Gateway's account; `--local` queries the database `dev` uses instead. `--binding` picks a D1 binding other than the migrations one; `--gateway` and `--account-id` as for `deploy`; `--json` puts the rows in the `done` event.

### `everyapp workflows`

Run from an app directory. Manages the deployed app's [Workflows](/docs/how-it-works/sdk#workflows) through `cf workflows`, with your Cloudflare login in the Gateway's account. Name a Workflow by its binding in `everyapp.config.ts` (`RANK_CHECK`), its class or its full name; only a Workflow that runs on the app's own Worker is touched.

| Command                                  | What it does                                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `list`                                   | Each Workflow the app declares, with its instances' counts by status, or "not deployed yet". |
| `instances <workflow>`                   | Its instances; `--status <status>` filters them, `--limit <n>` (1-100, default 25).          |
| `get <workflow> <instance-id>`           | One instance: its status, params, steps, output and error.                                   |
| `start <workflow>`                       | Starts an instance, with `--params '<json>'` and, optionally, its `--id`.                    |
| `pause`, `resume`, `restart` (same args) | Pauses an instance, resumes a paused one, or runs one again from the start.                  |
| `terminate <workflow> <instance-id>`     | Stops an instance for good. Asks first at a terminal; unattended, it needs `-y`.             |

All take `--gateway`, `--account-id` and `--json`. Locally, `dev` links to the Local Explorer, which does the same for the Workflows `cf dev` runs.
