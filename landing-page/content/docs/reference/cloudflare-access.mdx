Your Gateway can let people sign in through [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/access-controls/): your company's identity provider, Access's one-time PIN, its MFA and device rules. It is a way to sign in, not a second login system. The Gateway's own accounts stay the source of truth for who is a member, their role, invitations, personal access tokens and connected AI apps. An Access sign-in ends in an ordinary Gateway session, so everything after it (app access, the identity apps receive, `/mcp`, tokens, deactivation) works exactly as after a password.

Everything is configured with Worker secrets. Nothing about sign-in can be changed from the admin UI, so a stolen admin session can't add a way in.

## Choose a mode

|                      | OIDC sign-in (recommended)                        | Outer ring                                                          |
| -------------------- | ------------------------------------------------- | ------------------------------------------------------------------- |
| What people see      | **Continue with Company SSO** on the sign-in page | Access's login before they reach anything, then no second login     |
| What Access protects | The sign-in                                       | Every request to your Gateway's and apps' hostnames, minus bypasses |
| Access app type      | Access for SaaS (OIDC)                            | Self-hosted, hostname-based                                         |
| Mobile app           | Works                                             | Not supported                                                       |
| MCP clients, the CLI | Unaffected                                        | Need bypass paths                                                   |

Use OIDC sign-in unless your security team requires Access in front of everything. You can turn on both.

## Who gets in

Access only says who someone is. Whether they are a member is still your Gateway's decision, the same for both modes:

- **Members** sign in; **deactivated** members don't, whatever Access says.
- **Invited people** sign in with the invited email and join with the invited role, like accepting the invite link.
- **Your company's domains**, if you list them in `CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS`, join as members with the apps marked **Available to everyone**, like someone who accepted an invitation. An admin grants the others.
- **Everyone your Access policy admits**, only through the outer ring and only with `CLOUDFLARE_ACCESS_OUTER_RING_AUTO_JOIN=everyone`. Your Access policy then is your member list.
- **Anyone else** is refused, and nothing is created for them. Before the Gateway is claimed, nobody gets in through Access.

To take someone off, **Deactivate** them in **Admin → Users**: it signs them out everywhere and revokes their tokens and AI connections at once. Removing them from your Access policy stops new sign-ins (and, behind the outer ring, their browser once their Access session runs out), but tokens and AI connections never pass through Access. Neither does deploying, which takes the Cloudflare login: revoke that in Cloudflare. With auto-join, **Delete** deactivates instead, since a deleted account would simply join again at the next sign-in.

An existing account (one made with a password, including yours as the owner) connects to Access once, while signed in: sign in with the password through the outer ring, or with **Continue with Company SSO** then the password when asked, or **Connect Company SSO** in the account menu. After that, Access alone signs it in. This is what stops someone who registered with another person's email from being handed that person's account. Behind the outer ring, an account's email must be the one Access knows the person by, so claim the Gateway and invite people with those addresses.

Enable only identity providers in Access that verify email addresses (one-time PIN, Google Workspace, Okta, Microsoft Entra ID and the like): your Gateway trusts the email Access vouches for.

## 1. Set up Access (once)

With the [`cf` CLI](https://developers.cloudflare.com/cf/) (beta; checked against `cf@1.0.0-beta.14`, whose login includes Access permissions):

```bash
npx cf@1.0.0-beta.14 auth login
export CLOUDFLARE_ACCOUNT_ID=<your account id>

npx cf@1.0.0-beta.14 zero-trust organization get
# none yet? the team domain is permanent once used
npx cf@1.0.0-beta.14 zero-trust organization create --name "Acme" --auth-domain acme.cloudflareaccess.com

# New organizations only let in members of your Cloudflare account:
# add the one-time PIN so teammates can log in with their email.
npx cf@1.0.0-beta.14 zero-trust identity-providers create \
  --body '{"name":"One-time PIN","type":"onetimepin","config":{}}'

# Who may use Every App. Note the policy id.
npx cf@1.0.0-beta.14 zero-trust access policies create --name "Every App users" \
  --decision allow --include '[{"email_domain":{"domain":"acme.com"}}]'
```

In the dashboard: open **Zero Trust** (pick a team name), add **Integrations → Identity providers → One-time PIN**, and create an **Access controls → Policies** policy for your people.

## 2a. OIDC sign-in

Create an Access for SaaS application whose redirect URL is your Gateway's callback, with PKCE:

```bash
npx cf@1.0.0-beta.14 zero-trust access applications create --body '{
  "name": "Every App",
  "type": "saas",
  "saas_app": {
    "auth_type": "oidc",
    "redirect_uris": ["https://your-domain.dev/api/auth/callback/cloudflare-access"],
    "grant_types": ["authorization_code_with_pkce"],
    "scopes": ["openid", "email", "profile"]
  },
  "policies": ["<policy id>"]
}'
```

(Dashboard: **Access controls → Applications → Create new application → SaaS application → OIDC**, add the redirect URL, turn on **PKCE**, attach your policy.) Then give the Gateway the client id, the client secret (shown once) and the issuer, `https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client id>`:

```bash
npx everyapp gateway secret set CLOUDFLARE_ACCESS_OIDC_ISSUER
npx everyapp gateway secret set CLOUDFLARE_ACCESS_OIDC_CLIENT_ID
npx everyapp gateway secret set CLOUDFLARE_ACCESS_OIDC_CLIENT_SECRET
npx everyapp gateway secret set CLOUDFLARE_ACCESS_OIDC_LABEL   # optional, e.g. Company SSO
```

The sign-in page (and the mobile app) now shows **Continue with Company SSO**.

## 2b. Outer ring

Put two **hostname-based** self-hosted Access applications in front: one for your Gateway's own domain, one for its app subdomains. Only the Gateway's application signs people in; the apps' application only vouches for a session on an app. (One application for both works, but then every app's Access cookie is also a Gateway login.) On each, bypass only the endpoints machines use, which check their own credentials:

- `/mcp` and `/mcp/*` (Gateway and apps): MCP clients;
- `/oauth/token`, `/oauth/register` and `/.well-known/*` (Gateway): the OAuth server MCP clients connect through. Keep `/oauth/authorize` and the consent pages behind Access: they're for people;
- `/api/admin/has-owner` (Gateway): the CLI's check whether the Gateway is claimed;
- each app's public routes (its `everyapp.config.ts` `public` list), on that app's host.

Keep Access's cookie **HttpOnly** (the default) and turn on its **binding cookie** on both.

```bash
# The Gateway's own domain: its AUD tag goes in CLOUDFLARE_ACCESS_AUD.
npx cf@1.0.0-beta.14 zero-trust access applications create --body '{
  "name": "Every App gateway",
  "type": "self_hosted",
  "destinations": [
    {"type": "public", "uri": "your-domain.dev", "overrides": [
      {"path_pattern": "/mcp", "behavior": "public"},
      {"path_pattern": "/mcp/*", "behavior": "public"},
      {"path_pattern": "/oauth/token", "behavior": "public"},
      {"path_pattern": "/oauth/register", "behavior": "public"},
      {"path_pattern": "/.well-known/*", "behavior": "public"},
      {"path_pattern": "/api/admin/has-owner", "behavior": "public"}
    ]}
  ],
  "policies": ["<policy id>"],
  "http_only_cookie_attribute": true,
  "enable_binding_cookie": true
}'

# The app subdomains: its AUD tag goes in CLOUDFLARE_ACCESS_APPS_AUD.
npx cf@1.0.0-beta.14 zero-trust access applications create --body '{
  "name": "Every App apps",
  "type": "self_hosted",
  "destinations": [
    {"type": "public", "uri": "*.your-domain.dev", "overrides": [
      {"path_pattern": "/mcp", "behavior": "public"},
      {"path_pattern": "/mcp/*", "behavior": "public"}
    ]}
  ],
  "policies": ["<policy id>"],
  "http_only_cookie_attribute": true,
  "enable_binding_cookie": true
}'
```

<Callout type="warn">
  Don't use **Protect this Worker** on the Worker's page. Access attached to a
  Worker refuses WebSocket upgrades (403), which breaks apps that sync live, and
  the outer ring identity reaches your Gateway either way.
</Callout>

Give the Gateway your team domain and the two AUD tags (`aud` in each response, or **Application Audience (AUD) Tag** in the dashboard):

```bash
npx everyapp gateway secret set CLOUDFLARE_ACCESS_TEAM_DOMAIN   # acme.cloudflareaccess.com
npx everyapp gateway secret set CLOUDFLARE_ACCESS_APPS_AUD      # the apps application's
npx everyapp gateway secret set CLOUDFLARE_ACCESS_AUD           # the Gateway application's: last
```

Set `CLOUDFLARE_ACCESS_AUD` last: the outer ring starts with it, so the apps' tag must already be there.

Your Gateway verifies the token Access adds to every request itself (signature, team, AUD tag, expiry) and never trusts the header on its own. A Gateway session only counts with Access's word for that same person on the request, so when someone's Access session ends, so does their Gateway session in the browser. Apps never see Access's headers or cookies: they get only the Gateway's identity pass. Signing out of the Gateway signs out of Access too.

## Optional: turn passwords off

```bash
npx everyapp gateway secret set EMAIL_PASSWORD_SIGN_IN   # false
```

It takes effect once Access sign-in is configured and you (an owner) have connected your account to Access, so it can't lock you out. Then nobody signs in, signs up or resets a password; have everyone sign in with Access once before. To turn passwords back on, set it to `true`: `npx everyapp gateway secret set EMAIL_PASSWORD_SIGN_IN`.

## Troubleshooting

- **No "Continue with" button:** the Worker's logs show `access.config_problem` for a missing or malformed setting.
- **"An account with this email already exists":** sign in with the password once to connect Access.
- **"You're signed in to Cloudflare Access as X, but this account is Y":** behind the outer ring an account's email must be the one Access asserts, so claim the Gateway and invite people with the addresses Access knows them by. Sign out of Access and sign in there as Y, or have an admin invite X. For the owner's account, change its email to X in the Gateway's database (`npx cf@1.0.0-beta.14 d1 query <id> --sql "UPDATE users SET email = 'x@acme.com' WHERE email = 'y@acme.com'"`, with the id from `npx cf@1.0.0-beta.14 d1 list --name every-app-gateway`), then sign in with the password through Access once.
- **Teammates can't log in at Access:** add the one-time PIN identity provider.
- **MCP clients get an HTML login page:** a bypass path is missing. (Deploys never go through the Gateway's hostname: the CLI writes its database directly.)
- **The mobile app can't sign in behind the outer ring:** use OIDC sign-in for teams on the app.
