This is the agent's side of the journey the user docs describe in [/docs/gateway](/docs/gateway), [/docs/create-an-app](/docs/create-an-app), [/docs/update](/docs/update) and [/docs/people](/docs/people). Its short form is the `everyapp` skill, `packages/cli/skills/everyapp/SKILL.md`, which `create` copies into every new app; this page follows the skill's rules and spells out what each command emits and where it stops. Step-by-step setup of each integration (the Gateway, Access, email, the AI providers, Google, Microsoft 365, Slack) is in `packages/cli/skills/everyapp/setup/` (index `README.md`), copied into every app as `.claude/skills/everyapp/setup/` and `.agents/skills/everyapp/setup/`; the matching file is named at each step below. The prompt a person pastes into their agent is in [/docs/gateway](/docs/gateway#or-let-your-coding-agent-do-it).

Every command below is `everyapp …` (`npm install -g everyapp`, or `npx everyapp@latest …`); in a checkout of the EveryApp repository it is `pnpm everyapp …`, which builds the Gateway from the tree instead of downloading the published release. Agents always add `--json`.

**How long setup takes, and why the timeout matters.** A fresh `setup` runs 5 to 20 minutes end to end. The Gateway download (or, from a checkout, its build, usually 1 to 2 minutes), the upload and the new hostname's certificate (`gateway.tls`, up to 10 minutes, `DEFAULT_MAX_WAIT_MS` in `packages/cli/src/lib/domains/certWait.ts`) take 5 to 10 together, which the `setup.gateway` start event says in `data.expectedMinutes: { min: 5, max: 10 }`; then comes the owner link, which the run polls every 5 seconds for up to 15 minutes (`OWNER_WAIT_MS` in `packages/cli/src/lib/gateway/setup-link.ts`). Give the command a long timeout, or run it in the background and keep reading its events; a tool that stops a command after a few minutes (Claude Code's shell moves one to the background after 120 seconds and ends it at 10 minutes when run with `-p`) loses the owner link mid-wait. Nothing is lost for good: run `data.rerun` as it is (`pnpm everyapp setup --json`: `--json` included because this run had it) and setup resumes, minting a new link and retiring the old one.

## How a --json run talks to you

From `packages/cli/src/lib/output/events.ts` and `packages/cli/src/lib/errors.ts`:

- stdout carries one JSON object per line, each `{ "v": 1, "ts": "…", "type": "…", … }`; `type` is `step`, `progress`, `warning`, `action_required`, `error` or `done`. Nothing is ever prompted under `--json`.
- Exit codes: 0 after `done`; 1 after an `error`, whatever came before it; 2 when the run stopped on an `action_required`; 251 for a command it can't find (`error` `UNKNOWN_COMMAND`) and 252 for bad arguments (`UNKNOWN_FLAG`, `INVALID_VALUE`, `MISSING_ARGUMENT`, …), whose `data` carries `help` (the `--help` command to run), `usage` or `didYouMean` (`packages/cli/src/argumentErrors.ts`).
- `action_required` has `action` (one of `cloudflare_login`, `register_workers_subdomain`, `claim_owner`, `upgrade_workers_paid`, `rerun_interactive`, `add_domain`, `choose_account`, `install_gateway`), `message` (headline on the first line, detail after), `data.url`, `data.code` (device login), `data.expiresAt`, `data.waiting`, `data.rerun` and `data.rerunNote`, or `data.choices[]` (each with `rerun` and `label`) when the way on is one of several commands.
- `data.waiting: true` means the run waits for the person (a login to approve, the owner link): show `url` and `code`, keep reading. If the person acts in time the run goes on to `done` (exit 0) or an `error` (exit 1); if not, a last `action_required` ends it (exit 2).
- `error` has a stable `code`, `retryable`, `data.fix` (a remedy in words), `data.rerun` with `data.rerunNote`, and `data.authorize: true` when the rerun carries a flag that takes something over (`--force-dns`, `--allow-delete-durable-object-data`, `--allow-delete-workflows`, `--enable-email-routing`, `--yes`, `--allow-downgrade`): show the error and ask before running it, never retry with it on your own. `code: "CANCELLED"` is a person declining a prompt.
- `data.rerun` is the same command, `--json` included when this run had it (`thisCommand` in `packages/cli/src/lib/output/command.ts`): run it as it is. The exception is `data.needsTerminal: true` (`ActionData` in `events.ts`: "Only a person at a terminal can do the rerun"), which both `rerun_interactive` and the `OWNER_NOT_CLAIMED` warning carry; those reruns are built without `--json` (`thisCommand([], { terminal: true })`), and their `data.rerunNote` is "in a terminal" ("in a terminal, and confirm cf's prompt" when cf refused the upload) or "at a terminal" for the warning. Hand those commands over as they are, never with `--json`; with it added the run stops at the same point again. Every suggested command starts the way the CLI was started (`everyapp`, `pnpm everyapp`, `npx everyapp`; `invocation` in `packages/cli/src/lib/output/command.ts`).
- A warning is emitted once per run; `done` carries `data.durationMs`, and for setup and deploy `data.facts` and `data.next`.
- "Interactive" means `canPromptInTerminal` (`packages/cli/src/lib/output/prompt.ts`): stdin and stderr are TTYs, no `--json`, and no `CI` environment variable; piping stdout changes nothing. Without `--json` and without a terminal on stdin and stderr (an agent's shell, CI), setup stops at `cloudflare_login` with no device code ("Log in to Cloudflare with pnpm everyapp login. Unattended? Set CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID instead."): only `--json` hands cf's device link and code over (`onDeviceLogin` is wired when `flags.json` in `packages/cli/src/commands/setup/runSetup.ts`; `logIn` in `packages/cli/src/lib/cf/account.ts`). Always pass `--json`.

## The setup procedure

### Step 1: ask which domain

Ask the person which domain (on Cloudflare) the Gateway should live under and propose `apps.<domain>`. The rules, from `packages/cli/src/commands/setup/deployGateway.ts` and `runSetup.ts`:

- Any hostname under one of the account's active zones works. Apps get one label below it: the Gateway at `apps.example.com` puts an app at `todo.apps.example.com`.
- Under `--json`, a new install needs `--domain`: without it setup fails with `DOMAIN_REQUIRED` ("Choose the Gateway's address with --domain", `data.zones` lists the account's active domains). Once the install row exists `--domain` is optional: the host is remembered, and an install that stopped before its first upload may still move to another name.
- The Gateway can't move once it is live: `--domain` naming another host fails with `DOMAIN_CHANGE_UNSUPPORTED`, whose `data.rerun` is the command without `--domain`.
- A zone apex (`--domain example.com`) is allowed with the warning `GATEWAY_AT_ZONE_APEX`: the sign-in cookie covers every subdomain and apps take names directly under the domain; `data.suggestedDomain` is `apps.example.com`.
- A `--domain` that isn't a full hostname is refused before anything is asked of Cloudflare.

```bash
pnpm everyapp setup --domain apps.example.com --json
```

### Step 4: resume

Exit 2 means a person has to do something; once they have, run `data.rerun` as it is: it is this same command, `--json` included when this run had it, and so is each `choices[].rerun` (`choose_account` names one per choice). Only a `rerun` that names another command (`install_gateway` names setup) is written without `--json`: add it to that one. Every step looks at what is there first and acts only on what is missing, so a rerun never repeats work:

- A login already approved, a plan already paid, a zone now active: the run passes those steps.
- An install that stopped before its first upload resumes from its install row (`data.change: "resume"`); `--domain` is optional and may still be another name. One that stopped after it (`register_workers_subdomain`: the Worker and its Custom Domain are live, the row names no version) resumes the same way: the hostname's placeholder record and the Worker count as this install's own (`gateway.resume`), with no `DNS_RECORD_CONFLICT` and no terminal. When the row did record the version but not the hostname, the rerun is `change: "resume"` too, start "Finishing the Gateway's first publication at `host` (`release`)" and ok "The Gateway (`release`) is live at `url`", `data.gateway: "installed"` in `done`; `repair` is for app drift on a Gateway that is live.
- The owner link: each run that reaches the owner step with no owner mints a new link, and any earlier unused one stops working (`data.replaced: true`, message "Open this new link…"). Don't rerun setup while the person is still about to open a link they have; rerun it when they report they opened it (the run finds the owner) or lost it (a new link).
- A live Gateway on the same release: `setup.gateway` skip and `data.gateway: "up-to-date"`; nothing is uploaded.

## Recommended: put Cloudflare Access in front

`everyapp access on|off|show` (`packages/cli/src/commands/access/command.ts` and `index.ts`, with `packages/cli/src/lib/access/plan.ts`, `record.ts` and `sync.ts`; the person's page is [/docs/access](/docs/access), the reference [/docs/agent/access](/docs/agent/access)). It is the default: `setup` puts it in front once the owner exists, offered at a terminal ("Put Cloudflare Access in front of your Gateway?", Yes by default) and done without a question under `--json` or `--yes`; with no Zero Trust team it stops on `ACCESS_TEAM_REQUIRED` until the person picks the name (`setup --team <name> --json`). Only `--no-access`, a No, or an earlier `access off` leaves it off, remembered, with the warning `ACCESS_SETUP_SKIPPED` (not recommended); never add `--no-access` unless the person says so. The Gateway signs people in by itself without it. Step by step for an agent: `packages/cli/skills/everyapp/setup/access.md` (in an app `.claude/skills/everyapp/setup/access.md`). What Access adds to the security boundary: [/docs/agent/repo/threat-model](/docs/agent/repo/threat-model) (assets, actors, trust boundaries, one testable invariant per boundary).

```bash
pnpm everyapp access on --json
```

What it does, from the Cloudflare login alone: finds or creates the Zero Trust team, keeps both ways to sign in (Sign in with Cloudflare for the members of the operator's Cloudflare account, and Access's one-time PIN, a code emailed to everyone else; each created when the team lacks it), keeps the allow policy "Every App gateway members" with every member's and invitee's email, puts one Access application in front of the Gateway's host and one in front of the apps' hosts (the Gateway's `/mcp`, the OAuth endpoints and `/health`, and each app's public routes and, where its manifest sets `mcp`, its `/mcp`, stay reachable without a login), and sets the three Gateway settings `CLOUDFLARE_ACCESS_TEAM_DOMAIN`, `CLOUDFLARE_ACCESS_APPS_AUD` and `CLOUDFLARE_ACCESS_AUD` in one new version. It is rerunnable and changes only what differs; it never removes anyone from the policy. The settings are written when one is missing on the Worker, an application was just created, nothing recorded what they were set to, or the record `access on` keeps in the Gateway's D1 (table `_everyapp_access`, `packages/cli/src/lib/access/record.ts`; values can't be read back from a Worker) names another team or other AUD tags (an application recreated by hand); `done.data.settings` says `outcome` `set` with that `reason` (`missing`, `created`, `unrecorded`, `changed`, or `asked` for `--write-settings`), else `kept`.

Handoffs and stops:

- No members or invitations yet, no `--email`, and no policy from an earlier run: `error` `ACCESS_NOBODY_ALLOWED` ("Nobody to let in yet … Claim the Gateway first, or name who will (the setup link is then behind Access too)."), `data.rerun` `pnpm everyapp access on --email <your address>`. Two ways on: finish setup first, or, when the person wants Access up before the claim, run that rerun with their address (the owner link is then behind Access). An `--email` with no account on the Gateway yet: warning `ACCESS_EMAIL_NOT_INVITED` ("Access will let them through, but the Gateway refuses anyone it doesn't know. Invite them in Manage workspace → Users.", `data.emails`).
- The account has no Zero Trust team: `error` `ACCESS_TEAM_REQUIRED` with `data.suggested` (the zone's first label). The team name is permanent: its sign-in page is `<name>.cloudflareaccess.com` for good. Ask the person (table above), then rerun with `--team <name>`. Lowercase letters, digits and dashes (`ACCESS_TEAM_INVALID`); a name taken elsewhere on Cloudflare fails with `ACCESS_TEAM_CREATE_FAILED`: ask for another.
- A hosted Gateway: `error` `ACCESS_HOSTED`; hosted Gateways ignore the Access settings.
- `done.data.signIn`: `url`, `pending` (the emails of members who have a password and no Access identity yet) and `first` (`both`: Access's chooser between Sign in with Cloudflare and the emailed code, the usual case; `pin`; `idp`). Tell the person: each of those people opens the Gateway once, picks Sign in with Cloudflare if they are a member of the Cloudflare account (it asserts that account's email, which must be their Gateway address: `ACCESS_LOGIN_NOT_MEMBER` warns when the login's isn't) or gets a code from Access by email, then signs in with their Gateway password as usual; after that Access alone signs them in. `done.data.signInMethods` lists the providers; `done.data.identityProviders` says which of the two this run created. `done.data.next` lists `pnpm everyapp secret set EMAIL_PASSWORD_SIGN_IN` (`false`, once everyone has linked Access) and, with `--email-domain`, `CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS`; run either only when the person asks.
- Run `access on` again after the person invites someone, so Access lets them in. `access show --json` reports without changing anything: `data.on`, and `data.fixes` lists `pnpm everyapp access on` when something differs from what `on` would make. `access off` asks first ("Turn Cloudflare Access off for `host`?"); under `--json` without `--yes` it is `error` `CONFIRMATION_REQUIRED` ("Turning Access off needs confirmation at a terminal, or --yes") with `--yes` in `data.rerun` and `data.authorize: true`: add `--yes` only on the person's word.
- Behind Access, `setup` warns `ACCESS_IN_FRONT` before the owner link. A deploy's live wait can't see past Access either, so once Access answers its request it only reads the app's row while the Gateway, nudged through its activation queue (its per-minute cron as the fallback), makes the app live (`progress` "Waiting for the Gateway to make <app> live"), and ends live like any other deploy; only after 10 minutes still deploying does it warn `ACCESS_IN_FRONT` ("The deploy stalled", `data.rerun` `status`) and skip `app.live`.
- After `app.live`, every deploy (and `delete`) keeps the apps application in step when one exists (`syncAppsAccessAfter` in `packages/cli/src/lib/access/sync.ts`): `step` `app.access` ok "Cloudflare Access lets `appId`'s `<public routes | /mcp | public routes and /mcp>` through." or skip "Cloudflare Access already matched `appId`'s `<…>`." (`data.changed`, `data.removed`; the words follow what the manifest opens: its `public` routes, its `/mcp` where it sets `mcp`, or both). A login that can't read Access warns `ACCESS_NOT_CHECKED` (only when the app has public routes or sets `mcp`), a failed update `ACCESS_SYNC_FAILED`, both with `data.rerun` `pnpm everyapp access on`; neither fails the deploy, and nothing is emitted when Access isn't in front.

## Create, run, deploy, share

### Create

```bash
everyapp create <name> --json
```

From `packages/cli/src/commands/create/index.ts`, `command.ts` and `steps/appId.ts`:

- From an everyapp installed with npm (`everyapp create <name>`, no checkout), the template comes packed in the package (`packages/cli/scripts/bundle-starter.mjs`, `templateSource` in `packages/cli/src/lib/checkout.ts`) and the app goes in `./<name>` wherever it runs, or where a path names. Each app is its own git repository (one repository per app): its `package.json` takes `@every-app/sdk` and `everyapp` from npm at the published range (`^<version>`, from `packages/cli/src/lib/app/publishedVersions.ts`), and its first commit includes the `pnpm-lock.yaml` its install wrote. From a checkout, run it from the every-app folder with a path beside it, `pnpm everyapp create ../<name>`: that app is its own repository too, but linked to the checkout (`link:` to its `packages/sdk` and `packages/cli`), so its `pnpm run deploy` runs the checkout's CLI, which can rebuild and rebind a Gateway set up from the checkout (the npm CLI can't: `GATEWAY_RELEASE_UNAVAILABLE`). It gets no Release workflow, since its links install only next to the checkout. `create` says which it did: "Linked to this checkout" or "Pinned to everyapp ^<version>" (step `create.deps`, `data.kind` `linked` or `published`); for someone with many apps, a folder of apps inside the checkout also works: a bare `pnpm everyapp create <name>` from anywhere in the checkout makes `apps/<name>`, untracked by git, no repository of its own.
- The argument is a path when it has a slash (or a backslash on Windows) or starts with `.`, `~` or `/` (`isPathArgument` in `steps/appId.ts`): resolved from the current directory, `~` (`~/` or `~\`) being the home directory, and its last part is the name. A path outside the checkout is the "anywhere else" rule above; `apps/<name>` inside it (or `../../apps/<name>` from `packages/cli`) is the inside rule; any other place inside the checkout is refused, `APP_DIR_IN_CHECKOUT`, with a `data.fix` naming the two places it can go. A bare name goes in `apps/<name>` inside the checkout and in `./<name>` anywhere else.
- The name becomes the app id and part of its address, `<name>.<app base domain>`. Rules: `^[a-z]([a-z0-9-]*[a-z0-9])?$`, 64 characters or fewer, no `--`, not reserved for the platform. A bad name is `error` `INVALID_APP_ID` with a `data.fix` that suggests a slug ("Analytics_App" becomes `analytics-app`; for a path, its last part). Under `--json` the name is required: `APP_ID_REQUIRED`.
- Run from inside an app: `NESTED_APP`. The directory exists: `APP_DIR_EXISTS`.
- Steps: `create.copy` (the starter, `starter`), outside the checkout `create.deps` (where the SDK and CLI come from: `data` `{ kind: "linked", root }` from a checkout, `{ kind: "published", version }` from npm), `create.skill` (the everyapp and build-every-app skills copied to `.claude/skills/<name>` and `.agents/skills/<name>`, and `AGENTS.md` pointing at both: "Before running everyapp, read the everyapp skill: `.agents/skills/everyapp/SKILL.md`" and "To build or change this app, read the build-every-app skill: `.agents/skills/build-every-app/SKILL.md`"), `create.install` (a failure is `INSTALL_FAILED` with rerun `cd <dir> && pnpm install`: the app exists, only the install is left), `create.types` (warning `WORKER_TYPES_FAILED`; `pnpm dev` tries again), `migrations.local` (warning `MIGRATIONS_FAILED`), and outside the checkout `create.git` (warning `GIT_FAILED`).
- `done.data`: `appId`, `dir` (absolute), `next` (`cd <dir>` with the path to type from where create ran, `cd ../<name>` for the default and the whole path when it was given absolute or from `~`; `pnpm dev` "run it locally"; `pnpm run deploy` "put it live"; the app's `package.json` scripts `dev` and `deploy` run `everyapp dev` and `everyapp deploy`, `starter/package.json`). Nothing is deployed: the deploy is the next command, from the app's directory ([Deploy](#deploy)).
- `--yes` asks nothing (a name is then required). `--verbose` streams the install and git output to stderr.

Then `cd` into it (the `next` line) and work in its `src/`; the manifest is `everyapp.config.ts`; `pnpm dev` runs it ([Run locally](#run-locally)). The Gateway handles sign-in: never add a login page.

### Run locally

```bash
pnpm everyapp dev
```

From the app's directory (`pnpm dev` runs the same thing). It is long-running and human-facing, and takes no `--json`: start it in the background and read the printed URL, `http://<app-id>.localhost:8787` (`--port`, or `$PORT`, default 8787). A busy port is `error` `DEV_PORT_IN_USE` ("Port 8787 is already in use") with `data.rerun` `pnpm everyapp dev --port <free>` (`data.free`; `packages/cli/src/commands/dev/gatewayServer.ts`). The person is signed in as a seeded dev user. Stop it with Ctrl+C (SIGINT) to the everyapp process, which signals cf dev's own process group; never a pattern kill of vite or workerd, which hits other projects too (pnpm prints ELIFECYCLE after a clean Ctrl+C). A `pnpm install` or a deploy while dev runs rebuilds `packages/sdk/dist` (the root `postinstall`) and breaks dev for a few seconds. Reference: [/docs/agent/dev](/docs/agent/dev).

### Deploy

```bash
pnpm everyapp deploy --json
```

From the app's directory; an agent runs `pnpm everyapp deploy --json` there. `pnpm run deploy` is the same command as a person runs it, the user docs' spelling (the template's `package.json` script `deploy` is `everyapp deploy`). Nothing is asked first: the first line, step `app.deploy`, says "Deploying `appId` to `gatewayHost` (`organizationName`)". From `packages/cli/src/commands/deploy/command.ts`, `index.ts`, `deployApp.ts` and `steps/offerGateway.ts`:

- No Gateway in any account the login sees: `action_required` `install_gateway` (exit 2): "Install a Gateway first: `account` has none yet. Apps deploy behind one. Setup needs a person once, to create the owner account." `data.rerun` is `pnpm everyapp setup --domain apps.<zone>` (the account's first active zone, or the placeholder `<hostname>` when it can't tell), with `data.accounts` and `data.domain`. Ask the person, run the setup procedure, then deploy again. At a terminal the same deploy asks "Install a Gateway at apps.`zone`?" and runs setup inline, owner link included; `--yes` installs there without asking; declining is `CANCELLED` (exit 1, nothing deployed).
- Login under `--json`: `cloudflare_login` on step `app.login`, as in setup.
- Which Gateway: the one the login finds in its accounts; its URL always comes from the install row. `--gateway <url>` (or `EVERYAPP_GATEWAY_URL`) and `--account-id <id>` only pick among several (`requestedGatewayUrl` and `connectToGateway` in `packages/cli/src/lib/gateway/connect.ts`). A URL whose host isn't the Gateway found: `error` `GATEWAY_URL_MISMATCH` ("The Gateway here is `found`, not `host`", "For `host`, pass its account with --account-id"), with `data.rerun` the command without `--gateway`, or when the URL came from the environment the fix "unset EVERYAPP_GATEWAY_URL to use `found`" (`checkGatewayUrl` in `packages/cli/src/lib/gateway/discover.ts`). Not a full URL: `INVALID_GATEWAY_URL`.
- Steps: `app.connect`, `app.register` (a first deploy carries the access facts below), `app.domain` (a new hostname's DNS check, before anything is created: the same `DNS_RECORD_CONFLICT`, `DNS_UNREADABLE` and `ZONE_CUSTOM_DOMAIN_LIMIT` as setup, `--force-dns` the takeover, and the warnings `CUSTOM_DOMAIN_OWNER_UNCHECKED` and `ZONE_CUSTOM_DOMAIN_LIMIT_NEAR` as in setup's domain row; `preflightAppHost` in `packages/cli/src/lib/domains/preflight.ts`), `app.resources` (D1, KV and Hyperdrive created or found, `progress` "Created …"; warning `RESOURCE_RECREATED` means a database or namespace the app used before is gone from the Cloudflare account and a new, empty one was made: tell the person), `app.install`, `app.build`, `app.schema` (drizzle migrations that don't describe the schema stop the run before anything changes: `error` `SCHEMA_DRIFT`, headline "The schema has changes no migration covers", `data.rerun` `pnpm db:generate` with `data.rerunNote` "then run this again", in the app's directory; `packages/cli/src/commands/deploy/steps/checkSchemaDrift.ts`), `app.migrations` (a restore point first; `pnpm everyapp db restore --json` undoes it, only when the person asks), `app.upload`, then for a new app or a new hostname `app.bind`, with `gateway.upgrade` ("Upgrading the Gateway `from` → `to`", or "Redeploying the Gateway … (…; not the live release)" for the same version from other sources, `data.sameVersion`) nested inside it, between `app.bind` start and ok, only when the rebind can't deploy the live Gateway's own release again ([Keeping things up to date](#keeping-things-up-to-date); an older one is refused: `DOWNGRADE_REFUSED`), then `app.live`, then `app.access` when Cloudflare Access fronts the apps ([above](#recommended-put-cloudflare-access-in-front)). A redeploy of an app the Gateway already binds has no `app.bind`: it goes from `app.upload` to `app.live` (`bindIfNeeded` in `packages/cli/src/commands/appGateway.ts`). The other steps (`app.email`, `app.hyperdrive`, `app.helper`, `app.workflows`): [/docs/agent/deploy](/docs/agent/deploy).
- Takeover errors, each with `data.authorize: true` and the flag in `data.rerun`: `DNS_RECORD_CONFLICT` (`--force-dns`), `DURABLE_OBJECT_REMOVED` (`--allow-delete-durable-object-data`), `WORKFLOW_REMOVED` (`--allow-delete-workflows`), `EMAIL_ROUTING_DISABLED` (`--enable-email-routing`), `CONFIRMATION_REQUIRED` (`--yes`). Show the error, ask, and rerun with the flag only on yes. `DOWNGRADE_REFUSED` when the checkout is behind the live Gateway: `git pull`, same command. `rerun_interactive` when the app's Worker was changed outside everyapp.
- `app.live` (`packages/cli/src/commands/deploy/steps/waitForLive.ts`, `awaitLive` in `appGateway.ts`): the deploy waits up to 10 minutes for the registry to say `active`, requesting `https://<hostname>/` every 3 s, with a `progress` line every 15 s (`data.waitedMs`, `data.answered`). Live: `step` ok with `data.url` and, when the wait showed, `data.waited` (`certificate` or `live`). Not live: a `warning` says why, then `step` skip with no `data.reason`: `CERT_PENDING` (no answer in 10 minutes; "goes live on its first visit once it has one", `data.hostname`, `data.fix` about the zone's CAA records), `ACCESS_IN_FRONT` (10 minutes behind Cloudflare Access with the Gateway's cron never making it live: "The deploy stalled", `data.rerun` `pnpm everyapp status`), or `APP_DISABLED` (switched off in Admin → Apps). The Gateway answered but the app never went `active` in 10 minutes: `error` `APP_NOT_LIVE`, retryable, `data.rerun` `pnpm everyapp status` "then deploy again". With `--no-wait` there is no wait: ok at once for an app that was live before this redeploy, otherwise skip with `data.reason` `certificate` (a new hostname) or `first-visit` (a hostname already published). `data.reason` `outside-base` (the hostname isn't one label below the app base domain; warning `APP_HOST_OUTSIDE_BASE`, never routed, never waited for). Warning `LOCAL_DNS_STALE`: live, but this computer's resolver has no address for it yet.
- After the upload, step `app.secrets` warns `APP_NEEDS_SETUP` ("`<app>` won't open until `<names>` is set", the first unmet setting's `why` under it, `data.setup`) when a required setting is unset, and `next` gets the one command that opens it, `pnpm everyapp configure <app>` (note "asks for each; `<app>` opens once they are set"). The run goes on; the app is live but answers its setup gate until then ([/docs/agent/manifest](/docs/agent/manifest#required-optional-or-one-of-a-group)).
- `done.data`: `url`, `workerName`, `versionId`, `live` (boolean), `organization`, `publicRoutes` (`[{ path, methods }]`, what the manifest opens to the internet), `next`.
- Safe to repeat; a redeploy of an app the Gateway already serves never touches the Gateway.
- Someone else's app from GitHub, no clone: `pnpm everyapp install https://github.com/<owner>/<repo> --json` deploys its latest release's `everyapp-release.tar.gz`. `NO_RELEASE`: clone it, `pnpm install` in it, then this checkout's `pnpm everyapp deploy` from its directory (a clone's own CLI copy can't deploy: a deploy updates the Gateway, which only a checkout builds). Never build a repository from its URL yourself.

### What to tell the person after a deploy

Three facts the human sink prints, which you reconstruct from the events (`packages/cli/src/lib/output/events.ts`, milestones `app.live` and `app.register`); `formatFacts` (`packages/cli/src/lib/output/table.ts`) pads every label in the block to the longest one, so under `Who can open` the `Live` and `Public` lines print wider than these samples:

- `Live  https://<app>.<base>` from `app.live` ok (`data.waited: "certificate"` adds `Certificate issued` above it). Not live yet: `URL …`, plus a `Status` line only when the skip carries `data.reason` (a `--no-wait` run): `Goes live on its first visit, once its certificate comes (a few minutes)` for `certificate`, `Goes live on its first visit` for `first-visit`; `outside-base` prints `Live  Not routed`. After a waited run that stopped on `CERT_PENDING`, `ACCESS_IN_FRONT` or `APP_DISABLED`, the skip has no `reason`: tell the person what that warning said.
- `Who can open  … · change it at https://<gateway>/admin/apps` from `app.register` ok on a first deploy (`data.firstDeploy: true`): `data.scope: "shared"` → "Members of every organization (shared app)"; `data.defaultAccess: true` → "Everyone in `organizationName`"; `data.deployerAccess: false` → "Private to owners and admins"; otherwise "Private to you, owners and admins". `data.hasOwner: false` adds "The Gateway has no owner yet; its first owner gets the app (pnpm everyapp setup)".
- `Public  Open to the internet without sign-in: GET /hooks/*, POST /collect` from `app.register` ok `data.publicRoutes` (also on `done.data`): the manifest's `public` routes, the first six, then `… and N more (everyapp.config.ts public)`; nothing when the manifest has no `public`. Say it: those routes answer without sign-in.
- The admin URL `https://<gateway>/admin`; the app shows under **All apps** on the Gateway. A redeploy keeps the app's data.
- Warning `APP_NEEDS_SETUP` means a required setting is unset: the app shows **Needs setup** on the Gateway and opens its setup dialog instead, and its tools stay out of `/mcp` until it is. `done.data.next` carries the one command, `pnpm everyapp configure <app>` (note "asks for each; `<app>` opens once they are set"): the person runs it at a terminal, or an agent pipes `NAME=value` lines into it or adds `--from-env` ([AI keys and app secrets](#ai-keys-and-app-secrets)); it ends with `<app> is ready`, and `pnpm everyapp secret list <app> --json` shows `data.app.setup.ready: true`.
- Then `pnpm everyapp status --json`: its `data.next` says what to do with the app now that it is live (invite people, connect an AI client, an AI key the app runs without), each with a `why` to pass on ([Verification checklist](#verification-checklist)).

### Invite people

Invitations are in the Gateway UI, not the CLI ([/docs/people](/docs/people)): **Manage workspace** at the bottom of the sidebar → **Users** → **Invite user**, email and role (**Member** opens the apps they're given; **Admin** also invites and manages apps). Without email set up the UI offers **Copy invite link**, which expires after 72 hours. Who opens an app: **Apps** → **⋯** → **Manage access**, or **Edit app** → **Available to everyone**. **Deactivate** removes someone everywhere at once.

Email, so invites and resets go out by mail: the person onboards the domain in the Cloudflare dashboard (**Compute & AI** → **Email Service** → **Email Sending** → **Onboard Domain**), then the Gateway settings are set with `secret set`: `EMAIL_FROM` (an address at that domain) and a display name, from `EMAIL_FROM_NAME` or embedded as `EMAIL_FROM="Name <address>"`; without both the Gateway has no sender (`parseEmailSender` in `packages/sdk/src/internal/email.ts`). Under `--from-env` one name per command (`SECRET_SEVERAL_NAMES` otherwise). Step by step: `packages/cli/skills/everyapp/setup/email.md` (in an app `.claude/skills/everyapp/setup/email.md`); the person's steps are in [/docs/people](/docs/people#send-email).

### Connect an AI client

The person connects Claude, ChatGPT, Claude Code or Cursor to the Gateway's one MCP address, `https://<gateway>/mcp`, once: the assistant signs in to the Gateway as them and asks which apps it may use. The steps per client are in [/docs/connect-ai](/docs/connect-ai) (Claude Code: `claude mcp add --transport http everyapp https://<gateway>/mcp`, then `/mcp` → **everyapp** → **Authenticate**); a tool that can't sign in takes a personal access token from **Admin** → **Tokens** → **New token** as `Authorization: Bearer`. Connections are listed and revoked under **AI connections** (`https://<gateway>/settings/connections`). It works behind Access. Reference: [/docs/agent/mcp](/docs/agent/mcp).

### AI keys and app secrets

```bash
pnpm everyapp configure <app> --from-env --json
```

From `packages/cli/src/commands/configure/index.ts`, `packages/cli/src/commands/secret/index.ts` and `packages/cli/src/lib/secretValue.ts`:

- `pnpm everyapp configure <app>` sets up everything the app's manifest declares (its AI providers, capabilities and own secrets): from anywhere once the app is deployed (its deployed manifest), or in its directory before that, for the Gateway's settings. At a terminal it shows what is set (names only, never values), asks for each required setting that isn't with why and where to get it, asks which member of an any-of group, offers the optional ones, and sets each where it is held in one go. One name by itself is `pnpm everyapp secret set NAME [--app <id>]` (`pnpm everyapp secret set OPENAI_API_KEY --from-env OPENAI_API_KEY --json` for an agent). Reference: [/docs/agent/secrets](/docs/agent/secrets#everyapp-configure-app).
- `OPENAI_API_KEY` (and `OPENROUTER_API_KEY`, `EMAIL_FROM`, …) are Gateway settings: set from any directory, live at once, no deploy. Every app that uses AI goes through the Gateway's key. Step by step per provider: `packages/cli/skills/everyapp/setup/openai.md`, `setup/openrouter.md`, `setup/workers-ai.md`, `setup/dataforseo.md`, `setup/context.md` (the index `setup/README.md` lists them all; in an app under `.claude/skills/everyapp/setup/`). `DATAFORSEO_API_KEY` can also back an MCP app: `pnpm everyapp mcp on dataforseo --json` offers DataForSEO's tools to members' AI clients at `/mcp` with the Gateway's key, nothing to deploy; it shows **Needs setup** until the key is set (`PROVIDER_KEY_UNSET` names it). `mcp list --json` says which are on and whether each key is set. Reference: [/docs/agent/mcp](/docs/agent/mcp#mcp-apps).
- A value never comes from the command line (`configure NAME=value` is refused, `VALUE_ON_COMMAND_LINE`; a second argument after the app id, or `--from-env=<value>`, is refused by the argument parser before that, `TOO_MANY_ARGUMENTS` or `INVALID_VALUE`, with the value cut out or never shown and the line `A value never goes on the command line: it lands in the shell's history and the process list. Rotate it if it was real.`; nothing is set). Under `--json` there is no prompt: `configure <app>` takes `NAME=value` lines on stdin (one per line; blank lines and `#` lines skipped, an `export ` prefix allowed, one pair of quotes around a value dropped, the value otherwise as it is; a line that isn't `NAME=value` is `PIPED_LINE_INVALID` and never echoed, since a bare value piped in may be a secret; a name the manifest doesn't declare is `SECRET_NOT_DECLARED`, echoed only when it looks like a setting name; a blank value `SECRET_EMPTY`; each refused before anything is written) or, with `--from-env`, each unset setting from the environment variable of its own name (`DATAFORSEO_API_KEY` from `$DATAFORSEO_API_KEY`; a set name is never replaced, so a pair with one name set gets only the other; stdin isn't read); the two never combine. `secret set NAME` takes `--from-env VAR` or one piped value. With nothing to read and a required setting unset: `error` `SECRET_VALUE_REQUIRED` ("Can't ask for <app>'s settings without a terminal", then "<app> needs <names>. Run this at a terminal, pipe NAME=value lines in (one per line), or export them under those names and add --from-env (which also takes the variable of any unset optional setting).", `data.names` the names still missing, `data.rerun` `pnpm everyapp configure <app> --from-env` once deployed, `pnpm everyapp configure --from-env` in the app's directory before its first deploy; from `secret set`: "Can't ask for …'s value without a terminal", `data.rerun` `pnpm everyapp secret set NAME --from-env NAME`; its variable unset: `SECRET_EMPTY`). The value is the person's: if it isn't already in your environment, hand them the interactive command to run themselves (table above). Never ask for it in chat, never print it.
- An app's own secret (`GITHUB_TOKEN`, …) must be listed under `secrets` in its `everyapp.config.ts` and is set after its first deploy: `configure <app>` from anywhere, or `secret set` from the app's directory or from anywhere with `--app <id>` (against the manifest its last deploy stored). Before that deploy, `configure` in the app's directory sets the Gateway's settings and leaves the app's own for after it (`next` `pnpm everyapp deploy`, then `pnpm everyapp configure <id>` for them; while a Gateway setting is still missing, `next` is `pnpm everyapp configure` with note `in the app's directory: …`; a piped own secret is `APP_NOT_FOUND`, "`id` isn't deployed yet. Its own NAME can be set after its first deploy. Nothing was set."), and `configure <id>` by name is `APP_NOT_FOUND` ("`id` isn't deployed to this Gateway", `data.rerun` `pnpm everyapp status`; a row whose first deploy never finished, `status: "pending"`, counts as undeployed). From `secret set` before that deploy: `error` `APP_NOT_FOUND` ("`id` isn't deployed yet. Its secrets can be set after its first deploy. Nothing was changed.", `data.rerun` `pnpm everyapp deploy`). A name the manifest doesn't list: `SECRET_NOT_DECLARED`, whose `data.fix` quotes the `secrets: […]` line to add and whose `data.rerun` is `pnpm everyapp secret set <name>`; no `everyapp.config.ts` in the directory and no `--app`: `SECRET_NOT_DECLARED` with fix "cd into the app's directory and run this again, or add --app <id>"; `--app` naming an app that isn't deployed: `APP_NOT_FOUND` ("`id` isn't deployed to this Gateway") with `data.rerun` `pnpm everyapp status`; a Gateway setting or declared name typed in another case or without its underscores: `SECRET_NOT_DECLARED` with `data.didYouMean` and a corrected `data.rerun`. Later deploys keep it. For `dev`, the person puts it in the app's `.dev.vars`.
- `pnpm everyapp secret list <app> --json` (from anywhere; in the app's directory the id can be left out) names what is set and what the app still needs, never values: `data.app.setup` has `ready`, `unmet` (each with `names`, `holder`, `need.kind`, `why`, `docs`, `setup`, the guide file) and `command`, `{ command: "pnpm everyapp configure <app>" }`, the one command that opens the app (`null` once it is ready). `pnpm everyapp status --json` carries the same per app as `data.apps[].setup`, and lists `APP_NEEDS_SETUP` in `fixes`. Reference: [/docs/agent/secrets](/docs/agent/secrets), the shape on [/docs/agent/json](/docs/agent/json#done).

## Keeping things up to date

- The Gateway, from an everyapp installed with npm: `npm install -g everyapp@latest`, then `everyapp update --json`, takes the published release for that version (`--release` names another; `status` says where the live one came from: `data.release.origin`, `data.release.gitSha`, and the Release row "from every-app/every-app release gateway-v…" or "from a checkout at …"). In a checkout: `git pull && pnpm install`, then `pnpm everyapp update --json` (`packages/cli/src/commands/update/command.ts`; `setup --json` does the same). It takes setup's flags without `--domain`, upgrades the Gateway where it is (migrations first, with a restore point) and keeps its data, users and apps. It never installs one: with none, `GATEWAY_NOT_FOUND` with rerun `pnpm everyapp setup --domain <hostname>`; an install that never uploaded is `GATEWAY_NOT_INSTALLED`. `done.message` "Upgraded to `releaseName`" and `data.gateway: "upgraded"`; already current: `setup.gateway` skip and `data.gateway: "up-to-date"`. On a live self-hosted Gateway behind Cloudflare Access, `update` (and `setup`) then brings both Access applications in line with what this release lets through (its bypass paths, the sign-in methods `access on` vouches for, the policy), under the `access` lease, as step `gateway.access` (`ok` when one changed, `skip` when both matched; [Cloudflare Access](/docs/agent/access#how-update-keeps-both-applications-in-step)): a rollout that moves a Gateway path never leaves the live bypass list behind. Whether Access is on is read from the live applications, so `access off` stays off; a failure there is the warning `ACCESS_RECONCILE_FAILED` (or `ACCESS_NOT_CHECKED` when the applications couldn't be listed) with `data.rerun` `pnpm everyapp access on`, never a failed update; an application deleted by hand is `ACCESS_APPLICATION_MISSING` (nothing is created: that is `access on`'s job). The Gateway's three settings aren't rewritten by `update`: an AUD tag that changed is `access on`'s to fix.
- A deploy that rebinds the Gateway (a new app or a new hostname) or a delete deploys the live Gateway's own release again, had from where the install row says it came (`packages/cli/src/lib/gateway/liveRelease.ts`: its GitHub release by tag, its URL or file, or this checkout's build cache for the row's tree hash; step `gateway.release` "Using the live Gateway … from …"), so deploying or deleting an app never changes the Gateway's code. When that release can't be had again (a row from before origins were recorded, a file that is gone, a checkout that hasn't built that tree, an everyapp outside a checkout facing a checkout-built Gateway, a tag that is gone or whose asset was replaced), the command stops before anything changes with [`GATEWAY_RELEASE_UNAVAILABLE`](/docs/agent/errors#gateway_release_unavailable): run `pnpm everyapp update` (it records where the new Gateway came from), then the same command. A redeploy of an app the Gateway already binds never touches it, however new the checkout is; `status` then lists `GATEWAY_OUTDATED` ("Your every-app folder has a newer Gateway than the one online", detail "Run update now, or leave it: the next new app's deploy updates it too.") as `severity: "info"`, with `run` `pnpm everyapp update` and `note` "updates it now"; it comes last in `fixes` and doesn't count in `message` (`packages/cli/src/commands/status/problems.ts`).
- `DOWNGRADE_REFUSED` (`packages/cli/src/lib/gateway/apply.ts`): "This checkout's Gateway (…) is older than the live one (…)", or "The Gateway from … is older than the live one (…)". Someone deployed with a newer everyapp: `npm install -g everyapp@latest` (in a checkout, `git pull && pnpm install`), then the same command. From `setup` and `update` the error's `data.rerun` adds `--allow-downgrade` with `data.authorize: true`; use it only for a rollback the person asked for.
- `CLI_TOO_OLD`: the release needs a newer everyapp; `npm install -g everyapp@latest` (in a checkout, `git pull`).
- An app: `pnpm everyapp deploy --json` in its directory. Its data stays; a change to what it stores needs a migration (`pnpm db:generate`) or the deploy stops with `SCHEMA_DRIFT` at `app.schema`.
- After either, `pnpm everyapp status --json`.

## Verification checklist

`pnpm everyapp status --json` reads the Gateway's D1 and cf, asks nothing of the Gateway over HTTPS, and ends with one `done` event (`packages/cli/src/commands/status/index.ts`, `problems.ts`). Its `message` is "Gateway https://…: N apps live, nothing to fix" or "… M problems to fix". Its `data.next` says what isn't done yet (`next.ts`): at most four `{ code, command?, url?, note, why }`, an AI key, an [MCP app](/docs/agent/mcp#mcp-apps) to turn on, Cloudflare Access, people to invite, an AI client to connect, the first app, email, each from the Gateway's state and gone once it changes, never repeating a fix (the codes and the reads on [/docs/agent/json](/docs/agent/json#status---json)). After the fixes are done, tell the person each step's `why` and offer its `command` or `url`. No Gateway in any account the login sees (a setup that stopped before the database was created): `status` stops with `action_required` `install_gateway` (exit 2), "No Gateway in `account`'s Cloudflare account (logged in as …). Gateway in another account? Log in to it: pnpm everyapp login", `data.rerun` `pnpm everyapp setup` ("installs one"), `data.accounts` (`existingGateway` in `packages/cli/src/lib/gateway/connect.ts`). That rerun carries no `--domain`: add `--domain <host>` before running it under `--json`, or `DOMAIN_REQUIRED` follows.

| `gatewayUrl`, `appBaseDomain`       | `https://<host>` and the host apps go under.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `mode`                              | `self_hosted` (what `setup` installs: `GATEWAY_DEPLOYMENT_MODE`, set with the first upload's secrets and kept by every later one, `packages/cli/src/lib/gateway/apply.ts`) or `hosted` (EveryApp's own install of the same Gateway, `apps/every-app-gateway/src/server/platform-policy.ts`); `null` before the first upload.                                                                                                                                                            |
| `release.version`, `release.sha256` | The live release.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `versionId` = `recordedVersionId`   | The Worker serves the version setup uploaded. Different: fix `GATEWAY_CHANGED` (setup redeploys, asking first).                                                                                                                                                                                                                                                                                                                                                                         |
| `owner`, `claimed`                  | `{ email, organizationName }` and `true`. `null` and `false`: fix `NO_OWNER`, run setup for a new link.                                                                                                                                                                                                                                                                                                                                                                                 |
| `tls`                               | `true` once the Gateway host has its certificate; `null` when cf couldn't list certificates (`CERTIFICATES_UNKNOWN`). `certificates[]` has `{ host, ready }` per hostname; `CERT_PENDING` settles by itself.                                                                                                                                                                                                                                                                            |
| `inSync`                            | `true`: the live Gateway binds exactly `desiredApps` and publishes exactly `domains`. `false`: fix `BINDINGS_DIFFER`, run setup.                                                                                                                                                                                                                                                                                                                                                        |
| `upToDate`, `checkout`              | `true` when the live release was built from this checkout's Gateway sources (by tree hash); `null` when unknown (a release not built from a checkout); `false`: `GATEWAY_OUTDATED` (info; `pnpm everyapp update` updates it) or `CHECKOUT_BEHIND` (`git pull`).                                                                                                                                                                                                                         |
| `leases`                            | `[]`; an entry is a run in progress (`DEPLOY_RUNNING`, settles).                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `access`                            | `{ on, teamDomain }` (`accessStateOf` in `packages/cli/src/lib/access/settings.ts`, from the Worker's secret names and the D1 record; `teamDomain` is `null` when nothing recorded it), or `null` for a hosted Gateway, before the first upload, or when cf couldn't say (then warning `ACCESS_UNKNOWN`, "Couldn't check whether Cloudflare Access is on", detail "Cloudflare said: …").                                                                                                |
| `fixes`                             | `[]`. Each entry is `{ code, severity, message, run, note?, fix? }` (`fixData` in `index.ts`); `severity` is `error`, `warning`, `info` or `settling`, and only `error` and `warning` count as problems in `message` (`needsFixing` in `problems.ts`); `run` is the command to execute, `null` when there is none (the remedy is then in `fix`, in words, or nothing is to be done); `note` says what `run` does ("updates it now").                                                    |
| `next`                              | On a fresh Gateway `CREATE_APP` (`pnpm everyapp create ../my-app`); once the owner has claimed, `ACCESS_OFF` (`pnpm everyapp access on`, self-hosted only) and, with an app live, `INVITE` (`https://<gateway>/admin/users`, until someone is invited), `CONNECT_AI` (`https://everyapp.com/docs/connect-ai`, the note naming `https://<gateway>/mcp`), `AI_KEY`, `PROVIDER_OFFER` and `EMAIL_UNSET` as they apply, four at most. Each goes when its state changes; none repeats a fix. |

Then open `https://<gateway>/` (the sign-in page, or the owner's session) and `https://<gateway>/admin`. A fresh hostname can take a few minutes to answer over HTTPS.

### After a deploy

- `apps[]` has the app: `status: "active"`, `bound: true`, its `hostname`, `deployedBy` (the login's email, or `api-token:<account>`), `publicRoutes` (the PUBLIC column counts them) and `setup` (`null` when the manifest declares nothing to set; else `{ ready, settings, unmet, groups, command }`: `ready: false` means the app shows **Needs setup** and doesn't open until `command`, `pnpm everyapp configure <app>`, has run). `status: "binding"` with `bound: true` is `APP_BINDING`: it goes live on its first visit, so open it. `status: "pending"` is `APP_NOT_UPLOADED`: registered, but no deploy finished.
- `domains` and `liveDomains` both include the app's hostname; `inSync: true`.
- `certificates[]` shows the hostname `ready`, or `CERT_PENDING` for a few minutes.
- Open `https://<app>.<base>/`: the Gateway's sign-in, or the app for a signed-in person.
- What the Gateway UI shows (`apps/every-app-gateway/src/client/lib/appStatus.ts`): **Needs deploy** means no hostname or `status: "pending"` (the app isn't online: `pnpm everyapp deploy --json` in its directory); **Deploying** means `binding` (open it once; it goes live on the first visit); **Disabled** means an admin switched it off; **Needs setup** means it is bound and active but a required setting is unset (`status --json` `data.apps[].setup.unmet`; the setup dialog opens in its place and its tools stay out of `/mcp`: `pnpm everyapp configure <app>`); **Active** opens, except for an MCP app (`pnpm everyapp mcp on`; tier `provider`, an "MCP" chip beside its name, listed under "MCP apps"), which never opens: its tools are on `/mcp`, and its card opens the "Use it from your agent" dialog.

Fix codes `status` can report, with what `run` says:

| Code                                                                                              | Run                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Recovery

| Situation                                      | What you see                                                                                                                                                                     | What to do                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Setup stopped on a handoff                     | Exit 2 and an `action_required`.                                                                                                                                                 | Hand off (table above); when the person is done, run `data.rerun` with `--json`.                                                                                                                                                                                                                                       |
| Setup stopped before the first upload          | `status`: `GATEWAY_NOT_UPLOADED` ("Setup finishes it, then prints the link…") or `GATEWAY_NOT_INSTALLED` ("asks for the hostname again"); app commands: `GATEWAY_NOT_INSTALLED`. | `pnpm everyapp setup --domain <host> --json`; it resumes.                                                                                                                                                                                                                                                              |
| Owner link lost, expired or replaced           | `claim_owner` "Use the newer setup link, or get a new one"; `status` `NO_OWNER`.                                                                                                 | Run setup again: it mints a new link and the old one stops working. Only the person opens it. Whoever opens a link first becomes the owner; nothing in the CLI undoes a claim.                                                                                                                                         |
| The person opened the link after the run ended | The run exited 2 with `claim_owner` and `data.setupUrl`.                                                                                                                         | Run setup again: `setup.owner` skip "Owner account is …" and `done`.                                                                                                                                                                                                                                                   |
| `DOWNGRADE_REFUSED`                            | "This checkout's Gateway (…) is older than the live one (…)", `data.live`, `data.candidate`.                                                                                     | `git pull && pnpm install`, same command. `--allow-downgrade` (`data.authorize`) only for a rollback the person asked for.                                                                                                                                                                                             |
| `LEASE_HELD`                                   | "… is still running after 5m. It's from `deployer` on `machine`. If it stopped without cleaning up, it's released within …" (`data.holder`); retryable.                          | `pnpm everyapp status --json` shows the holder under `leases`. A dead holder is released within 3 minutes (the lease TTL, `packages/cli/src/lib/gateway/lease.ts`). Rerun once it is gone.                                                                                                                             |
| `DNS_RECORD_CONFLICT`                          | "… already points somewhere else. Its DNS record: …", `data.authorize: true`.                                                                                                    | Ask the person to delete the record (their domain → DNS in the Cloudflare dashboard) or choose another name; `--force-dns` only on their word.                                                                                                                                                                         |
| Worker changed outside everyapp                | `rerun_interactive`, or `status` fix `GATEWAY_CHANGED`.                                                                                                                          | The person runs `data.rerun` at their own terminal and confirms cf's prompt.                                                                                                                                                                                                                                           |
| `DOMAIN_CHANGE_UNSUPPORTED`                    | "The Gateway can't move to `host`", "It's installed at `gatewayHost`, and moving an installed Gateway isn't supported."                                                          | Run `data.rerun` (the command without `--domain`, `data.rerunNote` "(without --domain) to update it where it is"). Tell the person the Gateway can't move.                                                                                                                                                             |
| `GATEWAY_UNREACHABLE` warning before the link  | `data.kind` `tls` (certificate on its way), `dns` (no address yet) or `other`.                                                                                                   | Nothing: the link works as soon as the host answers, usually within minutes.                                                                                                                                                                                                                                           |
| `CLOUDFLARE_LOGIN_FAILED`                      | The device login wasn't approved in 5 minutes, or didn't complete.                                                                                                               | `pnpm everyapp login --json` and hand off the new link and code.                                                                                                                                                                                                                                                       |
| `UNEXPECTED`                                   | "everyapp hit an unexpected error … This is a bug in everyapp".                                                                                                                  | Read `data.stack` from the event (it is there whenever the thrown error has a stack, with or without `--verbose`; the suggested `--verbose` rerun, "for a stack trace to report", is only added to a non-verbose run so a person's terminal prints the frames; `packages/cli/src/lib/output/report.ts`) and report it. |

Codes and messages in full: [/docs/agent/troubleshooting](/docs/agent/troubleshooting) and [/docs/agent/errors](/docs/agent/errors); the person-facing version is [/docs/troubleshooting](/docs/troubleshooting).

## Safety rules for agents

From `packages/cli/skills/everyapp/SKILL.md`:

- `everyapp` (installed from npm), or `pnpm everyapp` in a checkout or an app. Always `--json`, except for `dev`, which is long-running and human-facing: run it in the background and read its URL.
- Exit 2: show the person the last `action_required` (`message`, `data.url`, `data.code`), then run its `data.rerun`. Exit 1: show the error; if `data.authorize` is set, ask before running `data.rerun`. `data.waiting: true`: keep reading (5 minutes for the Cloudflare login, up to 15 for the owner link).
- Never add `--yes`, `--purge`, `--force-dns`, `--allow-delete-durable-object-data`, `--allow-delete-workflows`, `--enable-email-routing` or `--allow-downgrade` without the person's word, and never to `delete` unless they asked.
- Never print, log or ask in chat for a secret value: not the Gateway's Cloudflare deploy token, not an AI key, not `POSTGRES_DATABASE_URL` from `.everyapp/secrets.env`. Values travel through `--from-env`, stdin, or a hidden prompt the person answers; never the command line.
- Only a person approves the Cloudflare login, opens the owner link, picks a workers.dev subdomain, pays for Workers Paid, buys a domain, enters the Gateway's deploy token, picks the Access team name, picks the account (`choose_account`: one `rerun` per choice) and confirms at a terminal a Worker changed outside everyapp (`rerun_interactive`, which like the `OWNER_NOT_CLAIMED` warning carries `data.needsTerminal: true`: hand over `data.rerun` as given, never with `--json`).
- `pnpm everyapp db restore --json` (undoes the last deploy's migrations and every write since) only when the person asks. A production `db query` write stops with `CONFIRMATION_REQUIRED`; add `--yes` only if they said so.
- Never build a repository from its URL yourself; `install <url>` takes its published release.
- `pnpm everyapp teardown --account-id <id> --dry-run --json` deletes everything EveryApp made in one Cloudflare account, the Gateway included: only a dedicated test account the person names (`EVERYAPP_TEST_ACCOUNTS`, a `CLOUDFLARE_API_TOKEN` scoped to it), `--dry-run` first and show `data.plan`, and never `--confirm <id>` unless they explicitly asked (`TEARDOWN_CONFIRMATION_REQUIRED`, `authorize: true`).
