## The three places a value can live

| Place                                        | What it is                                                                                                                                                                                                                                                                                                                 | Who sets it                                                                                                                            | How an app uses it                                                                                                                                                                                                                                                |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A Gateway setting                            | One plain secret on the Gateway Worker (`every-app-gateway`), held once for every app and every organization: an AI provider's key, a capability's key or OAuth client, the email sender, MCP and Cloudflare Access switches. The names are `SETTABLE_GATEWAY_SETTINGS` in `packages/sdk/src/internal/gatewaySettings.ts`. | The operator, with `pnpm everyapp secret set NAME`, from any directory. The Gateway reads it on its next request.                      | Never directly. The app lists a `provider` or `capability` in `everyapp.config.ts` and calls through the SDK over its private `EVERY_APP_GATEWAY` binding; the Gateway puts the key on the call. An app's manifest may not take a Gateway name as its own secret. |
| The app's own secret                         | A name the app's manifest lists under `secrets`, set on the app's Worker and on each of its helper Workers (`<app worker>--<helper>`).                                                                                                                                                                                     | Whoever deploys the app, with `pnpm everyapp secret set NAME` from the app's directory, after its first deploy. Later deploys keep it. | `env.NAME` in the Worker, a string.                                                                                                                                                                                                                               |
| A capability or provider the Gateway brokers | Not a value the app holds at all: the Gateway holds the key or client (a Gateway setting) and performs or forwards the call. Three kinds: `api_key`, `oauth_client`, `service` (`packages/sdk/src/internal/capabilities.ts`).                                                                                              | The operator sets the Gateway setting; the app lists the capability.                                                                   | `createGatewayFetch()` for AI providers, `integrationFetch()` for keys and OAuth clients, `sendEmail()` and `listMembers()` for services; `integrationStatus()` to ask whether it is ready.                                                                       |

The deploy itself also sets two secrets on every one of the app's Workers with `cf deploy --secrets-file`: `GATEWAY_URL` and `EVERY_APP_ORG_ID`. They are not the app's to set, and `secret list` hides them unless `--verbose`.

## Where `everyapp secret set NAME` puts a name

`packages/cli/src/commands/secret/index.ts` routes every name before it touches the network or asks for a value, so a refusal never costs a typed value. One call may mix Gateway settings and app secrets; each name goes where it belongs, the Gateway's first.

1. The name is in `SETTABLE_GATEWAY_SETTINGS`: it goes to the Gateway Worker, from any directory. The manifest in the current directory is never read for it.
2. Any other name needs an `everyapp.config.ts` in the current directory (`cwd`). If that manifest lists the name under `secrets`, it goes to the app's Worker and each helper Worker. (`unset` also takes a name the manifest no longer lists, so a secret dropped from the manifest can still be removed; such names are reported as "NAME isn't listed in everyapp.config.ts." above the confirmation.)
3. Otherwise the call is refused, in this order:

| Condition                                                                                    | Code                   | Message (first line) and next step                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A known name (a Gateway setting or a declared secret) differs only in case or underscores    | `SECRET_NOT_DECLARED`  | `NAME isn't a Gateway setting` (in an app's directory: `… or one of <id>'s secrets`); `data.didYouMean` holds the match, `rerun` is the same command with it substituted.                                                                                                                                            |
| An install-owned Gateway name (`INSTALL_OWNED_GATEWAY_SETTINGS`), outside an app's directory | `SECRET_NOT_SETTABLE`  | `NAME can't be changed with secret set` then `It's one of the Gateway's own keys, written once by setup.`; for `THIRD_PARTY_DEPLOYS`: `It's the hosted Gateway's launch gate, opened by hand.`                                                                                                                       |
| A dev-only Gateway name (`MCP_ACCESS_TOKEN_TTL`)                                             | `SECRET_NOT_SETTABLE`  | `NAME only works in local development` then `A deployed Gateway doesn't read it.`; fix: `set it in the Gateway's .dev.vars`.                                                                                                                                                                                         |
| Not an identifier (`^[A-Za-z_][A-Za-z0-9_]*$`)                                               | `SECRET_NAME_INVALID`  | `"NAME" isn't a valid secret name`; fix: `use letters, digits and underscores, starting with a letter, e.g. GITHUB_TOKEN`.                                                                                                                                                                                           |
| A reserved app-secret name (below)                                                           | `SECRET_NAME_RESERVED` | `NAME is a reserved name` then `everyapp manages GATEWAY_URL, CF_VERSION_METADATA and the EVERYAPP_*, EVERY_APP_* and APP__* names.`; fix: `pick another name`.                                                                                                                                                      |
| No `everyapp.config.ts` in the current directory                                             | `SECRET_NOT_DECLARED`  | `NAME isn't a Gateway setting, and there's no app here`, then `An app's own secrets are set from the app's directory (where everyapp.config.ts is).` and `Gateway settings: pnpm everyapp secret list`; fix: `cd into the app's directory and run this again`.                                                       |
| `set`: the manifest doesn't list the name                                                    | `SECRET_NOT_DECLARED`  | `<id> doesn't list NAME as a secret` then `It isn't a Gateway setting either.` (for an install-owned name: `It's one of the Gateway's own keys; listing it under secrets gives <id> a secret of its own.`); fix: `add it to secrets in everyapp.config.ts: secrets: [...],`; rerun: `pnpm everyapp secret set NAME`. |

4. The CLI then connects to the Gateway (login and account as every Gateway command; `--gateway`, `--account-id`) and, for app names, finds the app in the registry. An app that was never deployed is refused with `APP_NOT_FOUND`: `<id> isn't deployed yet` then `Its secrets can be set after its first deploy. Nothing was changed.`; rerun `pnpm everyapp deploy`.
5. Only now is each name's value read (one prompt per name, in the order given).
6. The change is applied under leases (`gateway.secrets`, then `app.secrets`; `acquireGatewayLease` and `acquireAppLease` in `packages/cli/src/lib/gateway/lease.ts`). While another run holds one (a deploy, `setup`, `email set`, or another secret change), the command waits up to 5 minutes, saying so as `progress` on `gateway.lease` or `app.lease` (`Waiting for a change to the Gateway's settings to finish (<who> on <machine>, started 1m ago)`, `Waiting for a secret change on <id> to finish (…)`), then fails with [`LEASE_HELD`](/docs/agent/errors#lease_held) before anything changes: `A change to the Gateway's settings is still running after 5m` or `A secret change on <id> is still running after 5m` (`roughly()` in `packages/cli/src/lib/output/time.ts` renders the wait as `5m`), then `It's from <who> on <machine>. If it stopped without cleaning up, it's released within <time>.`; retryable, `data.holder`, rerun `once it's done (pnpm everyapp status shows it)`. The command never calls `lease.check()`, so it doesn't raise [`LEASE_LOST`](/docs/agent/errors#lease_lost); a heartbeat renews each lease every 30 seconds until it is released. For the Gateway, the install row must exist (`GATEWAY_NOT_INSTALLED`, rerun `pnpm everyapp setup`). Every target Worker is checked first (`assertReplaceable` in `packages/cli/src/lib/cf/deploy.ts`): if the version serving is not one everyapp recorded, an unattended run stops with `action_required` (`rerun_interactive`: "… was changed outside everyapp; confirm in a terminal") and a person is asked "Set NAME on it anyway?". Then one `cf workers secrets bulk --worker <name> --body @<file>` call per Worker makes a new version with the change (`packages/cli/src/lib/cf/secrets.ts`): the Gateway's Worker, then the app's Worker, then each helper. The new version id is recorded as everyapp's own (the install row's `live_version_id`, or the app's resource records), so the next `deploy` or `setup` replaces it unattended. No deploy happens; the secret is live at once.

Events: `progress` `secrets.route` (`NAME is a Gateway setting → Worker every-app-gateway` or `NAME is <id>'s secret → Worker <app>, <helper>`), `step` `secrets.gateway` and `secrets.app` (message `Updating the Gateway...` / `Updating <id>...`, then `Set NAME on the Gateway`; `data: { action, names, versions }`), `progress` `secrets.version` (`<worker> is now at version <id>`), and `done` with message `Set OPENAI_API_KEY on the Gateway, and GITHUB_TOKEN on todo` and `data: { gateway?: { names, versions }, app?: { id, workerName, names, versions } }` (`versions` maps each Worker name to its new version id).

A failure after one destination already changed is `SECRETS_PARTIALLY_APPLIED` (retryable): `Couldn't set NAME on <destination>`, `Cloudflare said: …`, `X is set; only Y is left.`, with `rerun` naming only what is left and `data: { applied, left }`, so no value is asked for twice.

### Flags of `secret set`

| Flag              | Effect                                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| `--from-env VAR`  | Read the value from the environment variable `VAR`. One name per call.                                                |
| `--gateway URL`   | The Gateway to reach, as on every Gateway command.                                                                    |
| `--account-id ID` | The Cloudflare account.                                                                                               |
| `--json`          | NDJSON events on stdout and never a prompt: the value must come from `--from-env` or stdin.                           |
| `--verbose`       | Show which Worker each secret goes to and its new version (the `secrets.route` and `secrets.version` progress lines). |

## How a value is read: never the command line

`packages/cli/src/lib/secretValue.ts` takes a value from exactly one source, decided before anything else is checked:

| Source           | When                                                | Rule                                                                                                                                                                                                                                                                                  |
| ---------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--from-env VAR` | The flag is given                                   | `process.env[VAR]`; empty or unset is `SECRET_EMPTY` (`$VAR is empty or not set`; fix: `export VAR first, or name another variable with --from-env`). This is the form for agents and CI.                                                                                             |
| stdin            | No `--from-env` and stdin is not a terminal (piped) | The whole input, one trailing newline dropped (`echo "$STRIPE_KEY" \| pnpm everyapp secret set STRIPE_KEY`). Empty input is `SECRET_VALUE_REQUIRED`.                                                                                                                                  |
| A hidden prompt  | No `--from-env` and stdin is a terminal             | `Value for NAME`, typed invisibly (no length shown), echoed as a fixed mask, trimmed. Asked only when a person can be asked: stdin and stderr are terminals, not `--json`, and `CI` is not set in the environment (`canPromptInTerminal` in `packages/cli/src/lib/output/prompt.ts`). |

With `--json`, in CI, or without a terminal, and no `--from-env` or piped value, the command fails with `SECRET_VALUE_REQUIRED`: `Can't ask for NAME's value without a terminal` then `Or pipe it in: echo "$NAME" | pnpm everyapp secret set NAME`; rerun `pnpm everyapp secret set NAME --from-env NAME`.

`--from-env` and a piped value hold one value, so naming several secrets with either is `SECRET_SEVERAL_NAMES` (`--from-env sets one secret at a time, and you named 2`; fix: run it once per name). The prompt asks once per name, so `pnpm everyapp secret set LINKEDIN_CLIENT_ID LINKEDIN_CLIENT_SECRET` works at a terminal.

A value never appears on `cf`'s command line: `patchWorkerSecrets` writes a JSON merge patch (`{ "secrets": { "NAME": { "name", "type": "secret_text", "text" } } }`, `null` to remove) to a file in a private temp directory (mode `0600`, removed afterwards; `packages/cli/src/lib/cf/runner.ts`) and passes `--body @<file>`. The first deploy's `GATEWAY_URL` and `EVERY_APP_ORG_ID` travel the same way, in `cf deploy --secrets-file`. Do not put a value in a chat message or a shell argument: `export` it and use `--from-env`.

## `secret unset`

`pnpm everyapp secret unset NAME…` routes names as `set` does (an undeclared name still goes to the app). Before asking, it checks whether any target Worker holds any of the names; none does, and the result is `done` with `NAME isn't set on the Gateway or <id>. Nothing changed.` and `data: { removed: false }`. Otherwise it asks `Remove NAME from the Gateway, and OTHER from <id>?` (No by default). `--yes` (`-y`) skips the question; without a terminal (`--json`, CI) and without `--yes` it fails with `CONFIRMATION_REQUIRED` (`Removing secrets needs confirmation, and there's no terminal to ask in`), whose `rerun` adds `--yes` and is marked `authorize`: show it and ask before running it.

Under the leases, each target keeps only the names it holds (a merge patch of `null` for an absent name would make a version with no change); `--verbose` shows `NAME isn't set on <worker>` (`progress` `secrets.held`). The `done` message is `Removed NAME from the Gateway, and OTHER from <id>`, `Live now. No deploy needed.`, with the same `data` shape as `set`.

## `secret list`

`pnpm everyapp secret list` prints names, never values. Flags: `--gateway`, `--account-id`, `--json`, `--verbose`.

Outside an app's directory it lists the Gateway Worker's secrets as a `NAME` / `SET BY` table under `Gateway secrets · <host>`: every name that is not install-owned as `you`, each install-owned name present as `setup`, and every settable name not set as `not set`. The `done` event's `data` is `{ gateway: { workerName: "every-app-gateway", names, settable } }` (`names`: the Worker's secrets, sorted; `settable`: `SETTABLE_GATEWAY_SETTINGS`).

In an app's directory it is a `NAME` / `WHERE` / `STATUS` table:

- Once the app is deployed, one row per secret on its Worker (`WHERE` is the app id) and on each helper Worker (`WHERE` is `<helper> helper`), `set`; reserved names (`GATEWAY_URL`, `EVERY_APP_ORG_ID`) only with `--verbose`. Each name the manifest lists that a Worker lacks is `not set`.
- Before the first deploy, every declared name is `after first deploy`, with the note `<id> isn't deployed yet; its own secrets can be set after that.`
- Then one row per Gateway setting the manifest needs (`gatewaySettingsFor`, below), `WHERE` `Gateway`: `set`, `not set` (required) or `not set (optional)`.
- No rows at all: `<id> has no secrets yet. Add one: list it under secrets in everyapp.config.ts, then pnpm everyapp secret set <name>` (shown whether or not the app is deployed; before the first deploy that `secret set` fails `APP_NOT_FOUND`).

Its `data`: `{ app: { id, deployed, workerName, declared, workers: [{ workerName, names, missing }] }, gateway: { workerName, names, needed: [{ name, required, set }], missing, settable }, next? }`. `next` is `["pnpm everyapp secret set A B"]` listing the app Worker's missing secrets and the required Gateway settings not set, or `["pnpm everyapp deploy"]` when the app is not deployed.

## Gateway settings

Every name `pnpm everyapp secret set` changes on the Gateway, from `SETTABLE_GATEWAY_SETTINGS` (`packages/sdk/src/internal/gatewaySettings.ts`), with what it configures (`apps/every-app-gateway/src/env.d.ts` and the modules named) and the manifest entry an app lists to use it. "Required" and "optional" are what `gatewaySettingsFor` reports for an app that lists the entry: required ones show as `not set` in `secret list`, optional ones as `not set (optional)`.

Where a setting has a setup skill, its section names it as `setup/<name>.md`: that is `packages/cli/skills/everyapp/setup/<name>.md` in the Every App checkout and, in an app, `.claude/skills/everyapp/setup/<name>.md` (also under `.agents/skills/everyapp/setup/`; `everyapp create` copies the skill into both, `packages/cli/src/lib/app/skill.ts`); the index is `setup/README.md`. The skills hold the step-by-step setup of each integration; this page holds what each setting does.

A path is allowed only when both this and the app's `ai.routes` list it (`apps/every-app-gateway/src/server/ai-proxy.ts`). | `ai: { routes: [...] }` (required when `routes` is non-empty) |

### Email

The `email` service capability (`sendEmail()`), and the Gateway's own invitation and password-reset mail. The sender needs an address and a display name (`parseEmailSender` in `packages/sdk/src/internal/email.ts`): `EMAIL_FROM` is required; the name comes from `EMAIL_FROM_NAME` or, when that is unset, from `EMAIL_FROM` written as `Name <address>` (surrounding quotes are dropped), so `EMAIL_FROM_NAME` is required unless `EMAIL_FROM` carries the name. The Gateway can send once that sender parses and a provider is selectable: `isEmailConfigured()` in `apps/every-app-gateway/src/server/email/sendEmail.ts` is `configuredSender()` (the parse above) and `selectEmailProvider()` (`chooseEmailProvider`, below) both answering. Its own mail otherwise fails `EMAIL_SENDER_NOT_CONFIGURED`: `Email sender is not configured. Set EMAIL_FROM and EMAIL_FROM_NAME, or use EMAIL_FROM="Name <email@example.com>".` when `EMAIL_FROM` is set without a name, else `Email sender is not configured. Set EMAIL_FROM and EMAIL_FROM_NAME.` The capability registry lists `EMAIL_FROM` and `EMAIL_FROM_NAME` as the capability's `settings` and the four provider settings as `optionalSettings` (`packages/sdk/src/internal/capabilities.ts`), so `gatewaySettingsFor` reports both names as required and `secret list` shows `EMAIL_FROM_NAME` as `not set` even when `EMAIL_FROM` carries the name. Step by step: `setup/email.md`.

| Setting                | Configures                                                                                                                                                                                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EMAIL_FROM`           | The sender address a message without `from` goes out as: an address, or `Name <address>` with the display name in it. Required. The sender is null unless both an address and a name are set.                                                                                                   |
| `EMAIL_FROM_NAME`      | The sender's display name; when set it wins over a name embedded in `EMAIL_FROM`. Required unless `EMAIL_FROM` carries the name.                                                                                                                                                                |
| `EMAIL_REST_API_TOKEN` | Cloudflare Email Sending's REST API, with `CLOUDFLARE_ACCOUNT_ID`, instead of the Gateway's `EMAIL` binding (a Gateway outside Workers, local dev).                                                                                                                                             |
| `RESEND_API_KEY`       | Resend as the provider.                                                                                                                                                                                                                                                                         |
| `EMAIL_PROVIDER`       | `cloudflare` or `resend` (any case): which provider sends when both are set up; it must be set up. Unset: the first provider in `cloudflare, resend` order the operator gave settings to, else the `EMAIL` binding (`chooseEmailProvider`). An unknown value leaves the Gateway unable to send. |

An app's own senders and inbound addresses are not Gateway settings: `pnpm everyapp email set --sender … --inbound …` in the app's directory, after its first deploy ([/docs/agent/email](/docs/agent/email)).

### MCP

Switches of the Gateway's `/mcp` and its OAuth authorization server (`apps/every-app-gateway/src/server/oauth-flag.ts`, `mcp-auth/`, `toolbus/gateway-mcp.ts`). No app lists anything for these.

| Setting                    | Configures                                                                                                                                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MCP_OAUTH_ENABLED`        | The OAuth authorization server for MCP clients: on when unset or `true` (`1`, `on`, `yes`); off with `false` (`0`, `off`, `no`). Off, `/oauth/*` and the discovery documents 404 and `/mcp` takes personal access tokens only. Any other value is off, with a warning `mcp.oauth.flag_unrecognized`. |
| `MCP_DCR_ENABLED`          | Dynamic client registration (`/oauth/register`), the same values. Off, only clients with a Client ID Metadata Document connect; clients registered before keep working.                                                                                                                              |
| `MCP_ALLOWED_ORIGINS`      | Browser origins, besides the Gateway's own, allowed to call `/mcp` (comma or space separated http or https URLs, e.g. `http://localhost:6274` for MCP Inspector). Empty by default.                                                                                                                  |
| `MCP_AUDIT_RETENTION_DAYS` | Days of `mcp_tool_calls` rows the hourly cron keeps: an integer of 1 or more, capped at 3650; unset, a non-integer or a value below 1 is the default, 90 (`retentionDays` in `apps/every-app-gateway/src/server/mcp-auth/maintenance.ts`).                                                           |

### Cloudflare Access and sign-in

Read by `apps/every-app-gateway/src/auth/cloudflare-access/config.ts` on a self-hosted Gateway only; a hosted Gateway ignores them and `EMAIL_PASSWORD_SIGN_IN` (its `platformPolicy` has no Access sign-in; the log says so once, `apps/every-app-gateway/src/auth/cloudflare-access/index.ts`). Operator-only; see [/docs/agent/access](/docs/agent/access) and `docs/runbooks/cloudflare-access.md`. Step by step: `setup/access.md`.

Three of them the operator does not set by hand: `everyapp access on` (`packages/cli/src/commands/access/index.ts`) writes `ACCESS_SETTINGS` from `packages/cli/src/lib/access/settings.ts`, `CLOUDFLARE_ACCESS_TEAM_DOMAIN`, `CLOUDFLARE_ACCESS_APPS_AUD` and `CLOUDFLARE_ACCESS_AUD`, in one new version of the Gateway Worker after it has created or updated the two Access applications, through `applyGatewaySettings` in `packages/cli/src/commands/secret/index.ts`: the same `gateway.secrets` lease, replaceable-version check, `cf workers secrets bulk` call and version record as `secret set`. Values can't be read back from a Worker, so it records what it wrote (team domain and both AUD tags) in the Gateway's D1, table `_everyapp_access` (`packages/cli/src/lib/access/record.ts`), and writes the three again only when one is missing on the Worker, when it created an application, when there is no record or the record doesn't name the current team and applications (an application recreated in the dashboard has a new AUD tag, and the old one locks everyone out), or with `--write-settings`; otherwise it reports `Gateway settings kept: they name these applications already (--write-settings writes them again).` `everyapp access off` removes whichever of the three the Worker holds, in one version, so passwords sign people in again at once, then clears the record. `everyapp status` reports Access as on when all three are on the Worker (`data.access: { on, teamDomain }`, `readAccessState`). On a hosted Gateway `access on` fails `ACCESS_HOSTED` (`This Gateway can't be put behind Cloudflare Access`). The rest of the table stays `secret set`: `access on` ends by naming `pnpm everyapp secret set CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS` (when run with `--email-domain`) and `pnpm everyapp secret set EMAIL_PASSWORD_SIGN_IN` (`false`, once everyone has signed in through Access) as next steps.

### Install-owned settings: never set by hand

`INSTALL_OWNED_GATEWAY_SETTINGS`: `GATEWAY_URL`, `APP_BASE_DOMAIN`, `BETTER_AUTH_SECRET`, `JWT_PRIVATE_KEY`, `JWT_PUBLIC_KEY`, `GATEWAY_DEPLOYMENT_MODE`, `CLOUDFLARE_ACCOUNT_ID`, `THIRD_PARTY_DEPLOYS`. `secret set` refuses them outside an app's directory (`SECRET_NOT_SETTABLE`); in an app's directory they are app names like any other: `SECRET_NOT_DECLARED` unless the manifest lists them, in which case they go to the app (`notRoutable` in `packages/cli/src/commands/secret/index.ts`). `secret list` shows the ones present on the Gateway as `setup`.

- The Gateway's first upload generates and sends `GATEWAY_URL`, `BETTER_AUTH_SECRET` (32 random bytes, base64), `JWT_PRIVATE_KEY` and `JWT_PUBLIC_KEY` (RS256, 2048-bit, PKCS#8 and SPKI PEM), `GATEWAY_DEPLOYMENT_MODE` (`self_hosted` on a Worker's first upload; `hosted` is the only other value `apps/every-app-gateway/src/server/platform-policy.ts` accepts, the hosted Gateway this page refers to, and no command sets it any more; anything else, unset included, is `invalid` and turns every capability off; a mode the install row already records is kept, so it is fixed for the Gateway's life: `packages/cli/src/lib/gateway/apply.ts`) and `CLOUDFLARE_ACCOUNT_ID` with `cf deploy --secrets-file` (`packages/cli/src/lib/gateway/secretsFile.ts`). `APP_BASE_DOMAIN` is a text binding the deploy patches into the Gateway's Build Output (`packages/cli/src/lib/gateway/patchBuildOutput.ts`).
- `THIRD_PARTY_DEPLOYS` is the hosted launch gate: exactly `on` opens the third-party deploy API. The CLI never sets it: set it by hand on the `every-app-gateway` Worker's secrets once the launch checks pass, and delete it to close the API again (deployed apps keep running; nobody can deploy) (`docs/runbooks/hosted-install.md`, [/docs/agent/repo/runbooks/hosted-install](/docs/agent/repo/runbooks/hosted-install)).
- An app's own Worker may hold a secret of the same name (OpenSEO's `BETTER_AUTH_SECRET`): list it under the app's `secrets` and set it from the app's directory; the two never meet.
- Rotating the identity pair is `docs/runbooks/key-rotation.md` ([/docs/agent/repo/runbooks/key-rotation](/docs/agent/repo/runbooks/key-rotation)): generate the pair with `node apps/every-app-gateway/regenerate-secrets.js` (a PKCS#8 private key and an SPKI public key, RS256, 2048-bit; an OpenSSH public key or a PKCS#1 `BEGIN RSA PRIVATE KEY` private key deploys without error and fails at runtime), replace `JWT_PRIVATE_KEY` and `JWT_PUBLIC_KEY` together in the Cloudflare dashboard (never one half), write the new public key into the install row (`_everyapp_install.jwt_public_key`, where app deploys read it), run `pnpm everyapp setup --redeploy` in a terminal, then `pnpm everyapp deploy` from every app's directory, since each app carries the public key in `EVERYAPP_IDENTITY_PUBLIC_KEYS`. Until every app is redeployed, apps with the old key answer `401` to new identities: the SDK tries each key in `EVERYAPP_IDENTITY_PUBLIC_KEYS` and throws `IdentityError` (status 401, `identity verification failed: …`, `packages/sdk/src/internal/identity.ts`), which the app's handler answers as `{ "error": "unauthenticated" }` (`packages/sdk/src/server/everyApp.ts`). A deploy that stops with [`IDENTITY_KEY_UNKNOWN`](/docs/agent/errors#identity_key_unknown) is reading an install row with no public key (a Gateway first deployed by an older CLI): do the install-row step with the Gateway's current `JWT_PUBLIC_KEY`. Every other key (a provider's, a client's, an app's own) rotates with `pnpm everyapp secret set NAME` again: one new Worker version, live at once.

### Dev-only settings

`DEV_ONLY_GATEWAY_SETTINGS`: `MCP_ACCESS_TOKEN_TTL`. Set in the Gateway's own `.dev.vars`, never deployed: shorter OAuth access tokens in seconds (clamped to 60 through 3600, the normal lifetime), honored only when `GATEWAY_URL` starts with `http://` (`apps/every-app-gateway/src/server/mcp-auth/config.ts`). `secret set` refuses it (`SECRET_NOT_SETTABLE`).

### Reserved names an app secret cannot take

Checked without regard to case, in the CLI (`assertAppSecretName`, `packages/cli/src/lib/app/secrets.ts`), the manifest validator and `everyAppWorker()`:

| Reserved                | Why                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| `GATEWAY_URL`           | The deploy sets it on every Worker.                                                                          |
| `CF_VERSION_METADATA`   | The version-metadata binding every Worker gets.                                                              |
| The prefix `EVERYAPP_`  | The identity settings and dev flags (`EVERYAPP_APP_ID`, `EVERYAPP_DEV`, `EVERYAPP_IDENTITY_PUBLIC_KEYS`, …). |
| The prefix `EVERY_APP_` | The gateway binding and organization (`EVERY_APP_GATEWAY`, `EVERY_APP_ORG_ID`).                              |
| The prefix `APP__`      | The platform's own namespace.                                                                                |

The SDK keeps the same rule as a regex in `packages/sdk/src/cloudflare/worker.ts` (`^(GATEWAY_URL|CF_VERSION_METADATA|EVERYAPP_\w*|EVERY_APP_\w*|APP__\w*)$`, case-insensitive): a manifest listing one fails the Worker definition with `secrets: NAME is a name the deploy sets or a binding it builds.`

## App secrets

### Declaring them

In `everyapp.config.ts`:

```ts
export default {
  id: "todo",
  secrets: ["GITHUB_TOKEN", "STRIPE_KEY"],
} as const;
```

`AppSecretsSchemaStrict` in `packages/perimeter/src/manifest/manifest.ts` checks the list when the CLI parses the manifest (`validateManifestStrict`; errors read `Invalid everyapp.config: secrets.<index>: …`):

| Refusal                                                                                                                                                                  | When                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `binding names must be JavaScript identifiers`                                                                                                                           | Not `^[A-Za-z_][A-Za-z0-9_]*$`. The Gateway's registration parse (`validateManifest`, tolerant of unknown keys) applies the same pattern as `a secret's name is an identifier` and also caps a name at 64 characters and the list at 100. |
| `duplicate secret NAME`                                                                                                                                                  | Listed twice.                                                                                                                                                                                                                             |
| `NAME is set by everyapp itself (GATEWAY_URL, CF_VERSION_METADATA and the EVERYAPP_*, EVERY_APP_* and APP__* names)`                                                     | A reserved name, in any case.                                                                                                                                                                                                             |
| ``NAME is a Gateway setting, which `everyapp secret set NAME` sets on the Gateway for every app; list `<id>` under providers instead`` (or `under capabilities instead`) | The upper-cased name is in `SETTABLE_GATEWAY_SETTINGS` and an AI provider or capability reads it (`gatewaySettingOwner`): `openai_api_key` names `openai`, `DATAFORSEO_API_KEY` names `dataforseo`.                                       |
| ``NAME is a Gateway setting, which `everyapp secret set NAME` sets on the Gateway for every app; give the app's secret another name``                                    | A settable name no provider or capability owns (`MCP_OAUTH_ENABLED`, `CF_DEPLOY_TOKEN`, …).                                                                                                                                               |
| `Invalid everyapp.config: secrets: NAME is one of the app's bindings; pick another name for the secret`                                                                  | The name is a D1, KV, R2, Durable Object, Workflow or Hyperdrive binding, a helper Worker's `binding`, `DATABASE_PROVIDER` (when `database` is set) or `ASSETS` (`bindingNamesOf`).                                                       |

Install-owned Gateway names are not refused here: an app may list `BETTER_AUTH_SECRET` as its own.

### Setting and reading them

1. Deploy the app once (`pnpm everyapp deploy`): the production build declares no app secret, and the upload carries only `GATEWAY_URL` and `EVERY_APP_ORG_ID`.
2. From the app's directory: `pnpm everyapp secret set GITHUB_TOKEN` (a person at the prompt) or `pnpm everyapp secret set GITHUB_TOKEN --from-env GITHUB_TOKEN --json` (an agent). The value lands on the app's Worker and on every helper Worker in one new version each; later deploys keep it: the production build declares no app secret (`packages/sdk/src/cloudflare/worker.ts`, the `secrets` field), and `cf deploy` (the CLI's pinned `cf`, 1.0.0-beta.14) uploads every version with `keepSecrets` on, which puts `secret_text` and `secret_key` in the upload's `keep_bindings`, so a secret absent from the Build Output and the `--secrets-file` stays on the Worker.
3. In the Worker, `env.GITHUB_TOKEN` is the string. Type it as optional, since it is absent in development until set locally, by adding to the app's `src/env.d.ts`:

```ts
declare namespace Cloudflare {
  interface Env {
    GITHUB_TOKEN?: string;
    STRIPE_KEY?: string;
  }
}
```

(the shape `packages/sdk/src/env.d.ts` and `apps/every-app-gateway/src/env.d.ts` use; `cf` generates the bindings' own types from `cloudflare.config.ts`).

4. `pnpm everyapp secret unset GITHUB_TOKEN` removes it from every Worker that holds it. Dropping the name from the manifest does not remove the value: `unset` still accepts the dropped name.

A secret's value is never read back by the CLI: `secret list` and the Gateway's Admin → Apps (where a shared app's manifest, its `secrets` names included, is visible to every organization's admins) show names only.

### In development

`everyapp dev` runs the app with `cf dev` and no Gateway binding. `everyAppWorker()` (`packages/sdk/src/cloudflare/worker.ts`, `addSecrets`) declares as a secret binding each of these names that is set locally, so the Vite plugin passes the value through:

- every name under the manifest's `secrets`;
- the Gateway settings of the manifest's `providers` and `capabilities` (`DEV_GATEWAY_KEYS`: `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `WORKERS_AI_API_TOKEN` with `CLOUDFLARE_ACCOUNT_ID`, `DATAFORSEO_API_KEY`, `CONTEXT_API_KEY`, each OAuth client's id and secret and `MASTODON_URL`, email's `EMAIL_FROM`, `EMAIL_FROM_NAME`, `EMAIL_REST_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `RESEND_API_KEY`, `EMAIL_PROVIDER`), under the same names the Gateway uses;
- `EVERYAPP_EMAIL_SENDERS` when the manifest lists `email` (the senders standing in for `everyapp email set --sender`).

"Set locally" is read as the Vite plugin reads secrets (`localEnv`): when `.dev.vars.<mode>` or `.dev.vars` exists in the app root, that file alone; otherwise `.env`, `.env.local`, `.env.<mode>`, `.env.<mode>.local` and the process environment, later ones winning. A name that is not set is not declared, so `env.NAME` is `undefined`. `everyapp dev` never writes `.dev.vars`; keep it out of git.

The SDK's direct fallback then uses those values in place of the Gateway, only with `EVERYAPP_DEV` set (which `everyAppWorker()` sets in development):

- `createGatewayFetch({ env })` (`packages/sdk/src/server/gatewayFetch.ts`): with no binding and no provider fully set, it throws `ConfigurationError`: `AI gateway unavailable: deploy with the EVERY_APP_GATEWAY binding, or set the provider's key (OPENAI_API_KEY, OPENROUTER_API_KEY or WORKERS_AI_API_TOKEN with CLOUDFLARE_ACCOUNT_ID) in .dev.vars for direct local development.` A call to a provider that is not set throws `Set OPENAI_API_KEY in .dev.vars to call openai in local development.` Otherwise the call goes to the provider's origin with `Authorization: Bearer <key>`; Workers AI's path is joined under `/client/v4/accounts/<id>/ai` and its stream normalized as the Gateway does. Only `/api/ai/openai`, `/api/ai/openrouter` and `/api/ai/workers-ai` paths are accepted.
- `integrationFetch({ env, provider })` (`packages/sdk/src/server/integrationFetch.ts`): with no binding and no local credentials it throws `<Label> is unavailable: deploy with the EVERY_APP_GATEWAY binding, or set <SETTINGS> in .dev.vars for local development.` (e.g. `DataForSEO is unavailable: … set DATAFORSEO_API_KEY …`; an OAuth client names its id, secret and host setting). Otherwise the call goes straight to the provider with the developer's key, or to the network's token endpoint with the developer's client injected by the Gateway's own rule; an API host or path outside the capability's is a `TypeError`. Naming a service (`email`, `members`) throws `<id> is a gateway service: call its helper from @every-app/sdk/server (sendEmail(), listMembers()), not integrationFetch().`
- `integrationStatus({ env, provider })` in dev answers `requested: true` and `configured`/`ready` true when `EVERYAPP_DEV` and the key are set (an OAuth client: its id and secret; `email`: `EMAIL_FROM`; `members`: `EVERYAPP_DEV` alone).

Deployed, none of this applies: the binding exists, the fallback is never taken, and provider keys set as an app's own secrets are refused by the manifest validator.

## Capabilities, providers or your own secret

| You need                                                                    | Manifest                                                   | SDK call                                                                                                    | Where the credential lives                                                                                                        | Access                                                            |
| --------------------------------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| AI inference (OpenAI, OpenRouter, Workers AI)                               | `providers: ["openai"]`, optional `ai: { models, routes }` | `createGatewayFetch({ env, for })` on `/api/ai/<provider>/v1/...`                                           | The Gateway (`OPENAI_API_KEY`, …)                                                                                                 | inference `POST`s; extra routes only with `AI_PROXY_EXTRA_ROUTES` |
| A provider API whose key the Gateway holds (DataForSEO, Context.dev)        | `capabilities: { dataforseo: { access: "read", why } }`    | `integrationFetch({ env, provider: "dataforseo", for })` on the provider's real URLs                        | The Gateway (`DATAFORSEO_API_KEY`)                                                                                                | `read`                                                            |
| Connecting people's accounts on a social network, Gmail or Outlook          | `capabilities: { linkedin: { access: "write" } }`          | `integrationStatus()` for `clientId` (and Mastodon's `origin`); `integrationFetch()` on the token endpoints | The Gateway (`LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`); user tokens in the app                                              | `write`                                                           |
| Sending mail                                                                | `capabilities: { email: { access: "write" } }`             | `sendEmail({ env, for, message })`                                                                          | The Gateway (`EMAIL_FROM` with a display name from `EMAIL_FROM_NAME` or embedded in it, and a provider); senders per installation | `write`                                                           |

| Anything else: an API only this app calls, X's OAuth 1.0a keys, a bot token | `secrets: ["X_API_KEY"]`                                   | `env.X_API_KEY`                                                                                             | The app's Workers                                                                                                                 | the app's                                                         |

A capability entry takes `access` (a level the capability offers; `write` on an `api_key` capability or `read` on an OAuth client is refused at deploy) and an optional `why` (at most 200 characters). An unknown id is refused: `unknown capability (the gateway offers: dataforseo, context, email, members, linkedin, …)`.

**Attribution.** Every brokered call says whom it is for (`packages/sdk/src/server/attribution.ts`): `for: request` attributes it to the request's user by the identity the Gateway put on it; `for: { background: true, organizationId }` to an organization for work no request started (crons, Workflows, queues, an `email()` handler). An organization's own app may omit `for` for background work (the call is the app's); a shared app's Worker (`EVERYAPP_SHARED`) must pass one or the other or the SDK throws `AttributionError` (code `attribution_required`) before any call. The organization travels as `x-everyapp-org`.

**Status.** `integrationStatus({ env, provider })` answers `{ requested, configured, ready }` (over the binding, `GET /api/integrations/<id>`, without calling the provider): `requested` is whether the deployed manifest lists the capability, `configured` whether the Gateway holds its settings, `ready` whether calls would go through. `configured` is `false` for an app that doesn't list the capability, so no app learns what the operator holds (`api_key`: `apps/every-app-gateway/src/server/integration-proxy.ts`; `oauth_client`: `capabilities/oauthClient.ts`; `email`: `capabilities/email.ts`). `members`, which holds nothing, answers `configured: true` whether or not the app lists it and lets only `ready` follow `requested` (`capabilities/members.ts`). `email` adds `sender`, `senders` and `provider` (`cloudflare` or `resend`); an OAuth client adds `clientId` and, for Mastodon, `origin`, only once the Gateway holds the client. Show "an admin needs to set up X" from `ready` instead of failing mid-task.

**Refusals.** A refusal the Gateway makes itself carries its code in the `x-everyapp-error` header; `gatewayRefusal(response)` returns `{ status, code, message }` or `null` for the provider's own answer, and `sendEmail()`/`listMembers()` throw `GatewayRefusalError` with the same fields. The full check order per kind, the email message rules and codes, and the OAuth clients' tables are in [/docs/agent/repo/capabilities](/docs/agent/repo/capabilities) (`docs/capabilities.md`).

## The Postgres secrets file

`.everyapp/secrets.env` in the app root (`packages/cli/src/lib/app/deploySecrets.ts`) holds what `everyapp deploy` itself needs to reach the app's Postgres database, in dotenv syntax. The deploy reads it only when the manifest has `migrations.dialect: "postgresql"` or `resources.hyperdrive`, adds `.everyapp/` to the app's `.gitignore` when it reads it, and never uploads, prints or records a value from it (output that would echo one is redacted). Unlike the app's own secrets, nothing in it reaches the Worker: it binds the Hyperdrive config, which holds the origin's credentials in Cloudflare.

| Variable                | Used for                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POSTGRES_DATABASE_URL` | The database `drizzle-kit migrate` (or `prisma migrate deploy` on the `prisma` engine) runs against before the upload, when `migrations.dialect` is `"postgresql"`. The tool gets it as `POSTGRES_DATABASE_URL` in its own environment, never argv (`packages/cli/src/lib/migrations/localCli.ts`), so `drizzle.config.ts` or `prisma.config.ts` (`datasource: { url: process.env.POSTGRES_DATABASE_URL }`) reads `process.env.POSTGRES_DATABASE_URL` (`packages/sdk/README.md`). Missing: [`POSTGRES_URL_MISSING`](/docs/agent/errors#postgres_url_missing) (`<id> needs a Postgres URL to migrate its database`; fix: `set POSTGRES_DATABASE_URL in .everyapp/secrets.env, then deploy again`). A run that fails is [`MIGRATION_FAILED`](/docs/agent/errors#migration_failed): `drizzle-kit couldn't migrate the Postgres database` (fix: `check POSTGRES_DATABASE_URL in .everyapp/secrets.env and the migrations`; `packages/cli/src/lib/migrations/postgres.ts`) or `prisma migrate deploy couldn't migrate the Postgres database` (fix: `check POSTGRES_DATABASE_URL in .everyapp/secrets.env, prisma.config.ts (its datasource reads it) and the migrations`; `prisma.ts`), with the first `error` line (Prisma: its `P1001`-style code line) of the tool's output, the URL and password replaced, and `Nothing was uploaded.`; the serving version keeps running. Also the origin of the app's Hyperdrive config when it has exactly one. |
| `<BINDING>_ORIGIN_URL`  | The origin a Hyperdrive config for that binding (`resources.hyperdrive[].name`) connects to; an app with one config may leave it to `POSTGRES_DATABASE_URL` (`hyperdriveOriginUrl`). Missing when the config must be created: [`HYPERDRIVE_ORIGIN_MISSING`](/docs/agent/errors#hyperdrive_origin_missing) (`<binding> needs the database its Hyperdrive config connects to` then `Creating the config needs its URL.`; fix: `set <BINDING>_ORIGIN_URL (or POSTGRES_DATABASE_URL, when it is the app's only config) in .everyapp/secrets.env to postgres://<user>:<password>@<host>:<port>/<database>`). A config of that name that no deploy of this app created, and that doesn't connect to this origin, is [`RESOURCE_NAME_TAKEN`](/docs/agent/errors#resource_name_taken): `A Hyperdrive config named "<name>" already exists in this Cloudflare account` then `No deploy of this app created it.`; fix: `to use it, set <BINDING>_ORIGIN_URL in .everyapp/secrets.env to the URL of the database it connects to; otherwise delete or rename it` (the fix names the binding's own variable even for an app with one config). Both in `provisionHyperdrive`, `packages/cli/src/lib/app/resources.ts`.                                                                                                                                                                                                                                          |

Each value is `postgres://user:password@host:5432/database` (`postgres`, `postgresql` or `mysql`; the port defaults to 5432 or 3306). A value that isn't a URL, isn't one of those schemes, or lacks a host, database, user or password is `DATABASE_URL_INVALID`, whose message names the variable and never the value. Every origin is checked before any config is created. A Hyperdrive config not recorded as the app's is adopted only when it connects to the origin in this file, so binding it gives the app no database it couldn't already reach; a recorded one whose host, port, database or user differ is pointed at the origin (`packages/cli/src/lib/app/resources.ts`). In development, a local Postgres URL goes in `.dev.vars` or `.env` as `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING>`.

## Hosted third-party apps

An app on the dispatch tier (a third-party app the Gateway's own deploy API or a browser install deploys, `apps/every-app-gateway/src/server/deploy/`) cannot have secrets of its own yet. Both go through `parseManifest` in `run.ts` (`routes.ts` for the deploy API, `install.ts` for the browser install), which refuses the manifest (`manifestProblems` in `apps/every-app-gateway/src/server/deploy/metadata.ts`) as [`BUNDLE_REFUSED`](/docs/agent/errors#bundle_refused), 422: `The app can't be deployed as a third-party app:` then `it declares secrets, which third-party apps can't have yet`; a Build Output with any secret binding besides `GATEWAY_URL` and `EVERY_APP_ORG_ID` is refused the same way (`bundleProblems`: `<name> is a secret; third-party apps can't have secrets of their own yet`). `manifestTierProblems` (`packages/perimeter/src/manifest/manifest.ts`: `secrets: third-party apps can't have secrets of their own yet`) is the same rule in `pnpm everyapp deploy` (`packages/cli/src/commands/deploy/deployApp.ts`), [`TIER_POLICY`](/docs/agent/errors#tier_policy) (`<id> can't be deployed as configured` then each problem; fix: `change everyapp.config.ts, then deploy again`), for an app the registry already records on the `dispatch` tier. Such an app reaches keys only through `providers` and `capabilities`. The deploy API's bearer is a deploy key: a personal access token with the `deploy` scope and nothing else (`*` doesn't count), of a live owner or admin of the organization it is bound to, checked on every request and minted in the Gateway's Admin → Tokens as `Deploy key` (`apps/every-app-gateway/src/server/deploy/auth.ts`; `DEPLOY_SCOPE` in `apps/every-app-gateway/src/server/user-pat-scopes.ts`). The Gateway keeps its hash (`hashUserPat`, `apps/every-app-gateway/src/server/services/UserPatService.ts`) and the caller keeps the value, so it is in none of the three places above and never a secret on any Worker.

## Security notes

From `docs/security-model.md` ([/docs/agent/repo/security-model](/docs/agent/repo/security-model)):

- Secret values reach `cf` only in private temp files (`0600`, removed afterwards) or the environment, never argv or output; `.everyapp/secrets.env` values never reach a Worker.
- `secret set|unset` change the live Worker without a deploy; they take the Cloudflare login's authority and do not yet check the platform-admin rule of the hosted Gateway.
- The Gateway's logs redact `cookie`, `authorization`, `set-cookie` and any token, secret, password or code field; capability logs name hosts, paths and status, never bodies or keys.
- Cloudflare Access settings are Worker secrets only, never the admin UI (`everyapp access on|off` writes them as Worker secrets too). `CF_DEPLOY_TOKEN` on a hosted Gateway lets whoever reads the Gateway's secrets deploy into the namespace.

The boundaries these rules follow (which Worker holds which key, what reaches an app's Worker, what only the Gateway brokers) are in `docs/threat-model.md` (assets, actors, trust boundaries, one testable invariant per boundary; mirrored under /docs/agent/repo when it lands).
