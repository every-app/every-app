A Gateway is one Worker (`every-app-gateway`) with one D1 database (`every-app-gateway`) in the person's own Cloudflare account, at `https://<gateway host>`, installed by `pnpm everyapp setup --domain <host>`. It signs people in, decides who may open which app, holds every key, and serves one MCP connector for every app. This page says what it offers and how an agent reads each part; the deeper pages are linked, not repeated.

## The shape

- **The Gateway.** The sign-in, the app launcher, **Manage workspace** (`/admin`, owners and admins) and the connector `https://<gateway>/mcp`. Its state is the D1 database; the CLI reads and writes that database through the Cloudflare login, never through the Gateway (ADR-0003, `docs/security-model.md`). `pnpm everyapp status --json` is the one state query ([the CLI by job](#the-cli-by-job)).
- **Apps.** Each app is a Worker of its own on a host under the app base domain (`<app>.<base>`), built from its `everyapp.config.ts` ([manifest](/docs/agent/manifest)) by `pnpm everyapp deploy` from the app's directory, or by `pnpm everyapp install <GitHub URL>` from a release someone published ([deploy](/docs/agent/deploy)). An app lives beside the checkout in a repository of its own, linked to it ([the CLI by job](#the-cli-by-job)). The Gateway gives an app only what its manifest declares: a signed identity, its own `secrets`, AI through `providers`, services through `capabilities` ([identity](/docs/agent/identity), [secrets](/docs/agent/secrets)). Every route is private unless the manifest lists it under `public`, which only a route the internet must reach needs (a webhook, a collector, an OAuth callback); the starter has none. An app's AI tools are `defineTools()` in its code, snapshotted by the Gateway and served as `<app>_<tool>` ([mcp](/docs/agent/mcp)). An agent writes one with the build skill ([Build an app](/docs/agent/build), [Example patterns](/docs/agent/patterns)).
- **MCP apps.** A data provider, or any remote MCP server, the Gateway offers to members' AI clients as an app with no page and no Worker (a provider app in the code: an `apps` row of tier `provider`, `PROVIDER_APP_TIER`), turned on by `pnpm everyapp mcp on <id>` or added by `pnpm everyapp mcp add <url>`, its key or credential a Gateway setting. The registry is `PROVIDER_APPS` in `packages/sdk/src/internal/providerApps.ts`; the ids are `PROVIDER_APP_IDS`, today `dataforseo` alone (key `DATAFORSEO_API_KEY`; seventeen read tools in `apps/every-app-gateway/src/server/provider-apps/dataforseo.ts`, listed in full on `/mcp` as `dataforseo_<tool>`); a remote server is a row whose manifest carries a `remote` block (`packages/perimeter/src/registry/remoteMcpApps.ts`), its tools served through `packages/toolbus/src/remote/`. To a person, a card under "MCP apps" on the launcher with a "Use it from your agent" dialog (this Gateway's MCP address, the tool prefix); its row in **Apps**, its calls in **Usage** and **Activity**. Reference: [mcp](/docs/agent/mcp#mcp-apps); `docs/design/2026-10-mcp-apps-ui.md` (section 3, every person-facing surface), `docs/design/2026-10-mcp-provider-apps.md`, `docs/design/2026-10-mcp-by-url.md`.
- **The one connector.** `https://<gateway>/mcp` serves every app the caller can use plus the built-ins named under the reserved app id `everyapp` (`packages/toolbus/src/builtins.ts`): five core ones, `everyapp_list_apps`, `everyapp_whoami`, `everyapp_search_tools`, `everyapp_call_read` and `everyapp_call_write`, and the workspace tools (`packages/toolbus/src/workspace.ts`): every action of **Manage workspace** as `everyapp_workspace_<action>` for an owner or admin, four every member has over their own tokens and AI connections ([People](#people)), and the MCP app tools (`packages/toolbus/src/mcpApps.ts`, owners and admins): `everyapp_mcp_list`, `everyapp_mcp_show`, `everyapp_mcp_add`, `everyapp_mcp_remove`, `everyapp_mcp_on`, `everyapp_mcp_off`, `everyapp_mcp_refresh` and `everyapp_mcp_tool`, the `mcp` commands' twins; and the provider tools (`packages/toolbus/src/providers.ts`): `everyapp_provider_list` for every member, `everyapp_provider_add` and `everyapp_provider_remove` for owners and admins on a self-hosted Gateway, the `provider` commands' twins ([the provider tools](/docs/agent/mcp#provider-tools)); and the sign-in provider tools (`packages/toolbus/src/signin.ts`, owners and admins): `everyapp_signin_list` and `everyapp_signin_show`, the reads of **Sign-in**, with no tool that adds or removes a provider ([the sign-in provider tools](/docs/agent/mcp#sign-in-provider-tools)). Behind the Gateway's OAuth and consent page, or a personal access token `epat_…`; every call audited as one `mcp_tool_calls` row. An app host serves its own `https://<app-host>/mcp` only where its manifest opts in (`mcp: { by, why }`, [manifest](/docs/agent/manifest#mcp)): that one app, to a personal token, with no OAuth; none of the four open apps does. A member connects once and every app they can open follows ([Connecting clients](/docs/agent/mcp#connecting-clients)).

## People

Roles are `owner`, `admin` and `member` (`apps/every-app-gateway/src/server/org-roles.ts`; the action-by-role table is in `docs/design/2026-10-teams.md`). A member opens the apps they are given and connects AI clients; an admin also invites, manages apps and groups, deletes a user or an app, sets caps and reads Usage and Activity; an owner can also make or demote another owner and remove one (owners are peers; the workspace always keeps one; only an owner acts on an owner). The identity an app receives carries `org_role`; `everyapp_whoami` answers `user.role`.

Everything below is **Manage workspace** (`/admin`, the sidebar footer's link; `apps/every-app-gateway/src/routes/_app/admin.tsx`), for owners and admins; a member who opens it sees "You don't have access to this page". The terminal and the connector do the same, tab by tab, below. The person's page is [/docs/people](/docs/people). Every command and every tool, paired with the UI action each stands for, is on [Managing the workspace: the CLI and the MCP tools](/docs/agent/workspace).

## Cloudflare Access

When: a company's Gateway, before people are invited; it is free for up to 50 people and adds a second sign-in at Cloudflare's edge (a one-time PIN by email, or the company's identity provider). Recommend it to every person whose Gateway more than one person will use ([the index](/docs/agent#what-to-tell-the-person)).

The one command is `pnpm everyapp access on` ([access](/docs/agent/access); the setup file `packages/cli/skills/everyapp/setup/access.md`): the Zero Trust team (`--team <name>` when the account has none; the name is permanent), the one-time PIN, an allow policy with every member's and invitee's email (`--email`, `--email-domain` add more), two Access applications in front of the Gateway's host and the apps' hosts, and the three `CLOUDFLARE_ACCESS_*` Gateway settings. Rerunnable; run it again after inviting someone, since Access keeps its own list. `pnpm everyapp access show` reports; `pnpm everyapp access off` takes it down (`--yes` only when the person said so).

What changes for MCP clients: nothing, without Managed OAuth. The plan (`packages/cli/src/lib/access/plan.ts`) lets `/mcp`, `/mcp/*`, `/oauth/token`, `/oauth/register` and `/.well-known/*` past Access on the Gateway's host, `/mcp` on an app host whose manifest opts in (`mcp: { by, why }`), and each app's `public` routes on its own host; the person passes Access's login once in the browser at `/oauth/authorize`. With Access's **Managed OAuth** on the Gateway's application (switched on by hand, never by `access on`), Access itself is the OAuth server: [MCP and API clients behind Access](/docs/agent/access#mcp-and-api-clients-behind-access).

## What to suggest next

The playbook is the proactive next-steps design; `everyapp status` has no `Next:` block on main yet (when it lands, rows 1 to 5, 8 and 9 print there and in `data.next`). Until then an agent reads the signals itself. Commands are `pnpm everyapp …`.

| --- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1   | No AI key (`OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `WORKERS_AI_API_TOKEN`) while an app lists `providers`, and no fix names it | Apps that use AI need a key                                 | `secret set OPENROUTER_API_KEY` (or the provider the apps name)                               |

| 3   | Access off, self-hosted, Worker uploaded                                                                                       | Put Cloudflare Access in front                              | `access on`                                                                                   |
| 4   | One member, an app live                                                                                                        | Invite people                                               | `workspace invite <email>` (prints the link to hand over), or `https://<gateway>/admin/users` |
| 5   | No live AI connection and no live token, and an app serves tools                                                               | Connect an AI client                                        | `https://<gateway>/mcp`, [/docs/connect-ai](/docs/connect-ai)                                 |
| 7   | An app needs setup                                                                                                             | Already a fix (`APP_NEEDS_SETUP`); never repeated as a next | `configure <app>`                                                                             |

| 10  | The most-used apps (`usage_monthly.calls` this month; allowed `mcp_tool_calls` in 30 days)                                     | Nothing: a ranking for where to start, never a nudge        | `workspace usage --json`; `everyapp_workspace_usage`; **Usage**                               |

Noise rules, which bind an agent as they bind the Gateway: rows 1 to 4 and 7 to 9 are for owners and admins, and a member hears one thing, connect an AI client (`everyapp_whoami` says which the person is; row 10 is an order members see, not a nudge); once per state, said while the signal is true and dropped when it isn't, never a list of what was suggested; at most four at a time, in the table's order, never one the person cannot act on, never a fix `status` already prints; never "you have not used X" to a person (usage ranks, it does not prompt) and no cap nudges (a cap is opt-in); one command or one URL per suggestion, and a value (a key) never through the chat ([secrets](/docs/agent/secrets#how-a-value-is-read-never-the-command-line)).

Where each signal is read: `pnpm everyapp status --json` (`data.apps[]` with `status`, `bound`, `publicRoutes`, `email` and `setup`; `data.owner`, `data.claimed`, `data.access`, `data.mode`; `data.fixes[]` as `{ code, severity, message, run, note?, fix? }` with the codes in `ProblemCode`, `packages/cli/src/commands/status/problems.ts`) for rows 3, 7 and 8, every line explained on [status](/docs/agent/status); `pnpm everyapp secret list --json` outside an app directory (`data.gateway.names`, the Gateway Worker's settings, names only; `data.apps[].setup`) for rows 1, 2, 2b and 9, with which apps list `providers` or `email` in each manifest or `data.apps[].setup.unmet[].need`; `pnpm everyapp mcp list --json` (`data.providers[]` with `id`, `name`, `on` and `key: { name, set }`; `data.next` already carrying `mcp on <id>` and `secret set <KEY>`) for rows 2 and 2b in one call; from an AI client, `everyapp_list_apps` (a `tools` count per usable app; `available: false` with `reason` for one that needs setup) and `everyapp_whoami` (`user.role`, `connection.kind`, `access`, `apps`), where row 5's "serves tools" is a count above zero; `pnpm everyapp workspace users --json`, `pnpm everyapp workspace connections --json`, `pnpm everyapp workspace tokens --json` and `pnpm everyapp workspace usage --json` for rows 4, 5 and 10 (what **Users**, **AI connections**, **Tokens** and **Usage** show); from an AI client, `everyapp_workspace_users` and `everyapp_workspace_usage` as an owner or admin, and a member's own `everyapp_my_connections` and `everyapp_my_tokens`.

## Other MCP servers to recommend

A server the whole team should reach goes on the Gateway as an MCP app (`pnpm everyapp mcp add <url>`; the Gateway holds its credential), never into each person's client. For the client itself two are worth adding, and nothing else. The Gateway's own connector first: `https://<gateway>/mcp`, every app the caller can reach plus the `everyapp_` built-ins, behind the Gateway's OAuth and consent ([Connecting clients](/docs/agent/mcp#connecting-clients)); every member should have it. Cloudflare's, below, is for the owner or operator, the person whose Cloudflare login ran `everyapp setup`. The rule for both, decided for the launch (`TODO.md`, "Agent-forward layer (2026-10-24)"): `everyapp setup` and `everyapp create` install none and print nothing about them; an agent names one in a single line when the person's task needs it and waits for a yes; it never writes a client config unasked, and never one the repository shares (`.mcp.json` from Claude Code's `--scope project`, `.cursor/mcp.json`, `.codex/config.toml`). The same rule, with the add and remove lines per client, is the setup skill's section "Optional: MCP servers worth having beside Every App" (`packages/cli/skills/everyapp/setup/gateway.md`); the person's page is [/docs/connect-ai](/docs/connect-ai#also-worth-connecting).

### Cloudflare's MCP server

`https://mcp.cloudflare.com/mcp` (Streamable HTTP). Four tools: `search` and `execute` (code mode over the Cloudflare API: the agent writes JavaScript that is run on Cloudflare's side, the token outside the sandbox), `docs` (developers.cloudflare.com) and `whoami`. Auth: OAuth with the person's Cloudflare login (**Minimal** on the consent page is the least; a call that lacks a scope asks the person to add it), or an API token as a bearer header for automation. Scope: the whole account, as the person, within the granted permissions; `execute` takes an `account_id`. There is no Gateway narrowing.

When it helps: reading what `everyapp status` and `everyapp access show` do not report about the account the Gateway runs in (the zone's records, the Workers and their versions, the D1 database, the Access team and policies, email, logs, API tokens, the plan and the bill). When it is noise: anything `everyapp` does. The CLI writes the Gateway's database and the deploy ledger beside Cloudflare, and a deploy refuses to replace a Worker last changed in the dashboard or through the API until a person confirms in a terminal (`assertReplaceable` in `packages/cli/src/lib/cf/deploy.ts`; `rerun_interactive`), so a Worker, secret, record or policy written through this server stops the next deploy. Read before write; a write is a live API call on the whole account, as the person, with no undo. When the person says yes, in Claude Code: `claude mcp add --transport http cloudflare https://mcp.cloudflare.com/mcp`, then they authenticate under `/mcp`; Codex, claude.ai, Claude Desktop and Cursor are in the setup skill's section.

### GitHub

Nothing to add. `pnpm everyapp install <GitHub URL>` fetches `releases/latest/download/everyapp-release.tar.gz` anonymously ([deploy](/docs/agent/deploy)). For what surrounds a repository (which release, its README, an issue, the Actions runs of an app the person builds), a terminal harness has `gh`, and claude.ai has its built-in GitHub connector.

### Not recommended

Cloudflare's separate docs server `https://docs.mcp.cloudflare.com/mcp` (the API server's `docs` tool is the same search) and its product servers. A docs MCP for Every App: none; the agent docs are Markdown at `https://everyapp.com/docs/agent/<page>.md` and `/llms.txt`, fetched without MCP.
