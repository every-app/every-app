`pnpm everyapp deploy` deploys the app in the current directory (or an app release) as a private Cloudflare Worker behind the Gateway. The one-sentence model: Cloudflare's own CLI, `cf`, does everything in the Cloudflare account with your Cloudflare login, including writing the app registry in the Gateway's own D1 with the rules in `@every-app/perimeter/registry`; binding an app is a redeploy of the Gateway this run builds, and the Gateway makes a bound app live itself on the first request that reaches it. The entry point is `packages/cli/src/commands/deploy/index.ts`; the pipeline is `packages/cli/src/commands/deploy/deployApp.ts`. In an app, `pnpm run deploy` runs the same command (the template's `package.json` script is `everyapp deploy`, `starter/package.json`; the user docs spell it that way); an agent runs `pnpm everyapp deploy --json` from the app directory.

Error codes on this page link to [the errors page](/docs/agent/errors); event shapes (`step`, `progress`, `warning`, `action_required`, `error`, `done`) are on [the JSON page](/docs/agent/json). Trust boundaries are in `docs/security-model.md` ("Trust Zones", "Operator Authority (Self-Host)", "Hosted Deploy API"), mirrored at [/docs/agent/repo/security-model](/docs/agent/repo/security-model), and in `docs/threat-model.md` (assets, actors, trust boundaries, one testable invariant per boundary), mirrored at [/docs/agent/repo/threat-model](/docs/agent/repo/threat-model) (the register behind it, `docs/threat-model-invariants.md`, is not mirrored and stays on GitHub); this page links there rather than repeating them.

## One credential

The credential is the Cloudflare login (`cf auth login`, via `pnpm everyapp login`) or `CLOUDFLARE_API_TOKEN` with `CLOUDFLARE_ACCOUNT_ID`. The Gateway is found through that login (`packages/cli/src/lib/gateway/discover.ts`); `--gateway` or `EVERYAPP_GATEWAY_URL` only picks among several. Every deploy runs `deployApp` (`packages/cli/src/commands/deploy/deployApp.ts`) with that login; the Gateway issues no credential of its own.

Self-host is ADR-0003 (`adr/ADR-0003-self-host-authority.md`): write access to the Gateway's D1 database in the Gateway's Cloudflare account **is** operator authority. The CLI reads and writes the registry, the install row, the deploy lease, the resource ledger and the restore points with `cf d1 query`, under the operator's own login or token. The Gateway issues no deploy credential and has no deploy API in self-host; the CLI never calls it over HTTPS except for the live wait's plain `GET`. Who deployed is recorded on the app row (`deployed_by_actor`): the login's email, or `api-token:<account id>` when `CLOUDFLARE_API_TOKEN` is set (`deployerFor`, `packages/cli/src/lib/gateway/registry.ts`). The Gateway's own deployer records `deploy-key:<token id>` for its deploy API (`routes.ts`, `pipeline.ts` in `apps/every-app-gateway/src/server/deploy/`) and the admin's email for a browser install (`install.ts`); both are below.

`--gateway`, else `EVERYAPP_GATEWAY_URL` (the variable isn't read when the flag is given; the flag has no default of its own, `packages/cli/src/commands/flags.ts`), is normalized by `requestedGatewayUrl` (`packages/cli/src/lib/gateway/connect.ts`): a value `new URL()` can't parse is [`INVALID_GATEWAY_URL`](/docs/agent/errors#invalid_gateway_url) (`--gateway must be a full URL, not "<value>"` with "For example https://apps.example.com."; for the variable `EVERYAPP_GATEWAY_URL must be a full URL, not "<value>"` with fix `set it to https://<value without its scheme>, or unset it`); anything else keeps its scheme, host, port and path and loses its query, fragment and trailing slashes (`https://apps.example.com/?x=1` becomes `https://apps.example.com`; the function's comment wants no path, but one is kept, not refused). Only its host counts (discovery picks the Gateway whose install row's `gatewayHost` is that host, `checkGatewayUrl` compares hosts) and the run's `gatewayUrl` is always `https://<gatewayHost>` from the install row; a host that isn't the Gateway found is [`GATEWAY_URL_MISMATCH`](/docs/agent/errors#gateway_url_mismatch) (`packages/cli/src/lib/gateway/discover.ts`: "The Gateway here is `<found>`, not `<host>`", "Found in `<account>`. For `<host>`, pass its account with --account-id."; from the flag, rerun this command without `--gateway` "to use `<found>`"; from the variable, fix `unset EVERYAPP_GATEWAY_URL to use <found>`).

## Flags

From `packages/cli/src/commands/deploy/command.ts` (`install` declares the same flags). "Yes" in the last column means the flag takes something over: an agent shows the refusal and asks the person before rerunning with it (`TAKEOVER_FLAGS` in `packages/cli/src/lib/errors.ts` makes the rerun `authorize: true`).

| Flag                                 | Brief (as the command says it)                                                                                                                                                                                                                  | Needs the person's yes                                                                                                       |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `--gateway <url>`                    | The Gateway's URL, checked against the Gateway in your Cloudflare account (default: `EVERYAPP_GATEWAY_URL`)                                                                                                                                     | no                                                                                                                           |
| `--account-id <id>`                  | The Cloudflare account of the Gateway, when your login sees several (default: `CLOUDFLARE_ACCOUNT_ID`)                                                                                                                                          | no                                                                                                                           |
| `--allow-delete-durable-object-data` | Deploy even though Durable Object classes were removed, deleting their data                                                                                                                                                                     | yes ([`DURABLE_OBJECT_REMOVED`](/docs/agent/errors#durable_object_removed))                                                  |
| `--allow-delete-workflows`           | Deploy even though Workflows were removed, deleting them and their instances                                                                                                                                                                    | yes ([`WORKFLOW_REMOVED`](/docs/agent/errors#workflow_removed))                                                              |
| `--force-dns`                        | Publish the app's new hostname even where a DNS record answers it (one at the hostname is replaced)                                                                                                                                             | yes ([`DNS_RECORD_CONFLICT`](/docs/agent/errors#dns_record_conflict), [`DNS_UNREADABLE`](/docs/agent/errors#dns_unreadable)) |
| `--enable-email-routing`             | Turn on Email Routing for the domains the app's inbound addresses (`everyapp email set --inbound`) name that don't route mail yet (locks their MX and SPF records to Cloudflare)                                                                | yes ([`EMAIL_ROUTING_DISABLED`](/docs/agent/errors#email_routing_disabled))                                                  |
| `--no-wait`                          | Don't wait for the app to go live (a new hostname's certificate included); it goes live on its first visit                                                                                                                                      | no                                                                                                                           |
| `--yes`, `-y`                        | Register the providers the app bundles (`.everyapp/providers/*.json`) without asking, and with no Gateway yet install one at `apps.<zone>` without asking (never cf's questions, or the one before replacing a Worker changed outside everyapp) | yes: it registers providers ([`CONFIRMATION_REQUIRED`](/docs/agent/errors#confirmation_required)) and installs a Gateway     |
| `--out <file>`                       | `release` only: where to write the release (default: `./everyapp-release.tar.gz`)                                                                                                                                                               | no                                                                                                                           |
| `--json`                             | Print NDJSON events on stdout and never prompt (exit 0 done, 1 error, 2 action required, 251/252 bad command or arguments)                                                                                                                      | no                                                                                                                           |
| `--verbose`                          | Show every step and progress line, the output of what everyapp runs, and an unexpected error's stack trace; also attaches `cf deploy` to the terminal so cf asks its own questions                                                              | no                                                                                                                           |

`deploy` takes no positional. A published release is installed by `pnpm everyapp install <source>` (a GitHub repository URL for its latest release, a release tarball's URL, or a downloaded `everyapp-release.tar.gz`), which takes the same flags (the four takeovers included: a release can drop a class or a Workflow, and its hostname and inbound domains are checked the same way; `packages/cli/src/commands/install/command.ts` spreads `appTakeoverFlags` from `packages/cli/src/commands/flags.ts`), and packed by `pnpm everyapp release [--out <file>]`. See "Release installs" and "`release`: packing a release".

There is no `--skip-migrations` flag. `migrate` (`deployApp.ts`) returns before emitting anything for an app with no D1 bindings and no `migrations.dialect: "postgresql"`: no `app.migrations` event at all. `app.migrations` with status `skip` and "No migrations to apply." (`skipMigrations`) is emitted for a D1 app whose migration binding has no provisioned database id or whose migrations directory is missing, and for a Postgres app whose migrations directory is missing (drizzle: `migrations.dir`, default `drizzle`; Prisma: only a `migrations.dir` the manifest names, since Prisma finds its migrations through its config).

### Before the first step

`deploySteps` (`deployApp.ts`) runs these before `app.connect`:

- A release with `migrations.dialect: "postgresql"` is refused: [`RELEASE_MIGRATIONS_UNSUPPORTED`](/docs/agent/errors#release_migrations_unsupported), "can't deploy from a release: its Postgres migrations need the source"; fix `clone it, then run pnpm install in it and this checkout's pnpm everyapp deploy from its directory`.
- An app with Postgres migrations or Hyperdrive configs reads `.everyapp/secrets.env` (`packages/cli/src/lib/app/deploySecrets.ts`, dotenv syntax, kept out of git by `ensureGitignored`). Postgres migrations with no `POSTGRES_DATABASE_URL` there: [`POSTGRES_URL_MISSING`](/docs/agent/errors#postgres_url_missing), fix `set POSTGRES_DATABASE_URL in .everyapp/secrets.env, then deploy again`. Nothing in that file reaches the Worker, is printed or is recorded.
- No `cloudflare.config.ts` (not for a release): [`MISSING_CLOUDFLARE_CONFIG`](/docs/agent/errors#missing_cloudflare_config). One that doesn't use `everyAppWorker()`: warning [`NONSTANDARD_CLOUDFLARE_CONFIG`](/docs/agent/errors#nonstandard_cloudflare_config), "The deploy checks the Worker it builds against the app policy."
- The Gateway a rebind would deploy is the live one, had again from where the install row says it came (`gatewayFor`, `packages/cli/src/commands/appGateway.ts`, through `liveGatewaySource`, `packages/cli/src/lib/gateway/liveRelease.ts`: a GitHub release by tag, a URL or file, or this checkout's build cache for the row's tree hash). A deploy that will bind the app (a new app, or one whose Worker the install row doesn't list) checks it can be had before anything is registered: when it can't, [`GATEWAY_RELEASE_UNAVAILABLE`](/docs/agent/errors#gateway_release_unavailable), rerun `pnpm everyapp update` "then run this again". Deploying or deleting an app never changes the Gateway's code; only `update` and `setup` do. A redeploy of an app the Gateway already binds needs no Gateway release, so it runs anywhere, a checkout or not.

### `app.connect`: the login and the Gateway

`connectToGateway` (`packages/cli/src/lib/gateway/connect.ts`): `cf auth whoami`, then login if needed, then discovery.

- Login (`packages/cli/src/lib/cf/account.ts`): at a terminal `cf auth login`; under `--json` the run emits `action_required` with `action: "cloudflare_login"` on step `app.login`, `data.url`, `data.code`, `data.expiresAt`, `data.waiting: true`, and waits for the person to approve the device link (`cf auth login --no-browser`). Piped without `--json` it stops with the same action and no wait. A rejected `CLOUDFLARE_API_TOKEN` is [`CLOUDFLARE_TOKEN_REJECTED`](/docs/agent/errors#cloudflare_token_rejected) ("A token needs Workers, D1, KV and Zone DNS Read access"); a login that didn't complete is [`CLOUDFLARE_LOGIN_FAILED`](/docs/agent/errors#cloudflare_login_failed).
- Discovery (`discoverGateway`, `packages/cli/src/lib/gateway/discover.ts`) probes each account the login lists for the Gateway's D1 (`every-app-gateway`) and reads its install row. `--account-id`, else `CLOUDFLARE_ACCOUNT_ID`, names the account (it is probed even when the login doesn't list it: an API token may list none) and the Gateway is that account's or none. Without it, one Gateway found is the one; with several, the `--gateway` host matching exactly one install row's `gatewayHost` picks it, a terminal asks `Which Gateway?` (each by its host, the account beside it), and an unattended run stops with `action_required` `choose_account` ("Choose which Gateway to use", "`<email>` sees a Gateway in `<n>` Cloudflare accounts. Run one of:"), `rerun: null`, and `data.choices[]` of `{ accountId, accountName, gatewayUrl, label, rerun }`, each `rerun` this command with `--account-id <id>` appended, ready to run.
- [`GATEWAY_NOT_FOUND`](/docs/agent/errors#gateway_not_found) (`requireGateway`, `discover.ts`; `data.accounts` lists the accounts probed) has three forms: the named account has no Gateway while others do ("Cloudflare account `<id>` has no Gateway", "This login's Gateway is in `<account> at https://<host>`"; fix `pass that account's id to --account-id (or CLOUDFLARE_ACCOUNT_ID), or drop it`); the login lists no accounts and none was named ("This Cloudflare login lists no accounts"; fix `pass the Gateway's account with --account-id, or set CLOUDFLARE_ACCOUNT_ID`); none anywhere ("No Gateway in `<account>`, the only account this login sees" or "No Gateway in the `<n>` accounts this login sees", "Or log in to the Gateway's account: pnpm everyapp login"; rerun `pnpm everyapp setup --domain <hostname>` "to install one"). For `deploy` the last case is normally taken over by the install offer below, which runs when no account has a Gateway and at least one was probed.
- None anywhere, the command naming no Gateway (no `--gateway`, `EVERYAPP_GATEWAY_URL`, `--account-id` or `CLOUDFLARE_ACCOUNT_ID`: those are [`GATEWAY_NOT_FOUND`](/docs/agent/errors#gateway_not_found)) and every account asked (one cf refused or didn't know twice is [`GATEWAY_CHECK_FAILED`](/docs/agent/errors#gateway_check_failed), never an offer): `deploy` calls `offerGateway` (`packages/cli/src/commands/deploy/steps/offerGateway.ts`). First, any account the login sees that already runs the `every-app-gateway` Worker (or whose Workers can't be listed) stops it with `GATEWAY_CHECK_FAILED`: a second Gateway beside one is never offered. At a terminal it offers `Install a Gateway at apps.<zone>?` (the zone the only active one or a choice), runs setup's `installGateway` inline (owner link included), then discovers again; `--yes` installs without the question ("`<account>` has no Gateway yet, so --yes installs one at `apps.<zone>` first."); No is [`CANCELLED`](/docs/agent/errors#cancelled) ("Cancelled. Nothing deployed."). The account is `resolveAccount`'s (`packages/cli/src/lib/cf/account.ts`): `--account-id`, then `CLOUDFLARE_ACCOUNT_ID`, then the only account the login lists, else the choice `Which account should the Gateway go in?`; one named that the login lists but can't use is [`ACCOUNT_NOT_ACCESSIBLE`](/docs/agent/errors#account_not_accessible) (the message lists the usable accounts; fix `pass one of these with --account-id, or log in as someone else`, rerun `pnpm everyapp login`), a login listing no accounts with none named is [`ACCOUNT_REQUIRED`](/docs/agent/errors#account_required) (fix `pass --account-id, or set CLOUDFLARE_ACCOUNT_ID`). Unattended (`--json`, piped) it stops with `action_required` `install_gateway`, "Install a Gateway first: `<account>` has none yet", rerun `pnpm everyapp setup --domain apps.<zone> [--account-id <id>]`, `data.accounts`, `data.domain`; the suggested host is `apps.<first active zone>` of the account the same lookup picks without a terminal, and when that lookup fails (several accounts, or either `ACCOUNT_*` code; it is swallowed) the rerun says `--domain <hostname>` literally and `data.domain` is absent.
- An install row whose first upload never finished (`liveVersionId` null) or a database with no row: [`GATEWAY_NOT_INSTALLED`](/docs/agent/errors#gateway_not_installed), rerun `pnpm everyapp setup` (`requireInstall`, `connect.ts`; `notDeployedByEveryapp`, `packages/cli/src/lib/gateway/install.ts`).

`app.connect` ends with `data.gatewayUrl`. The connection carries `cf` pinned to the account, the D1 handle, the install row (`_everyapp_install`: account, zone, `gatewayHost`, `appBaseDomain`, the live release and version, `liveDomains`, `liveAppWorkers`, `jwtPublicKey`, `deploymentMode`) and the deployer.

### `app.deploy`: the first line and the guards

`app.deploy` is emitted `ok` at once, before anything can stop the run: message `Deploying <appId>[ <version> from <origin>] to <gatewayUrl>.`; `data`: `appId`, `organizationName` (the install organization's, else the account's), `firstDeploy` (true when the app isn't registered or its status is `pending` or `binding`: `NEVER_LIVE`), `gatewayUrl`, `gatewayHost`, and for a release `version`, `origin`, `release.{version,gitSha,origin,sha256}`. A person sees `Deploying todo to apps.example.com (Acme)`.

Then, before the registry changes:

- No `jwt_public_key` on the install row: [`IDENTITY_KEY_UNKNOWN`](/docs/agent/errors#identity_key_unknown) ("The Gateway is missing its sign-in public key", "App Workers need it to check who is signed in."), fix `restore JWT_PUBLIC_KEY as in https://github.com/every-app/every-app/blob/main/docs/runbooks/key-rotation.md` (the runbook is mirrored at [/docs/agent/repo/runbooks/key-rotation](/docs/agent/repo/runbooks/key-rotation)).

### `app.providers`: the providers the app bundles

Before the manifest is checked against the Gateway's registry, the provider specs the app bundles are registered on it (`registerBundledProviders`, `packages/cli/src/commands/deploy/steps/bundledProviders.ts`; [/docs/agent/providers](/docs/agent/providers#specs-an-app-bundles)): `.everyapp/providers/<id>.json` under the app for `deploy`, a release's `providers` for `install`. Every spec is parsed and checked first and nothing is written until all pass: a file that isn't a spec is [`PROVIDER_SPEC_INVALID`](/docs/agent/errors#provider_spec_invalid) naming it; an id whose row holds another spec is [`PROVIDER_SPEC_DIFFERS`](/docs/agent/errors#provider_spec_differs) (a deploy never replaces a row); a catalog id is the warning [`PROVIDER_BUNDLED_BUILTIN`](/docs/agent/errors#provider_bundled_builtin) and the file is ignored; a row with the same spec is noted (`app.providers` `ok`: `<ids> is registered on <host> already, as <app> bundles it.`). What is left is listed (`app.providers` `start`: each provider's name, id, the hosts its key goes to and its settings; `data.providers[]` with `id`, `name`, `file`, `hosts`, `settings`, `outcome`) and registered after one confirmation: `--yes`, or the person's answer to `Register <ids> on <host>?` at a terminal; under `--json` without `--yes` the run stops with [`CONFIRMATION_REQUIRED`](/docs/agent/errors#confirmation_required) (`data.providers`, rerun with `--yes`, `authorize: true`), nothing registered. Then `app.providers` `ok`: `Registered <names> on <host>.`; the rows are the login's, as `provider add` writes them, and the keys are set next (the app's setup warning names them). An app that bundles nothing emits no `app.providers`.

### `app.register`: the registry row

`registerFromManifest` (`packages/cli/src/commands/appGateway.ts`) → `register` (`packages/cli/src/lib/gateway/registry.ts`) runs the pure rules in `packages/perimeter/src/registry/registration.ts` and writes one `cf d1 query` batch, which D1 applies atomically.

- The install organization is the oldest with an owner, else the oldest of all; none yet: one is created from the Cloudflare account's name (slugified; `My Organization` when blank) for the setup claim to adopt. The organization's key is claimed from `orgKeyCandidates(slug)` (its slug's `[a-z0-9]` up to 12 characters, then with `2`, `3`, … appended) into `organization_keys`; all taken is [`ORG_KEY_UNAVAILABLE`](/docs/agent/errors#org_key_unavailable).
- Names are assigned once, at first registration, and kept by a tombstone: the Worker `every-<orgKey>-<appId>`, its D1, KV and R2 after it (`every-<orgKey>-<appId>--<binding>` with the binding lowercased and `_` as `-`, except that the bindings `DB`, `KV` and `R2` take the Worker's own name: `resourceNameFor` and `bucketNameFor` in `packages/perimeter/src/manifest/manifest.ts`), the hostname `<appId>.<appBaseDomain>` for the install's own organization (`<appId>-<orgKey>.<base>` for any other). Refusals from the rules, each a `RegistrationError` turned into an error of the same code: `RESERVED_APP_ID`, [`INVALID_APP_ID`](/docs/agent/errors#invalid_app_id) (an id holding `--`, the resource separator), [`INVALID_MANIFEST`](/docs/agent/errors#invalid_manifest) (also an R2 bucket name Cloudflare refuses), `INVALID_APP_HOSTNAME`, `INVALID_WORKER_NAME` (over 63 characters, or one of the Gateway's own names), [`HOSTNAME_TAKEN`](/docs/agent/errors#hostname_taken), [`WORKER_NAME_TAKEN`](/docs/agent/errors#worker_name_taken) (another app's row, tombstones included), `RESOURCE_NAME_CONFLICT` (two bindings of one kind sharing a name), `SHARED_APP_NOT_PLATFORM`, `APP_SCOPE_MISMATCH` (an `org` app asked for as `shared` or the reverse), `APP_TIER_MISMATCH` (a `dispatch` row, which only the Gateway's own deployer writes, or a `provider` row from `everyapp mcp on`, deployed from the CLI).
- A new app (or a deleted one of its own organization coming back, `revived`) is written `pending` with its initial access: the deployer (by verified email), owners and admins; with `access: "everyone"` every member and `is_default`. An `existing` row only gets its name and description updated: a redeploy never changes names, status, scope or access.
- A row already `shared` (the CLI passes no `scope` to `register`, `registry.ts`: a new app is `org` and a redeploy keeps the row's) needs a login that is an owner or admin of the platform organization: [`SHARED_APP_FORBIDDEN`](/docs/agent/errors#shared_app_forbidden). An API token has no person to check and passes.
- `manifestTierProblems` (`packages/perimeter/src/manifest/manifest.ts`) runs on the row's tier: `service_binding` has no limits; `dispatch` refuses Hyperdrive, R2, Workers AI (`resources.ai`), Browser Rendering (`resources.browser`), Images (`resources.images`), Vectorize (`resources.vectorize`), AI Gateways (`resources.aiGateway`), Email sending (`resources.sendEmail`), Secrets Store (`resources.secretsStore`), Analytics Engine (`resources.analyticsEngine`), `email.inbound: true` and `secrets`; any other tier `apps on tier "<tier>" can't be deployed`. Problems are [`TIER_POLICY`](/docs/agent/errors#tier_policy), fix `change everyapp.config.ts, then deploy again`.

`app.register` is emitted `ok`: `Registered <appId> as <workerName> at https://<hostname> (pending).` (or `Updating … (active)`), `data`: `appId`, `workerName`, `hostname`, `status`, `existingApp`, `firstDeploy`, `defaultAccess`, `deployerAccess`, `hasOwner`, `publicRoutes` (`[{ path, methods }]`, what the manifest opens to anyone on the internet), `mcp` (`{ by, why }` when the manifest sets it: its host answers `/mcp`; else `null`), `scope`, `organizationId`, `organizationName`, `gatewayUrl`. A person sees nothing here; the data becomes the `Public` fact at the end on every deploy with public routes, the `MCP` fact (`Serves /mcp on its own host (gateway): <why>`) on every deploy whose manifest sets `mcp`, and the `Access` fact on a first deploy.

### `app.domain`: the hostname preflight

`preflightAppHost` (`packages/cli/src/lib/domains/preflight.ts`). A hostname not exactly one label below `appBaseDomain` is `outsideBase`: never published, neither checked nor a reason to redeploy the Gateway, and the run ends with warning [`APP_HOST_OUTSIDE_BASE`](/docs/agent/errors#app_host_outside_base). A hostname the install row doesn't list in `liveDomains` is `newHost` and is checked now, before anything is created or uploaded (the rebind checks again):

- Over 100 Custom Domains in the zone: [`ZONE_CUSTOM_DOMAIN_LIMIT`](/docs/agent/errors#zone_custom_domain_limit); at 95 or more, warning [`ZONE_CUSTOM_DOMAIN_LIMIT_NEAR`](/docs/agent/errors#zone_custom_domain_limit_near).
- `cf dns records list -z <zone> --name-exact <host>`: an `A`, `AAAA`, `CNAME` or `NS` record at the name, or a wildcard (`*.<parent>`) over a name with no records of its own, is [`DNS_RECORD_CONFLICT`](/docs/agent/errors#dns_record_conflict): "`<host>` already points somewhere else … Publishing it replaces the record." With `--force-dns` the record is replaced and warning [`DNS_RECORD_REPLACED`](/docs/agent/errors#dns_record_replaced) says so. A login that can't read the zone's records: [`DNS_UNREADABLE`](/docs/agent/errors#dns_unreadable), fix `give the API token Zone → DNS → Read`, rerun with `--force-dns` (authorize).
- A record at the name that is the Gateway's own Custom Domain (Cloudflare's placeholder `AAAA 100::`, left by a run that stopped after publishing the hostname; `cf workers list` says which Worker holds it) is no conflict: a `progress` line says "`<host>` is already this Gateway's Custom Domain (an earlier run published it, then stopped)". Which Worker holds a hostname with no record in the way isn't read; unless cf is attached (`--verbose` at a terminal), warning [`CUSTOM_DOMAIN_OWNER_UNCHECKED`](/docs/agent/errors#custom_domain_owner_unchecked): "If another Worker already serves `<host>`, it will be replaced by this deployment."

### `app.lease`: one deploy per app

`acquireAppLease` (`packages/cli/src/lib/gateway/lease.ts`) takes the row `app:<workerName>` in `_everyapp_deploy_lease` (the CLI creates the table itself) with purpose `app.deploy`, the app id, the login's email and the machine name. A lease expires 3 minutes after its last renewal; a heartbeat renews it every 30 seconds (each renewal given up after 20 seconds), so a dead deploy frees it within 3 minutes while a live one holds it as long as it runs. A run waiting on another says so as `progress` on `app.lease` ("Waiting for a deploy of todo to finish (ben@example.com on Bens-MacBook-Pro, started 1m ago)") and emits `app.lease` `ok` ("The other deploy finished.") once it gets the lease. A waiting run retries the acquire every 5 seconds; after 5 minutes of waiting: [`LEASE_HELD`](/docs/agent/errors#lease_held), retryable, rerun "once it's done (`pnpm everyapp status` shows it)", `data.holder`. A renewal that fails emits warning [`LEASE_HEARTBEAT`](/docs/agent/errors#lease_heartbeat) ("Can't reach Cloudflare to keep hold of `<target>` (`<time>` so far)", with how long until another run can take over). The lease counts as lost in two cases (`renewOnce`): a renewal that returns no row (the row is another holder's, or gone), or renewals that have kept failing for more than 90 seconds, half the TTL (then the heartbeat warns once more: "This run lost its hold on `<target>` … It stops before its next change."). `lease.check()`, called right before migrating and before each `cf deploy`, renews once more and throws [`LEASE_LOST`](/docs/agent/errors#lease_lost) ("Stopped: this run lost its hold on `<target>`", "Its hold expired, so it stopped before its next change to avoid overlapping another run.", retryable) when it is lost. Ctrl+C frees the lease. The lease is released in a `finally` once the registry records the upload; the rebind that follows takes the `gateway` lease instead.

### `app.install` and `app.build`

`app.install` runs the manifest's `install` command, or the detected package manager's install, unless `install: false` or the deploy is from a release; output goes to a log file, a failure is [`INSTALL_FAILED`](/docs/agent/errors#install_failed) (`packages/cli/src/lib/package-manager.ts`).

`app.build` (`packages/cli/src/lib/app/buildApp.ts`): `cf build` with `EVERYAPP_BUILD=1` (without it `everyAppWorker()` refuses a production build), no `--mode` (cf refuses it for TanStack Start; Vite builds production by default), 10 minutes at most, or the manifest's `build` command through a shell with the same variable. A failure is [`BUILD_FAILED`](/docs/agent/errors#build_failed) with cf's last lines. The output is the Build Output `.cloudflare/output/v0` (`packages/cli/src/lib/app/buildOutput.ts`): a root `config.json` and `workers/<name>/worker.config.json` plus `bundle/`, `default` for the app's Worker.

### The install rewrite

Every production build is tenant-neutral: `everyAppWorker()` builds from `sentinelDeployTarget()` (`packages/sdk/src/cloudflare/sentinel.ts`), so the same output comes out whoever builds it, with placeholders where an install's values belong: `BUILD_SENTINEL.workerName` `every-hosted--sentinel`, `organizationId` `everyapp-hosted-deploy-sentinel`, `gatewayUrl` `https://every-hosted--sentinel.invalid`, `accountId` `every-hosted--sentinel-account`, a sentinel public key, and `resourceSentinel(binding)` = `every-hosted--sentinel--<binding>` for each D1 (name and id), KV (id), Hyperdrive (id), R2 (name), queue (name, in the producer binding and in the consumer trigger's `name` and `deadLetterQueue`) AI Gateway (the json binding's `value.id`, with `value.accountId` the account placeholder and `value.url` `https://gateway.ai.cloudflare.com/v1/<account placeholder>/<id placeholder>`) and Secrets Store secret (store id and secret name).

`installAppBuildOutput` (`packages/cli/src/lib/app/installBuildOutput.ts`) rewrites each Worker's `worker.config.json` in place for this install (`InstallTarget`: `workerName`, `organizationId`, `accountId`, `gatewayUrl`, `identityPublicKeys: [install.jwtPublicKey]`, `resources`, `deletedDurableObjects`, `helperWorkers`):

1. Every `d1`, `kv`, `hyperdrive`, `r2` or `vectorize` binding whose placeholder field (`name` for D1, R2 and Vectorize, `id` for KV and Hyperdrive) is `resourceSentinel(binding)` gets the provisioned resource; one the target has none for is [`INSTALL_INPUTS_MISSING`](/docs/agent/errors#install_inputs_missing) ("The build binds D1 database `<NAME>`, which the deploy didn't provision"; fix `declare it in everyapp.config.ts's resources`). A binding of those kinds that doesn't hold its placeholder was written by hand in `cloudflare.config.ts` and stays for the policy to judge. A `json` binding whose `value.id` is `resourceSentinel(<its own binding name>)` is an AI Gateway's: its whole value becomes the provisioned `{ id, accountId, url }` (none provisioned: `INSTALL_INPUTS_MISSING`, "The build binds AI Gateway `<NAME>`, which the deploy didn't provision"); every other `json` binding is the app's own data and is never handed a gateway. A `queue` binding whose `name` is `resourceSentinel(binding)` gets the provisioned queue's name, and so does every `queue` trigger's `name` and `deadLetterQueue` that holds a queue placeholder (the placeholder carries the binding); a queue the target has none for is `INSTALL_INPUTS_MISSING` ("The build binds Queue `<NAME>`", "The build consumes Queue `<NAME>`" or "sends failed messages to Queue `<NAME>`", fix `declare it in everyapp.config.ts's resources.queues`). A `secrets-store-secret` binding whose `secretName` is `resourceSentinel(binding)` gets the provisioned `{ storeId, secretName }` the same way (`INSTALL_INPUTS_MISSING` with "Secrets Store secret `<NAME>`" and fix `declare it in everyapp.config.ts's resources.secretsStore` when there is none).
2. Every remaining string: the sentinel key list becomes the install's keys; the gateway URL and the account id (first, since they hold the Worker name's placeholder), the organization id and the Worker name are replaced wherever they appear (the Worker's name, its audience, Durable Object and helper service bindings, Workflow names, buckets named after it).
3. The app's Worker gets `{ type: "durable-object", state: "deleted" }` for each class in `deletedDurableObjects`; a class both exported by the build and deleted is [`APP_POLICY`](/docs/agent/errors#app_policy) ("declare it in everyapp.config.ts, or stop exporting it").
4. Any surviving placeholder (or its JSON-encoded form, in a key or a value) is [`INSTALL_PLACEHOLDER_LEFT`](/docs/agent/errors#install_placeholder_left), naming the paths: "Build the Worker from everyAppWorker() in cloudflare.config.ts, and leave its names, keys and ids to the deploy."
5. A Workflow name over Cloudflare's 64 characters (only known once installed, since names carry the Worker's) is [`WORKFLOW_NAME_TOO_LONG`](/docs/agent/errors#workflow_name_too_long), fix `shorten its binding name in everyapp.config.ts`.

### The policy check: everything it refuses

`prepareAppBuildOutput` (`packages/cli/src/lib/app/policy.ts`) checks the installed Build Output and throws one [`APP_POLICY`](/docs/agent/errors#app_policy) with every problem: `The built Worker can't be deployed as an EveryApp app:` then one `- <problem>` line each, then `Build it from everyAppWorker() in cloudflare.config.ts.` The purpose, from the module comment: `cloudflare.config.ts` is the app author's code; this keeps it from shipping a Worker the Gateway's model doesn't allow: public on workers.dev or a domain of its own, without its identity keys or in dev mode, bound to another Worker or to resources the deploy didn't provision for it or that aren't named after it, with a binding type the model doesn't know, or giving away or deleting Durable Object data. The Gateway's own deployer (its deploy API and browser installs) runs its own policy (below). Placeholders in angle brackets stand for the actual names.

**Build Output as a whole** (`prepareAppBuildOutput`), each its own `APP_POLICY`:

| -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| ``The app's Build Output isn't a production build. The manifest's build command must run `cf build` (production by default).``                     | `config.json`'s `buildContext.mode` isn't `production` or `isPreview` is set |

**`bindingProblems`** (`env`): the allowed binding types are `text`, `json`, `secret`, `version-metadata`, `assets`, `d1`, `kv`, `r2`, `durable-object`, `workflow`, `worker`, `hyperdrive`, `queue`, `ai`, `browser`, `images`, `vectorize`, `send-email`, `secrets-store-secret`, `analytics-engine-dataset`. Everything else is refused "until the model covers it: most reach account-wide resources by id or name (a dispatch namespace, private network, rate-limit counters, …), or account-wide capabilities the gateway is meant to broker (email)". Workers AI (`ai`) "is account-wide inference billed to the account, outside the Gateway's budgets, caps and usage tap (its `workers-ai` provider is the brokered path), and the deploy provisions nothing to check it against: so only under a binding name the manifest declares in `resources.ai`, never one cloudflare.config.ts adds on its own". Browser Rendering (`browser`) is the same: "account-wide browser time billed to the account, so only under a name `resources.browser` declares". Images (`images`) the same, under `resources.images`: "transformations bill the account". A `send-email` binding (Cloudflare's own email sending, which goes around the Gateway's budgets, sender list and log) is allowed only as `everyapp.config.ts` declares it in `resources.sendEmail`: under a declared binding name, with exactly the declared `allowedSenderAddresses`, `destinationAddress` and `allowedDestinationAddresses` (lists compared as sets: order and repeats don't matter; a list is never a single address; absent is absent). The upload itself checks no address (an unverified sender or destination uploads, and Cloudflare refuses it only when the Worker sends), so the policy judges the lists against the manifest, which is the operator's declaration. The addresses are accepted as the manifest writes them: they need not be among the installation's senders (`everyapp email set --sender`), since Cloudflare refuses a `from` whose domain isn't onboarded to Email Sending in the account at send time anyway; every entry must name its senders (the strict validator requires a non-empty `allowedSenderAddresses`), so a binding never sends as an address the manifest didn't list, the Gateway's own sender included. An Analytics Engine dataset (`analytics-engine-dataset`) "only under a binding `resources.analyticsEngine` declares, and only the dataset it declares (named after the Worker unless it names one): a dataset's name is account-wide". The declared names reach the check as `InstallTarget.declared` (the manifest's `resources`), from the deploy and from `release` alike. A Secrets Store secret (`secrets-store-secret`) "holds a credential in the account's store: only the store and secret the deploy provisioned for a binding `resources.secretsStore` declares, under that binding's name" (`InstallTarget.resources.secretsStore`, by binding: the same store id and secret name).

### `app.schema`: the schema-drift check

`checkSchemaDrift` (`packages/cli/src/commands/deploy/steps/checkSchemaDrift.ts`) runs after the build, before the database or the Worker changes, for a drizzle app with D1 bindings or `migrations.dialect: "postgresql"`. It runs the app's own `drizzle-kit generate` with a two-line config that extends the app's and points `out` at a copy of the migrations under `.everyapp/schema-check-*` (drizzle-kit 0.31 refuses `--out` next to `--config`, and resolves `out` against the working directory). A new `.sql` file in the copy is the verdict: [`SCHEMA_DRIFT`](/docs/agent/errors#schema_drift), "The schema has changes no migration covers. drizzle-kit would write a new migration for them. Nothing was migrated or uploaded.", rerun `pnpm db:generate` "then run this again". A run that fails without writing one (a schema that doesn't load, a rename drizzle-kit would ask about at a terminal; made an exit code by a `--require` hook since drizzle-kit exits 0 on its own errors) is [`SCHEMA_CHECK_FAILED`](/docs/agent/errors#schema_check_failed), rerun `pnpm db:generate` "in a terminal; it asks about renamed columns and tables". The scratch copy is removed in `finally` and on interrupt.

Two cases are not checked and emit no `app.schema` event at all (the function returns before anything): `migrations.engine` other than `drizzle` or `prisma` (`"d1-sql"`), and an app with no D1 bindings that isn't Postgres. drizzle-kit gets 120 seconds (`GENERATE_TIMEOUT_MS`); past that the run is `SCHEMA_CHECK_FAILED` with the reason `no answer in 120 s` when drizzle-kit printed nothing (else its first `Error` line, or its last). Skips, each a warning [`SCHEMA_CHECK_SKIPPED`](/docs/agent/errors#schema_check_skipped) on `app.schema` ("Can't check the schema against the migrations: `<why>`"): drizzle-kit not installed (fix `add drizzle-kit to devDependencies`), no `drizzle.config.ts`/`.js` (or none at `migrations.config`; "An app that writes its SQL by hand sets migrations.engine to \"d1-sql\""). `migrations.engine: "prisma"` is never checked (Prisma compares only against a shadow database): `app.schema` `skip`, "Schema not checked against migrations (Prisma needs a shadow database; --verbose shows how)". A release skips the step with a `progress` line: its publisher checked when it packed. A passing check is `app.schema` `ok`, "The schema matches the migrations."

### Replacing a Worker changed outside everyapp

Before the database changes, `assertReplaceable` (`packages/cli/src/lib/cf/deploy.ts`) runs for the app's Worker and each helper: the version serving must be one everyapp recorded (`plan.versionId` from the registry, or the ledger's `version_id`). cf's strict mode refuses to replace a Worker last changed in the dashboard or through the API unless a person confirms, and that question would come after migrating; so it is asked now. Unattended: `action_required` `rerun_interactive`, "`<app>` was changed outside everyapp; confirm in a terminal … Nothing changed.", `data.workerName`, `data.versionId`, `data.needsTerminal: true`, `data.rerun` (this command) with `data.rerunNote` "in a terminal": an agent hands `data.rerun` to a person as it is and never adds `--json` back (with it the run stops here again). At a terminal: `Replace the version that's serving?` with "Migrations run first." and "Cloudflare may ask to confirm again."; No is `CANCELLED`. `--yes` never answers this question.

### `app.migrations`: migrations and restore points

`lease.check()` first ([`LEASE_LOST`](/docs/agent/errors#lease_lost)), then `migrate` (`deployApp.ts`). The database changes only once nothing else can stop the upload; a failed migration leaves the version that is serving untouched.

D1 (`migrateRemoteD1`, `packages/cli/src/lib/migrations/remote.ts`), on the migration binding (`migrations.binding`, else the first D1 binding) from `migrations.dir` (default `drizzle`; drizzle-kit's `<tag>/migration.sql` layout and flat `*.sql` both read):

1. `cf d1 migrations list`: nothing pending ends the step `ok`, "The app's database is up to date."
2. Unless the database had none of the migrations yet (`fresh`: nothing to go back to, and any old restore point is forgotten), a Time Travel bookmark (`cf d1 time-travel get-bookmark <id>`) is recorded in `_everyapp_restore_points` (`packages/cli/src/lib/gateway/restorePoints.ts`) under target `app:<workerName>` with the pending migrations, the deployer's actor and the time.
3. `cf d1 migrations apply`, which keeps its own `d1_migrations` table.

`app.migrations` `ok` says `Applied <names>. Restore point saved; to undo: pnpm everyapp db restore` (for a release: `pnpm everyapp db restore <appId>`, since the release isn't deployed from the app's directory); `data`: `applied`, `fresh`, `restoreCommand`, `rollbackCommand`. `rollbackCommand` is cf's own `npx cf@<pinned> d1 time-travel restore <id> --bookmark <bookmark> --force` (prefixed with the account id; `restoreCommand` in `packages/cli/src/lib/cf/d1.ts`), for scripts. A failure is [`MIGRATION_FAILED`](/docs/agent/errors#migration_failed): "Database migration failed … Nothing was uploaded; the version that's serving keeps running. To roll the database back to before this run: `pnpm everyapp db restore`", `data.fix` `correct the migration`, `data.rollbackCommand`. Any later failure in the run (the upload, the rebind) carries the same restore point (`afterMigration`, `packages/cli/src/lib/errors.ts`). The Gateway's own database is restored with `pnpm everyapp db restore --gateway`.

Postgres (`migrations.dialect: "postgresql"`): the app's own `drizzle-kit migrate` (`packages/cli/src/lib/migrations/postgres.ts`) or, with `migrations.engine: "prisma"`, `prisma migrate deploy` (`packages/cli/src/lib/migrations/prisma.ts`), with `migrations.config` when set, against `POSTGRES_DATABASE_URL` from `.everyapp/secrets.env`. The URL reaches the CLI only in its environment, and its output comes back with the URL and password replaced (`packages/cli/src/lib/migrations/localCli.ts`, 10 minutes at most). There is no restore point: the database's own backups are the way back. A missing CLI is [`DRIZZLE_KIT_MISSING`](/docs/agent/errors#drizzle_kit_missing) or [`PRISMA_MISSING`](/docs/agent/errors#prisma_missing); a failure `MIGRATION_FAILED` with the first `error` (or `P\d{4}`) line. `app.migrations` `ok`: `Migrated the app's Postgres database (drizzle-kit migrate)`, `data.dialect`, `data.engine`, and for Prisma `data.applied`.

### `app.helper` and `app.upload`: `cf deploy --prebuilt`

`cfDeploy` (`packages/cli/src/lib/cf/deploy.ts`) runs `cf deploy --prebuilt --no-provision --mode production --message "everyapp <cli version> <appId>[ <helper>]" [--worker <helper>] --secrets-file <0600 temp file>` in the Build Output root, 15 minutes at most. `--no-provision` (every upload, the Gateway's too): cf otherwise creates a missing D1 database, KV namespace, R2 bucket or queue that a binding names, which no deploy would record as the app's; with it, a binding to something missing is refused before the upload (`Queue "<name>" does not exist. …`). The secrets file holds `GATEWAY_URL` and `EVERY_APP_ORG_ID` (`versionSecrets`, `deployApp.ts`), so they ship in the same Worker version as the code ("A helper calls the gateway too, and without EVERY_APP_ORG_ID it would name the app's own organization id, which the gateway refuses"). Helper Workers go first (`app.helper` per helper, `data.name`, `data.workerName`): the app's Worker binds them, so each must exist, with any new class, before the version that uses it. `lease.check()` runs before each upload. cf's output stays in memory unless `--verbose` at a terminal attaches it (then cf asks its own questions).

The uploaded version is recorded in the ledger as soon as it is known (`recordUploadedVersion`, `onUploaded`), also on the way out of a Ctrl+C or a cf failure after the upload, "so a retry must find this upload was everyapp's, however this run ends". Failures:

### `app.workflows`, `app.email` and the registry record

- Each Workflow dropped with `--allow-delete-workflows` is deleted now, before the registry records the new manifest ("so a retry after a failed delete deletes them still"): `app.workflows` `ok`, `Deleted the Workflow <binding> (<name>) with its instances.`
- `app.email` (when there are routes to make or remove): `lease.check()`, then `applyEmailRoutes`; `ok` with `data.addresses`, `data.removed`, `data.enabled`, and `data.replyHint` when senders are missing for a routed domain. An app that declares inbound mail with no stored address: `app.email` `skip`, "`<app>` receives no mail yet.", and `done.data.next` gets `pnpm everyapp email set --inbound <address>`. An app whose manifest declares sending (`capabilities.email` with `access: "write"`: `emailDeclarations`, `packages/cli/src/lib/app/emailRoutes.ts`) on a Gateway whose `deploymentMode` isn't `hosted` (`sendersSettable`: the installation's senders are its own to set) with no sender stored: `done.data.next` also gets `{ command: "pnpm everyapp email set --sender '*@<domain>'", note: "lets <app> send as your domain" }`; until a sender is set, the app sends as the Gateway's sender. Setting up the Gateway's mail step by step: `packages/cli/skills/everyapp/setup/email.md`, in an app `.claude/skills/everyapp/setup/email.md`.
- A helper Worker the manifest dropped keeps running: warning [`HELPER_WORKER_KEPT`](/docs/agent/errors#helper_worker_kept) ("the deploy never deletes a Worker"; fix `delete that Worker in the Cloudflare dashboard`).
- `markDeployed` (`registry.ts`) writes `manifest`, `version_id`, `deployed_at`, `deployed_by_actor` and the status (`pending` → `binding`, any other kept: "an admin switching the app off meanwhile keeps it off"), only over the status it was read with, three attempts; a row that keeps changing is [`APP_CHANGING`](/docs/agent/errors#app_changing) ("The upload is kept.", retryable); a row that is gone is [`APP_NOT_FOUND`](/docs/agent/errors#app_not_found). The manifest's route policy goes live with this write.
- After the upload is recorded, the manifest's settings are checked against the Gateway's names and the Worker's own (`warnIfNeedsSetup`, `deployApp.ts`): an app with an unmet required setting gets warning [`APP_NEEDS_SETUP`](/docs/agent/errors#app_needs_setup) on step `app.secrets` ("`<app>` won't open until `<NAMES>` is set", the first unmet setting's `why` under it; `data.setup`) and one `next` entry with the command that opens it, `pnpm everyapp configure <app>` (note "asks for each; `<app>` opens once they are set"). Until then the app shows "Needs setup" and its tools stay out of `/mcp` ([the secrets page](/docs/agent/secrets)).

The app lease is released.

### `app.bind`: the Gateway rebind

`bindIfNeeded` (`packages/cli/src/commands/appGateway.ts`) returns at once when the install row's `liveAppWorkers` already lists the Worker and the hostname isn't new: a redeploy of an app the Gateway already serves never touches the Gateway. Otherwise `app.bind` starts (`Binding APP__<workerName> on the gateway[ and publishing its hostname]...`) and `reconcileGateway` (`packages/cli/src/lib/gateway/reconcile.ts`, `force: true`) redeploys the Gateway with a fresh set of `APP__<worker>` service bindings and Custom Domains:

1. The release is the live one again (`liveGatewaySource`, `packages/cli/src/lib/gateway/liveRelease.ts`, through `gatewayFor` in `appGateway.ts`): its GitHub release by the tag the install row records, its URL or file, or this checkout's build cache for the row's tree hash, or a new build when this checkout's Gateway sources hash to that tree (an untagged Gateway: the same sources are no upgrade; a row from before origins were recorded counts as a checkout's); `gateway.release` `ok` "Using the live Gateway X from <origin>" (`data.live: true`). Opened, its SHA-256 must be the row's `releaseSha256`. When it can't be had (a row from before origins were recorded, a file that is gone, a checkout build this machine doesn't have, a checkout-built Gateway from an everyapp outside a checkout, a tag that is gone or whose asset was replaced), [`GATEWAY_RELEASE_UNAVAILABLE`](/docs/agent/errors#gateway_release_unavailable) before anything on the Gateway changes; `update` is the way on. Nothing here builds or downloads a newer Gateway. A release whose `minCli` is newer than the CLI: [`CLI_TOO_OLD`](/docs/agent/errors#cli_too_old) (`refuseNewerThanCli`, `packages/cli/src/lib/gateway/release.ts`, called by `reconcileGateway` in `packages/cli/src/lib/gateway/reconcile.ts` once the release is open, before `gateway.lease`).
2. Why an upload at all: Cloudflare's script-settings PATCH (`inherit` for every binding, plus the new service binding), which the browser installer uses (`apps/every-app-gateway/src/server/deploy/cfRestDeployer.ts`), binds an app without one, but cf has no command for a Worker's settings and a `cf auth login` session gives everyapp no API token of its own. So the rebind uploads the same release with the new binding list; the Worker's version changes, its release does not.
3. `gateway.lease` (purpose `gateway.reconcile`), [`LEASE_HELD`](/docs/agent/errors#lease_held) after the wait, rewrapped by `bindIfNeeded`: "This app's upload is kept; deploying again binds it and makes it live.", rerun "once the other deploy finishes".
4. `applyGateway` (`packages/cli/src/lib/gateway/apply.ts`), under the lease: the downgrade guard again; the release is the live one (by SHA-256 or tree hash), so the checks and migrations only a different release gets (Build Output validation, `assertReplaceable`, `gateway.migrations`) are skipped. Then the desired state is read from the registry (apps whose Worker isn't the registered one get warning [`APP_NOT_BOUND`](/docs/agent/errors#app_not_bound), whose Worker is missing [`APP_WORKER_MISSING`](/docs/agent/errors#app_worker_missing); the Gateway won't route to them), every new hostname is preflighted (`DNS_RECORD_CONFLICT`, `--force-dns`), and `gateway.deploy` uploads once with `cf deploy --prebuilt` from a private patched copy of the release (`Uploading Gateway <version> with <n> apps`, `data.appWorkers`, `data.domains`). The install row records the version as soon as it is known and the hostnames only once cf published them.
5. `app.bind` `ok`: `The gateway binds APP__<workerName> (gateway version <id>).`, `data.versionId`, `data.newHosts`.

### `app.live`: the live wait

`waitForLive` (`packages/cli/src/commands/deploy/steps/waitForLive.ts`) runs unless `--no-wait` or the hostname is outside the base. The Gateway makes a `binding` app `active` itself, on the first request that reaches it over the service binding; this step sends that request (`GET https://<hostname>/`, `probeHttps`, resolved at the zone's nameservers so a stale local resolver can't hold it back) every 3 seconds, reads the app's row after each, and emits `progress` every 15 seconds ("Waiting for the certificate for `<hostname>` (usually under 5m)" until something answers, then "Waiting for `<app>` to go live"). The request is the trigger, D1 is the truth: no HTTP status says an app is live by itself. Two more triggers make the same probe and the same transition (`activateBindingApps` and `activateDeployingApps`, `apps/every-app-gateway/src/server/app-activation.ts`): the Gateway's per-minute cron sweeps every `binding` app of the install (at most 50 a run), and the Gateway's home page and Admin → Apps probe each `binding` app they list (the launcher reads its list again every 5 seconds while one is deploying). So an uploaded app is live within a minute whether or not anyone visits. Behind Cloudflare Access this step's request never reaches the Gateway: Access answers it with a redirect to its login. From that answer on the step sends nothing more and only reads the row (D1, through the Cloudflare API, which Access doesn't stand in front of), with the `progress` line "Cloudflare Access answers before the Gateway; waiting for the Gateway to make `<app>` live (it looks every minute)" (`data.access: true`), until the sweep makes it `active`. The one `app.live` event of the transition says which trigger made it (`request`, `list` or `scheduled`; [events](/docs/agent/events)).

| Outcome                                      | Event                                                                                                                                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Row says `active`                            | `app.live` `ok`, `<app> is live at https://<hostname>.`, `data.hostname`, `data.url`, `data.waited` (`certificate` or `live` when it waited). Warning [`LOCAL_DNS_STALE`](/docs/agent/errors#local_dns_stale) when this computer's resolver still can't resolve the name |
| Row says `disabled`                          | Warning [`APP_DISABLED`](/docs/agent/errors#app_disabled) ("switched off in Admin → Apps"); the run ends not live                                                                                                                                                        |
| Cloudflare Access answers before the Gateway | No event of its own: the wait goes on reading the row (the `progress` line above) and ends like any other, `active` within a minute in the normal case                                                                                                                   |
| 10 minutes behind Access                     | Warning [`ACCESS_IN_FRONT`](/docs/agent/errors#access_in_front): "Cloudflare Access answers before the Gateway, and the Gateway hasn't made `<app>` live after …; The deploy stalled: …", `data.rerun` `pnpm everyapp status` "then deploy again"; `app.live` `skip`     |
| 10 minutes with no answer at all             | Warning [`CERT_PENDING`](/docs/agent/errors#cert_pending) ("No certificate for `<hostname>` after …; It usually comes within 5 minutes"; fix: check the zone's CAA records allow Cloudflare's certificate authorities); `app.live` `skip`                                |
| 10 minutes while the Gateway answers         | [`APP_NOT_LIVE`](/docs/agent/errors#app_not_live): "`<app>` isn't live after …: the Gateway can't reach its Worker yet. `<app>` stays uploaded and bound.", retryable, rerun `pnpm everyapp status` "then deploy again"                                                  |
| Row gone or `deleted` during the wait        | [`APP_NOT_FOUND`](/docs/agent/errors#app_not_found): "was deleted during this run"                                                                                                                                                                                       |

Without the wait, or when it ended early, `app.live` is `ok` for an app whose status was already `active` (a redeploy), else `skip` with `<app> isn't live yet: https://<hostname>.` and `data.reason`: `certificate` (`--no-wait` with a new hostname), `first-visit` (`--no-wait`, hostname already published), `outside-base` (never routed; also warning `APP_HOST_OUTSIDE_BASE`: "The Gateway only serves names directly under `<base>`").

### `app.access`: the manifest's `public` routes behind Cloudflare Access

After the live wait (and before `APP_HOST_OUTSIDE_BASE`), `deployApp` calls `syncAppsAccessAfter` (`packages/cli/src/lib/access/sync.ts`) with the manifest's public surface (`{ publicRoutes, mcp }`: whether it has `public` routes or `publicAssets`, and whether it sets `mcp`), so an app's public routes, and its `/mcp` where asked for, are reachable without an Access login as soon as the app is. It never fails the run: everything that goes wrong inside it is a warning. It lists the account's Access applications (`listAccessApplications`, `packages/cli/src/lib/cf/access.ts`) and returns silently when none is a `self_hosted` application with a public destination on `*.<appBaseDomain>` (Access isn't in front; `findAccessApplications`, `packages/cli/src/lib/access/plan.ts`, finds the applications by what they cover, not by name). Otherwise it takes the registry lease `access` (`ACCESS_LEASE_ID`, purpose `access.sync`; `access on` holds the same lease while it writes the applications, `turnAccessOn` in `packages/cli/src/commands/access/index.ts`): a wait is `progress` on `gateway.lease` ("Waiting for an update of Cloudflare Access to finish (…)"), lasts up to 60 seconds (`SYNC_LEASE_WAIT_MS`) and ends with `gateway.lease` `ok` "The other Cloudflare Access update finished."; past it, `LEASE_HELD` becomes the `ACCESS_SYNC_FAILED` warning below. Under the lease it reads the applications again and every served app (`readPublicSurfaces`: `apps` rows with status `binding`, `active` or `disabled` and a hostname, each with the `public[].path` list and the `mcp` of the manifest it was last deployed from; a manifest that doesn't parse counts as neither), plans the apps application's destinations (`appsDestinations`: the wildcard `*.<base>` with nothing let through, then one destination per app with public routes or `mcp`, by host: `/mcp` and `/mcp/*` first only where the manifest sets `mcp`, then its routes as Access path patterns in manifest order, each once, up to 25; with Managed OAuth on the Gateway host's application no `/mcp` is let through anywhere, and an app with `mcp` alone gets no destination), keeps every destination that isn't EveryApp's as found (and the Gateway host's own when one application covers both), and writes the application back (`updateAccessApplication`) only when the result differs from what Access has (`sameDestinations`: lowercased, trailing slashes dropped, overrides sorted). The result is step `app.access` with `data: { appId, applicationId, changed, removed }`: `ok` `Cloudflare Access lets <app>'s <public routes | /mcp | public routes and /mcp> through.` (a person sees that line, `packages/cli/src/lib/output/events.ts`), or `skip` `Cloudflare Access already matched <app>'s <…>.` (shown to nobody); the words follow what the manifest opens (`surfaceWords`), and a `delete` says `no longer lets <app>'s <…> through.`

Warnings:

- [`ACCESS_NOT_CHECKED`](/docs/agent/errors#access_not_checked) on `app.access` when the applications couldn't be listed. For a login or token without the Access permissions (cf's `auth` refusal, which `lib/cf/access.ts` turns into [`ACCESS_PERMISSION_MISSING`](/docs/agent/errors#access_permission_missing), "This Cloudflare login can't manage Access") the warning is "This Cloudflare login can't read Cloudflare Access, so `<app>` wasn't checked against it", said only when the app has public routes or sets `mcp`, the things a sync would change for it (a CI token deploying an app with neither gets nothing); for any other refusal "Couldn't check Cloudflare Access for `<app>`" with the error's first line, always said; each followed by "If the Gateway is behind Access, `<app>`'s `<public routes | /mcp | public routes and /mcp>` need a login there until it is updated." `data`: `appId`, `rerun` `pnpm everyapp access on`, `rerunNote` "with a login that can manage Access, if the Gateway is behind it" (permissions) or "if the Gateway is behind Access".
- [`ACCESS_SYNC_FAILED`](/docs/agent/errors#access_sync_failed) on `app.access` when the sync itself failed (the lease wait included): "Couldn't update Cloudflare Access for `<app>`'s `<public routes | /mcp | public routes and /mcp>`", the error's first line, "Until it is updated, they need an Access login."; `data`: `appId`, `rerun` `pnpm everyapp access on`.
- The plan's leftovers, on step `access.routes` (`emitPlanWarnings`), without a `rerun`: [`ACCESS_ROUTE_NOT_EXPRESSIBLE`](/docs/agent/errors#access_route_not_expressible) ("A public route stays behind Access: `<app> <path>`" or "`<n>` public routes stay behind Access: …", then "Access path patterns take one \* per segment, so these have no equivalent. People signed in to Access still reach them."; `data.routes`), [`ACCESS_TOO_MANY_PUBLIC_ROUTES`](/docs/agent/errors#access_too_many_public_routes) (the same first line, then "Access lets through at most 25 paths per host (two of them for /mcp where the manifest sets mcp). Merge routes under one prefix, or keep these behind the login."; `data.routes`), [`ACCESS_APP_OUTSIDE_BASE`](/docs/agent/errors#access_app_outside_base) (an app with public routes whose host isn't one label below the base gets no destination: "`<app>` isn't under the apps' domain, so Access isn't set up for it."; `data.apps`), [`ACCESS_FOREIGN_DESTINATION`](/docs/agent/errors#access_foreign_destination) ("The Access application "`<name>`" also covers `<uris>`", "That destination isn't EveryApp's and stays as it is. access off won't delete this application."; `data.application`, `data.uris`).

`delete` runs the same with `removing: true` (below). Putting the Gateway behind Access is `pnpm everyapp access on` (step by step: `packages/cli/skills/everyapp/setup/access.md`, in an app `.claude/skills/everyapp/setup/access.md`); patterns, destinations and `everyapp access on|off|show` are on [the Access page](/docs/agent/access).

## Idempotence: what is safe to rerun

Every step looks before it acts, so the same command runs again after any stop:

- Registration of an existing row only updates name and description; a first deploy that stopped is still `pending` and still the first (`firstDeploy`).
- Resources are recorded as the app's before they are created, and an upload's version as soon as cf reports it, so a retry finds both; a claim whose create never recorded an id is finished by the next run ("Claimed, then created, but the id never recorded: it's this one").
- The deploy lease is freed on Ctrl+C, on release, and expires 3 minutes after a dead holder's last heartbeat; the next run waits up to 5 minutes for it.
- Migrations run before the upload, with a restore point; a failed upload leaves the migrated database and says how to put it back.
- Dropped Workflows are deleted before the registry records the new manifest, so a retry deletes them still.
- The rebind compares the install row with the registry and uploads the Gateway only when something differs (or `force`); an app the Gateway already binds and serves never redeploys it.
- Nothing about an install is kept on the machine; a second machine needs only the login and the CLI.

What is never done twice by itself: deleting a Worker (never done by `deploy` at all), replacing a Worker changed outside everyapp (asked each time), replacing a DNS record (`--force-dns` each time).

## Release installs: `install <source>`

`pnpm everyapp install <source>` installs an app release with no checkout of the app (`fetchAppRelease`, `packages/cli/src/lib/app/release.ts`; `packages/cli/src/lib/release/fetch.ts`, `packages/cli/src/lib/release/github.ts`):

- `source` is a github.com repository URL (its latest release; `…/releases/tag/<tag>` or `…/releases/latest`: that one), any other HTTPS URL (a tarball to download), or a local file. A repository that publishes no `everyapp-release.tar.gz` is [`NO_RELEASE`](/docs/agent/errors#no_release) ("publishes no everyapp release … Its GitHub releases have no everyapp-release.tar.gz"; fix `clone it, then run pnpm install in it and this checkout's pnpm everyapp deploy from its directory`): the CLI never builds a repository from its URL. A path that isn't there is [`RELEASE_NOT_FOUND`](/docs/agent/errors#release_not_found).
- Downloads are anonymous (no token, cookie or identifying header, so a private repository's releases answer 404), follow redirects by hand and only to HTTPS (5 at most), refuse a body over 200 MB ([`RELEASE_TOO_LARGE`](/docs/agent/errors#release_too_large)) or over 5 minutes ([`RELEASE_DOWNLOAD_FAILED`](/docs/agent/errors#release_download_failed), retryable), and land in the CLI's private temp dir. The tag comes from the `/releases/download/<tag>/` URL GitHub redirects to.
- A release (`packages/cli/src/lib/gateway/release.ts` `extractRelease`) holds only `release.json`, `.cloudflare` (the Build Output `v0`, placeholders and all) and `migrations` (the manifest's migrations directory, when there is one); `release.json` is schema 1, `kind: "app"`, with `appId`, `version`, `gitSha`, `builtAt`, `cfVersion`, `cliVersion`, `sdkVersion`, `buildOutputVersion`, `sha256`, `migrations` (the drizzle journal), `minCli`, `minSdk` and the evaluated `manifest` (its `migrations.dir` rewritten to `migrations`). Checks: the kind ([`RELEASE_INVALID`](/docs/agent/errors#release_invalid)), nothing else at the top level (`RELEASE_INVALID`), a Build Output this CLI deploys (`v0`, else [`RELEASE_UNSUPPORTED`](/docs/agent/errors#release_unsupported)), the SHA-256 of every file but `release.json` (`hashReleaseTree`: each path and its content hash, in path order; a mismatch is [`RELEASE_CORRUPT`](/docs/agent/errors#release_corrupt)), `minCli` not newer than the CLI ([`CLI_TOO_OLD`](/docs/agent/errors#cli_too_old)), a manifest the strict parser takes whose `id` is the release's `appId` and whose `migrations.dir` is `migrations` (`RELEASE_INVALID`).
- The pipeline is then the same with the extracted release as the Build Output root and its manifest as the app's: nothing is installed or built (`app.build` `ok`: "Installed the release and checked its Worker."; a person sees `Release checked`), the install rewrite and the policy check run on it all the same, and the schema check is left to the publisher's build. The app's `.everyapp/secrets.env` is read from the current directory. `app.deploy` says `Deploying <app> <version> from github.com/<owner>/<repo> (release <tag>) to …` and carries `data.release`.
- What a release deploy can't do: Postgres migrations ([`RELEASE_MIGRATIONS_UNSUPPORTED`](/docs/agent/errors#release_migrations_unsupported): drizzle-kit and Prisma need the app's source and config; a Prisma app can't even be packed). The migration restore command is `pnpm everyapp db restore <appId>`.
- The release's `providers` (the specs the app bundled) are registered on the Gateway as `deploy` registers an app's own (`app.providers`, above): listed, then after `--yes` or a yes at the terminal; `install --json` without `--yes` stops with `CONFIRMATION_REQUIRED`.
- Publisher trust (`docs/security-model.md`, "Trust Zones"): the SHA-256 proves only that the tarball is whole, not who built it; whoever deploys a release trusts its publisher as they would trust the repository's code.

## `release`: packing a release

A repository publishes one on every push with the Release workflow `pnpm pack-for-app <app> --workflow` installs from an EveryApp checkout (`starter/.github/workflows/release.yml`: checkout, pnpm, Node, `pnpm install --frozen-lockfile`, then one step, `pnpm exec everyapp release --publish` with `GITHUB_TOKEN`, below, and the tarball kept as a run artifact; the runbook is `docs/runbooks/app-releases.md`, which also covers how an app's clone builds on its own: the CLI and the SDK pinned to one published version, `pnpm pack-for-app <app> --npm <version>`; vendored `file:` tarballs were retired on 2026-10-26). `bundleApp` (`packages/cli/src/commands/release/bundleApp.ts`) needs no Gateway and no Cloudflare login: `app.install`, `app.build` (`cf build`, then the policy check with the build's own placeholders, `sentinelDeployTarget(manifest)`, and the helper names derived from the sentinel Worker name), `app.schema`, then `packAppRelease` (`packages/cli/src/lib/app/release.ts`):

- The Build Output must be `v0` alone in `.cloudflare/output` and a production build, else [`RELEASE_PACK_FAILED`](/docs/agent/errors#release_pack_failed).
- The staged tree is the Build Output, the migrations directory (drizzle, or `d1-sql`) as `migrations/`, and `release.json` (`version` from `package.json`, `0.0.0` when it has none or can't be read; `gitSha` the checkout's `HEAD` with `-dirty` when `git status --porcelain` shows changes under the app, `unknown` outside a git checkout; `cfVersion` from the app's cf, `unknown` when it can't be resolved (`bundleApp.ts`); `sdkVersion` the app's `@every-app/sdk` version, `null` without it (`appSdkVersion`, `release.ts`); `minCli` and `minSdk` `0.3.0`). macOS litter (`.DS_Store`, `._*`) is never staged; `tar` runs with `COPYFILE_DISABLE=1`.
- The provider specs the app bundles (`.everyapp/providers/*.json`) ride in `release.json` as `providers` (`packAppRelease`; a file that isn't JSON is `RELEASE_PACK_FAILED` naming it); `.everyapp/` itself never ships.
- [`RELEASE_LOCAL_STATE`](/docs/agent/errors#release_local_state) refuses to pack `.dev.vars*`, `.env*`, `*.pem`, `.cloudflare/state`, `.cloudflare/types`, `.wrangler/` or `.everyapp/` ("Refusing to pack local state or secrets into the release").
- A Prisma app is refused before staging: `RELEASE_MIGRATIONS_UNSUPPORTED` ("migrates with Prisma, which a release can't carry").

`app.release` `ok`: `Packed <app> <version> (<sha256 prefix>) into <path>.`, `data`: `tarball`, `shown`, `appId`, `version`, `sha256`; a person sees the facts `Release <path>` and `SHA-256 <the full hash>`. `done.data` adds `next`: `{ command: "pnpm everyapp install ./everyapp-release.tar.gz", note: "installs it on your Gateway" }`, then `{ command: "pnpm everyapp install <repository url>", note: "installs it on any Gateway, once the tarball is attached to a GitHub release of the app's repository" }` (what the command's own description, `command.ts`, says).

### `release --publish`: the GitHub release

`--publish` (`packages/cli/src/commands/release/publish.ts`) runs after the pack, in GitHub Actions; plain `release` (no `--publish`) prints and emits exactly what it did before. Before anything is built, `githubRun()` reads the run: `GITHUB_REPOSITORY`, `GITHUB_SHA` and `GITHUB_EVENT_NAME` are required, else [`GITHUB_RUN_MISSING`](/docs/agent/errors#github_run_missing) (`data.missing`); `GITHUB_REF_TYPE`, `GITHUB_REF_NAME`, `GITHUB_API_URL` (default `https://api.github.com`), the default branch from the event payload at `GITHUB_EVENT_PATH` (`main` when it can't be read), and the token from `GITHUB_TOKEN`, else `GH_TOKEN`. `planRelease()` then picks the release:

| Run                                                     | Release                                                                                                                                                                                                             |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `push` to the default branch                            | `v<package.json version>`; `v<version>-<yyyymmdd>-<sha7>` (UTC date, the commit's first seven characters) when the repository has the tag `v<version>` already (`GET /repos/<repo>/git/ref/tags/<tag>`, 404 = free) |
| `push` of a tag                                         | that tag                                                                                                                                                                                                            |
| `workflow_dispatch`                                     | a draft, `v<version>-<yyyymmdd>-<sha7>`                                                                                                                                                                             |
| `pull_request`, a push to another branch, anything else | nothing: `app.publish` `skip`, `Not publishing: <reason>.`; the run still ends `done`, exit 0                                                                                                                       |

Publishing is two REST calls with `fetch` (no `gh`): `POST /repos/<repo>/releases` (`tag_name`, `target_commitish` = `GITHUB_SHA`, `name` = the tag, `body` = the notes, `draft`), then the tarball uploaded as `everyapp-release.tar.gz` to the release's `upload_url` (`application/gzip`). A failed upload deletes the release it just created, so a rerun starts clean. Either refusal is [`RELEASE_PUBLISH_FAILED`](/docs/agent/errors#release_publish_failed); no token at that point is `GITHUB_RUN_MISSING`. The notes (`releaseNotes()`): `Built from <sha> by everyapp release --publish.`, then `Install it on your Gateway, or update it there:` with `everyapp install https://github.com/<repo>` in a code block, then `everyapp-release.tar.gz SHA-256: <hash>`.

`--dry-run` (it implies `--publish`) does everything but the two writes: the tag lookup still runs, and `app.publish` `skip` says `Dry run: would publish the release <tag> of <repo>.` (`a draft release` on a manual run) with the notes in `data.notes`. Events: `app.publish` `start` (`Publishing <tag> on <repo>...`) and `ok` (`Published the release <tag>: <url>`; a person sees `Published <tag>` and the fact `GitHub release <url>`); `done.data.published` is `{ tag, draft, url, dryRun }`, null when nothing was published, and `done.data.next` the one `install https://github.com/<repo>` once a release is out. The job needs `permissions: contents: write`; a 401, 403 or 404 from GitHub says so in `data.fix`. `--publish` is newer than `0.3.0-rc.3`: an app pinned to that version keeps its old workflow until its pin moves.

## The Gateway's deploy API

The Gateway has a deploy pipeline of its own (`apps/every-app-gateway/src/server/deploy/`), reached two ways: its deploy API, with a deploy key, and the browser install below, with a session. No CLI command calls either: `deploy` writes the registry and uploads with `cf` as above, and the CLI's deploy-key path was removed on 2026-10-24 (`docs/security-model.md`, "Hosted Deploy API", names the commit it is restorable from).

The API's routes (`routes.ts`) exist only while `platformPolicy(env).thirdPartyDeploys` holds (`apps/every-app-gateway/src/server/platform-policy.ts`: a `hosted` Gateway whose `THIRD_PARTY_DEPLOYS` is exactly `on`; otherwise the paths are the control plane's 404s): `GET /api/v1/deploy-key` (who the key is: `organizationId`, `userEmail`, `role`, `appRowId`), `POST /api/v1/orgs/<orgId>/apps` (JSON `{ appId, manifest }`: the manifest is checked against the third-party policy, `manifestProblems` below, and the app registered by `registerApp`, `run.ts`, through `registerDispatchApp` in `registry.ts`: tier `dispatch`, scope `org`, Worker `every-<orgKey>-<appId>`, D1 `<worker>--<binding>`, hostname `<appId>-<orgKey>.<THIRD_PARTY_DOMAIN>` or none while that domain is unset; a `THIRD_PARTY_DOMAIN` on, under or above the Gateway's `APP_BASE_DOMAIN` is refused as [`DEPLOYER_NOT_CONFIGURED`](/docs/agent/errors#deployer_not_configured), 503, "third-party apps need a registrable domain of their own", because the Gateway's session cookie is scoped to its domain), `POST /api/v1/orgs/<orgId>/apps/<appId>/deploys` (one multipart body, the parts `HOSTED_DEPLOY_PARTS` names in `packages/perimeter/src/manifest/deploy.ts`, read by `bundle.ts`) and `GET /api/v1/orgs/<orgId>/deploys/<jobId>` (the job: `{ id, status: "running" | "succeeded" | "failed", error: { code, message } | null, app }`; the deploy runs in the request that starts it, which answers the finished job when the deploy took under 20 seconds, else `running` to poll; a job still `running` 5 minutes after it was created is answered as `failed` with `DEPLOY_ABANDONED`, below). Every call carries a deploy key as the bearer (`authenticateDeployKey`, `auth.ts`: a personal access token with the `deploy` scope and nothing else, of a live owner or admin of the organization it is bound to, checked on every request; no cookie is read). The job records `deployed_by_actor` as `deploy-key:<token id>` (`routes.ts`, `pipeline.ts`).

The pipeline (`run.ts` `startDeploy`, `pipeline.ts` `runDeploy`), the same for the API and a browser install: every refusal first, then its D1 databases through the same resource ledger rules, its static assets, the Worker's metadata with every binding rewritten from the manifest and the row (never from the bundle), its D1 migrations (statements split on `--> statement-breakpoint`, each file in one transaction, recorded in `d1_migrations`), the upload (into the dispatch namespace on a hosted Gateway; a self-hosted browser install uploads a private account Worker through the Cloudflare REST API, `cfRestDeployer.ts`), a read-back of the bindings, then the registry record (`pending` → `binding`; the Gateway activates it on the first request). Full detail: `docs/security-model.md`, "Hosted Deploy API".

Codes the routes answer (JSON `{ "error": "<code>", "message": "<sentence>" }` with the code's HTTP status, `DeployError` in `errors.ts`; anything else thrown is `INTERNAL_ERROR`) or the job records, which a browser install raises the same way: from `authenticateDeployKey` (`auth.ts`), in order, [`DEPLOY_KEY_REQUIRED`](/docs/agent/errors#deploy_key_required) (401: no bearer), [`DEPLOY_KEY_INVALID`](/docs/agent/errors#deploy_key_invalid) (401: "The deploy key is unknown, revoked or expired. Create one in Admin → Tokens (Deploy key)."), [`DEPLOY_SCOPE_REQUIRED`](/docs/agent/errors#deploy_scope_required) (403: the token isn't a deploy key, a scope beside `deploy` on the row), [`NOT_A_MEMBER`](/docs/agent/errors#not_a_member) (401: "The deploy key's owner is no longer a member of its organization, or is deactivated."), [`DEPLOY_FORBIDDEN`](/docs/agent/errors#deploy_forbidden) (403: not an owner or admin), [`ORGANIZATION_SUSPENDED`](/docs/agent/errors#organization_suspended) (403); from the routes (`routes.ts`), [`INVALID_REQUEST`](/docs/agent/errors#invalid_request) (400: a body that isn't JSON, or no string `appId`), [`NOT_FOUND`](/docs/agent/errors#not_found) (404: "No such deploy API route.", also when the path's organization isn't the key's), [`DEPLOY_NOT_FOUND`](/docs/agent/errors#deploy_not_found) (404: polling a job id the Gateway doesn't have for that organization, `run.ts` `jobAnswer`), [`INTERNAL_ERROR`](/docs/agent/errors#internal_error) (500: "The deploy API failed."); [`DEPLOY_KEY_APP_MISMATCH`](/docs/agent/errors#deploy_key_app_mismatch) (a key bound to another app), [`INVALID_MANIFEST`](/docs/agent/errors#invalid_manifest), [`INVALID_BUNDLE`](/docs/agent/errors#invalid_bundle), [`BUNDLE_TOO_LARGE`](/docs/agent/errors#bundle_too_large) (over 64 MiB or 10,000 files), [`PROTOCOL_TOO_OLD`](/docs/agent/errors#protocol_too_old) (a stamp below the Gateway's floor), [`APP_NOT_REGISTERED`](/docs/agent/errors#app_not_registered), [`DEPLOY_IN_PROGRESS`](/docs/agent/errors#deploy_in_progress) (one job at a time per app; "wait for it, then deploy again"), [`DEPLOYER_NOT_CONFIGURED`](/docs/agent/errors#deployer_not_configured), [`MIGRATION_FAILED`](/docs/agent/errors#migration_failed) ("Nothing was uploaded; the version that is serving keeps running."), [`BINDINGS_MISMATCH`](/docs/agent/errors#bindings_mismatch) (the read-back differed: the Worker was deleted), `DEPLOY_ABANDONED` (never thrown: `DeployJobRepository.toJob`, `apps/every-app-gateway/src/server/repositories/DeployJobRepository.ts`, answers a job still `running` 5 minutes after it was created, `DEPLOY_JOB_DEADLINE_MS`, as `failed` with this code and "The deploy stopped without finishing: the gateway gives a deploy about 50 seconds, and a large app (many assets, slow migrations) can run out of them. Deploy again."; no heading on the errors page), [`BUNDLE_REFUSED`](/docs/agent/errors#bundle_refused).

**`BUNDLE_REFUSED` and the tier limits** (`metadata.ts` `manifestProblems`, `bundleProblems` and `durableObjectMigrations`; limits from `platformPolicy(env).thirdPartyLimits`: `cpuMs` 5,000, `subrequests` 200, `durableObjectClasses` 2; the same numbers for self-hosted browser installs, `BROWSER_INSTALL_LIMITS`). ## Browser installs

An owner or admin (on a self-hosted Gateway: an owner or admin of the install organization, from a session signed in within 10 minutes, and only with `BROWSER_APP_INSTALLS=on`) can install a public GitHub repository's latest release, or an immutable `https://oss.new/apps/<key>` release, from Admin → Apps → Install app (`apps/every-app-gateway/src/server/deploy/install.ts`: `POST /api/admin/apps/install` with a session, `GET /api/admin/deploys/<id>` to poll). The Gateway downloads `https://github.com/<owner>/<repo>/releases/latest/download/everyapp-release.tar.gz` with no credentials (HTTPS redirects only, 100 MB compressed and again unpacked), reads the tar itself, checks it as the CLI does (`release.ts`: `RELEASE_INVALID`, `RELEASE_UNSUPPORTED`, `RELEASE_CORRUPT`, `RELEASE_TOO_LARGE`, `NO_RELEASE`, [`RELEASE_FETCH_FAILED`](/docs/agent/errors#release_fetch_failed), [`INVALID_REPO_URL`](/docs/agent/errors#invalid_repo_url), [`INVALID_RELEASE_URL`](/docs/agent/errors#invalid_release_url)), refuses helper Workers, and runs the same `startDeploy` pipeline through the same `registerApp` (`run.ts`): on a hosted Gateway a `dispatch` app of that organization on `THIRD_PARTY_DOMAIN`; on a self-hosted Gateway (`platformPolicy(env).mode === "self_hosted"`) a `service_binding` app under `APP_BASE_DOMAIN` ("Set APP_BASE_DOMAIN before installing apps." is `DEPLOYER_NOT_CONFIGURED` without it), the install organization (the oldest with an owner) getting the bare `<appId>.<base>` hostname and any other `<appId>-<orgKey>.<base>`; `deployed_by_actor` is the admin's email. Hosted Gateways keep the launch gate ([`APP_INSTALL_NOT_AVAILABLE`](/docs/agent/errors#app_install_not_available), 404, otherwise); self-hosted Gateways have it on once `CF_DEPLOY_TOKEN` is configured with `CLOUDFLARE_ACCOUNT_ID` and `APP_BASE_DOMAIN` (`selfHostedInstallEnabled`, `browser-install.ts`; `setup` offers it; `BROWSER_APP_INSTALLS=off` opts out), and run it under the app's install lease (`APP_CHANGING` when the row changed meanwhile). Refusals before anything is downloaded (`install.ts`): [`UNAUTHORIZED`](/docs/agent/errors#unauthorized) (401: no session or a banned user, "Sign in again."; no membership in the chosen workspace, "Organization membership required."), `INVALID_REQUEST` (400: an invalid `organizationId`, "Choose a valid workspace."; a body that isn't JSON, or both `repoUrl` and `releaseUrl`), [`APP_INSTALL_FORBIDDEN`](/docs/agent/errors#app_install_forbidden) (403: the signed-in person isn't an owner or admin of that organization; on a self-hosted Gateway, that organization isn't the install organization, the only one whose owners and admins may spend the account-wide `CF_DEPLOY_TOKEN`, and nobody installs before the Gateway has an owner; `GET /api/admin/apps/install` and `GET /api/admin/apps/install/context` answer by the person, whatever the session's active workspace, and the context offers no other workspace; a refusal of another organization is logged as `app_install.refused` at warn, with the organization ids and the user id), [`ORGANIZATION_SUSPENDED`](/docs/agent/errors#organization_suspended) (403), [`DEPLOYER_NOT_CONFIGURED`](/docs/agent/errors#deployer_not_configured) (503: the Gateway has no `GATEWAY_URL` or `JWT_PUBLIC_KEY` to give apps, `run.ts` `deployerSettings`; in the job, the CLI install row is missing, `browser-install.ts`); then `BUNDLE_REFUSED` on the release's own Worker before the row is written; and in the job [`DEPLOY_IN_PROGRESS`](/docs/agent/errors#deploy_in_progress) (409: another install or CLI operation holds the lease) and [`LEASE_LOST`](/docs/agent/errors#lease_lost) (409). Runbook: `docs/runbooks/browser-app-install.md` at [/docs/agent/repo/runbooks/browser-app-install](/docs/agent/repo/runbooks/browser-app-install); the hosted install itself: `docs/runbooks/hosted-install.md` at [/docs/agent/repo/runbooks/hosted-install](/docs/agent/repo/runbooks/hosted-install).

## `delete`: what it removes and keeps

`pnpm everyapp delete [<id>] [--purge] [--yes] [--gateway] [--account-id] [--json] [--verbose]` (`packages/cli/src/commands/delete/command.ts`, `index.ts`); without an id, the app in this directory's `everyapp.config.ts`.

Confirmation first: at a terminal, `Delete <app> from the Gateway?` ("Its Worker and data stay; --purge deletes them too."); with `--purge`, the app id must be typed (`Type <app> to confirm`; a mismatch is `CANCELLED`, "Nothing deleted."). Unattended it needs `--yes`: [`CONFIRMATION_REQUIRED`](/docs/agent/errors#confirmation_required), "Deleting an app needs confirmation at a terminal, or --yes", rerun with `--yes` (authorize). `--yes` with `--purge` skips the typed id too.

Then (`removeApp`): the live Gateway's release must be one it can have again (`GATEWAY_RELEASE_UNAVAILABLE` otherwise, before the registry changes); `app.delete` (`deleteApp`, `registry.ts`): the row becomes a tombstone (`status: deleted`, `is_default` off, its names still its organization's), and in the same batch its email configuration and recorded secret names, everyone's `user_app_access` and `group_app_access`, the personal access tokens bound to it (revoked), its `app_tools`, `app_tool_catalogs` and `mcp_connection_apps` rows, and its `org_app_settings` (a monthly cap) go; a shared app needs a platform owner or admin. When the row wasn't already deleted, or the install row still lists its Worker or hostname, `reconcileGateway` (`packages/cli/src/lib/gateway/reconcile.ts`, not forced) redeploys the Gateway without the binding and the Custom Domain: when the live Gateway already binds exactly the apps the registry lists (`registryDrift`; a delete rerun whose binding is already gone) it emits step `gateway.reconcile` `skip` ("The gateway already binds the 1 app its registry lists." or "… all `<n>` apps …") and uploads nothing; otherwise `gateway.release`, `gateway.lease`, `gateway.domains`, `gateway.migrations` and `gateway.deploy` run as for a rebind, with the live release. Then `syncAppsAccessAfter` with `removing: true` (whether the app had `public` routes is read with `readPublicSurfaces` before the row is tombstoned, so only a served row with a hostname counts): behind Cloudflare Access, `app.access` `ok` "Cloudflare Access no longer lets `<app>`'s public routes through." (a person sees it) or `skip` "Cloudflare Access had nothing of `<app>`'s to take back."; `ACCESS_NOT_CHECKED` ends "If the Gateway is behind Access, `<app>`'s host stays listed there until it is updated." and `ACCESS_SYNC_FAILED` "`<app>`'s host stays listed there until it is updated.", with the same `data.rerun` `pnpm everyapp access on`. The hostname's certificate packs are deleted (`app.certificate`, `packages/cli/src/lib/domains/certificates.ts`; never one that would leave the apex without an active certificate; a failure is warning [`CERT_CLEANUP_FAILED`](/docs/agent/errors#cert_cleanup_failed)).

Without `--purge` the Worker and data are kept: "its Worker and data are kept, and any cron triggers, Workflows and mail routes keep running. To delete those too: `pnpm everyapp delete <app> --purge`". With `--purge` (`app.purge`): the mail routes first, then the Workflows that run on the app's recorded Workers, then (when it recorded a queue) every queue consumer that is one of its Workers (`cf queues consumers delete <consumer-id> --queue-id <queue-id> --force`: Cloudflare won't delete a Worker that consumes a queue, `[10064]`), then the Workers (the app's before its helpers), D1 databases, KV namespaces, Hyperdrive configs, queues (`cf queues delete <id> --force`, with their messages; after the Workers, since a queue a Worker binds can't be deleted, `[11005]`: one a Worker outside the app still binds is kept and said so), Vectorize indexes (`cf vectorize delete <name> --force`, their vectors with them), AI Gateways (with their stored logs) and Secrets Store secrets (`cf secrets-store secrets delete <id> --store-id <store> --force`; the store stays), **only those the ledger records as created by the app** (never whatever has its names; a Postgres database behind Hyperdrive is never touched), then the ledger is cleared. Anything under the app's names that isn't recorded stays with warning [`RESOURCES_KEPT`](/docs/agent/errors#resources_kept) and where to delete it by hand. `done.data`: `appId`, `workerName`, `alreadyDeleted`, `purged` (true when nothing of it is left), `removed`, `kept`. A delete that stopped part-way runs again safely: a tombstone writes nothing, and a Gateway that still binds it is reconciled again.
