# Cloudflare Access for the Gateway

Read [README.md](README.md) first: the rules every setup follows.

Cloudflare Access puts a second door in front of the Gateway and every app
host (`<app>.<app base domain>`: OpenSEO, Open CRM, OpenAnalytics,
agentic-inbox, any app made with `everyapp create`), at Cloudflare's edge:
nobody reaches them before Access has checked who they are, with their
Cloudflare account (members of the operator's Cloudflare account), a
one-time code emailed to them, or the team's identity provider. `pnpm
everyapp access on` does it all from the Cloudflare login: the Zero Trust
team (or the one Cloudflare's onboarding made, step 1), both sign-in
methods (Sign in with Cloudflare and the one-time PIN, each created when the
team lacks it), an allow policy with every member's and invitee's email, two
Access applications, and the three Gateway settings, in one run. At the end
the person has Access's login before the Gateway, MCP clients, the Gateway's
`/health` and each app's public routes still reachable without it, and
optionally no passwords. `pnpm everyapp setup` does the same by
default once the owner exists: a person at a terminal is asked ("Put
Cloudflare Access in front of your Gateway?", Yes by default); under
`--json` or `--yes` it goes on without a question when the account can (a
Zero Trust team exists, the Cloudflare login is an owner or admin of the
Gateway), and otherwise the warning `ACCESS_SETUP_SKIPPED` says why and
names `access on`: then the offer is yours. `setup --no-access` leaves it
off. This
is the "outer ring" of `docs/runbooks/cloudflare-access.md`; the other way,
a "Continue with Company SSO" button, is
the runbook's "OIDC sign-in" and isn't covered here.

What it adds, and what it doesn't (`docs/threat-model.md`, "What
Cloudflare Access adds, and what it doesn't", and its credentials table):
every Gateway page and every app's private route is behind Access's login
before the Gateway sees the request; a stolen session cookie gets nothing
in a browser that hasn't passed Access as that person; taking someone out
of the policy ends their browser access when their Access session ends
(720h as `access on` sets it). It does not cover personal access tokens or
the OAuth tokens of connected AI apps (they use the bypassed paths and work
until revoked), apps' public routes (reachable by anyone), deploy authority
(the Cloudflare login, not a Gateway account). Taking
someone off is **Deactivate** in the Gateway's **Users** page (the threat
model's "Admin → Users"), which revokes their tokens and connections at once.

## Settings

All three written by `everyapp access on`; nothing to type. Values can't be read back.

| NAME                                     | required or optional | what it holds                                                                                                          |
| ---------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_ACCESS_TEAM_DOMAIN`          | required             | the Zero Trust team's domain, `<team>.cloudflareaccess.com`                                                            |
| `CLOUDFLARE_ACCESS_AUD`                  | required             | the AUD tag of the Access application on `<gateway host>` (several: comma separated); only its tokens sign people in   |
| `CLOUDFLARE_ACCESS_APPS_AUD`             | required             | the AUD tag of the Access application on `*.<app base domain>`; its tokens only vouch for a session on an app host     |
| `EMAIL_PASSWORD_SIGN_IN`                 | optional             | `false` turns passwords off once an owner has linked Access; unset or `true` keeps them. Not a secret                  |
| `CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS`    | optional             | email domains whose people join on their first Access sign-in without an invitation, comma separated (`<your domain>`) |
| `CLOUDFLARE_ACCESS_OUTER_RING_AUTO_JOIN` | optional             | `everyone`: anyone the Access policy lets in joins the owner's organization                                            |

## Costs and plans

As of October 2026: Cloudflare's Zero Trust Free plan costs nothing and
covers 50 users; once the seats are used, the next person to sign in is
blocked. Beyond that, pay-as-you-go is $7 per user per month. Every person
who signs in through Access uses a seat; the bypassed paths (MCP, OAuth,
public routes) and service tokens use none. Cloudflare's dashboard onboarding
asks for payment details even on the Free plan and says it won't charge. The
login page is `<team>.cloudflareaccess.com`: no domain of the person's own.
An Access session lasts up to one month (`720h`, the command's default); a
one-time PIN expires 10 minutes after it is sent.

## Only a person can

- Choose the Zero Trust team name: `<name>.cloudflareaccess.com` is the sign-in page. Cloudflare lets it be changed later (Zero Trust → **Settings** → **Team name and domain**), but that frees the old name for anyone to claim and breaks the Gateway's `CLOUDFLARE_ACCESS_TEAM_DOMAIN` until `pnpm everyapp access on --write-settings --json` is rerun: better avoided.
- Approve the Cloudflare login in the browser (the Access permissions come with it).
- Sign in through Access: with their Cloudflare account, or the code that lands in their inbox; each existing member does it once, with their password.
- Decide who else gets in (`--email`, `--email-domain`), how long a sign-in lasts (`--session`), whether passwords go, and whether people join without an invitation (step 3).
- Ask for `access off` or `secret unset`; you never run them unasked.

## Before you start

1. `pnpm everyapp access --help` exits 0 (any `access` subcommand that answers, such as `access show --json`, proves the same); otherwise (`Unknown command access`, exit 251) the checkout predates 2026-10-24: `git pull` in the `every-app` checkout (the CLI rebuilds itself on its next run), then check again.
2. `pnpm everyapp status --json`: `data.installed` and `data.claimed` true (claimed means an owner exists, so the policy has someone); `data.mode` is `self_hosted` (a hosted Gateway refuses `on`: `ACCESS_HOSTED`); `data.gatewayUrl` gives `<gateway host>`, `data.appBaseDomain` gives `<app base domain>`. `data.access` is `{ on, teamDomain }`: `on` true means the Worker holds all three settings, so Access is on already, go to Verify (`teamDomain` is what `access on` recorded; null when nothing was recorded yet); the human report shows the same as an `Access  on|off` row, and no separate `secret list` is needed. `data.access` null means a hosted Gateway, no Worker yet, or that cf couldn't read the settings (then `data.fixes` has `ACCESS_UNKNOWN`, severity `warning`: run it again, or go on to `access show`). A `data.fixes` entry's `severity` says whether it is a problem (`error`, `warning`) or not (`info`, such as `GATEWAY_OUTDATED`; `settling`). Not installed or no owner: [gateway.md](gateway.md) first. `action_required cloudflare_login` with `waiting: true` (`status` logs in by itself): show `data.url` and `data.code`, keep reading; `pnpm everyapp login --json` is only for logging in ahead of time. Several accounts: add `--account-id <account id>` to every command.
3. `pnpm everyapp access show --json` (changes nothing; on a hosted Gateway it answers `data.hosted` true instead of the error): `data.team` null means the account has no Zero Trust team (or never opened Zero Trust: both the same to `on`) and `on` will need `--team`. What `on` would change: `data.applications.gateway.inSync` and `data.applications.apps.inSync` (paths and public routes), both `signInInSync` (every provider of the team allowed), both `policyAttached`, `data.signIn` (`cloudflare` and `pin`: whether the team has each sign-in method; `openToAnyCloudflareAccount`: provider ids whose "Restrict to account members" is off, with the warning `ACCESS_IDP_ANY_CLOUDFLARE_ACCOUNT`, which the person turns on in Zero Trust → Settings → Authentication), `data.policy.notYet` (members and invitees the policy doesn't name yet), `data.settings` (`{ names, current }`: `names` the Access settings on the Worker; `current` `false` means they name an application that no longer exists, so nobody signs in; null when nothing is recorded yet or Access is off) and `data.desired.apps`. `data.linkPending` lists members who still have to sign in once; `data.fixes`, when present, is only the rerun, `pnpm everyapp access on` (there whenever Access is off, something is out of step, a sign-in method is missing, or `current` is `false`).
4. Optional: `cf auth whoami`, whose `scopes` include Access ones such as `access:write`. cf 1.0.0-beta.14's login asks for them; an older login may lack them, which `on` reports as `ACCESS_PERMISSION_MISSING` on its first Access call, before it changes anything (If it fails says what to do), so skipping this check costs one failed run at most. Never repeat the output's email or ids.
5. Apps with public routes (a tracking script, a webhook): `on` reads them from the deployed manifests. Deploy such apps first, or rerun `access on` after; deploys keep them in step by themselves. `pnpm everyapp status --json` lists each app's as `data.apps[].publicRoutes` (`{ path, methods }`; the PUBLIC column in the human report), so you can tell the person which routes Access will let through.
6. Ask the person: whether everyone at `<your domain>` should pass Access, who else, and the session length. The team name is step 1's.

## Steps

1. **You, then the person:** the team name, when `data.team` was null in Before you start 3 (with a team already there is nothing to choose; `--team` is ignored, not even checked). The person chooses it: lowercase letters, digits and dashes (everyapp's check; Cloudflare only asks that it be unique), like the company's name. Say that `https://<name>.cloudflareaccess.com` is where everyone signs in, that names are shared across Cloudflare (a taken one fails), and that changing it later is possible but costly (Only a person can). Wait for the name; step 2 passes it with `--team`, and `on` creates the team, on an account that never opened Zero Trust too (no dashboard onboarding, plan pick or payment details first; checked live 2026-10-24).
2. **You:** turn it on. Nothing to `secret set`: the three settings are README's "a command produced it" case, written by `on` itself in one new Worker version.
   ```sh
   pnpm everyapp access on --json
   ```
   Add `--team <name>` on step 1's first path (ignored once a team exists), `--email-domain <your domain>` so everyone at that domain passes Access (they still need an invitation to get an account; `data.next` then suggests `CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS`, step 3), `--email <address>` for one person, `--session 24h` for a daily code (default `720h`, 30 days; Cloudflare's maximum is one month; an existing application keeps its own unless given). Its order: the team, the two ways to sign in (Sign in with Cloudflare, restricted to the Cloudflare account's members, and the one-time PIN; each created when the team lacks it, any other provider kept), the policy "Every App gateway members", the application on `*.<app base domain>`, the one on `<gateway host>` (both allowing those two and never the team's other providers, listed in `data.signInMethods` with `allowed: false` for the person to allow in the dashboard if wanted; an application from before gains the two, `data.applications.<which>.signInAdded`), then the settings. It never removes anyone from the policy, never takes a sign-in method off an application, and leaves alone what it didn't make. In the `done` event read `data.team.domain` and `data.team.created`, `data.identityProviders.oneTimePinAdded` and `cloudflareAdded`, `data.signInMethods`, `data.policy.emails` and `data.policy.domains`, `data.applications.gateway.outcome` and `data.applications.apps.outcome` (`created`, `updated`, `unchanged`, `skipped`), `data.settings.outcome` (`set`, with `data.settings.reason` one of `missing`, `created`, `unrecorded`, `changed`, `asked`; or `kept` with `reason` null, said as "Gateway settings kept: they name these applications already (--write-settings writes them again)"), `data.signIn` (`url`, the Gateway; `pending`, who signs in once with their password; `first`, `both` for Access's chooser between Sign in with Cloudflare and the emailed code, else `pin` or `idp`), `data.team.globalSession` (the team's global session: null, or shorter than `--session`, has meant a daily code; say so and ask before `--team-session 720h`, next paragraph), and `data.next` (`command` and `note` pairs). Relay every `warning` (codes under If it fails). Don't print the AUD tags.
   `data.team.globalSession` null is Access's default, 24h (`show` reports the same value as `data.team.sessionDuration`). Observed on one Gateway, not Cloudflare's documented rule: a `720h` application session still asked for the code daily until the team's global session was raised to match; Cloudflare only says the global session is usually set to equal or exceed the application's. When it is null or shorter than `--session`: tell the person they may be asked for the code daily, and that `pnpm everyapp access on --team-session 720h --json` raises it for every Access application in the account (it is how often people sign in at the identity provider); run it only when they say so.
3. **You, only when the person asks:** the two membership settings. Neither is a secret, so a pipe is README's "a command produced it" way. `echo "<your domain>" | pnpm everyapp secret set CLOUDFLARE_ACCESS_AUTO_JOIN_DOMAINS --json` (several: comma separated) lets people at that domain who pass Access join as members on their first sign-in, with no invitation; `echo everyone | pnpm everyapp secret set CLOUDFLARE_ACCESS_OUTER_RING_AUTO_JOIN --json` lets anyone the Access policy admits join (the policy becomes the member list). Live at once; `secret unset` undoes either, when asked.
4. **Person:** each address in `data.signIn.pending` signs in once. Give them these four lines, the buttons' labels as written:
   1. Open `https://<gateway host>`; Access's page on `https://<team>.cloudflareaccess.com` opens, with **Sign in with Cloudflare** and the email field.
   2. A member of the Cloudflare account whose Cloudflare email is their Gateway address selects **Sign in with Cloudflare** (the warning `ACCESS_LOGIN_NOT_MEMBER` at step 2 means the person's isn't: they use the code). Everyone else types the email and selects **Send login code**, then pastes the code from the email (sender `noreply@notify.cloudflare.com`; it lasts 10 minutes) and selects **Sign in**.
   3. The Gateway's own sign-in page follows: sign in with the Gateway password as usual.
      That links the two; from then on Access alone signs them in. The code page says "A code has been emailed to you" whether or not the address is in the policy (an address outside it gets no email at all: see If it fails). Someone with a pending invitation signs in through Access and joins without a password. Wait until everyone has done it.
5. **You:** `pnpm everyapp access show --json`: `data.linkPending` is empty.
6. **You:** only when the person asks, and only with `data.linkPending` empty, turn passwords off. Not a secret, so it may be piped:
   ```sh
   echo false | pnpm everyapp secret set EMAIL_PASSWORD_SIGN_IN --json
   ```
   The Gateway applies it only once an owner has linked Access, so it can't lock the owner out; a member who never linked can't sign in until it is `true` again: `echo true | pnpm everyapp secret set EMAIL_PASSWORD_SIGN_IN --json`.
7. **You:** after every invitation later, `pnpm everyapp access on --json` again, so Access lets the new person in. Taking someone off is Deactivate in the Gateway (**Manage workspace → Users → ⋯ → Deactivate**; the threat model's "Admin → Users"), never the policy: the policy doesn't end their tokens or AI connections, and their Access session runs to its end.

## Verify

1. `pnpm everyapp status --json`: `data.access` is `{ "on": true, "teamDomain": "<team>.cloudflareaccess.com" }` (the human report's row: `Access  on · everyone signs in through Cloudflare Access first`), and no `ACCESS_UNKNOWN` in `data.fixes` (an `APP_NEEDS_SETUP` there, like `data.apps[].setup`, says what an app still needs set: an integration's file, never this one, since none of these settings is an app's). This reads the Worker's secret names and the record `on` kept, so no separate `secret list` is needed; it asks nothing of Zero Trust, which is the next step's job. `on` true with `teamDomain` null: the settings predate the record (set by hand, or by a CLI from before the record existed); `pnpm everyapp access on --json` writes and records them (`data.settings.reason` `unrecorded`).
2. `pnpm everyapp access show --json`: `data.on` true, `data.settings.names` lists all three and `data.settings.current` true, `data.signIn.cloudflare` and `data.signIn.pin` true with `openToAnyCloudflareAccount` empty, `data.applications.gateway.inSync` and `data.applications.apps.inSync` true, both `signInInSync` true, both `policyAttached` true, `data.policy.notYet` and `data.linkPending` empty, no `data.fixes`. Then `GET https://<gateway host>/health` answers `200 {"status":"ok"}` with no login: the uptime monitor's path.
3. Smoke check, from your shell: a bypassed path answers the Gateway, the rest answers Access.
   ```sh
   curl -sS -o /dev/null -w '%{http_code} %{content_type} %{redirect_url}\n' https://<gateway host>/.well-known/oauth-authorization-server
   curl -sS -o /dev/null -w '%{http_code} %{content_type} %{redirect_url}\n' https://<gateway host>/ | sed -E 's/kid=[^&]*/kid=…/'
   ```
   Expected: the first `200 application/json` (the Gateway's OAuth discovery document, let through by `/.well-known/*`; `/mcp` answers `401` with no HTML); the second `302` to `https://<team>.cloudflareaccess.com/cdn-cgi/access/login/...`, which is Access (its `kid=` is the gateway application's AUD tag; the `sed` keeps it off the screen). HTML or a redirect on the first means a bypass is missing: `pnpm everyapp access on --json`. `404 application/json` on the first means `MCP_OAUTH_ENABLED` is off, not a missing bypass: curl `https://<gateway host>/mcp` instead and expect `401 application/json`.
4. **Person:** open `https://<gateway host>` in a private window (Access's email page first, then the Gateway signed in), then `https://<app>.<app base domain>`; ask them to tell you whether the app opened with no second sign-in page (it should; a sign-in page there is If it fails' "apps send people back to the sign-in page"). An AI app connected over MCP keeps working.
5. Logs: Cloudflare dashboard, README's path: **Workers & Pages** → `every-app-gateway` → **Observability** (**Logs** on older accounts) → **Live** (cf 1.0.0-beta.14 has no `workers tail`; its `cf o11y telemetry query` needs a query body, so the dashboard is the practical path). `access.config_problem` names a malformed setting; `access.jwks_fetch_failed` means the team's keys couldn't be fetched: sign-ins keep working on the cached keys for up to 10 minutes after the first failure, then stop until a fetch succeeds. A line that keeps coming means `CLOUDFLARE_ACCESS_TEAM_DOMAIN` is wrong or Cloudflare is unreachable.

## Rerun, rotate, remove

- Rerun: `pnpm everyapp access on --json` any time; it changes only what differs. Run it after inviting someone and after a change by hand. It records what it wrote in the Gateway's D1 (table `_everyapp_access`) and rewrites the three settings itself when one is missing, when it created an application, when nothing is recorded yet (settings written before the record existed: `data.settings.reason` says `unrecorded`), or when the applications it finds don't match the record (an application recreated in the dashboard has a new AUD tag: `changed`); `--write-settings` (`asked`) forces the rewrite when `show` still reports `data.settings.current` true.
- Rotate: nothing here is a secret; the team name can be changed in the dashboard but better not (Only a person can). To end every Access session: dashboard **Zero Trust → Access controls → Applications → Configure → Revoke existing tokens**, or, when the person asks, `cf zero-trust access applications revoke-tokens <id>` for both ids in `access show --json` (`data.applications.gateway.id`, `data.applications.apps.id`). One person: Deactivate in the Gateway (**Manage workspace → Users → ⋯ → Deactivate**), which also revokes their personal access tokens and AI connections, which Access never sees; their Access sessions alone: **Team & Resources → Users → Action → Revoke**, or `cf zero-trust access users revoke --email <address>` when asked.
- Remove: `pnpm everyapp access off --json` (asks; `--yes` only when the person said so; `--keep-applications` leaves Access asking while the Gateway stops requiring it). It removes the three settings first, so passwords sign people in again at once (`EMAIL_PASSWORD_SIGN_IN=false` is ignored without Access; set it to `true` anyway: `echo true | pnpm everyapp secret set EMAIL_PASSWORD_SIGN_IN --json`), then deletes the two applications. The team, the one-time PIN and the policy stay in the Cloudflare account; nothing to revoke elsewhere. Never delete the Zero Trust organization itself in the dashboard: Cloudflare reserves a deleted team's name forever, for every account.
