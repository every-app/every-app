## Hand-off to the onboarding-DX thread (findings 1 to 12)

The text below was written for the onboarding-DX and agent-docs threads; the thread-send tool
refused from the loop thread all day, so it lives here. Excerpts are untrusted agent and CLI output.

1. PRODUCT, worth a look before Monday (verified against the code by an independent read): an app created inside the Gateway checkout joins the root pnpm workspace (`apps/*` in pnpm-workspace.yaml), so `create`'s plain `pnpm install` (lib/package-manager.ts:60-73; deploy's app.install does the same, deploy/deployApp.ts:530) writes a new importer into the root `pnpm-lock.yaml`. That file is one of the Gateway's hashed sources (lib/gateway/checkoutRelease.ts:41-48), so the checkout's tree hash moves (run 8: ee816b8a → 8c7be472) although no Gateway dependency changed. Consequences seen live:
   - The first `deploy` binds the app on the Gateway and uploads the Gateway anyway (appGateway.ts:116/144, by design), but with the hash changed it also rebuilt the release from source instead of reusing the cached tarball (checkoutRelease.ts:203-206):
     ```text
     step gateway.release  Building the Gateway from this checkout (usually 1–2m)
     step gateway.release  Built the Gateway 0.2.0 from this checkout.
     step gateway.deploy   Uploading Gateway 0.2.0 with 1 app
     ```
     so the first app deploy carries a full Gateway build (82 s deploy in run 8).
   - `everyapp status` from a fresh clone of the same commit answers `upToDate: false` with the info fix GATEWAY_OUTDATED ("this checkout has newer Gateway changes"); in the same checkout it says true (status/index.ts:340-343).
   Fix options, best first: (a) make apps created inside the checkout their own workspace, as apps outside it already are (apply starter.ts:77's standalone pnpm-workspace.yaml and updateConfiguration.ts:31's `link:` rewrite unconditionally), so the root lockfile is never touched; (b) hash only the lockfile importers the Gateway uses (checkoutRelease.ts and apps/every-app-gateway/scripts/build-release.ts must keep identical lists); (c) install the app with `--filter` and lockfile settings that leave the root file alone (weaker). The loop records upToDate=false as a finding and no longer fails a run on it.

2. Confirmed live: a fresh account's first `setup` upload stops on register_workers_subdomain (the audit's open check). After the subdomain exists it never recurs on that account, so only a never-used account reproduces it.

3. Resume after that stop works since #498 (own Custom Domain / own stopped Worker recognised). Setup end to end on the test account: 52 s including the 42 s Gateway build; the owner link is claimed by the loop 1 s after the CLI mints it.

4. On a fresh account Cloudflare Access is not enabled: `deploy` warns ACCESS_NOT_CHECKED with `[9999] access.api.error.not_enabled`; `everyapp teardown` reads the 403 as empty (#497). Whether `everyapp access on` can create the Access app on such an account is still unverified (the --with-access run will tell).

5. Setup and deploy both emit CUSTOM_DOMAIN_OWNER_UNCHECKED under --json (quiet without --verbose at a terminal); fine, noted so nobody is surprised by it in event logs.

6. Docs nit for agent-docs: docs/manifest-settings.md:255 still cites `/api/me/apps`, which the gateway no longer serves (the launcher's list is a server function).

7. https://everyapp.com/llms.txt answers 302 → https://everyapp.com/ (HTML) until the site is redeployed; the loop's runs read the checkout's agent docs, but the public prompt variant is blind until then (orchestrator).

8. PROMPT (owner link relay): measured with the loop's claim deferred (run 13). Claude Code DOES relay the link and wait: its final message was "The Gateway is live. Open this link to create the owner account. It works once and expires in 24 hours… waiting for you", and it kept setup running in the background. With the default immediate claim (runs 10, 12) the step resolved within a second, so nothing was said about it then; that is the loop's doing, not the agent's. Codex ran setup in the foreground and the link sat in its output. No prompt change needed for this; the CLI's action_required message is what the agents quote.

9. PROMPT: both agents stop once to ask for the domain (expected; the prompt leaves it to the person). Codex ends the turn by announcing "I'll pause to ask your domain" without the question, so a person sees a plan, not a prompt; the loop nudged it. "Ask for the domain in one line and stop" would be a cheap fix.

10. PROMPT (gpt-6.1-sol, both Codex CLI and OpenCode): the model prefixes its domain question with the prompt's stop word: "BLOCKED: Waiting for your domain. Which domain should I use for `apps.<your domain>`?" (Codex) and "BLOCKED: Which Cloudflare domain should I use for `apps.<your-domain>`? Dependencies are installed." (OpenCode). It reads "if stuck print BLOCKED: <why> and stop" as the way to hand any question to the person. gpt-5.3-codex and claude-opus-5-5 never did this. Suggested wording: "Questions for me are not BLOCKED: just ask and stop. Print BLOCKED: <why> only when something I cannot fix stops you." The loop now treats a BLOCKED-phrased domain question as the question (#564) and records it as a hesitation, so the ledger will show how often each model does it.

11. PRODUCT (infra flake on first upload after a delete): run 19's setup failed at `gateway.deploy` ("Uploading Gateway 0.2.0 with 0 apps") with `CF_NOT_FOUND [10007] This Worker does not exist on your account` (404), 30 minutes after the previous wipe deleted every-app-gateway; the identical sequence succeeded in nine other runs. `cf deploy --prebuilt` likely PUTs a sub-resource (settings, subdomain, domains) before Cloudflare has the just-created script everywhere. Suggest: retry the upload once on 10007 when this run created the Worker, or make it an exit-2 "run setup again" stop; and a line in errors.md saying CF_NOT_FOUND during upload is transient. The agent read errors.md, the cf source and node_modules, ran `cf workers list`, and gave up with BLOCKED, which is what a person would have seen too.

12. PROMPT/HARNESS (OpenCode on gpt-6.1-sol, run 20): the prompt says setup "can run 20 minutes: give it a long timeout or run it in the background and read its output". OpenCode (like `codex exec`) kills background children when its turn ends, so when the agent relayed the owner link and yielded, its background setup died ("setup (pid 533) is gone with no exit line"). The rerun resumed in 4 s thanks to #498, so it cost one extra turn, not the run. Claude Code keeps its process alive while a background task runs, so it never hits this. Consider "run it in the foreground with a long timeout; if you must background it, rerun `setup` after the owner step" in the prompt.
