## #0 [identity-orgs] critical
**Claim.** A page on a subdomain (e.g. evil-acme.X) can set a cookie with Domain=X through document.cookie, unless X is on the Public Suffix List, so the shared session cookie lets org-deployed apps plant session cookies the gateway reads.
Source given: MDN Set-Cookie (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie); GitHub blog 2013-04-05 github.io post
- **docs: confirmed.** Spec and docs: RFC 6265 §4.1.2.3 (https://www.rfc-editor.org/rfc/rfc6265.txt lines 623-633): "the user agent will accept a cookie with a Domain attribute of 'example.com' or of 'foo.example.com' from foo.example.com ... NOTE: For security reasons, many user agents are configured to reject Domain attributes that correspond to 'public suffixes'." §5.3 step 5 (lines 1224-1241): if the domain-attribute is a public suffix and not the request host, "Ignore the cookie entirely"; the same §5.3 algorithm governs cookies "received from a 'non-HTTP' API", i.e. document.cookie (step 11.2). MDN Set-Cookie (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie, last modified Sep 1, 2026): "The value must be the domain of the server that sends the Set-Cookie response header, or a parent domain of that server's domain. It cannot be a public suffix such as com, co.uk, or github.io. For example, a response from api.example.com can set Domain=api.example.com or Domain=example.com". MDN Document.cookie (Jun 15, 2026) documents the ";domain=" attribute for script writes; only "__Http-" prefixed cookies "can't be set or modified via JavaScript". GitHub blog, Ryan Tomayko, April 5, 2013 (https://github.blog/2013-04-05-new-github-pages-domain-github-io/): because Pages "may include custom JavaScript and were hosted on github.com subdomains ... it was possible to write (but not read) github.com domain cookies". publicsuffix.org/learn lists Firefox, Chromium, Opera and IE as using the PSL for "preventing cookies set on one domain from being accessible to other domains under the same public suffix".

Repo (applies to this design): apps/every-app-gateway/src/auth/config.ts:204-221 scopes the Better Auth session cookie to APP_BASE_DOMAIN (else the gateway host) via crossSubDomainCookies at :280-286; apps/every-app-gateway/src/server/app-hosts.ts puts every org app one label below it (`<appId>-<orgKey>.<base>`); the gateway reads the cookie on app hosts at apps/every-app-gateway/src/perimeter/betterAuthAuthenticator.ts:116 (`auth.api.getSession({ headers: request.headers })`). The only defence, packages/perimeter/src/headers.ts:179-187 `stripSetCookieDomains`, rewrites HTTP Set-Cookie headers and cannot touch document.cookie, so docs/security-model.md:284 ("apps cannot set parent-domain cookies") overstates it. The current PSL (https://publicsuffix.org/list/public_suffix_list.dat, fetched 2026-10-15) has no entry for thecomeup.cc (it does list workers.dev, pages.dev, github.io). Better Auth 1.7.7 names the cookie `__Secure-better-auth.session_token`; the `__Secure-` prefix does not block script writes.

One precision caveat, not a refutation: RFC 6265 §5.3 step 11.2 (lines 1307-1309) says script cannot overwrite an existing HttpOnly cookie with the same name, domain and path, so against a user who already holds a legit session cookie the planted one must use a different Path (longer paths are listed first per §5.4 lines 1418-1419) or be set before login (fixation); the token must also be a validly signed one, e.g. the attacker's own.
- **adversary: confirmed.** Browser rule: MDN Set-Cookie (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) says Domain "must be the domain of the server ... or a parent domain", "a response from api.example.com can set ... Domain=example.com", and "It cannot be a public suffix such as com, co.uk, or github.io" (links publicsuffix.org; the page never says "Public Suffix List" verbatim). It states no different Domain rule for document.cookie; RFC 6265 §5.3 (https://www.rfc-editor.org/rfc/rfc6265.html) applies the same storage model to "non-HTTP" APIs. GitHub post (https://github.blog/2013-04-05-new-github-pages-domain-github-io/, dated 2013-04-05) confirms "it was possible to write (but not read) github.com domain cookies ... fixate a user's CSRF token". PSL (publicsuffix.org/list, fetched today): workers.dev, pages.dev, github.io are listed; everyapp.app/.host/.com and thecomeup.cc are not. A web search found no 2025-2026 browser or rfc6265bis change restricting parent-domain cookies.

Repo: apps/every-app-gateway/src/auth/config.ts:204-287 sets the session cookie with crossSubDomainCookies Domain=APP_BASE_DOMAIN (the gateway host) and Better Auth's __Secure- prefix (not __Host-, which forbids Domain and so cannot span app subdomains). packages/perimeter/src/headers.ts:179-187 strips Domain= only from apps' HTTP Set-Cookie headers, which cannot reach document.cookie.

One mechanism detail the claim glosses but which does not weaken it: RFC 6265 §5.3 step 11.2 stops document.cookie from overwriting the existing HttpOnly cookie at the same name/domain/path, so the attacker plants a sibling cookie on a longer Path (as the research doc already says). §5.4 orders longer paths first, and better-call 1.4.0's parseCookies (apps/every-app-gateway/node_modules/.pnpm/better-call@1.4.0_zod@4.6.5/node_modules/better-call/dist/cookies.mjs:33, `if (!cookies.has(key))`) is first-wins, so the gateway's getSignedCookie reads the planted value. The attacker supplies a validly signed value by copying their own session cookie, so signing is not a defence.

## #1 [identity-orgs] critical
**Claim.** Cloudflare Workers allow at most 100 Custom Domains per zone, so hosted app hostnames need a wildcard route or a dispatch Worker instead of per-app Custom Domains.
Source given: https://developers.cloudflare.com/workers/platform/limits/ (fetched 2026-10-15)
- **docs: confirmed.** Checked https://developers.cloudflare.com/workers/platform/limits/ (page states "Last updated Oct 12, 2026"; fetched 2026-10-15). The "Routes and domains" table reads verbatim: "Custom domains per zone | 100" (alongside "Routes per zone | 1,000" and "Routed zones per Worker | 1,000"). The same section says: "If you require more than 100 custom domains per zone, consider using a wildcard route." and "If you require more than 1,000 routes or 1,000 routed zones per Worker, consider using Workers for Platforms." The page offers no "Need a higher limit?" form for this row (that notice appears only for Account plan limits and Worker startup time). Corroborated by https://developers.cloudflare.com/workers/configuration/routing/custom-domains/ (Last updated Sep 29, 2026): "Custom Domains do not support wildcard DNS records." and "An incoming request must exactly match the domain or subdomain your Custom Domain is registered to." So per-app Custom Domains cap at 100 per zone and cannot be wildcarded; Cloudflare's own documented escape hatch is a wildcard route (or Workers for Platforms / dispatch Worker at larger scale), exactly as the claim states.
- **adversary: confirmed.** Checked the live limits page (https://developers.cloudflare.com/workers/platform/limits/, "Last updated Oct 12, 2026") and its source (cloudflare-docs production: src/content/docs/workers/platform/limits.mdx). The "Routes and domains" table has a single Value column with no Free/Paid/Enterprise split: Routes per zone 1,000; Custom domains per zone 100; Routed zones per Worker 1,000. The section text says verbatim: "If you require more than 100 custom domains per zone, consider using a wildcard route." The "Limit Increase Request Form" partial (limits_increase) is rendered only under "Account plan limits" and "Worker startup time", not under Routes and domains, so no documented increase path for this limit. Custom Domains page (https://developers.cloudflare.com/workers/configuration/routing/custom-domains/, Sep 29, 2026): "Custom Domains do not support wildcard DNS records. An incoming request must exactly match the domain or subdomain", so a wildcard Custom Domain can't dodge the cap. WfP hostname-routing page (https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/hostname-routing/, Sep 24, 2026) recommends exactly the alternatives the claim names: a `*/*` or `*.saas.com/*` wildcard route to a dispatch Worker "without hitting traditional route limits". Commit history for limits.mdx (GitHub API, 30 most recent, back to Feb 2026) shows no change to the custom-domain row; no changelog entry raising it was found (the only recent hostname-limit changelog is Cloudflare for SaaS custom hostnames 5,000 -> 50,000, a different product). Implementation caveats the design already records (docs/research/2026-10-hosted-platform/raw/perimeter-dispatch.md:308): the wildcard route needs a proxied wildcard DNS record (e.g. `*` A 192.0.2.0) and Universal SSL covers only one wildcard level.

## #2 [identity-orgs] critical
**Claim.** The perimeter grants app access only when the session's active organization equals the app's organization, and a session belonging to two or more orgs with no active org fails to authenticate.
Source given: apps/every-app-gateway/src/perimeter/betterAuthAuthenticator.ts:119-136; src/server/organization/orgContext.ts:94-98; src/auth/config.ts:380-394
- **docs: confirmed.** Read the code at HEAD e1d9d3c6 (2026-10-15) in /Users/bensenescu/.t3/worktrees/private-every-app/t3-afce8c8f. All three parts of the claim are in the source verbatim.

(1) Org must equal the app's org — apps/every-app-gateway/src/perimeter/betterAuthAuthenticator.ts:136, in hasAppAccess: `if (session.orgId !== app.organizationId) return false;` (comment at 134-135: "The org the session acts under must be the org the app belongs to").

(2) Session's orgId comes from the active org — betterAuthAuthenticator.ts:119-123: `const org = await resolveOrgContext({ userId: session.user.id, activeOrganizationId: session.session.activeOrganizationId ?? null }); if (!org) return null;` so a null org context means authenticate() returns null (unauthenticated).

(3) Multi-org with no active org yields null — apps/every-app-gateway/src/server/organization/orgContext.ts:94-98 (resolveOrgContextFromDatabase): when activeOrganizationId is null it runs `findMany({ where: eq(members.userId, userId), limit: 2 })` and `return rows.length === 1 ? toOrgContext(rows[0], userId) : null;`. Doc comment at :39: "Falls back only when the user belongs to exactly one organization." A user in two or more orgs therefore gets null, and via (2) fails authentication. When an active org IS set, :87-93 requires a members row for (userId, activeOrganizationId) and returns null otherwise.

(4) Session creation only auto-sets the active org for sole-org users — apps/every-app-gateway/src/auth/config.ts:380-394, databaseHooks.session.create.before calls `resolveOrgContext({ userId, activeOrganizationId: null })` and returns `{ data: { ...session, activeOrganizationId: org.orgId } }` only when org is non-null, else `undefined` (no activeOrganizationId written). So a multi-org user's new session has no active org until one is set explicitly, and the perimeter rejects it until then.

Caveat (not a contradiction): the PAT bearer path (betterAuthAuthenticator.ts:68-108) bypasses the active-org lookup entirely; orgId comes from the PAT's own organizationId via resolveLiveOrgRole. The claim as stated concerns cookie sessions and holds for them.
- **adversary: partly.** Read the cited code plus the perimeter package and tests. Core claim holds for cookie sessions: betterAuthAuthenticator.ts:119-123 calls resolveOrgContext with session.activeOrganizationId and returns null if it resolves null; orgContext.ts:84-98 returns the active-org membership (null if not a member) and, with no active org, the sole membership only (`limit: 2`, `rows.length === 1`); hasAppAccess at :136 denies when `session.orgId !== app.organizationId`; config.ts:383-391 pre-sets activeOrganizationId at session creation only for sole-org users. Pinned by orgContext.test.ts:136 ("fails closed when the user belongs to multiple organizations") and :108, :150. Better Auth 1.7.7's setActive also requires membership (organization.mjs:67), and resolveOrgContext re-verifies from DB regardless. Qualifications the claim omits: (1) PAT requests (betterAuthAuthenticator.ts:70-105) take orgId from the token (`pat.organizationId`), not the session's active org, so a multi-org user with no active org DOES authenticate via PAT; only the orgId===app.organizationId check applies. (2) Zero memberships also fail, not just two-or-more (orgContext.ts:98; test :150). (3) On manifest-declared public routes a wrong-org session is not rejected; the request proceeds anonymously with the public marker (packages/perimeter/src/gateway.ts:269-291, 355-359). (4) Membership is cached per isolate for 30s (orgContext.ts:15-16, 63-64), so revocation lags. (5) Dev-only authenticators bypass it entirely (packages/perimeter/src/dev/devGateway.ts:91 and packages/cli/src/commands/dev/remoteAuth.ts:92 return hasAppAccess true) but are not the production perimeter (apps/every-app-gateway/src/server.ts:246 wires createProdAuthenticator).
  - Correction: For cookie-authenticated sessions, the perimeter grants app access only when the session's verified active organization (or the user's sole organization when no active org is set) equals the app's organization; a cookie session whose user has zero or two-plus memberships and no active org fails to authenticate. PAT-authenticated requests instead take their org from the token and bypass the active-org rule (the org must still equal the app's org). Public routes still serve a wrong-org session anonymously, and the membership check is cached per isolate for up to 30s.

## #6 [perimeter-dispatch] 
**Claim.** A first-time WfP script upload is dispatchable as soon as the API returns 200, so the hosted deploy API can mark an app active with no binding or activation step.
Source given: https://developers.cloudflare.com/changelog/post/2025-02-20-synchronous-uploads/
- **docs: confirmed.** Timing half: Cloudflare changelog "Workers for Platforms - Instant dispatch for newly created User Workers", Feb 20, 2025 (https://developers.cloudflare.com/changelog/post/2025-02-20-synchronous-uploads/) says verbatim: "With this update, first-time uploads of User Workers are now deployed synchronously. A 200 OK response guarantees the script is fully provisioned and ready to handle traffic immediately." It explicitly contrasts this with the old behaviour where "an API request could return a 200 OK response, [but] the script might not yet be ready to handle requests".

No-per-app-binding half: the dispatch namespace binding lives once on the dispatch Worker, not on each uploaded script.
