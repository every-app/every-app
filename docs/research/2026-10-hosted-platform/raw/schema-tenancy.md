# Hosted Every App: data model and tenant isolation

Researcher report, 2026-10-15. Scope: the gateway's D1 schema and
repositories, the perimeter registry and naming helpers, the migrations
(including PR #286's one-baseline rule), and what a hosted, multi-tenant
tier on Workers for Platforms (WfP) needs on top. All paths are relative to
the repo root of this worktree unless they start with `/`.

## In short

- **Org scoping today is mostly sound.** Every tenant-domain table carries
  `organization_id`, and the app-scoped child tables are tied to their app
  by a composite FK `(app_row_id, organization_id) -> apps(id,
  organization_id)`, so the database itself rejects a cross-org child row.
  The leaks that are left come from the code assuming a single install,
  not from missing `WHERE organization_id = ?` clauses. Examples: the
  "install organization", the global owner bootstrap, global bans issued
  by tenant admins, identity JWTs scoped to an app slug, binding props the
  app builds itself, and org deletion that cascades away tombstones.
- **Naming.** Keep `every-<orgKey>-<appId>` (`registryWorkerNameFor`,
  `packages/perimeter/src/manifest/manifest.ts:379-387`) for user Worker
  scripts, D1 databases and R2 buckets in hosted too. Drop the "install
  organization" bare hostname. Make the org key collision-proof (random
  suffix). **Do not give apps their own KV namespaces in hosted**: 1,000
  per account is the ceiling. KV becomes a prefixed share served through
  a gateway capability. Refuse `resources.workflows` on the dispatch tier
  until Cloudflare's conflicting documentation is resolved.
- **New tables.** One table, 1:1 with organizations: `organization_platform`
  (status, shard, deletion state). Catalog and installs (an install is an
  `apps` row with `catalog_app_id`), `app_versions`, `deploy_jobs`,
  `app_resources` (the hosted resource ledger), `app_capability_grants`
  (generalizing PR #281's `app_integration_grants`),
  `organization_data_keys` + `app_secrets` (envelope encryption, crypto-
  shred on delete), `billing_customers` (an Autumn mirror only), a per-org
  `OrgMeter` Durable Object for the usage ledger with a `usage_daily`
  rollup in D1, `audit_events`, and `platform_operators`.
- **Deletion.** Soft-delete with a grace period. Purge Cloudflare
  resources from the ledger: bulk-delete scripts by tag (with `force` for
  Durable Objects), delete D1 databases by UUID, empty and delete R2
  buckets, delete KV keys by prefix. Then crypto-shred the org's data key
  and delete its rows. Keep tombstones (the org row, `organization_keys`,
  `apps` hostnames and worker names) so no name or host is ever reused.

### 1.4 Naming helpers today

- `registryWorkerNameFor` gives `every-<orgKey>-<appId>`; legacy rows keep
  `every-<appId>` (`manifest.ts:379-387`). `isRegistryWorkerName` refuses
  reserved names, names over 63 characters and app ids containing `--`
  (`:395-407`). `MAX_WORKER_NAME_LENGTH = 63` (`:342`).
- `resourceNameFor`: `DB`/`KV` take the Worker name; other bindings get
  `<worker>--<binding>` (`:417-427`). The SDK keeps a **diverging dev-only
  copy** with a single hyphen (`packages/sdk/src/cloudflare/worker.ts:510-514`).
- Workflows: `workflowNameFor(worker, binding) = <worker>--<binding>`
  (`worker.ts:459`). The 64-character check runs **only at SDK build time**
  (`worker.ts:252,382-385`), never at registration.
- Org key: the slug's `[a-z0-9]`, cut to 12, with a numeric suffix on
  collision, at most 50 attempts (`AppRegistrationService.ts:214-252`).
  Assigned on first registration and never changed.
- Hostname: `<appId>.<base>` for the **install's own org**, otherwise
  `<appId>-<orgKey>.<base>` (`AppRegistrationService.ts:141-163`;
  `server/app-hosts.ts:1-15`). The label is checked to be at most 63
  characters (`:119-133`). Registration validates the Worker name length
  only; **D1, KV, R2 and Workflow name lengths are not validated there**
  (`:254-288,388-404`).
- The manifest declares `d1`, `kv`, `durableObjects` and `workflows`, but
  **not `r2`** (`manifest.ts:34-50`). OpenSEO binds R2
  (`/Users/bensenescu/workspaces/open-seo/wrangler.jsonc:143`).

## 2. What the hosted tier needs (requirements this report designs to)

1. One gateway and one control-plane D1 for every org. Org apps run as
   WfP user Workers in a dispatch namespace. Catalog apps run either as
   one shared platform Worker or as a dedicated user Worker per org
   (founder question Q1).
2. Every row an org owns is reachable by `organization_id`, both for
   enforcement and for deletion or export. Nothing the platform creates in
   Cloudflare exists without a ledger row naming its org.
3. Names are unique where Cloudflare requires it (script per namespace;
   D1, R2 and Workflows per account), fit Cloudflare's length limits,
   derive from immutable keys, and are **never reused** after deletion.
4. Account-level quotas are budgeted per org: D1 is 50,000 databases and
   1 TB per account, and 10 GB per database, which cannot be raised. KV is
   1,000 namespaces per account. R2 is 1,000,000 buckets. Workflows are
   counted against 500 scripts per account (sources §6).
5. An app's identity at the gateway (for brokered AI, integrations,
   secrets and KV) is set by the platform, never by the uploaded code.
6. Org deletion and export are complete, resumable and audited.
7. Per-request hot-path writes do not all land on one single-threaded D1.
   "Each individual D1 database is inherently single-threaded"; at 1 ms
   per query that is about 1,000 queries per second (D1 limits page).

## 3. Gaps and the smallest change that closes each

### 3.1 Cross-org leakage and tenancy risks (ranked)

**R1. The "install organization" gets bare hostnames.**
`hostnameFor` gives the oldest org with an owner `<appId>.<base>`
(`AppRegistrationService.ts:152-163`, `OrganizationRepository.ts:37-52`).
In hosted, the first tenant to sign up would own `todo.everyapp.host`,
`openseo.everyapp.host` and so on: a namespace grab, and a phishing surface
that looks official.
*Fix:* in hosted mode, `hostnameFor` always uses `<appId>-<orgKey>`, and
bare `<appId>.<base>` is reserved for platform catalog apps (if any). The
redesign is already moving this function into `@every-app/perimeter/registry`
(`docs/cli-redesign.md:67-80`), so add a `mode` argument there.
**0.25 day.**

**R2. Single-install assumptions in auth.**
`hasAnyOwnerMembership` is global (`organization/owner-membership.ts:10-19`)
and guards org creation (`auth/config.ts:368-377`). Sign-up is invite-only
(`:89-108,360-366`). The session-create hook picks an org only when the
user has exactly one (`:380-393`, `orgContext.ts:94-98`).
*Fix:* in hosted mode, open sign-up, create a personal org (owner) in a
`user.create.after` database hook, and set it active. `owner_bootstrap` and
`owner_setup_tokens` stay self-host only. **1.5-2 days** (likely shared
with the onboarding research).

**R3. `findByAppId` is a global slug lookup in the registry interface.**
`registry.ts:45,105-107`, `drizzleAppRegistry.ts:62-64`.
*Fix:* remove it from `AppRegistry`. The dev gateway resolves by hostname
or with `findByOrgApp`. **0.25 day.**

**R4. Org deletion cascades away the tombstones.**
`organization_keys` cascades on org delete (`organization-keys.schema.ts:12-14`),
and so do `apps` rows, tombstones included (`apps.schema.ts:19-21`).
`AppRepository.ts:239-247` explains why tombstones exist: "Dropping the
row would let another org register the same slug, and the old Worker would
accept identity tokens minted for it." Deleting an org therefore undoes
that protection, and frees `every-<orgKey>-*` names for the next org that
derives the same key.
*Fix:* hosted never hard-deletes `organizations`. The org row becomes a
scrubbed tombstone (status in `organization_platform`), `organization_keys`
and the `apps` tombstones stay, and `app_resources` uses `ON DELETE NO
ACTION`, so a row with live Cloudflare resources can't be removed.
**Included in §3.5.**

**R5. Identity tokens are scoped to the slug, and apps don't pin their org.**
`aud = app.appId` for identity and public-marker JWTs (`gateway.ts:153,327`).
One signing key serves every tenant. The SDK checks `aud`, but nowhere
compares `orgId` with the app's org (`EVERY_APP_ORG_ID` is bound but unused,
`worker.ts:323`). Org A's "todo" and org B's "todo" accept each other's
tokens. Today only the perimeter mints and injects them, but in hosted,
tenant code receives every token for its users. A token leaked from one
tenant's Worker should be useless anywhere else.
*Fix:* `aud = apps.id` (the install's row id; shared catalog Workers check
`aud` against their install table, or use `aud = catalog:<id>` plus an
`install` claim). The SDK rejects `orgId` that differs from the org the
platform pinned: for dedicated scripts that is a text binding set at
upload; for shared Workers, the install mapping. Key the public-marker
cache by install. **1 day.**

**R6. Tenant admins can ban and delete platform accounts.**
`MembershipService.deactivate` calls `UserRepository.deactivate`, which
sets `users.banned`, deletes every session, and revokes every PAT and
deploy token in every org (`MembershipService.ts:107-118`,
`UserRepository.ts:61-88`). `AdminService.deleteUser` deletes the `users`
row once the user has no other membership (`AdminService.ts:136-143`). The
guard `requireAccountWideManageable` (`MembershipService.ts:81-99`) only
allows this for users in no other org. In hosted that still lets an org
admin lock someone out of the whole platform, including any future
personal org.
*Fix:* in hosted mode, member removal never touches `users`; banning is
an operator action (`platform_operators`). **0.5 day.**

**R7. Binding props come from the app's own build.**
The `EVERY_APP_GATEWAY` binding's `props {organizationId, appId,
workerName}` are written by `everyAppWorker()` from `.everyapp/deploy.json`
(`worker.ts:311-319`). The gateway compares them with the registry
(`app-gateway-entrypoint.ts:104-115`), but props are identifiers, not
secrets. In self-host only account operators deploy. In hosted, tenant
code is uploaded by the platform.
*Fix (a rule, not code yet):* the hosted deploy job builds every binding
in the WfP upload `metadata` itself and ignores the bundle's own binding
config. For request-scoped identity, use dispatch `props` (claim C2).

**R8. `mcp_connection_apps` has no org column.**
`mcp.schema.ts:122-136`. The only guard is the write-time check in
`mcp-auth/authorize.ts:228-241`.
*Fix:* add `organization_id`, a composite FK to `apps(id, organization_id)`,
and a unique `(id, organization_id)` on `mcp_connections` as the target of
a second composite FK. Add the org predicate in `listActiveForUser`.
**0.5 day.**

**R9. `members` has no unique `(organization_id, user_id)`.**
*Fix:* declare the index through a plugin `schema` the way #286 did for
`accounts` (`auth/cloudflare-access/plugin.ts` in that PR). **0.25 day.**

**R10. A single active org per session.**
`hasAppAccess` refuses unless `session.orgId === app.organizationId`
(`perimeter/betterAuthAuthenticator.ts:136`), and the session's org is its
*active* org (`:119-123`). A hosted user in a personal org and an invited
org gets a 403 on the other org's app hosts until they switch. That isn't
a leak, but it is the most common hosted path.
*Fix:* on an app host, derive the org from the app (`app.organizationId`),
check live membership in that org (`OrganizationMembersRepository.findMembership`),
and mint the JWT for that org. **1 day.**

**R11. One gateway-wide DCR budget.**
`oauth-register:gateway:<day>` (`mcp-auth/registration-limit.ts:114`).
Registration happens before the org is known, so a per-org budget isn't
possible. *Fix:* raise the global budget in hosted, or prefer CIMD
clients. This is a noisy-neighbor issue, not a leak. **0.25 day.**

**R12. Hot path on one global D1.**
Every proxied app request reads `sessions` (cookie cache off,
`auth/shared.ts:8-12`) and `user_app_access` (uncached,
`betterAuthAuthenticator.ts:148-152`). PAT requests also write `last_used_at`
(`:83`). At 1,000 queries per second per database, that caps the whole
platform.
*Fix:* turn on Better Auth's cookie cache (short max age), add an
isolate-level access cache with the same 30 s trade-off as `orgContext`,
and send per-call writes (usage, audit) to the per-org `OrgMeter` DO (§3.3).
**1 day.**

**R13. Cookie scope spans every tenant's hosts.**
The session cookie's Domain is `APP_BASE_DOMAIN` (`auth/config.ts:204-221,280-287`).
The perimeter strips `Domain=` from app `Set-Cookie` headers
(`packages/perimeter/src/headers.ts:178-187`), but tenant JavaScript can
still set `document.cookie = "...; domain=everyapp.host"` (cookie tossing
across tenants). The fix (the Public Suffix List plus per-host session
handoff) belongs to the security research. It is flagged here because it
is a tenant boundary.

`apps.schema.ts:32`. This blocks N installs of a shared catalog Worker.

**The KV decision: a prefixed share served through a capability, not a
namespace per app.**

- Why not one per app? 1,000 namespaces per account ("can be raised ...
  case by case", KV limits page, 2026-10-08) caps the whole platform at
  about 1,000 KV-using apps. OpenSEO alone binds two (`KV`, `OAUTH_KV`;
  `open-seo/wrangler.jsonc:109`), so dedicated OpenSEO installs would stop
  at 500 orgs.
- Why not a shared namespace bound straight to user Workers? KV has no
  per-key access control, so one tenant could read another's keys.
- **How it works.** Hosted maps `resources.kv: ["KV"]` to a capability.
  The SDK exposes a `KVNamespace`-shaped wrapper (`get`, `getWithMetadata`,
  `put`, `delete`, `list`) that calls the gateway broker. The broker
  prefixes `<orgKey>/<appRowId>/<binding>/` and reads or writes one of a
  small pool of platform namespaces (`organization_platform.kv_pool`
  records which).
- **What it buys.** No per-org account resources. Org deletion is "list
  the prefix and bulk-delete". Export is "list the prefix". The broker
  meters operations per org for free.
- **What it costs.** One RPC hop per operation. About 83 bytes of each
  key's 512-byte limit go to the prefix. KV-specific options (`cacheTtl`)
  must be passed through.
- **Dependency.** The capability has to reach background code (crons, DO
  alarms) as well as requests. Dispatch `props` stubs are valid "only
  during the request that received it" (dynamic dispatch docs,
  2026-09-16), so background use needs a binding the platform sets at
  upload. That is claim C3, unverified.
- **Fallback if C3 fails:** an SDK-provided Durable Object (SQLite) that
  stores KV per script. It is isolated by construction and deleted with
  the script, but it is single-location and harder to export.

### 3.4 Migration plan under the one-baseline rule

1. **Now, while nothing hosted is live.** Each PR edits `*.schema.ts` and
   regenerates `0000_*.sql` and `meta/` (PR #286's rule). Stacked PRs will
   conflict in the generated SQL and snapshot. Resolve by deleting both
   and running `pnpm db:generate` after the rebase; never merge them by
   hand. This matters with parallel agents.
2. **Better Auth tables.** Never hand-edit `auth.schema.ts`. Platform
   state goes in `organization_platform`, and the `members` index is
   declared through a plugin `schema`, as #286 did for `accounts`.
3. **Hosted tables ship in self-host too** (created, empty). One schema,
   one baseline, one codebase (ADR-0001). Keep them under
   `src/db/hosted/` so a later open-core split (ADR-0001 Decision 4) is a
   directory move.
4. **The `OrgMeter` DO gets its own drizzle config**
   (`driver: "durable-sqlite"`, its own `0000` baseline). Its migrations
   are bundled into the Worker and run in the DO constructor under
   `blockConcurrencyWhile` (Drizzle's Durable Objects guide).
5. **Tenant app D1s.** The hosted deploy job applies the app version's
   migrations per install, recording a Time Travel bookmark per binding in
   `deploy_jobs.d1_bookmarks`, as the CLI does for self-host. Upgrading a
   catalog app with dedicated installs fans out N migrate jobs; shared
   catalog apps migrate one database (Q1).
6. **The day hosted D1 holds data someone cares about,** freeze the
   baseline. From then on, numbered append-only migrations, checked by
   `release-migrations.test.ts`, with `-- everyapp:contract` for drops.
   The hosted gateway is deployed by us, so migrate-before-code works
   unchanged.

### 3.5 Org deletion and export

**Deletion (owner-only, with re-authentication and a typed confirmation).**

0. **Request.** Set `organization_platform.status = 'deleting'` and
   `purge_after = now + grace`. In the same transaction, set every app of
   the org to `disabled`. The perimeter serves 503 within the 30 s
   host-cache TTL (`server.ts:55-57`). Also revoke MCP connections
   (`revokeAllForUser` per member, or a new `revokeAllForOrg`), PATs and CI
   credentials, cancel the Autumn subscription, and flush the `OrgMeter`
   ledger to Autumn (final usage). Write `audit_events org.delete_requested`.
1. **Grace period** (Q4; default 7 days). The owner can restore. An export
   is offered.
2. **Cloudflare purge, driven by `app_resources`** (one gateway Workflow
   instance per org, resumable, each step idempotent):
   - Scripts: `DELETE .../dispatch/namespaces/{ns}/scripts?tags=o-<orgKey>:yes`
     (bulk delete by tag), or per script with `force=true` so the DO
     namespaces they implement go too.
   - D1: `DELETE /d1/database/{uuid}` per ledger row.
   - R2: buckets must be empty first. Set a lifecycle rule that expires
     everything, then delete the bucket on a later pass.
   - KV: list `<orgKey>/` in the org's pool namespace and bulk-delete.
   - Custom hostnames, if any.
   - Shared catalog apps: the gateway calls each installed catalog app's
     `onOrgDeleted(orgId)` hook (a new contract, §3.6 PR H), since OpenSEO
     keeps its own `organization_id` rows
     (`open-seo/src/db/better-auth-schema.ts:120`).
   - Mark each ledger row `deleted`.
3. **Gateway rows.** Delete `app_secrets`, then `organization_data_keys`
   (**crypto-shred**). Then delete `members`, `invitations`,
   `user_app_access`, `user_access_tokens`, `mcp_connections` (cascades
   `mcp_connection_apps`), `mcp_tool_calls WHERE organization_id = ?`
   (there is no FK, so this must be explicit), `app_tools` and catalogs,
   grants, `app_versions` (and their R2 bundles), `deploy_jobs`,
   `usage_daily`, `billing_customers`, and pending exports. In the
   `OrgMeter` DO, call `ctx.storage.deleteAll()`. Clear
   `sessions.active_organization_id = ?` so members aren't stuck on a 401.
4. **Tombstones that stay forever.** The `organizations` row (name
   scrubbed, slug renamed to `deleted-<id>` to free it), `organization_keys`,
   `organization_platform` (`status = 'deleted'`), and the `apps` rows as
   `status = 'deleted'` with name, description and manifest scrubbed but
   hostname and worker name kept. The same reason `AppRepository.tombstone`
   exists applies to a whole org. `audit_events` for the org are kept for
   the retention window, then pruned.
5. **Users are platform identities and are not deleted** with the org
   (Q3). A user left with no org gets a fresh personal org on their next
   sign-in.
6. **Backups.** Rows stay readable in D1 Time Travel for 30 days, and that
   can't be turned off. The privacy policy says so, and secrets are
   already unreadable from step 3.

**Export** (owner or admin; produces an R2 object served by a 7-day signed
link, recorded in `organization_exports`):

- Gateway rows as JSON: org, members, apps, access, grants without secret
  values, versions and manifests, `usage_daily`, `audit_events`. Secrets
  are exported **by name only**.
- Each dedicated app's D1 through `POST /d1/database/{uuid}/export`, which
  returns a signed SQL URL valid for an hour. It must be polled
  continuously or it cancels, and "your D1 will be unavailable to serve
  queries" during a large export. So exports run per app and are
  announced to the org.
- R2: object listing plus copies.
- KV: the prefix dump.
- Durable Object state and shared catalog app data can only be exported
  by the app itself, through an `exportOrg(orgId)` hook. Catalog apps must
  implement it; org apps may.

## 4. Open questions only the founder can answer

**Q1. Do catalog apps run as one shared multi-tenant Worker, or as one
dedicated instance per org?**
- *Why it matters:* this decides whether `apps.worker_name` is unique,
  whether deletion and export need app hooks, how migrations fan out (1
  database or N), and whether OpenSEO can keep its Workflows. OpenSEO uses
  two Workflows, two KV namespaces, R2, Durable Objects, a second Worker
  and crons (`open-seo/wrangler.jsonc:22-148`), and it is already
  multi-tenant internally (`organization_id`).
- *Recommended default:* **shared** for catalog apps we ship (`tier =
  'platform'`, one `everyapp-cat-<id>` Worker; each org's install is an
  `apps` row with its own hostname and grants). **Dedicated** WfP Workers
  for org apps and forks.

**Q2. What should org keys look like? They appear in every app hostname,
forever.**
- *Why it matters:* readable keys leak org names into URLs. Slug-derived
  keys collide at scale (50 attempts, then `ORG_KEY_UNAVAILABLE`). Keys
  are immutable.
- *Recommended default:* up to 7 slug letters plus 5 random `[a-z0-9]`
  (`acmex7k2p`), hosted only.

**Q3. When an org is deleted, are its members' accounts deleted?**
- *Why it matters:* accounts span orgs, and invited users may have no
  other org. This decides whether deletion touches `users`.
- *Recommended default:* no. Accounts are platform-owned. Deleting your
  own account is a separate user action that also deletes the personal
  org.

**Q4. How long is the deletion grace period, and what do we promise about
backups?**
- *Why it matters:* restore is impossible once purged, and D1 Time Travel
  keeps rows for 30 days regardless.
- *Recommended default:* 7-day soft delete with restore, then purge.
  Secrets are crypto-shredded at purge. The policy states "residual
  backups up to 30 days".

**Q5. Can org admins ban users in hosted, or only remove them?**
- *Why it matters:* `users.banned` is platform-wide (R6).
- *Recommended default:* remove only. Bans are an operator action.

**Q6. KV for hosted apps: a brokered prefixed share, a DO-backed shim in
the SDK, or no KV?**
- *Why it matters:* at 1,000 namespaces per account, per-app KV can't
  scale. The broker adds a hop and depends on claim C3.
- *Recommended default:* the brokered share, with the DO shim as the
  fallback if C3 fails.

**Q7. Workflows for org apps.**
- *Why it matters:* Cloudflare's documentation conflicts on WfP support
  (C1), and Workflows also count against account-wide names and the
  500-script limit.
- *Recommended default:* refuse `resources.workflows` on the dispatch tier
  in v1, and ship a DO-alarm job helper in the SDK. Catalog apps on the
  platform tier keep Workflows.

**Q8. Does an invited user also get a personal org?**
- *Why it matters:* the vision says "gets their own organization, *or* is
  invited to one". The answer sets how many users are in multiple orgs (R6
  guards, R10 UX) and the free-tier cost per user.
- *Recommended default:* not at invite time. A personal org is created
  when they first choose "New workspace" or would otherwise have no org.

**Q9. Is usage recorded per user, or only per org and app?**
- *Why it matters:* per-user limits and "who spent this" need `user_id`
  in the ledger. Attribution already exists (`app-gateway-entrypoint.ts:230-260`).
- *Recommended default:* record `user_id` whenever the identity JWT is
  present, and roll up daily per (org, app, user, feature, provider).
  Autumn sees only org totals.

**Q10. One Cloudflare account for every tenant until a limit forces
sharding?**
- *Why it matters:* the limits are 50,000 D1 databases and 1 TB of D1
  storage per account, and the dispatch namespace is per account.
- *Recommended default:* yes. Record `cf_account_id` per org and per
  resource from day one, so sharding later is a data change, not a schema
  change.
