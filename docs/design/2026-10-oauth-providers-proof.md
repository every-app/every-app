# OAuth providers: the Google and GitHub proofs

Date: 2026-10-25. The proof lane of [2026-10-oauth-providers.md](2026-10-oauth-providers.md) (section 10, PR 6). Ben's steer: prove the general pattern with Google first, in OpenSEO on the port checkout, then GitHub as the proof that a provider with no hand-written entry works by upload alone. Three things ran; what each proved and what still needs Ben's real client ids is below.

## 1. The harness: the whole flow against a fake provider

`apps/every-app-gateway/src/server/oauth/google-proof.sqlite.test.ts`, on a migrated SQLite database with `src/test/fake-oauth-provider.ts` standing in for Google and GitHub (`pnpm -C apps/every-app-gateway exec vitest run --silent=true src/server/oauth/google-proof.sqlite.test.ts`). It tells OpenSEO's story end to end:

| Step | What the test drives                                                                                                                          | What it proves                                                                                                                                                                                                                                                                           |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | OpenSEO (an app listing `google-workspace` with `identity`, `search-console.read`, `analytics.read`) asks the status before any client exists | `configured: false`, so the app says "not set up in Every App yet"                                                                                                                                                                                                                       |
| 2    | The operator pastes the Google client in Admin → Providers (`setOAuthClient`)                                                                 | The catalog entry takes a client sealed in D1, no row, one Google client; the summary carries the redirect URI and never the secret                                                                                                                                                      |
| 3    | The status again                                                                                                                              | `configured: true`, `connectPath: /connect/google-workspace`, the three sets, `connection: null`                                                                                                                                                                                         |
| 4    | A member starts `/connect/google-workspace?return=<OpenSEO page>&account=user`                                                                | A 302 to `accounts.google.com` with `client_id`, the Gateway's `redirect_uri`, PKCE S256, `access_type=offline`, `prompt=consent`, and exactly the scopes of the three sets (no Gmail)                                                                                                   |
| 5    | Google answers; the callback runs                                                                                                             | The code exchange carries the verifier and the client in the form body; the connection row holds ciphertext only, labeled by the userinfo email; `provider.connected` is emitted; the browser returns to the OpenSEO page                                                                |
| 6    | The status for the member, and for another member                                                                                             | The member reads `ready: true` with their connection; the other member reads `connection: null`                                                                                                                                                                                          |
| 7    | OpenSEO's calls as `gscClient.ts` and `ga4Client.ts` make them, with an app-supplied `Authorization` header                                   | `GET /webmasters/v3/sites`, `POST …/searchAnalytics/query`, `POST /v1/urlInspection/index:inspect`, `GET analyticsadmin …/accountSummaries`, `POST analyticsdata …:runReport`, `GET userinfo` all reach Google with the member's bearer; the app's header, cookies and identity never do |
| 8    | A Gmail read, a DELETE on Search Console                                                                                                      | Refused (`integration_scope_not_allowed`; a write on a read grant), without a token read                                                                                                                                                                                                 |
| 9    | The access token is about to expire                                                                                                           | One `refresh_token` grant with the client; the new token is sealed and used; Google's unrotated refresh token is kept                                                                                                                                                                    |
| 10   | Disconnect                                                                                                                                    | The row goes, `provider.disconnected` is emitted, nothing is revoked at Google, a call now answers `integration_not_connected` with the connect path                                                                                                                                     |
| 11   | GitHub by upload alone: `addOAuthProvider({ preset: "github-oauth", clientId, clientSecret })`                                                | The preset becomes a row with its client sealed; the same connect flow runs (comma-joined scopes, `Accept: application/json` on the token request); `api.github.com/user/repos` sees the bearer; disconnect revokes GitHub's grant                                                       |

The flow lane's own `flow.sqlite.test.ts` pins the rules around it (state single use, foreign and expired states, provider errors on a page, return-to-own-hosts, scope excess, missing sets, the organization's account, the D1 client bound to the endpoints).

## 2. The local walk: the Gateway in a browser, to the providers' screens

A local gateway (`pnpm exec vite dev --port 5199`, `.dev.vars` from `regenerate-secrets.js` plus `GATEWAY_URL=http://localhost:5199` and `GATEWAY_DEPLOYMENT_MODE=self_hosted`, migrations through 0016, the owner claimed) driven by Playwright with the owner's session. Screenshots in [2026-10-oauth-providers/](2026-10-oauth-providers/):

1. `01-admin-providers.png`: Admin → Providers lists every registry entry by kind (AI, API key, Gateway service, OAuth), source and client state.
2. `02-add-dialog-presets.png`: Add OAuth provider, step one: the catalog's clients marked "Built in", the presets, Custom.
3. `03-add-dialog-github-redirect-uri.png`: step two for GitHub: the exact redirect URI to register (`http://localhost:5199/connect/github-oauth/callback`) with a copy button, the console link, the scope sets, the client id and secret fields, the `secret set` line for a terminal.
4. `04-admin-providers-with-github.png`: "GitHub added".
5. `05-settings-connected-accounts.png`: Settings → Connected accounts with Connect Google and Connect GitHub.
6. `06-github-consent.png`: Connect GitHub landed on github.com's sign-in, whose `return_to` is the authorize request: `client_id`, `redirect_uri=http://localhost:5199/connect/github-oauth/callback`, `code_challenge` with `S256`, `scope=read:user,user:email,repo,read:org`, `state`.
7. `07-google-consent.png`: Connect Google landed on `accounts.google.com` with the same shape (`access_type=offline`, `prompt=consent`, the preset's sets since no local app lists Google); Google answers `invalid_client` because the client id is a placeholder, which is the expected end of a walk without a real client.

What the walk showed beyond the harness: the Google client set as a Worker secret (`GOOGLE_WORKSPACE_CLIENT_ID` in `.dev.vars`) is read by the flow without a D1 row, as the design's precedence says; a registered row's own settings (`GITHUB_OAUTH_CLIENT_ID`) do not reach a local `vite dev` Worker because the dev config passes through the catalog's names only (`OPTIONAL_SECRETS`), so locally a row's client is pasted in the UI; deployed, `everyapp secret set` sets it on the Worker.

## 3. OpenSEO on the port checkout

[private-open-seo-everyapp#16](https://github.com/every-app/private-open-seo-everyapp/pull/16) (branch `everyapp/google-through-gateway`): in gateway mode OpenSEO lists `google-workspace` with the three sets, answers "available / connected" from the Gateway's status for the served request (`src/server/features/google/gatewayGoogle.ts`), sends a Connect click to the Gateway's connect page and back, and reads Search Console and GA4 through `integrationFetch` with no token of its own; one Google connection serves both. The own-client path is untouched. Unit tests cover the mode switch and both clients with a fake gateway fetch; the port typechecks apart from a pre-existing SDK binding-type drift in `vite-plugin-every-app.ts`. The SDK gained `for` on `integrationStatus` for this (the proof PR), so an app can ask whose connection the status reports.
