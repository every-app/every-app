# Code mode and skills on the gateway

Written 2026-10-23/24 as a research swath for the launch on Monday 2026-10-27; not launch-blocking. Ben asked two questions about the one MCP connector the Gateway serves (`https://<gateway>/mcp`), which lists every tool of every app a member can use: as apps multiply and some bring dozens or hundreds of tools, the tool list itself becomes the problem.

1. **Code mode.** Should the Gateway offer a code-mode surface on `/mcp` (a `search_tools` and `execute(code)` pair, the code run in a sandbox against a generated TypeScript API over the member's tools), or only tool search and lazy loading, leaving code mode to the harnesses? The confusion to resolve: the common advice is "implement code mode in the harness, not the MCP server", yet most harnesses don't have it.
2. **Dynamic skills.** With data providers such as Monid, Treg and DataForSEO, people automate workflows in Claude just by having the data. Ben pointed at Executor (executor.sh), described as creating and evolving skills at runtime, as the model to beat: is there a better way Every App could help people manage skills than leaving them to Claude Code's skill files, such as skills stored on the Gateway per organization, shared with teammates, suggested from usage, callable through `/mcp`? Or is that stepping on the harnesses' toes, and "just provide the data" is plenty?

Sections 0 to 8 are the decision; the evidence behind them, verified against current documentation and source, is Appendix A, and the review record in section 9 says how it was checked. Paths are in this repository unless marked. The sibling thread "Monid, Treg and DataForSEO as apps on the Every App MCP gateway" (TODO.md, "MCP apps (2026-10-24)") decides how provider apps are built; this document takes its tool counts and assumes its outcome (those tools land in the same list).

## 0. Summary

**Code mode: not on the Gateway, not now; tool search alone is not the fix either; one half-day PR now, a compact opt-in surface after launch.** The "implement it in the harness" advice is being followed: Claude Code, Codex, Cursor and VS Code's new default harness defer tool schemas on the models they support, OpenCode 2.x runs model code against MCP tools by default, Goose can be switched on to, and Codex carries it unshipped. Anthropic's own code execution cannot reach MCP tools and Claude Code has none, so code mode for Claude users could only ever be gateway-side; but the clients that still load every definition (claude.ai and Desktop, ChatGPT, Antigravity, and Claude Code in the configurations that turn tool search off) are served as well by a plain compact surface, and a Gateway `execute(code)` would wrap OpenCode's own code mode, add a sandbox the threat model must carry, and buy nothing for Claude Code's tool count. What it would uniquely buy, results filtered before they reach the model and many calls without a round trip each, is real and measurable, so section 4 names the triggers that reopen it. Recommended: **A** now (gateway instructions capped at 4,096 characters, Claude Code's default cut, with the app list first; `anthropic/alwaysLoad` on the built-ins; a longer `subscriptions/listen` hold on the surface that rechecks its caller; one line of description guidance; half a day, no invariant touched) plus a half-day `client_info` column so the Gateway can see which clients call it; **B** after launch, opt-in per connection (`everyapp_search_tools`, `everyapp_call_read`, `everyapp_call_write`, the read/write split Anthropic's directory rules require), built after a measurement on our own tools, because the one published evaluation scored meta-tools worst on completeness; **C** (code mode) only on the triggers in 4.4, and then gateway-side, read-only first, as a restricted interpreter in the Gateway isolate (Executor's and OpenCode's shape) or a Dynamic Worker behind a secret-free runner. A gateway-wide search tool without B helps no client today, so the sibling provider-apps thread has been asked not to add one.

**Skills: no store on the Gateway; apps should ship skills with their tools; "just provide the data" is right for people.** Every vendor has a server-held org skills layer, all vendor-locked and pulled into the harness's own directories; Skills over MCP is standardized (SEP-2640) and consumed live by no mainstream harness; Executor never built runtime-evolved skills; the data gateways people love ship a `SKILL.md` and a CLI. The hosted OpenSEO plugin ships twelve skills beside its tools and they are installable today from its public repository; what the Gateway cannot give them is the connector's URL and tool names, delivery to apps installed from a release, version coupling with the deployed catalog, and the member's app access. Recommended: nothing for launch (**S1**); an every-app plugin with a configurable gateway URL as a docs item right after (**S2**); then `defineTools(..., { skills })`, markdown only, snapshotted and served per organization through a built-in, a per-gateway marketplace and SEP-2640 as clients adopt it (**S3**); not a user-authored store or usage-mined suggestions (**S4**).

**Numbers.** On the four real launch apps a read & write caller's `tools/list` has 187 entries (185 app tools and the two built-ins), 419,932 bytes: between about 59,000 tokens (definitions without output schemas, which no model-facing tool format carries) and 105,000 (the whole response) per turn in a client that loads everything; how much of it claude.ai hands the model is unmeasured. With the starter the five catalogs hold 205 tools, 17 of them destructive and hidden, so a read & write caller is listed 190 entries, 66 short of claude.ai's reported 256-tool connector cap. **Found on the way (section 8):** the ToolBus ends every listen stream after ten minutes, which spends Claude Code's "five reopens an hour" budget. **For Ben:** the four decisions in section 7.

## 1. Today: what `/mcp` serves, and what a long list costs

The facts a decision rests on, from the code at `main` (`40afd187`, 2026-10-24; the measurements below were taken at `d0c3b73f` the same day, and nothing in between changed a limit):

- **One connector, one page.** `gatewaySurfaceView` (`packages/toolbus/src/view.ts`) lists the two built-ins (`everyapp_list_apps`, `everyapp_whoami`), then every reachable app's tools by app id then name, as `<app>_<tool>` (`packages/toolbus/src/server.ts`, `listTools`). `tools/list` returns the whole list in one response: the ToolBus implements no cursor, though the SDK's `ListToolsResult` carries `nextCursor`. The response carries the 2026-07-28 cache hint `ttlMs: 60000, cacheScope: "private"` (`TOOLS_LIST_TTL_MS`).
- **Tools are the only capability.** The server declares `capabilities: { tools }` and nothing else: no prompts, no resources, no logging (`server.ts`, `createToolBusServer`). The installed `@modelcontextprotocol/server` 2.3.1 knows `prompts/list`, `prompts/get`, `resources/*`, `tasks/*`, `elicitation/create`, `server/discover` and `subscriptions/listen`, and no `tools/search` or any other server-side tool lookup method.
- **Both protocol eras.** 2025-06-18 and 2025-11-25 clients get a session whose id ends in a hash of their tool list, so a changed list is announced with `notifications/tools/list_changed`; 2026-07-28 clients (Claude Code) hold a `subscriptions/listen` stream the Gateway re-reads every 30 s (`packages/toolbus/src/http.ts`; `apps/every-app-gateway/src/server/toolbus/gateway-mcp.ts`, `recheckFor`, `gatewayView`).
- **Limits.** 100 tools per app, 2048-character descriptions, 20 KiB per schema, 2048 characters of instructions per app (`CATALOG_LIMITS`, `packages/toolbus/src/catalog.ts`); on the gateway surface the instructions are a header line, the app list, since #396 one line per app that needs setup ("`<app>` is not available: `<reason>`"), then each app's own instructions clipped to 1024 characters, all of it to 8 KiB (`view.ts`). A namespaced name longer than 64 characters drops the tool.
- **Policy.** Destructive tools are hidden from every AI client; write tools from read-only connections; "hidden" means absent from `tools/list` and `Unknown tool` on call, so nothing about the tool leaks (`policy.ts`; invariants `tools.policy-destructive-hidden-write-gated`, `toolbus.hidden-equals-unknown`). The two built-ins are listed before the policy loop and executed before it (`server.ts`, `execute.ts`); they take no arguments and are read-only by construction (`toolbus.builtins-readonly-reserved`).
- **One identity per call.** `executeToolCall` (`execute.ts`) resolves the name, applies policy, checks the arguments against the snapshotted schema, mints a 120 s identity JWT for that call alone (`chan: "mcp"`, `act.sub` naming the credential, explicit `mcp:read`/`mcp:write`, `tc: { id, name }`), posts once to the app's `/__everyapp/tools/call` over its service binding (30 s, 1 MiB result), and emits one audit event: an `mcp.tool_call` log line and an `mcp_tool_calls` row with a keyed digest of the arguments, never the arguments or result (`apps/every-app-gateway/src/server/toolbus/runtime.ts`; invariants `tools.per-call-identity`, `audit.one-row-per-call-no-arguments`). The row carries a client name only for OAuth connections (the registration's `client_name`); personal tokens and Cloudflare Access callers have none, and the per-request `io.modelcontextprotocol/clientInfo` that 2026-07-28 makes mandatory is not read.
- **Who calls.** An OAuth 2.1 token the Gateway issued (consent chooses the organization, all apps or selected ones, read & write or read only), a personal access token, or a verified Cloudflare Access assertion (Managed OAuth; write access to every app, no connection row). Every request re-reads the caller; nothing is cached between requests (`apps/every-app-gateway/src/server/mcp-auth/validate.ts`, `access-caller.ts`).
- **What is counted.** `usage_daily` and `usage_monthly` count provider calls (AI proxy, `api_key` and OAuth-client capabilities), not tool calls (`docs/design/2026-10-teams.md` section 4.1); tool calls are counted only as audit rows, which Admin → Activity lists (#434) with `result_bytes` per call.
- **The agent-facing contract.** `landing-page/content/agent/mcp.md` (served as `https://everyapp.com/docs/agent/mcp.md`) and the skill `packages/cli/skills/everyapp/mcp.md` describe every built-in, limit, error and client behaviour above; a drift test in `packages/cli/src/docs` fails when the code defines a command, flag, error code, manifest field or setting the pages don't name. The built-in tool names in that test are a literal list, so a new built-in passes CI until someone adds it by hand; PR 1 in section 6 derives the list from `listBuiltinTools()`. Anything added to `/mcp` is documented there in the same PR.

**How long the list is today.** The launch apps' `defineTools()` catalogs, counted from their checkouts on 2026-10-24:

Two apps are 95% of the bytes: OpenSEO (72 listed, 218 KB, descriptions totalling 34,349 characters) and Open CRM (90 listed, 180 KB). ## 2. What must not break

- **The threat model's B5 invariants** (`docs/threat-model.md` "B5. AI client → `/mcp`"; the register in `docs/threat-model-invariants.md`): one protected resource (`mcp.one-protected-resource`); consent's scopes are the user's choice (`oauth.scopes-are-the-users-choice`); per-request recheck of the caller (`oauth.per-request-recheck`); destructive hidden, write gated (`tools.policy-destructive-hidden-write-gated`, `toolbus.policy-destructive-hidden-write-gated`); a hidden or absent tool answers `Unknown tool` (`toolbus.hidden-equals-unknown`); one fresh identity and exactly one app invocation per call, never `*`, never `mcp:destructive` (`tools.per-call-identity`, `toolbus.one-identity-per-call`); request-shape limits and no fan-out (`tools.request-shape-limits`, `toolbus.arguments-bounded-before-app`, `toolbus.app-answer-bounded`, `toolbus.http-bounds-and-origin`); one audit row per call without arguments (`audit.one-row-per-call-no-arguments`, `toolbus.audit-digest-never-raw`); the built-ins are read-only and `everyapp` is a reserved app id (`toolbus.builtins-readonly-reserved`); the browser `Origin` rule (`mcp.browser-origin-rule`). A new built-in with arguments is the first of its kind: built-ins are listed and run before the policy check today, so any option that adds one changes `listTools` and the built-in branch of `executeToolCall` and amends `toolbus.builtins-readonly-reserved`; a short default list would add a third state (unlisted but callable) that `toolbus.hidden-equals-unknown` and `mcp.md`'s "hidden means nothing about the tool leaks" do not describe; any new capability (prompts, resources, a sandbox) needs its own line in the register.
- **The OAuth and Access paths.** `/mcp` is bypassed on the Access applications (`everyapp access on`), served behind Managed OAuth from the header assertion only, and takes no cookie. A code-mode or skills surface changes nothing about who may call; it must not add a second protected resource, a cookie-read, or a route an `mcp:`-only token could reach beyond `/mcp` (`perimeter.mcp-only-token-scope`); a route outside `/mcp` needs its own credential and scope.
- **The agent docs contract.** `mcp.md`, the skill and `errors.md` name every built-in and error; the drift tests pin the CLI's codes and settings, and `packages/cli/src/docs/agentDocs.test.ts` holds the built-in names `mcp.md` must document as a literal list, which today a new built-in does not update on its own. Any option that adds a built-in adds it to that list, or PR 1 makes the list derive from the code first.
- **Metering and audit.** Tool calls are audited per call; provider calls are counted per organization and member. A surface that fans one request into many calls must keep one audit row per inner call and attribute provider spend to the member as today's `act.sub` does; it also relaxes the three register rows that forbid fan-out, which must say so.
- **The hosted tier.** Shared first-party apps on Workers for Platforms are served to every organization; a sandbox binding, a skills table or a marketplace endpoint must exist per Gateway and work on both tiers.

## 3. What the landscape settles

The evidence is in Appendix A; these are the findings the decisions rest on.

- **The harnesses are doing what the advice says.** Claude Code defers every MCP tool by default and searches names and descriptions client-side; Codex has tool search always on where the model supports it; Cursor and VS Code's new default Copilot harness load definitions on demand; OpenCode 2.x exposes MCP tools through its own code mode by default, Goose when switched on, Codex in source only. The clients that still load every definition are claude.ai and Desktop (the unit is the connector), ChatGPT, Antigravity, the retiring VS Code Local harness past 128 tools, and Claude Code in the configurations that keep tool search off (the HIPAA configuration, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`, a gateway that rejects it, Azure Foundry, models before Opus 4 and Haiku 4.5).
- **Anthropic's own code mode cannot reach MCP tools**, Claude Code has none, and claude.ai and Cowork cap a connector at 256 tools in two open, unanswered reports. Pagination is unsafe: claude.ai, Claude Desktop, Cursor and Gemini CLI read only the first page; Claude Code pages since 2.1.144; Codex fails past 2,048 items.
- **The MCP specification has no server-side tool search** in any revision or accepted proposal; every attempt (a `query` on `tools/list`, scope-filtered discovery, groups, server-side filters, `tools/manifest`) was closed and sent to a working group that is still exploring. The 2026-07-28 revision forbids a tool list that changes per connection or as a side effect of a call, which ends the "enable toolset" pattern (Apify and GitHub both removed theirs in 2026). The spec's own advice to hosts is a `search_tools` meta-tool or a single stable `call_tool`; its working group's note on the limits of tool search warns that a per-server search-plus-execute pair makes the real call a weakly typed executor the model provider cannot validate and "is unlikely to scale well if implemented per server".
- **Cloudflare ships code mode both in the agent and in the server**, the latter "when the client cannot be assumed to have a sandbox", with an opt-out so a code-mode client is not wrapped twice; its MCP portals made code mode opt-in in July 2026 and refuse upstream servers that run their own. Its SDK for it is experimental and being replaced; Dynamic Workers are billed, Paid-only, and used by Cloudflare's own production MCP server. Executor, OpenCode and Goose run model code in a restricted interpreter instead, with no isolate at all.
- **Every data gateway converged on meta-tools**: treg (10 tools over 4,021 endpoints, with a six-tool read/write-split surface for the Claude directory), Monid (13 fixed tools over about 2,900 endpoints), DataForSEO (four tools since August 2026, replacing about ninety), Apify, Firecrawl, Context7, Composio. Anthropic's directory rules reject a catch-all tool with a `method` parameter and require a read/write split with `readOnlyHint`, which "determine auto-permissions in Claude". The one published head-to-head (Stainless, March 2026, one API, a model as judge) scored meta-tool discovery 70% complete against 90 to 98% for three code modes.
- **Skills live in git and are pulled by the harness.** The format is settled (Agent Skills), every vendor has a server-held org layer that is vendor-locked, Skills over MCP (SEP-2640, a Specification Enhancement Proposal, Final since 2026-09-13) is consumed live by no mainstream harness (ChatGPT snapshots at submission; Claude Code carries a client behind a disabled gate), models prefer calling a tool to loading a skill unless the server's instructions point at it, and the only shipped "agent proposes a skill" flows land as pull requests. Executor never built runtime-evolved skills: its workspace store died unmerged and its v2 keeps skills as files in an app's source. The data gateways people love ship a `SKILL.md` and a CLI, and users make workflows repeatable with skills in git.

## 4. Question 1: a code-mode surface on `/mcp`, or search and lazy loading?

### 4.1 The confusion, resolved

"Implement code mode in the harness, not the MCP server" is advice the harnesses are following: OpenCode 2.x (by default), Goose (when switched on) and Codex (in source, not yet exposed) run the model's code against MCP tools themselves, and Claude Code, Codex, Cursor and the new default VS Code harness defer tool schemas so a long list costs names, not definitions. Cloudflare's own position moved from "in the agent" (2025-09) to "in the server too, when the client cannot be assumed to have a sandbox" (2026-02), and it ships both with an escape hatch (`?codemode=false`) so a code-mode client is not wrapped twice. Anthropic's harness-side code mode (programmatic tool calling) cannot reach MCP tools, and Claude Code has none, so a Claude user gets code mode against Every App's tools only if the Gateway provides it. The question is therefore not "harness or server" but three questions: which clients still need the server's help with a long list; what is the cheapest help that keeps the invariants; and is there a problem that only code execution solves.

### 4.2 Who still needs help, and with what

| Client | What 187 listed tools do today | What would help |
| --- | --- | --- |
| Claude Code (default) | Names and instructions only; schemas on demand | Self-describing names (`<app>_<tool>` already), instructions under its default 4,096-character cut, built-ins marked `anthropic/alwaysLoad` |
| Claude Code with tool search off (HIPAA configuration, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`, a rejecting gateway, Azure Foundry, pre-4.5 models) | Every definition loads | A smaller list: a compact surface |
| Codex | Tool search always on where the model supports it; otherwise every definition loads; a 2,048-item catalog cap; no prompts | Nothing beyond names; keep the first 512 characters of instructions self-contained |
| OpenCode 2.x; Goose with code mode on | Their own code mode over the list | Nothing; a Gateway code mode would be a sandbox inside theirs |
| Cursor; VS Code's default Copilot harness on supported models | Lazy loading and search; Cursor has a per-model cap and no 2026-07-28 | Keep the 2025 eras served (done) |
| claude.ai, Claude Desktop | Every tool of the connector loads, every turn; the person narrows at consent ("Only these apps") or unticks tools by hand; a 256-tool connector cap is reported | A smaller list: a compact surface |
| ChatGPT | Everything loads; manual confirmation on every write; no `readOnlyHint` means write | A smaller list; `readOnlyHint` on every read (done) |
| VS Code's retiring Local harness, and either harness on unsupported models; Goose with code mode off | Refuses past 128 tools unless experimental virtual tools are on; loads everything | A compact surface, or the person switches harness or mode |
| Antigravity; the legacy Cascade agent | Warns past 50, refuses near 100 (reported); Cascade documents a hard limit of 100 | A compact surface |

A gateway-wide `everyapp_search_tools` alone changes none of these rows: Claude Code and Codex already search, and the clients that load everything would still load everything. Search is the discovery half of a compact surface, not a fix by itself. Pagination makes every row worse (Appendix A.2). Per-session "enable app X" tools are forbidden on 2026-07-28 and were removed by Apify and GitHub in 2026.

**A second problem deferral does not touch.** The live complaint about the data providers is response size, not tool count (DataForSEO's open issue; Claude Code spills results over 50,000 characters to a file; claude.ai caps a result at about 150,000 characters). Multi-step workflows also pay a round trip per call. For Claude users the only lever on either is gateway-side code: the model's program filters results before they reach it and chains calls without returning. Anthropic measured 37% fewer tokens on complex research tasks with programmatic tool calling. The Gateway already records `result_bytes` per call, so whether this problem exists for Every App's apps is a query, not a guess.

### 4.3 The options

**A. Full listing, edges fixed.** Keep one page of `<app>_<tool>` entries (the 100-per-app cap and consent's app choice bound it) and fix four things the evidence surfaced: (1) the Gateway's combined instructions may reach 8 KiB but Claude Code's default cut for server instructions is 4,096 characters (since 2.1.296; 2,048 before, so an older Claude Code shows half; overridable with `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`) and Codex reads the first 512 as self-contained; today `view.ts` never clips the header, the app list or the "not available" lines, which grow with the app count, and drops each later app's guidance whole once the 8 KiB total is reached. Keep the 8 KiB (clients that show more, claude.ai and Cursor, lose nothing) and guarantee the part that matters: a test that the header, the app list and the "not available" lines together stay under 4,096 characters, so the app list is never what Claude Code cuts, and a sentence in `mcp.md` that an app's own guidance may fall past Claude Code's default cut and Codex's 512 (today's five apps total about 1,500 characters, so nothing is cut yet); (2) mark the built-ins `_meta: { "anthropic/alwaysLoad": true }` so Claude Code always sees `everyapp_list_apps` and `everyapp_whoami` without a search (the SDK's `Tool` type carries `_meta`; other clients ignore it); (3) hold `subscriptions/listen` longer than ten minutes on the surface that rechecks its caller (section 8); and (4) one line of guidance for app authors in the skill: Claude Code's search reads only the part of a description within its limit, so "put the words Claude would search for near the start". Nothing else changes; every invariant stands. **Effort: half a day** (`view.ts`, `builtins.ts`, `http.ts`, their tests, two paragraphs in `mcp.md` and the skill).

**B. A compact surface, opt-in per connection.** Beside the built-ins, three tools: `everyapp_search_tools({ query, app?, limit? })` returning compact descriptors (name, app, description, risk, input schema) from the caller's policy-filtered view; `everyapp_call_read({ name, arguments })` and `everyapp_call_write({ name, arguments })`, which resolve `name` and run the inner call through `executeToolCall` with a fresh per-call identity whose `tc.name` is the inner tool and one audit row naming the inner tool plus a `via` column. The read/write split is what Anthropic's directory rules require and treg's lesson for the Claude directory: one generic `call` loses the safety annotation clients key their confirmations on; two keep it. Three ToolBus changes make the security story true rather than assumed, because built-ins are listed and run before the policy check today: (1) a risk ceiling passed into `executeToolCall` per wrapper, so `everyapp_call_read` resolves only `risk: "read"` tools and mints `mcp:read` only, `everyapp_call_write` resolves read and write tools with the principal's own scopes and is hidden from read-only connections like any write tool, and destructive stays `Unknown tool` through either; the wrapper's own built-in audit is suppressed so each inner call leaves exactly one row, with `via` set; (2) built-ins gain arguments, which means the built-in branch of `executeToolCall` moves behind the shape checks (`measureJson`: depth 64, 1,000 values), `argumentsValidator` gets a key for built-ins, the built-in audit event gets an `argsDigest` as `audit.one-row-per-call-no-arguments` requires, and `listBuiltinTools(view)` and the branch gain a risk gate; (3) the compact list is a new state the register must name: in compact mode an app tool is absent from `tools/list` yet callable by name, directly or through a wrapper (unlisted is not hidden; a policy-hidden tool still answers `Unknown tool`), so B amends `toolbus.hidden-equals-unknown` and `mcp.md`'s "hidden means nothing about the tool leaks" to distinguish the two, and rewrites `toolbus.builtins-readonly-reserved` (a write wrapper is a write built-in). B amends two invariants and adds none. The surface is chosen on the consent page for OAuth connections ("Compact tool list, for clients that load every tool"), and by a header or `?tools=compact` for personal tokens and Access callers (the path stays `/mcp`, so `mcp.one-protected-resource` and the Access bypass hold; OAuth clients cannot take the query form because claude.ai requires the protected-resource metadata's `resource` to equal the URL the person typed; GitHub's remote server selects surfaces the same two ways, `/readonly` and `/x/{toolset}` paths or `X-MCP-Toolsets` headers); never by default, since Claude Code and Codex are better off with the full list, where their own search works on names. Precedents: Cloudflare's portal `optimize_context=search_and_execute`, treg `/mcp/v2/`, DataForSEO v3, Monid, Apify. What it costs the client side: the model provider can validate only the generic wrapper's schema (the working group's point; the ToolBus still validates every inner call against the snapshotted schema before it reaches an app); per-tool toggles and Team/Enterprise per-tool permissions in claude.ai see three tools instead of 187; Claude Code's per-tool allow rules and its own `ToolSearch` lose the names (an organization-managed "ask" prompt there is per tool name and cannot be remembered, so one wrapper's prompt would cover every inner tool, and "when Claude Code loads a settings file, it skips any `mcp__` rule that has parentheses", so an organization could no longer allow `openseo_*` and deny `crm_delete_*` once calls go through a wrapper); and the Stainless evaluation says the shape may cost completeness, which is why B is measured first (4.4). What it touches: the consent decision schema (`src/schemas/consent-decision.ts`), `mcp-auth/authorize.ts` (the choice written to the connection), a column on `mcp_connections` with its migration, `validate.ts` (the flag into `McpPrincipal`), the consent form and route, `McpConnectionService.ts`, the ToolBus's types, view, built-ins and execute path, the docs and the register. **Effort: three to four agent-days of code plus docs, plus one to two days of live tests against claude.ai and ChatGPT on both protocol eras, plus the held review: about a week.** It changes consent and the ToolBus's policy path, so it is a held PR.

**C. Code mode: `everyapp_execute({ code })`.** The design the evidence supports, if it is ever built. *What it is.* The Gateway never runs model code in its own isolate as JavaScript (Workers forbid `eval` and `new Function`, and an escape there reaches `JWT_PRIVATE_KEY`, `BETTER_AUTH_SECRET`, `CF_DEPLOY_TOKEN` and D1, the operator boundary); it runs it either as **C1**, a Dynamic Worker loaded per execution by a thin runner Worker that holds nothing but a service binding to a ToolBus entrypoint, with `globalOutbound: null`, a minimal compatibility-flag set (no `nodejs_compat`: the published escape went through `node:zlib`), an `env` holding exactly one stub minted with `ctx.exports` props carrying the execution id and a principal snapshot (unforgeable, host-only, no bearer inside the sandbox), `limits: { cpuMs, subRequests }` set explicitly (inner calls over the stub count as the sandbox's subrequests in workerd, so `subRequests` is the hard ceiling on fan-out, unverified against the documentation and to be pinned by a test), a wall-clock abort, and results truncated to a few thousand tokens as Cloudflare does; or as **C2**, a restricted interpreter inside the Gateway isolate, the shape Executor v2, OpenCode and Goose actually ship (`@opencode-ai/codemode` is "a lightweight, pure interpreter for a JavaScript-like language built around calling tools", with no network, filesystem, host globals or imports by construction, limits on time, tool calls and output bytes, and cooperative cancellation). Either way each inner call is an ordinary `executeToolCall` (fresh `tc.id`, same `act.sub`, scopes recomputed by the ToolBus, never widened) plus an execution id for the audit join, which is also what the spec's client best-practices page demands ("approving the script does not grant blanket approval for every tool call it makes at runtime"); v1 resolves only `read` tools from code (the write path is where injected results become arguments with nobody in between, the "toxic agent flow"; and a single `execute` that could write is exactly the catch-all Anthropic's directory criteria reject); budgets on inner calls, wall time, bytes per result and output returned; one `mcp_tool_calls` row per inner call and one execution row with counts, never the code, arguments, results or console output; no Tail Worker on sandboxes; a compact or plain mode for harnesses that already do code mode; `search` returns signatures, because 187 tools' input schemas are about 237 KB and no tool description can carry a generated TypeScript API. *What each variant bounds.* The runner and the props-bound stub bound what the code can reach by capability (Cloudflare documents stubs as unforgeable and props as host-only); a memory-safety escape from a V8 isolate is bounded only by Cloudflare's process cordons, which the operator does not choose, and what the runner buys is that such an escape lands in a Worker whose `env` holds no secret and no database. C2 has no isolate boundary to lose and no path to `env` short of an interpreter fault, which is code in the isolate that holds the signing key; its CPU counts against the `/mcp` request, a hot loop ends with the Worker's CPU limit, and its language is not JavaScript. *The register.* Nine new invariants (`code.sandbox-is-dynamic-worker` or `code.interpreter-has-no-host-reach`, `code.sandbox-no-nodejs-compat`, `code.stub-bound-to-execution`, `code.inner-call-is-a-tools-call`, `code.no-write-from-code`, `code.budgets`, `code.audit-per-inner-call-and-execution`, `code.loader-holds-no-gateway-secrets`, `code.sandbox-logs-never-persisted`), a new section in the threat model, and the explicit relaxation of the three rows that forbid fan-out (`tools.request-shape-limits`, `toolbus.one-identity-per-call`, `toolbus.http-bounds-and-origin`: the outer call fans out; each inner call still makes exactly one app invocation). *What the operator inherits with C1.* A Cloudflare primitive with an open-beta label on its March post and no general-availability post, billed since 2026-05-26 by its pricing page (the March changelog still says "not yet active"), Paid-only (Every App already requires Workers Paid), used by Cloudflare's own production MCP server and its portals; at most 4 concurrent executions per request context; $0.002 per execution-day past 1,000 a month (every execution is a new unique Worker because dynamic isolates disallow `eval`: fifty thousand executions a month is about $98 plus CPU); an isolate boundary Cloudflare itself rates weaker than a hypervisor's ("security bugs in V8 are more common than security bugs in typical hypervisors", in the post that explains the defence in depth Dynamic Workers get on managed Workers); and the lesson of Check Point's 2026 chain (five workerd memory-safety bugs, two rated Critical, from prompt injection through code-mode-generated TypeScript to a `node:zlib` use-after-free; the full escape demonstrated on self-hosted workerd with the V8 sandbox off; Cloudflare confirmed the bugs reproduce on production with one exception and patched both; no CVEs assigned), which on managed Workers is about the sandbox's flag set and for `everyapp dev` on local workerd is a version pin with no advisory feed. *What the repository needs.* The binding is a config line (`@cloudflare/config` 0.24.1 has `bindings.workerLoader()` and the CLI's build patch passes it through); `enable_ctx_exports` is not set today; the audit table needs a parent-call column; the gateway and ToolBus suites run in Node with no workerd pool (a new harness for C1, none for C2); `everyapp dev` cannot exercise either (built-ins exist only on the gateway surface). *What it buys and does not.* For claude.ai and ChatGPT users, one tool instead of 187 and results filtered before they reach the model; for every user, multi-call workflows without a round trip per call (Anthropic's 37%); nothing for Claude Code's tool count, or for OpenCode, which would wrap it by default unless the opt-in mode above is used. **Effort: four to seven agent-days of code by the file-level estimate for C1 (config, loopback entrypoint and executor, built-ins and generated signatures, audit column, a workerd test harness, docs and invariants), perhaps half of it for C2, plus the threat-model section, an adversarial review and live tests against four clients: about two weeks**; not a launch-week item under any rule.

### 4.4 Recommendation

**A now, B first after launch once measured, C on triggers.** A is a half-day PR with no boundary change (section 6). B is the right shape for the clients that load everything, costs a week not two, amends two invariants and adds none once the three ToolBus changes above are made, and is what every data gateway in Appendix A.5 converged on. C is not justified today on the definitions problem: that is solved client-side for the harnesses Ben's users run, the clients it would help are served by B at a fraction of the risk, and its security cost is a new boundary the threat model must carry. C is justified only by the second problem, results and round trips, which B does not touch and which no harness solves for MCP tools; whether Every App's apps have that problem is measurable.

**The triggers.** Build B when the `client_info` column (section 6) shows claude.ai, ChatGPT, Antigravity or tool-search-off Claude Code callers for an organization, or when an organization's list nears claude.ai's reported 256-tool connector cap; and before building it, run fifteen to twenty real tasks against the everyapp.team Gateway with the `claude -p` harness in `packages/cli/test/setup-skills` in three configurations (the full list, a compact search-plus-call surface, an `execute` tool) and record completion, tokens and wall time; Stainless's number (meta-tools 70% complete against 90 to 98% for code modes, on one API, judged by a model) is the only external figure and it argues against B's shape. Reopen C when B has shipped and Admin → Activity shows repeated multi-call sequences B does not collapse, or `result_bytes` shows results the clients' caps truncate, and the same measurement shows code mode recovering completeness that B loses; C2 needs no Cloudflare milestone, C1 waits for Dynamic Workers' general availability. If C is ever built it is gateway-side, read-only first, with the invariants above; "in the harness" is not an option Every App can choose for Claude users.

For the sibling thread's provider apps: list in full within the per-app cap and let the operator curate; do not collapse an app behind its own meta-tools (the compact surface, if built, is global and opt-in, which is also what the working group's note asks for); a proxied upstream that is itself a meta-tool server (treg's 10, Monid's 13, DataForSEO v3's four) is already compact. Watch one number: claude.ai's reported 256-tool connector cap is 66 tools away for an organization running the launch apps, 49 once the DataForSEO provider app (#489) is on.

## 5. Question 2: skills on the Gateway?

### 5.1 What the market settled while we were not looking

The format is settled (Agent Skills, `SKILL.md`), the distribution is git plus install CLIs, and every vendor has nonetheless built a server-held, per-organization layer on top: claude.ai's Plugins & skills admin (Required, Installed by default, review, usage counts), Cursor's team marketplace, ChatGPT workspace skills, Amp's hosted repositories, Devin's org-scope plugins, PostHog's skills store, and since 0.164.0 Codex's cloud-synced plugins. All of them are vendor-locked and pull-based into the harness's own directories; none reads a third party's server live. Skills over MCP is standardized (SEP-2640, Final) and consumed live by no mainstream harness (ChatGPT snapshots at most five at submission; Claude Code carries the client behind a gate compiled to false); the working group's own experiments found that models "frequently ignore available skills" and prefer calling a tool unless the server's instructions point at the skill. "Suggested from usage" is shipped only as pull requests a person merges (Devin, Claude Tag); Claude Code's `/insights`, `/usage` and `/skill-doctor` suggest hygiene, never a new shared skill. Executor, the product Ben named, never built runtime-evolved skills: its workspace store died unmerged and its v2 keeps skills as files in an app's source. And the data gateways people love "just for the data" (treg, Monid, DataForSEO v3) each ship a `SKILL.md` and a CLI, and users make workflows repeatable with skills in git (`claude-seo`, 19,924 stars), not with anything server-held.

**The fact that frames it for Every App: the apps already have skills, and the Gateway is not how they travel.** The hosted OpenSEO ships twelve skills beside its MCP server (`seo-audit`, `keyword-research`, `competitor-analysis`, `ai-visibility-audit`, `seo-report` and the rest), and they are installable today from its public repository's marketplace in Claude Code, Codex and Cursor formats. Through the Gateway those skills need four things the repository channel cannot give: the connector's URL and tool names (every one of the twelve names tools bare, `list_projects`, `get_domain_overview`, 36 such references, where the connector serves `openseo_list_projects`), delivery to members of an organization whose app was installed from a release tarball with no repository on anyone's machine, version coupling with the catalog the Gateway actually serves, and the member's app access (a person who cannot open the app should not get its skills). The SEP-2640 motivation is the same: "a server and the skill that teaches an agent to use it are versioned, discovered, and installed separately"; the fix is to keep them together.

### 5.2 The options

**S1. Just the data.** Keep today's two skills (the everyapp skill for app authors, the connect-ai page for people). Nothing to build. This is where launch stands.

**S2. Package the connector the way the gateways do.** One public "every-app" plugin and marketplace repository: an `.mcp.json` whose server `url` is `${user_config.gateway_url}/mcp` (Claude Code's `userConfig` substitution; a single public plugin cannot name a per-organization Gateway otherwise), plus one user-facing skill ("working with your Every App tools": `everyapp_list_apps` first, read-only versus read & write, what costs money, that scheduled tasks need the remote connector); installable with `/plugin marketplace add` and `npx skills add`, markable Required by a claude.ai admin or Claude Code managed settings (on claude.ai the admin adds the custom connector separately; a plugin's bundled connector is not added by availability). Docs and a repository, about a day; the first thing treg, Monid and DataForSEO did. S3's per-gateway marketplace supersedes the URL prompt.

**S3. Apps ship skills beside their tools, and the Gateway is the per-organization channel.** `defineTools(tools, { instructions, skills })` (or a `skills/` directory the SDK reads), **markdown only**: `SKILL.md` and markdown references; the SDK refuses `scripts/`, `allowed-tools`, `hooks` and `bin/`, because a skill with code or a tool grant is a new kind of authority reaching members' machines and this one is not. Skill bodies name tools as the Gateway lists them, `<app>_<tool>`, or the SDK rewrites backticked bare names at snapshot time (and the app-host `/mcp` serves them unprefixed); a drift test checks every tool name in a shipped skill against the app's catalog, because that is exactly how `claude-seo` broke when DataForSEO renamed its tools. Snapshotted into D1 with the catalog, policy-filtered like tools, capped per app (say eight, with a catalog warning like the 100-tool cap) because Claude Code's skill listing has a 1%-of-context budget and drops descriptions when it overflows, and served three ways as clients mature: as an `everyapp_get_skill` built-in whose description carries the catalog (works in every tool-capable client today, PostHog's pattern; the 4,096-character instructions cap leaves no room for a names index there); as a per-organization `marketplace.json` over HTTPS with `archive` plugin sources, one plugin per app, installed opt-in, behind its own credential (a `skills:read` scope on personal tokens minted by a read-only built-in, PostHog's install-command pattern, or signed per-organization URLs), since a token-reachable route outside `/mcp` needs its own scope and register line; and as SEP-2640 (`skills/list`, `skills/get`, `skill://` resources, a new `resources` capability) once the ToolBus moves to `@modelcontextprotocol/server` 2.4.0, for the clients that will consume it; Cloudflare's own aggregating server has served its skills that way since 2026-10-10, ahead of client support. `everyapp skills pull` writes them to `.agents/skills` and `.claude/skills` for everything else. Register lines: `skills.markdown-only`, `skills.policy-filtered-like-tools`, `skills.scope-read-only`. This is Executor v2's model and the MCP working group's. About three to five agent-days across SDK, catalog sync, a built-in, an endpoint and the CLI.

**S4. A per-organization skills store people author on the Gateway** (PostHog's shape): a D1 table, `everyapp_save_skill` and friends as write tools, versions, an Admin page, and usage-mined suggestions from `mcp_tool_calls`. Five to eight days, a new write surface for agents, and a decision about who may publish. The suggestion half has thin data: audit rows hold tool names, credential ids, timestamps and a keyed arguments digest, so recurring identical calls (same digest, weekly) and repeated per-connection sequences are detectable, which is a report an admin can read, not a skill the Gateway can write; the signal could be captured without storing arguments the way PostHog's MCP analytics does (a stripped `intent` argument on every tool, and a `get_more_tools` virtual tool agents call when "the available tools cannot complete a task"), but model-authored intent text is still text the audit rule keeps out of the table today, so that is a decision, not a free addition.

### 5.3 Recommendation

**S1 for launch; S2 right after, as docs; S3 as the direction, started when an app needs it; not S4.** "Just provide the data" is right for the person, and the harnesses own the person's skills. What Every App uniquely holds is the organization's apps, so the skill that belongs on the Gateway is the one an app ships with its tools, delivered only to members who can use the app, in the format every harness reads and over the channels they already pull from. Demand for an organization-held skills layer is demonstrated, six vendors shipped one within a year; the reason not to hold a third copy is redundancy: a single-harness team already has one from its vendor, and a mixed-harness team uses git, which reaches every harness. S4 is reconsidered if mixed-harness organizations on Every App ask for a shared catalog that git does not give them; it would then be S3's table with a write tool, not a separate system. "Suggested from usage" waits for a signal worth suggesting from, and the cheap instrument that tells us whether one exists (repeated sequences and repeated identical calls on Admin → Activity) is on the after-launch list in section 7.

## 8. Found on the way

**The ten-minute `subscriptions/listen` cap spends Claude Code's reopen budget.** `packages/toolbus/src/http.ts` ends every held stream gracefully after `LISTEN_MAX_MS` (10 minutes) and expects the client to open a new one (TODO.md, "Tool list changes (2026-10-19)", lists the cap as a value to decide). Claude Code's MCP documentation, read 2026-10-24: "The stream stays open longer than 10 seconds, then closes, as streams to serverless hosts commonly do: after five reopens in an hour, Claude Code waits about six hours before the next one", and "Until the stream reopens, you keep the server's last fetched tools, prompts, and resources." By that rule a ten-minute cap, six graceful completions an hour, stops reopens after about fifty minutes of a session unless a graceful completion is exempt, which the page does not say; a deploy, an isolate reset or a dropped connection spends the same budget, and a stream that closes within ten seconds three times stops reopens for the connection. The fix is PR 1 item 3: a longer hold on the gateway surface, which rechecks its caller every poll, the app-host window unchanged because it rechecks nothing, and a test that counts reopens before the constant moves. Not built here: it is a ToolBus change and this thread builds nothing without Ben's yes.

## Appendix A. The landscape, verified

Every claim below was fetched from its source on 2026-10-23/24; the URLs are in section 10. "Today" means that date. SEP is a Specification Enhancement Proposal of the MCP project; CIMD is Client ID Metadata Documents and DCR Dynamic Client Registration, the two ways an MCP client identifies itself to an OAuth server.

### A.1 Code mode as Cloudflare and Anthropic describe it

**The argument.** Cloudflare's "Code Mode: the better way to use MCP" (Varda and Pai, 2025-09-26) says LLMs are better at writing code against a TypeScript API than at emitting tool calls, and that agents handle many more, and more complex, tools that way. In that post code mode lives in the agent: the Agents SDK fetches each MCP server's schema, converts it to TypeScript, and runs the model's code in an isolate whose only bindings are the connected MCP servers, with "the agent supervisor, which holds the access tokens" in between. It says nothing about an `execute` tool inside an MCP server. Anthropic's "Code execution with MCP" (2025-11-04) makes the same argument with a worked example (150,000 tokens of tool definitions and intermediate results down to 2,000), names two ways to keep definitions out of context (a file tree of tool files the agent reads on demand, or "a `search_tools` tool added to the server"), filters intermediate results inside the execution environment, notes that saved code plus a SKILL.md "creates a structured skill", and warns that running agent-written code "requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring". It does not say whether the sandbox belongs to the client or the server.

**Where it ended up: both places, by who has a sandbox.** Cloudflare's follow-up "Code Mode: give agents an entire API in 1,000 tokens" (2026-02-20) weighs the two explicitly: client-side "requires the agent to ship with secure sandbox access", server-side needs "no modifications needed on the agent side". Its server, `mcp.cloudflare.com/mcp`, applies code mode server-side with two tools, `search` and `execute`: 2,594 endpoints that would cost 1.17 million tokens as native tool schemas cost about 1,100; results are capped at about 6,000 estimated tokens; and the server offers `?codemode=false` so a client that already does code mode is not double-wrapped. Cloudflare deprecated its per-product MCP servers in favour of that one. MCP Server Portals (Cloudflare One) do the same for an aggregator of many MCP servers, which is the Gateway's shape: `portal_codemode_search` and `portal_codemode_execute` run JavaScript in a Dynamic Worker; Cloudflare's April 2026 post measured four internal servers with 52 tools (about 9,400 tokens of definitions) collapsing to two tools at about 600, "and the cost does not grow with more servers". It shipped on by default in March and became a policy on 2026-07-30 (Off, Opt-in, On by default, Enforced; **new portals default to Opt-in**; On by default lets a client opt out with `?codemode=off`, "which avoids nested code execution when a client runs its own Code Mode implementation"), and portals "do not support upstream MCP servers that have their own Code Mode turned on". The same portals offer the non-code alternatives the Gateway could copy: per-portal tool enable/disable and aliases, `optimize_context=minimize_tools` (names only), and `optimize_context=search_and_execute` (every upstream tool hidden, `portal_query_tools` and `portal_execute` exposed, no code run).

**The SDK is moving under its users.** `@cloudflare/codemode` 0.5.5 (published 2026-10-20) is labelled experimental: "may introduce breaking changes. Use caution in production." Cloudflare's Think harness docs (2026-10-20) go further: its execute tool "keeps working until it is removed along with `@cloudflare/codemode`"; the replacement is `@cloudflare/computer`'s `WorkerJavaScriptBackend` (0.7.0, 2026-10-23), which also runs in a Dynamic Worker but sets `limits: { cpuMs }`, a 180-second maximum timeout, and hands tools to the sandbox as an importable module. The codemode package itself carries no deprecation notice yet. It offers `codeMcpServer()` (wraps an MCP server in one `code` tool whose description carries the generated types; "works well only when the generated type declarations fit comfortably in the code tool description"), `openApiMcpServer()` (`search` plus `execute` over an OpenAPI spec), and since 0.4.4 a runtime handle with `execute()`, `search()`, `describe()`, `approve()`, `reject()` for hosts without an AI-SDK adapter; the durable runtime is a Durable Object facet with approvals, replay, a 50-execution default cap and a 1,000,000-character cap per stored value. `DynamicWorkerExecutor` loads a fresh isolate per execution with `env.LOADER.load()`, `globalOutbound: null` by default (so `fetch()` and `connect()` throw), a 60-second in-sandbox timeout (a `Promise.race`, not a platform limit), no `limits.cpuMs` (a busy loop is not killed unless the host adds it), and tool calls dispatched back to the host over Workers RPC through a dispatcher passed as a call argument, so the sandbox needs no network to call tools. Cloudflare's own `execute` tool bakes the code into the module source because dynamic isolates disallow `eval`, uses a random Worker id per call, and routes outbound through a `WorkerEntrypoint` that injects the API token "so it never enters the user code isolate".

**Dynamic Workers.** Open beta for every Workers Paid account since 2026-03-24; no general-availability announcement as of 2026-10-23 and the pricing page no longer says beta. Billing since 2026-05-26: 1,000 unique Dynamic Workers a month included, then $0.002 per Dynamic Worker per day, plus normal request and CPU charges; a `load()` with unique code per execution is a new unique Worker each time. Limits: at most 4 distinct Dynamic Workers with in-flight requests per Worker request and 10 per Durable Object; per-invocation `limits: { cpuMs, subRequests }` (default: the plan's limits; exceeding one throws); no wall-clock timeout at the platform level; the general 128 MB per isolate. The `worker_loaders` binding "does not point at any external resource", so enabling it is a line in the Gateway's config, not a resource `everyapp setup` must provision. The Workers for Platforms documentation says nothing either way about a dispatch-namespace user Worker carrying the binding, which does not matter here: the Gateway is an ordinary Worker. The Sandbox SDK (`@cloudflare/sandbox` 1.0.3) runs Linux containers billed while alive; Cloudflare's own guidance sends "code that only needs to call methods that you define, such as a script against a known API" to Dynamic Workers, so containers are the wrong tool for a 30-second run against Gateway tools.

**Anthropic's side cannot reach us.** Programmatic Tool Calling on the Claude Developer Platform is generally available, but "tools provided by an MCP connector" cannot be called programmatically, and the code execution container has no internet access. Claude Code has no code mode of its own (nothing in its 9,483-line changelog or docs). So as of today, code that calls Every App's tools can run in exactly two places: the Gateway, or an agent a company builds itself on Cloudflare's Agents SDK (`McpConnector`, `createCodeTool`). No harness Ben's users run does it for them.

### A.2 What the harnesses do with large tool lists today

**Claude Code** (2.1.310, 2026-10-23). Tool search is on by default: every MCP tool is deferred, "only tool names and server instructions load at session start, so adding more MCP servers has minimal impact on your context window", and "Claude Code doesn't impose a fixed per-server tool cap". The model loads a schema on demand with `select:<name>` or a keyword query (five results by default). The deferral rides on the Claude API's `defer_loading` and `tool_reference` protocol (Claude Code still sends every definition on every request); the search itself is Claude Code's own `ToolSearch` tool, matching names and descriptions client-side, so the Gateway influences it only through names, descriptions and instructions. Knobs: `ENABLE_TOOL_SEARCH` (`true` by default; `auto` defers once definitions reach 10% of the context window; `false` loads everything), per-server `alwaysLoad`, and per-tool `_meta["anthropic/alwaysLoad"]` so a server can keep a few tools always visible. Server instructions and upfront descriptions are cut at 4,096 characters (since 2.1.296; 2,048 before, so a Claude Code older than two weeks shows the model half of that) and a deferred tool's description at 16,384 (since 2.1.295), both overridable with `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`; the docs say "server instructions help Claude understand when to search for your tools, similar to how skills work". Output: a warning at 10,000 tokens, `MAX_MCP_OUTPUT_TOKENS` 25,000 by default, results over 50,000 characters written to a file. Every tool loads upfront, with no way to defer, under the HIPAA configuration, under `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` (managed settings can override it since 2.1.227), behind a gateway that rejects the tool-search request shape (retried without it since 2.1.305), on Azure Foundry, and on models before Opus 4, Sonnet 4 and Haiku 4.5. It supports MCP prompts as slash commands, resources, form and URL elicitation, tasks (public beta, 2.1.304+, terminal and SDK sessions only) and the 2026-07-28 revision with a held `subscriptions/listen` stream (see section 8 about its reopen limits).

**The Claude Developer Platform.** The Tool Search Tool (regex and BM25 variants, no beta header on its page) is Anthropic's answer to exactly the Gateway's case: "You aggregate multiple MCP servers (200+ tools)" is a listed trigger; "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools"; a five-server setup of about 55k tokens of definitions is cut "by over 85 percent"; the advice is to keep the three to five most used tools loaded, "prefix by service or resource so one search matches the whole group", and add a system-prompt line naming the categories. Measured in the 2025-11-24 post: Opus 4 from 49% to 74% on MCP evals with tool search; Programmatic Tool Calling cut tokens 37% on complex research tasks. The Messages API MCP connector (beta) supports tool calls only and sets `defer_loading` per server.

**claude.ai and Claude Desktop.** The unit is the connector, not the tool. A per-conversation "Tool access" mode (Auto, Always available, On demand; On demand recommended at ten or more connectors) decides whether a connector is loaded at all; inside one connector every tool loads, and the "search" the support article describes for On demand mode is over connectors, not over the tools inside one. A user can untick tools by hand per conversation; Team and Enterprise owners can set per-tool permissions org-wide. Limits: about 150,000 characters per result, 240 seconds per call, 64-character tool names for directory review; the hosted client supports tools, prompts and resources but not subscriptions or sampling. A cap of exactly 256 tools per connector is reported twice and unanswered: claude-ai-mcp #587 (2026-07-09, "Cowork silently caps a connector's tools at exactly 256, tools past the cap are dropped with no warning (same endpoint loads all ~630 tools in Claude Code)") and claude-code #77704 (2026-07-15, "this is still happening" on 2026-10-07); no official document states a cap. **This is the client where Every App's list costs the most**: all 187 tools, about 59,000 tokens of definitions, every turn, and 69 tools short of the reported cap before any provider app. Nobody has measured it on the real connector; that is the first follow-up in section 7. (The legacy Windsurf Cascade agent, now under Devin, documents a hard "limit of 100 total tools"; its replacement, the Devin Local agent, was not checked.)

**Pagination is dropped on the floor by the hosted clients.** Claude Code has followed `nextCursor` since 2.1.144 (2026-05-18: "Fixed MCP servers with paginated `tools/list` responses only returning the first page, silently dropping tools"; a repeated-cursor guard followed in 2.1.295). claude.ai's web client does not (claude-ai-mcp #87, open since 2026-03-09), nor does Claude Desktop (#66537, closed "not planned" 2026-06-12). Cursor staff confirmed first-page-only on 2026-07-09 ("have the server return all tools in one response") with "no firm timeframe" on 2026-09-02; Gemini CLI has the same open issue (2026-10-19); Codex walks pages but fails outright past 2,048 catalog items or 100 pages. The SDK's own client aggregates pages, so a cursor would only split responses for the clients that handle it and hide apps from the ones that don't. One page it stays.

**The other harnesses.** Several have deferral or code mode of their own, and that changes the "harness or server" question: **Codex** turned tool search on by default for MCP tools in 0.142.2 (2026-06-25; the flag is now a no-op because it is always on where the model and provider support it, and every definition loads where they do not) and carries a JavaScript code mode in its source (added 2026-03-10, "ranked tool discovery" 2026-10-06) that is staged "under development", off, and not shown even in its experimental menu; it does not support MCP prompts at all (open since 2025-10-10), nor the 2026-07-28 revision end to end, and it reads only the first 512 characters of server instructions as self-contained. **OpenCode 2.x** exposes MCP tools through a default code mode grouped by server, with a per-server `codemode: false` opt-out (1.x has it as an experimental environment flag), and keeps a defaults plugin that turns its own code mode off for servers that are themselves code mode (executor.sh) and forces PostHog's MCP into plain "tools" mode with a header: double code mode is a real composition problem harnesses patch by hand. **Goose** shipped code mode in v1.17.0 (2025-12-15): `list_functions`, `get_function_details`, `execute_javascript` in a Boa sandbox, "tools from enabled extensions are discovered on-demand", text results only; but it is off by default (`default_enabled: false`; "Toggle Code Mode on"), and with it off every extension's tool definitions go in every call; it prefers 2026-07-28 but never opens `subscriptions/listen` (open issue). **Cursor** once sent only the first 40 tools; today the limit is "a per-model provider cap", the IDE and (since 2026-09-09) the CLI load tool definitions only when needed, it supports prompts, resources, elicitation and apps, and 2026-07-28 has "no timeline", so the legacy `initialize` path must stay. **VS Code and Copilot** changed on 2026-10-22, while this was being written: the documented hard limit, "a chat request can have a maximum of 128 tools enabled at a time", and the experimental "virtual tools" that hide the overflow are described on the tools page of the Local harness, and VS Code 1.143 made the Copilot harness the default for new sessions ("these controls are temporary while Local is retired"); that harness is the Copilot CLI engine, whose tool search is on by default on Claude 4 and later and GPT 5.4 and later ("below roughly 30 tools, the savings you get from tool search aren't worth it"; other models load every tool), and VS Code has deferred tool definitions and run a local embedding search since June 2026 ("upfront, the model sees only lightweight metadata, the name and description of each deferred tool"). Whether the 128 cap still applies in the Copilot harness on an unsupported model is not stated on either page. GitHub measured that the full built-in toolset cost 2 to 5 points on SWE-bench-style benchmarks and that embedding-based selection reached 94.5% coverage against 69% for a static list. **Gemini CLI** has no lazy loading or limit, was replaced by the closed Antigravity CLI for consumer tiers on 2026-06-18, and Antigravity warns above 50 tools and refuses around 100 (user reports; the request to raise it was closed without a fix). **ChatGPT** documents no tool limit, requires manual confirmation before write actions, treats a tool without `readOnlyHint` as a write, keeps the first 512 characters of instructions, and implements Skills over MCP only as a submission-time snapshot of at most five skills. A 2025 paper (RAG-MCP) measured retrieval-based tool selection at 43% accuracy against 14% for a flat list as tools grow.

**Put together.** With today's 187 listed tools: Claude Code, Codex, Cursor, VS Code's new default harness and OpenCode 2.x cope on their own on the models they support (deferral, search or code mode), Goose only once code mode is switched on; claude.ai and Desktop, ChatGPT, Antigravity, VS Code's retiring Local harness (over its cap), and Claude Code in the configurations that keep tool search off load everything or refuse. Every harness now reads the Agent Skills format from disk; none loads skills from an MCP server in a way the model uses.

### A.3 What the MCP specification offers

**The current revision is 2026-07-28** (the draft changelog is empty as of 2026-10-23). What it changed that matters here: no sessions and no `initialize` (`server/discover` is mandatory); `subscriptions/listen` replaces the GET stream; `ttlMs` and `cacheScope` are required on every list result; tools "SHOULD be returned in a deterministic order" for prompt-cache hits; list results "MUST NOT vary per-connection or as a side effect of other requests" but "MAY vary by the authorization presented on the request", which sanctions the Gateway's per-caller filtering (consent's apps, read-only hiding writes) and forbids the "toolsets" pattern where calling an enable tool makes tools appear (SEP-2567: "no longer permitted"); roots, sampling and logging are deprecated; tasks moved to an extension. `cacheScope: "private"` is what the spec wants for per-user lists, and it is what the ToolBus sends.

**There is no server-side tool search, grouping or lazy definition in any revision or accepted SEP**, and the Gateway's exact case has been proposed and parked repeatedly: SEP-1821 (a `query` on `tools/list`, closed 2026-06-24), SEP-1881 (scope-filtered discovery, closed), SEP-1300 and SEP-2084 (groups, rejected 2025-12-01 and 2026-02-05 because "the ecosystem around searching tools is quickly evolving and it's unclear what mechanism is the right one in the long run"), SEP-2564 (server-side filtering, motivated by gateways where "a single `tools/list` call can return hundreds of tools", closed 2026-09-22), SEP-1862 (`tools/resolve`) and SEP-2636 (`tools/manifest` plus `tools/describe`, names first and schemas on demand, closed 2026-09-22). All were redirected to the Progressive Disclosure Working Group (converted from an interest group on 2026-09-21, status "Active Exploration", hosting reference extensions for "grouping, tool-search, code-mode"), and the roadmap of 2026-08-22 commits a Core Primitives group to "progressive discovery" as an experimental server-side mechanism. Whatever the Gateway adds must be a tool, not a protocol extension, and replaceable when that lands.

**The spec's own advice is host-side**, from its client best-practices page: give the model a lightweight `search_tools` meta-tool, switch to it when definitions pass 1 to 5% of the context window, group tools by server, or "route every call through a single stable `call_tool({name, args})` meta-tool so the array never changes"; code mode is listed beside them; and "some model providers already offer built-in tool search ... when available, you may prefer the platform's tool search over a custom implementation". The Progressive Disclosure group's own note "The Limits of Tool Search" (2026-10-05) analyses the server-side `search_tools` plus `execute_tool` pair directly: the found tool "never becomes a native tool. Its schema is data returned by `search_tools`, while the actual native call is the weakly typed `execute_tool`. The model provider can validate only the generic executor's schema", and "the pattern also repeats per server ... unlikely to scale well if implemented per server". That is the known cost of any compact surface: schema validation moves from the model provider to the server (where the ToolBus already validates every call), and it must be done once at the aggregator, not per app. The only aggregator guidance is to prefix tool names with a server identifier (names 1 to 128 characters), which `<app>_<tool>` already does. The spec sets no budget for `instructions` (issue #2146 open); it says nothing for or against calling a tool absent from `tools/list` ("Unknown tool" on a hidden tool is the Gateway's own invariant, not a spec rule); its security best practices require a proxy to obtain per-client consent before forwarding, which the consent page does.

**`tools/list` takes only `cursor`** (schema 2026-07-28, `PaginatedRequestParams`), so a search query cannot ride on it. The installed `@modelcontextprotocol/server` 2.3.1 (2026-10-05) knows `tools/*`, `server/discover`, `subscriptions/listen`, `prompts/*`, `resources/*` (templates, subscribe), `tasks/*`, `elicitation/create`, `sampling`, `roots`, `completion`, `logging`; no `tools/search` or `skills/*` string exists in it; its own `McpServer` returns every enabled tool in one page and ignores `cursor`; its `RegisteredTool.enable()`/`disable()` are server-global and emit a global `list_changed`, so they cannot express a per-caller view. Version 2.4.0 (2026-10-23) adds the Skills extension under `ext/skills` and gateway-friendly `ServerEvent` params for forwarding change notifications.

**Prompts and resources.** Prompts are "user-controlled" templates "exposed from servers to clients with the intention of the user being able to explicitly select them", with arguments and completion; resources are "application-driven". Claude's connector client (claude.ai, Desktop, Code) supports tools, prompts and resources but "doesn't yet support" resource subscriptions, sampling or draft capabilities; Cursor lists prompts, resources, elicitation and roots as supported; Codex's and ChatGPT's documentation mention tools and server instructions only. The official per-client feature matrix was removed on 2026-05-27; only an extensions matrix (MCP Apps, Skills, auth) remains.

### A.4 Skills: the format, team sharing, runtime-created skills, skills over MCP

**The format is settled.** Agent Skills (agentskills.io; "originally developed by Anthropic, released as an open standard" on 2025-12-18) is a directory with a `SKILL.md` whose frontmatter has `name` (64 characters, lowercase, hyphens, must match the directory) and `description` (1,024 characters), plus optional files; harnesses load about 100 tokens of metadata per skill at startup and the body (under 5,000 tokens recommended) on activation. Claude Code, Codex, Letta, Vercel's `skills` CLI, PostHog and Executor all read it. Any Gateway store should hold this exact shape so a skill round-trips to every harness without translation.

**How a team shares skills today.** Files in git, pulled by the harness. Claude Code reads skills from the managed settings directory, `~/.claude/skills`, the project's `.claude/skills`, plugins (`<plugin>/skills/`), and, since 2.1.273 (about 2026-09-15), the skills enabled on the person's claude.ai account, synced one way into `~/.claude/skills/synced/` over a claude.ai REST endpoint (not MCP); it "downloads synced skills and never uploads them". Organizations distribute with claude.ai's Plugins & skills admin (Team and Enterprise: provision skills that appear for everyone; marketplaces synced from a GitHub or GitLab repository; each plugin Not available, Available, Installed by default or Required) or with Claude Code managed settings (`extraKnownMarketplaces` plus `enabledPlugins`, optional `autoUpdate`). A marketplace is a git repository or directory with `.claude-plugin/marketplace.json`; plugin sources are a path, `github`, a git `url`, `git-subdir`, `archive` (a zip over HTTPS, 2.1.224+, with optional auth headers), `npm` or `command`. Anthropic's recommended packaging for a product like the Gateway is a plugin: an `.mcp.json` pointing at the remote connector plus the skills that say when and how to use it; an org can mark it Required. A bare `marketplace.json` served over HTTPS is also a documented marketplace source (`url`, with `headers` and `headersHelper` for an authenticated fetch; its plugins must then use self-fetchable sources such as `archive`). Codex reads `.agents/skills`, `~/.agents/skills` and `/etc/codex/skills`, and since 0.164.0 (2026-10-23) also pulls plugins and "frozen cloud skill snapshots" from ChatGPT's server (workspace directory, shared-with-me), through "the universal plugin directory shared by ChatGPT and Codex"; Vercel's `npx skills add <owner/repo>` (2026-01-20; 36k stars) installs skills from git into each agent's directory and is the de-facto cross-harness distribution; skills.sh is a directory, not a store. Every listed skill costs Claude Code context on every turn (name, description and when-to-use, cut at 1,536 characters), which is why one umbrella skill per product beats one per app.

**Skills over MCP is standardized but not yet consumed.** SEP-2640, the Skills Extension, is Final (merged 2026-09-13): a server declares `io.modelcontextprotocol/skills`, answers `skills/list` and `skills/get`, and serves each file as a `skill://` resource with a sha256 digest; it is a read-only transport binding with no create or update method, and a skill is identified by URI, not name. The Claude Code 2.1.309 binary already contains `skills/list` and `skills/get` client calls and the extension's constant next to a gate that returns false; no document or changelog entry says MCP-served skills load. MCP prompts, which Claude Code does consume, appear as slash commands the person invokes, not as skills the model picks up.

**Server-stored, per-organization skills: one shipped precedent.** PostHog's skills store is team-scoped, versioned (every edit an immutable version with `base_version` concurrency checks) and driven through its MCP server's `skill-list`, `skill-get`, `skill-create`, `skill-update`, file tools and `skill-archive`; its docs' tip "Let agents update skills" is human-prompted (after an agent follows a skill, ask it to suggest improvements, then `skill-update`); and `skill-store-install-command` mints a read-only `llm_skill:read` credential and returns the Claude Code and Codex commands that install the team's store "as an auto-updating plugin marketplace". It has not shipped SEP-2640 serving (issue #99933, open). The other shipped "agent proposes a skill" flows land as pull requests a person merges: Devin's "suggest creating or updating a skill" with a Create PR button, and Claude Tag (public beta), which "can open pull requests to improve its own skills" but "won't open skill PRs unprompted". Anthropic's own Skills API stores custom skills per workspace with versions, but "custom Skills do not sync across surfaces" to claude.ai or Claude Code.

**Executor is not what the brief assumed.** Executor (UsefulSoftwareCo; MIT; YC S26; 4.3k stars; one author for 5,924 of about 6,200 commits; last commit 2026-10-23) is an MCP aggregator, "an open-source integration layer for AI agents" whose FAQ says "Executor runs no AI". On `main` (v1) the `skills` tool is a hand-curated registry of three of its own how-to documents, and the code tells a model that "a skill from your harness or the user's project is not reachable from here". A full workspace skills store (one Postgres row per tenant, owner and name; org-shared or personal; served by a `skills` tool whose description carries the catalog capped at 40 entries, by SEP-2640, and by `executor skills pull` into `~/.claude/skills`) was built as PR #1986 and closed unmerged on 2026-10-08 "ahead of the v2 launch", as was its successor with immutable revisions and upstream diffs (#2091). The shipped v2 (`executor@2.0.0-beta.27`, what executor.sh describes) keeps skills as `skills/<name>/SKILL.md` files inside an app's TypeScript source, versioned only with the app, created by a person in the dashboard or by an agent committing source, served read-only through a `skills` tool and the CLI, optionally loaded at read time from a GitHub repository or a `/.well-known/agent-skills/index.json` (Cloudflare's draft discovery RFC). There is no evaluation, no usage-driven editing and no "evolution" anywhere in either generation, only read telemetry; the marketing says "Give your agent instructions it can use again" and never claims learning. The runtime-authoring ideas (`skills.create` over MCP, skills surfacing in tool search, `executor pull` promotion) exist only in its `vision.md`.

**What "evolved at runtime" means where it exists.** Claude Code's skill-creator runs a measured improve loop (with-skill versus baseline test cases, graded assertions, blind A/B between versions, description-trigger optimization), locally and with a person in the loop. Letta's agents can "learn a skill from its experience" into the agent's own git-backed memory, with no evaluation. Voyager (2023) and MemSkill (2026) are the research designs: executable skills verified against an environment, and a designer that reviews hard cases to rewrite skills. No shipped product runs an automated, server-side eval or regression loop over an organization's skills.

### A.5 The data providers, and how people make "just the data" repeatable

**All three providers Ben named converged on the same shape within the last fifteen months: a remote Streamable HTTP server behind OAuth that exposes a handful of meta-tools (search the catalog, inspect one entry, execute) instead of one tool per endpoint.**

- **Treg** ("OpenRouter, but for agent tools"; repo created 2026-07-15, 6,018 stars): one endpoint `https://treg.to/mcp/` with 10 tools over a live catalog of 4,021 endpoints from 114 providers (`catalog_search`, `catalog_get`, `call`, `call_media`, `resources_list`, `balance`, `my_tools`, `catalog_request`, `feedback`, `review`); search works unauthenticated, calls need a grant; its own OAuth server, supporting both CIMD and DCR because "ChatGPT prefers CIMD; Claude Code and most other clients use DCR". For the Claude Connectors Directory it built a second surface, `/mcp/v2/`, with six tools and the generic `call` split into `catalog_call_read` and `catalog_call_write`, because a single generic call "can't give Claude a precise read-versus-write safety signal": "Claude can therefore treat GET, HEAD, and OPTIONS as reads and request approval for POST, PUT, PATCH, and DELETE." Its Claude Code plugin ships skills only and registers the MCP server after login, since a server declared in the manifest "would be registered at install time, before any human has signed in". Its "tool hub" publishes recipes ("a tool made of other tools") callable through the same `call`. It markets itself as "the DataForSEO MCP": DataForSEO, Serpstat, SE Ranking, SerpApi and Majestic behind one token, no markup.
- **Monid** (repo created 2026-08-26, 6,295 stars, MIT; wraps DataForSEO and Ahrefs among 33 connectors in the checkout, 725 endpoint files; the hosted server is closed source): `https://mcp.monid.ai/v1`, Streamable HTTP behind Clerk OAuth only (PKCE, RFC 9728 metadata; 401 before `tools/list`). The sibling thread's research, from Monid's plugin skill, gives the surface: 13 fixed tools, `monid_discover`, `monid_inspect`, `monid_run`, `monid_get_run`, `monid_stop_run`, `monid_list_runs`, `monid_balance`, `monid_list_workspaces` and five resource tools, every one taking a `workspaceId`, over a catalog of about 2,900 endpoints from 93 providers that is never listed as tools. Its Claude guidance is a `SKILL.md` and a CLI ("Never guess parameters": discover, inspect, run). Its own copy cannot settle on a count ("hundreds", "1,000+", "2,000+ across 72+ providers").
- **DataForSEO** is the most instructive precedent. Its v2 server exposed about ninety tools in ten modules (88 registered at the deprecated repository's head; issue #57 counted 89 on the version it measured) plus 21 prompts, with `ENABLED_MODULES`, `ENABLED_PROMPTS`, response trimming and a field configuration as the only controls. Issue #57 (2026-07-21) measured that surface at "89 tools totalling 42,288 tokens", about 25 times the median public MCP server; the reporter added the same day that "Claude Code and Codex now defer MCP tool schemas by default". DataForSEO answered on 2026-08-18 with v3 (tagged 2026-08-11): all 89 tools replaced by four, `docs_index`, `docs_list_sections`, `docs_search` and `api_request`, which read its own `llms.txt` documentation index (618 pages, about 344 of them endpoints) and then make one authenticated call, "rather than continuing to expose a large number of individual API endpoints as separate MCP tools"; "it should also help with the tool-selection problem"; "this was not just a matter of adding a module filter". OAuth is the default on the hosted server, Basic auth the fallback; for Claude Code it documents a `SKILL.md` plus CLI path as a first-class alternative to MCP. The open complaint is no longer tool count but response size (issue #27, open since 2025-08-27: "Your input exceeds the context window of this model").
- **Apify** ran the "add tools at runtime" experiment for sixteen months and deleted it: `add-actor` with `notifications/tools/list_changed` shipped 2025-03-12, became the default 2025-06-24, and was removed 2026-07-27 in the migration to the 2026-07-28 revision ("Migrate to MCP spec 2026-07-28 (stateless)", issue #1128), under which a per-session tool list is not expressible; the README still notes that "the level of support for dynamic tool discovery and other features may vary between clients". What remains is a stateless `search-actors`, `fetch-actor-details`, `call-actor` flow, with the advice to keep a configured list at ten to fifteen tools. Firecrawl (`find_tools` drills categories to one contract, then `scrape`; gated to teams with Alexandria access), Context7 (`resolve-library-id`, then `query-docs`), Composio's Tool Router (six meta-tools including `COMPOSIO_SEARCH_TOOLS` and `COMPOSIO_MULTI_EXECUTE_TOOL`) and Cloudflare's own server follow the same search-then-call pattern; Exa stays at four broad tools. The aggregator precedents the sibling thread catalogued for its proxy (Cloudflare One portals with `{server_id}_{name}` names, up to 80 upstreams and a two-hourly sync; Pipedream's per-user header; punkpeye's `mcp-proxy`, whose README admits "the upstream sees the proxy as its client, not the downstream caller") are in the sibling thread's documents (`docs/design/2026-10-mcp-provider-apps.md`, the design, and `docs/design/2026-10-mcp-provider-apps-research.md`, the sources; in its open PR #489, not on `main` yet). Its proxy kind, designed and not yet built, has the Gateway speak MCP as a client to the upstream with the operator's key only (never the member's token, which the spec forbids passing through), caches the upstream `tools/list` in the same D1 snapshot behind an operator allowlist, forwards each call with about 25 of the 30 seconds, pins the 2025 era and declares no elicitation, sampling or tasks.

**Anthropic's rule for its connectors directory settles the shape of any meta-tool.** The review criteria reject a catch-all: "A single tool that accepts both safe HTTP methods, such as GET, HEAD, and OPTIONS, and unsafe methods, such as POST, PUT, PATCH, and DELETE, is rejected. Don't ship a catch-all `api_request` tool with a `method` parameter"; "Split a catch-all tool into a read-only tool and one or more write tools"; every tool needs a `title` and `readOnlyHint` or `destructiveHint`, which "determine auto-permissions in Claude. Read-only tools can run without per-call confirmation, and destructive tools always prompt." That is why treg built `/mcp/v2/`, why DataForSEO v3's `api_request` could not be listed as is, and what any compact or code-mode surface on the Gateway must respect: one generic `execute` is a catch-all by definition. Claude's hosted client also still speaks only the 2025 revisions (2025-03-26, 2025-06-18, 2025-11-25) while Claude Code negotiates 2026-07-28, so the Gateway's two-era serving stays.

**Server-side `execute` on aggregators exists, with mixed results, and so does the surface-by-URL pattern.** Executor v2 ships `search`, `describe`, `call` and `execute` (plus `resume`): "for a few independent calls, use `call`", "write a JavaScript program for `execute` when one call's result feeds another"; limits of 65,536 characters of source, 100 tool calls and five minutes per execution; a call that needs a person returns `approval-required` and the program resumes after the decision, and the skill warns "never run the program's source again to continue it: earlier calls may already have taken effect". Its interpreter is `@opencode-ai/codemode`, "a lightweight, pure interpreter for a JavaScript-like language built around calling tools" with no network, filesystem or host globals by construction, running inside Executor's own Worker isolate with cooperative timeouts; no Dynamic Worker is involved. Redpanda's AI gateway adds a per-server `<server>-code` sibling with `search` and `execute` under fixed limits (64 KiB of code, 50 tool calls, 10 seconds), states that "code mode does not widen what the server can reach", and deliberately "applies to one server at a time and is not a way to combine multiple servers behind one endpoint". Stainless went the other way: its hosted sandbox mode is "deprecated" and its Cloudflare Worker target cannot run the code tool at all ("the Worker runtime cannot run code locally"); no reason is published. GitHub's MCP server removed its dynamic toolsets (`enable_toolset` and friends) on 2026-05-20 ("dynamic mode was local-only, never offered by the remote server") and keeps surface selection by URL (`/readonly`, `/x/{toolset}`) and headers (`X-MCP-Toolsets`, `X-MCP-Readonly`). The one published head-to-head is Stainless's own (2026-03-02, 31 tasks on one banking API, Claude Opus, an LLM judge, no variance): completeness 98% for its SDK code mode, 94% for Anthropic's programmatic tool calling with tool search, 90% for Cloudflare's code mode, and 70% for "dynamic" meta-tools that discover and invoke endpoints; factuality never passed 53% for any of them.

**How people make it repeatable today, and what they complain about.** The repeatability unit in the wild is a markdown skill or command in git, not an MCP prompt or a hosted workflow: `claude-seo` (19,924 stars, created 2026-02-07) is a Claude Code plugin of skills that pins `dataforseo-mcp-server@2.8.10`, sets `ENABLED_MODULES`, ships a field configuration that "reduces API response sizes by ~75%", checks a cost script before every call, and names about fifty v2 tool ids that no longer exist on v3; `dataforseo-claude` ("13 skills + 5 subagents", 169 stars) bypasses MCP for a direct client; `claude-code-seo` is nine slash commands over Google Search Console and DataForSEO; treg, Monid and DataForSEO each publish a `SKILL.md` and `npx skills add` packages; treg's worked example is a saved prompt with thresholds and a spend cap. On the hosted side, Claude Code cloud scheduled tasks and Cowork tasks are the automation path; they "belong to your individual claude.ai account", "are not shared with teammates", include every connected connector by default "including writes", and cannot see local `claude mcp add` servers (a sponsored DataForSEO demo's daily routine failed for that reason). Complaints cluster on tool-list token cost (an 82k-token, 12-server Claude Code measurement; Cursor's 40-tool cap cited on DataForSEO's product page), oversized responses, skills breaking when a provider renames tools, and automation runtimes that cannot reach the same MCP connection. Nobody found publishes claude.ai Projects or shared workflows for these providers; sharing with teammates is solved by the gateways themselves (treg's team tokens and `my_tools`, Monid's workspaces) or by committing skills to git. No first-hand user thread asking for server-held shared skills was found; the demand shows up in what the vendors built instead (A.4).

**What the sibling thread builds** (Ben's ruling in that thread, 2026-10-24): a provider becomes an `apps` row of a new tier with no Worker, its tools an SDK `defineTools()` app that runs inside the Gateway, so catalog sync, `tools/list`, `tools/call`, policy, audit and the usage counters are unchanged (#485 adds the registry rules and `everyapp provider on|off|list`; #489 serves the first provider: 17 curated DataForSEO read tools under `dataforseo_*`, every one with a title and the three hints, snapshotted into `app_tools` like any app's, hidden by #396's setup gate until the key is set; a generic remote-MCP proxy kind for treg and Monid follows). A provider's instructions block rides the same per-app clip, and anything built over catalog snapshots (search by name and description, deferred schemas) covers provider tools with no extra work. Those lists are already compact, so the question for the Gateway's connector is not the provider apps but the first-party ones: Open CRM and OpenSEO are 162 of the 187 entries; with DataForSEO on, an organization running the launch apps lists 207 tools to a read & write caller, 49 short of claude.ai's reported cap.
