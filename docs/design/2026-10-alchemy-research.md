# Alchemy for the Gateway and the CLI: evaluated, deferred (2026-10-24)

Written 2026-10-24, the Friday before the launch on Monday 2026-10-27. Ben asked, over [ratstack.sh](https://ratstack.sh/), what converting the Every App Gateway and the CLI's provisioning to [Alchemy](https://alchemy.run/) would entail, and whether that is a good choice now or something to do later. This is the record of the answer, kept so the question does not get re-argued from scratch: the Alchemy question has come up more than once and will come up again.

Method. The CLI and the Gateway were read at `e842be78` (paths and lines below are at that commit). Alchemy `2.0.0-beta.84` and `@alchemy.run/cloudflare 2.0.0-beta.84` (published 2026-10-24) were installed in a scratch directory and read at source; one offline test encoded a Worker upload through Alchemy's pinned HTTP client to see what reaches the wire. RatStack's site and repository, Alchemy's docs, changelog, issues and commit history, the OpenSEO port's existing Alchemy stage (pinned to beta.61) and the account's live Worker list (read-only) were read. Forty-one agents did the reading in a workflow: readers, a synthesis, two refuters per claim, three attackers of the verdict, a critic, three judges and three designs (full conversion, partial, defer). Every correction the refuters and the critic made is applied below; the two decisive Alchemy facts were re-verified by hand afterwards. Nothing was uploaded to any Cloudflare account, no PR touched code, and nothing was deployed.

**The verdict: not now. Keep `cf` plus the in-Worker REST deployer plus the Gateway's D1 as the operator path. Re-probe on 2026-12-01 and 2027-02-01, or when Alchemy 2.0.0 reaches GA, against section 8.** The conversion that is feasible is narrower than RatStack's, costs 40 to 70 engineer-days, meets one hard blocker in Alchemy's source today, and buys only the Worker and binding half of the job that cf already does. What Alchemy sells that the product genuinely lacks, a plan before mutation, can be built on the Gateway's D1 without the dependency.

## 1. What the deploy path is today

- `everyapp setup` and `update` deploy a prebuilt Gateway release into the operator's own Cloudflare account through Cloudflare's `cf` CLI (`1.0.0-beta.14`, spawned in `packages/cli/src/lib/cf/runner.ts`): get-or-create the D1 and KV (`lib/gateway/resources.ts`), take the deploy lease, run the downgrade guard and the strict-mode replace guard (`lib/cf/deploy.ts:208-255`, `assertReplaceable`), bookmark the database and apply migrations with `cf d1 migrations apply`, patch the release's Build Output with the install's bindings (`lib/gateway/patchBuildOutput.ts`), preflight DNS, then one `cf deploy --prebuilt`, with the first upload carrying the secrets file (`lib/gateway/apply.ts`, 684 lines).
- `everyapp deploy` does the app side the same way (`commands/deploy/deployApp.ts`, 1,191 lines): helpers, D1, KV, R2, Hyperdrive, Workflows, the ledger claim, the app to Gateway service binding with `props` (`packages/sdk/src/cloudflare/worker.ts:810-825`), Email Routing rules, Access.
- The Gateway's D1 is the record of truth: registry, install row, deploy lease, ownership ledger, restore points. ADR-0003: write access to that D1 **is** operator authority; the CLI keeps no state on the machine beyond the Cloudflare login (`adr/ADR-0003-self-host-authority.md:61-63, 75`).
- Secrets are set once and survive every deploy because cf uploads with `keep_bindings` for `secret_text` and `secret_key` (`landing-page/content/agent/secrets.md:268`; `lib/cf/secrets.ts:1-8`). The Gateway's `BETTER_AUTH_SECRET` and RSA JWT keypair are minted locally on the first upload (`lib/gateway/secretsFile.ts:34-47`) and exist nowhere but the Worker afterwards.
- The in-Worker deployer (`apps/every-app-gateway/src/server/deploy/`, 4,936 non-test lines, `cf-rest/` 1,418 of them) does the same by raw REST for browser installs and the hosted tier, because a Worker has no Node.
- The agent protocol is the CLI's own: `--json` NDJSON steps with `action_required` hand-offs, including the device login relayed as URL plus code from `cf auth login --no-browser` (`landing-page/content/agent/json.md:176`).

How much of that is infrastructure-as-code shaped, the thing an engine would replace: the four desired-state files (`desiredState.ts` 106, `reconcile.ts` 204, `patchBuildOutput.ts` 193, the upload half of `apply.ts`) total about 1,200 lines; about 1,500 with install, resources, change and the cf plan; about 3,900 if the Access, Email, resources and teardown reconcilers count. The CLI is 36,071 non-test lines and 28,160 test lines. Everything else (registry rules, lease, ledger, migrations and restore points, policy, release intake, hand-offs, the event protocol) is orchestration that sits under any engine.

## 2. What RatStack sells, and which part is missing here

RatStack is a template, not Alchemy: Effect plus Alchemy (beta.83 pinned) plus XState 6 alpha plus Foldkit plus Better Auth plus TypeScript 7.0.2 plus Vitest 5, labelled "pre-release, APIs move". Its pitch is three properties. Checked against this repository:

1. **Typed program plus infrastructure** ("remove a cloud resource and the code that uses it stops compiling"). Already here, without Alchemy. `cf workers types` infers the Worker's `Env` from `cloudflare.config.ts`; `types:check` is `cf workers types && tsc --noEmit` in the Gateway and the starter, and CI runs it (`.github/workflows/pr-checks.yml:33-34`). Verified 2026-10-24: deleting the `DB` binding (`apps/every-app-gateway/cloudflare.config.ts:203-206`) fails `tsc` with five errors (`src/auth/config.ts:566`, `src/db/index.ts:10`, `src/server.ts:199, 278, 352`); restoring it gives zero. Apps get the same through `everyAppWorker({ manifest })` in `starter/cloudflare.config.ts:10`. RatStack's own `VISION.md:106` lists this claim as "Not yet proven" and bridges it with a cast (`apps/site/src/worker.ts:185-188`).
2. **The fence** (compiler checks, lint rules, tests, hooks). Present as CI gates; the pre-commit variant was rejected on purpose for the many-PRs-a-day workflow.
3. **One capability, every surface** (`defineContract` projected to CLI, HTTP, MCP, RPC, code mode). The one idea this repository lacks: `defineTools` projects app tools to MCP only, and Gateway admin operations have hand-written UI and CLI surfaces that share a rule, not a contract (`everyapp workspace rename` is a direct D1 update beside `OrganizationService.rename`, which also logs the event). That is ADR-0003's design, not a tooling gap, and Alchemy would not change it.

## 3. What converting would entail

**The RatStack way is a rewrite, not a port.** RatStack's Worker is a class whose construction yields its bindings in Effect, its UI is Foldkit on Vite 8, state is `Cloudflare.state()`, and `alchemy dev` is the development loop. The Gateway is TanStack Start 1.168 plus React 19 plus Drizzle plus Better Auth on Vite 7.2 with `@cloudflare/vite-plugin` and local-only `cf dev`. Doing it RatStack's way means Effect 4 services everywhere, TypeScript 7 and Vitest 5. Not estimated; multiples of the design below.

**The only feasible design is narrow:** Alchemy as the uploader behind the CLI, over the Build Output `cf build` already makes (`bundle: false`), with a custom state layer backed by the Gateway's D1 so ADR-0003 survives, and cf kept for dev, build and types. `everyapp dev`, the starter and the built-CLI CI gate are untouched by it. ## 4. Why later, not now

Ranked. The first is the blocker; the next three are traps that would each need a decision; the rest are cost and context.

1. **Every Alchemy upload replaces the whole binding set.** The Worker provider sends `keepBindings: undefined` and no `inherit` entries (`@alchemy.run/cloudflare/src/Workers/WorkerProvider.ts:3722`; the gradual-rollout path at `:3785` sends no `keepBindings` key either), plus five `ALCHEMY_*` plain-text bindings (`:2394-2399`). Cloudflare's own cf release note for `1.0.0-beta.7` says why that matters: "Preserve existing Worker secrets during cf deploy ... prevents a redeploy from removing secrets added through the API or CLI". So a secret set outside the stack (`everyapp secret set`, the dashboard) is removed by the next upload that changes the script; an unchanged stack plans a noop and leaves it, silently. For an existing install the first converted `everyapp update` re-mints `BETTER_AUTH_SECRET` and the JWT keypair (`secretsFile.ts:34-47`): every session ends, every app's identity check breaks, and no restore point covers it because the private key exists only on the Worker. The launch doc forbids exactly that this weekend (`docs/launch-2026-10-27.md:98`). The PRs that would add keep-bindings are closed unmerged (#1452) or open (#1035, #2327). New installs are unaffected. Not verified live with Alchemy's client; verified at source and by Cloudflare's note. Re-verified by hand on 2026-10-24.
2. **Service-binding `props` reach the wire, but with renamed keys.** The source comment at `WorkerBinding.ts:149-157`, the docs caution and a skipped live test all say props are dropped at upload. They are not: the offline encode shows the multipart `metadata` carrying `{"type":"service", ..., "props": {...}}`, because Alchemy's HTTP client passes schema-unknown keys through. The real defect is that its Cloudflare key dictionary snake-cases nested keys it knows: `appId` becomes `app_id` (also `scriptName`, `zoneId`; `organizationId` and `workerName` pass). `AppGateway` reads `props.appId` and refuses the call with 401 when it is missing (`apps/every-app-gateway/src/server/app-gateway-entrypoint.ts:390-414`; `server.ts:276`), so an unmodified stack fails closed. The fix is a prop-key rename in the SDK, the in-Worker deployer and the entrypoint, or a one-entry dictionary patch. The OpenSEO port's note that Alchemy drops props dates from beta.61 and is stale. Live delivery of `ctx.props` through an Alchemy upload was not verified. Re-verified by hand on 2026-10-24.
3. **Secrets would land in plaintext in the Gateway's own D1.** Alchemy's apply persists each resource's declared props into state, and `StateEncoding` writes `Redacted` values as their real strings; no store under `alchemy/src/State` encrypts, only `Cloudflare.state()` does, with a key in the account's Secrets Store. Under a D1-backed state layer the first-upload secrets would be readable by `everyapp db query`, Time Travel restore points and the in-Worker deployer. That needs a decision (encrypt with a second credential, or keep secrets outside the stack, which makes item 1's patch load-bearing from the first deploy) and a threat-model row.
4. **D1 migrations are a one-way takeover.** With the `migrations` option Alchemy copies cf's `d1_migrations` history into `__alchemy_migrations` once and never writes the cf table again; pointing it at `d1_migrations` drops and rebuilds that table with a `hash NOT NULL` column cf's own insert cannot satisfy (`@alchemy.run/cloudflare/src/D1/Database.ts:84-90`; `@alchemy.run/sql` `Migrations/Convert.ts:49-53`). `everyapp db restore`, the restore points and the in-Worker pipeline (`apps/every-app-gateway/src/server/deploy/pipeline.ts:107-154`) share cf's table, so migrations must stay outside Alchemy, leaving it less of the job.
5. **Ownership and adoption point the other way.** Alchemy silently adopts, with `--adopt` off, any pre-existing D1 by name, KV by title, R2 by bucket name and Hyperdrive ("silent adoption is the norm", `alchemy/src/AdoptPolicy.ts:24-28`); Workers are the exception, branded `Unowned` without `alchemy:stack/stage/id` tags (`WorkerProvider.ts:1940-1949`). The invariant `resources.ledger-is-ownership` says a resource with the app's name that no deploy of it created is refused on every attempt (`docs/threat-model-invariants.md:353`; `packages/cli/src/lib/app/resources.ts:85-113`). The name-taken checks would have to run before every plan, and `adopt` never set stack-wide. The `alchemy` package also ships `alchemy unsafe nuke`, account-wide and state-ignoring (`alchemy/src/Nuke.ts:16-19`), unlisted and behind a prompt that defaults to Cancel, but with no account allowlist where `everyapp teardown` has `FORBIDDEN_ACCOUNTS` and typed confirmation (`packages/cli/src/lib/teardown/guards.ts:27`). The tsup bundle importing `deploy()` would not carry it; the operator's `node_modules` would.
6. **The agent surfaces are Alchemy's weakest side.** Its CLI has no JSON flag (every `Flag.*` declaration under `alchemy/src/Cli` enumerated: none). A programmatic `deploy()` exists (`alchemy/src/Deploy.ts:34-59`) and an `Alchemist` plan and apply API with 18 typed report events, but neither is documented. Its login is a device flow on cf's own OAuth client id (`Auth/OAuthClient.ts:5-16`), so relay is designed in, but completing it from a container is unverified. The launcher refuses Node below 22.22.3 or 24.11.1 (`alchemy/bin/cli.js:108-137`) while the CLI promises `>=22.18.0` (`packages/cli/package.json:17-19`); the gate is the launcher's TypeScript loader, so a programmatic `deploy()` from the built CLI is probably not gated, unverified on Node 22.18.
7. **Platform and footprint.** Peers `effect ^4.0.5` (required) and `vite ^8.0.7` (optional); the package that hosts the Vite plugin accepts `vite ^7 || ^8` and neutralizes `@cloudflare/vite-plugin` rather than crashing; `alchemy dev` emulates locally by default since beta.66 with `Alchemy.remote()` as the opt-in (the alchemy.run pages still say the opposite). None of that is used by the narrow design, which never touches the Gateway's Vite setup. What stays true: `effect` is a new dependency in a workspace with none, the install grows by about 398 MB and 87 packages (rolldown binaries, Docker and ACME providers through the monolithic Cloudflare providers), and the credential moves from a vendor subprocess into a process with 87 third-party packages.
8. **Bus factor, not churn.** Churn does not discriminate: cf shipped 22 betas between 2026-09-25 and 2026-10-23 (the repo pins beta.14, seven behind) with breaking notes in four of them, and the team swapped wrangler for cf in one PR eleven days before launch (#271, 328 files). Alchemy: 14 of the 24 releases beta.61 to beta.84 (2026-07-08 to 2026-10-24) carry a Breaking Changes section, one release every 4.5 to 4.7 days, a breaking one every 7.6, the Effect peer floor raised nine or ten times, the provider packages split in beta.84, "Don't roll back past beta.82" in beta.83. The difference is that one author wrote about 57 percent of the last 300 commits with one other merger, and the 1.x line has been frozen since 2026-08-01. The OpenSEO port froze at beta.61 for three and a half months and abandoned its one upgrade attempt (open-seo #879, "a migration, not a version bump").
9. **cf already delivers the half Alchemy would take.** `bindings.worker({ worker, exportName, props })`, `cf deploy --prebuilt` publishing the whole Build Output with `keep_bindings`, JSON output on its API-shaped commands, a credential-free `--dry-run` (`lib/cf/deploy.ts:38, 78, 138`). The in-Worker deployer stays REST under any engine. Email Routing, Access, leases, the ledger, restore points and the hand-offs stay exactly where they are. What Alchemy adds on top is a typed resource graph with dependency ordering, a plan before mutation, and one in-process HTTP client; of those, only the plan is something the product lacks, and section 7 builds it without the dependency.
10. **Timing.** The launch doc forbids upgrading TanStack Start or Vite, renaming Workers, changing the install row's shape (`docs/launch-2026-10-27.md:93`) and rotating the Gateway's secrets (`:98`). The onboarding loop's eight public runs on 2026-10-24 (seven reached app-live) are evidence for the API-token path and the `--json` protocol exactly as they are; they did not exercise the device login or the secrets commands, so a login change of either engine has no harness today.
11. **The team's own history.** The OpenSEO port's gateway-facing `everyapp` Alchemy stage never ran against a real account; its CLI prerequisites (`everyapp register`, `deploy --shared`) were removed by #441 on 2026-10-24; OpenSEO is live on everyapp.team through `everyapp deploy` with no Alchemy tags. The port still deploys app.openseo.so production, previews, self-host and a pentest stage through Alchemy, fine, behind no gateway.

## 5. Corrections to things people say about Alchemy

Recorded so the next reader starts from the right facts.

- "Alchemy drops service-binding props." Stale: props are sent; keys are snake-cased (section 4, item 2).
- "Alchemy's state must live in `.alchemy/` or a Worker in the account." Incomplete: the state store is a required, pluggable Effect Layer (`alchemy/src/Stack.ts:272-282`), documented at alchemy.run/state-store with a custom-store guide; Postgres, S3, GCS and in-memory stores need no Worker. What is true: the documented interface is stale (8 members documented, 12 shipped) and unversioned (core store version 5, the Cloudflare store 7 with "TODO: bump to 8 before release" at `StateStore/Api.ts:36-38`), and the Cloudflare store bootstraps a bearer-token Worker on workers.dev plus Secrets Store entries into every account.
- "Alchemy's Vite plugin crashes beside `@cloudflare/vite-plugin`." No: it neutralizes the official plugin's hooks when it is injected. What is true: `remoteBindings`, `persistState` and `inspectorPort` have no counterpart, and nothing was shown on TanStack Start 1.168.
- "`alchemy dev` targets real cloud resources." Not since beta.66; local emulation is the default.
- "Alchemy's `nuke` is a bare command." It is `alchemy unsafe nuke`, unlisted, prompt defaults to Cancel, has `--dry-run` and filters. No allowlist.
- "Alchemy has no Access, Email, Hyperdrive lookup, rate-limit or prebuilt support." It has `Access.Application` with `destinations` and bypass policies (whether the CLI's up-to-25 per-path policies map onto them is unverified), `Email/Routing` and `Rule`, `Hyperdrive/ConnectionLookup`, `ratelimit` bindings, assets with `runWorkerFirst`, Worker `domain`, `bundle: false` with a prebuilt source, and a `Random` resource that mints once and preserves. The resource-coverage gap is small; none of it removes item 1.

## 6. The two-engines rule

The main account already runs three deploy engines: wrangler for the landing page and its redirect Worker (`landing-page/wrangler.jsonc`, `every-app-landing-page`), cf for the Gateway and the apps, and the in-Worker REST deployer. That is fine because they touch disjoint Workers that share no state. The rule for any further engine, including a hands-on Alchemy experiment: only on Workers the CLI never names and that read no shared state. Never the Gateway Worker, the Access applications or an app Worker, because cf publishes whole binding sets and Custom Domain lists, `assertReplaceable` refuses versions the install row did not record, and item 1 wipes secrets. The judges rejected the proposed "Alchemy for the landing page only" experiment two to one: it exercises none of the blockers and puts an account-wide token beside `unsafe nuke` in the everyapp.team account.

A hosted-tier stack in the maintainers' own account (the wildcard route, the dispatch namespace, DNS, the email sending subdomain, the things the runbook says are "added in the dashboard") is the one place Alchemy could fit later: a directory outside `pnpm-workspace.yaml`, the hosted Gateway still installed by `everyapp setup`, disjoint Workers and disjoint dispatch namespaces. Forbidden before launch (`docs/launch-2026-10-27.md:91`).

## 7. What is worth borrowing without the dependency

Ranked by the three judges. Only the first two are pre-launch-safe (docs and CI only); the rest wait for the first week of real self-hoster `update` runs, and the plan items only if Ben names them.

1. **This record** and a TODO entry (done with this document).
2. **Pin the gateway test fixture to the real `cf build`.** `packages/cli/src/lib/gateway/__fixtures__/gateway-worker.config.json` is hand-copied, last touched 2026-10-13, and 42 apply tests run on it. Inside `packages/cli/src/lib/cfDryRun.test.ts` (already run after `build:release` in `cf-dry-run.yml`), assert env names and types, triggers, compat, observability, assets, `workersDev`, `previewUrls`, with a `fixtures:update` script. This is RatStack's "a removed binding fails the build", which the repo already has through `types:check` and RatStack itself has not proven. Half a day.
3. **A gateway binding fence test** asserting every name `patchBuildOutput` writes (`DB`, `OAUTH_KV`, `EVERYAPP_RELEASE`, `CF_VERSION_METADATA`, `APP_BASE_DOMAIN`; `patchBuildOutput.ts:89-92, 117`) is declared with the same type in `cloudflare.config.ts`, and that no `KV` or `APP__*` binding exists there (then delete the legacy `delete env["KV"]` at `:88`). Half a day to one.
4. **A plan before mutation, with the Gateway's D1 as the state.** A pure `planGateway()` in a new `lib/gateway/plan.ts` collapsing the two hand-maintained in-sync comparisons (`reconcile.ts:159-169`, `commands/status/index.ts:170`), and a `gateway.plan` NDJSON step listing `bind.add/remove` and `publish.add/remove` before `gateway.lease`, so an agent can stop and ask before a destructive rebind. One squashed PR with the `apply.test.ts` expectations byte-identical. Two to four days. This is the plan and diff benefit Alchemy sells.
5. **`everyapp setup --dry-run` and `update --dry-run`** on the `dryRun` branch `lib/cf/deploy.ts` already has: the read-only preflight plus the replaceable comparison, no lease, no migration, no upload, exit 0; `json.md` must say the output is not lease-protected and skips strict mode and DNS. One to two days, below item 4.
6. **Delete the dead `everyapp` Alchemy stage in the OpenSEO port repository** (scratch-venue rules; never open-seo main): `deploy/alchemy/alchemy.everyapp.ts`, its test and snapshot case, the binding script, `.env.everyapp.example`, `docs/EVERY_APP_DEPLOYMENT.md`, two `package.json` script lines, the stale comments in `everyapp.config.ts` and `docs/maintainers/every-app.md`; about 730 lines plus a slice of a shared snapshot. Keep upstream's hosted-prod, selfhost, preview and pentest stages and pins untouched. Closes the second half of the "OpenSEO onto `everyapp deploy`" item in TODO.md. Half a day to one.
7. **From RatStack's agent site, dependency-free:** `/.well-known/agent-skills/index.json` (agentskills.io 0.2.0: name, description, url, sha256 per skill) generated at the landing-page build from `packages/cli/skills/everyapp/SKILL.md` and `setup/*.md`, pinned by the agent-docs drift test; the "load it into this session only, do not install" prompt line; the "What it does / The standard / How to check" page format for `docs/threat-model-invariants.md`. Belongs to the docs threads, below the onboarding loop's findings.
8. **From RatStack's deploy discipline, as habits:** classify a plan before mutation and require separate sign-off for deletion, replacement and unbinding (item 4 closes the gap); write the receipt before mutation (the install row already does); read the live Worker version back after apply (already done through the deployments list).

Do not borrow: the Effect capability pattern as code (`defineContract` and projections are Effect 4 modules), lefthook pre-commit hooks and the `--no-verify` blocker, the no-comments rule (conflicts with the doc-comment house style), `Website.Vite` and `alchemy dev`, and Alchemy's D1 migrations.

Reverse trigger for the borrowed work: if a post-launch onboarding-loop run shows `everyapp update` or setup-resume regressions traceable to the plan and apply split, revert that PR and keep only this record, the fixture test and `gateway.plan` emitted from the existing paths.

## 8. When to reopen

Probe on 2026-12-01 and again on 2027-02-01, or when T1 fires, whichever is first; about an hour each. Record each probe's result at the end of this document.

- **T1. Alchemy 2.0.0 GA** with a written stability policy and three consecutive releases without a Breaking section; `@alchemy.run/cloudflare` out of beta. Probe: `npm view alchemy dist-tags`, the alchemy.run blog, the raw `CHANGELOG.md`. Today: 2.0.0-beta.84.
- **T2. Props arrive with keys unrenamed.** Probe: one upload into a loop test account, `cf workers settings get` shows `props` with `appId` spelled as sent, and a call through the binding reaches `AppGateway`'s `ctx.props`. The stale comment disappearing is not the signal; props already work.
- **T3. A documented keep-or-inherit bindings mode on the Worker resource**, so secrets set outside the stack and the patched `APP__` bindings survive. Probe: `WorkerProvider.ts` no longer sends `keepBindings: undefined`, or a documented `keepBindings` or `inherit` prop; verify with `cf workers secrets bulk`, then an Alchemy deploy, then `cf workers secrets list`. **This is the gating trigger.**
