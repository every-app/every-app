# The onboarding loop: proving the setup prompt on any coding agent, from nothing

Written 2026-10-24 for the launch. Status: **decided; building.**

The loop is a script in the checkout, `pnpm loop run --harness claude --account loop-1`, that a person or a T3 agent runs. Per run it wipes a dedicated test Cloudflare account (a separate Cloudflare user, never Ben's), starts one throwaway Linux container on this Mac from an image that holds Node 22, pnpm and the five harness binaries and nothing else, puts a real git clone of the commit under test inside, hands the harness the home-page setup prompt plus the account's API token and one provider key, and lets it run. A scripted user on the host answers only the hand-offs the prompt itself creates, completes the owner claim over HTTP the moment the CLI mints the link (the CLI tees its own events to a file; no browser, no transcript parsing on the critical path), and resumes the harness with its native resume when it ends a turn early. An outside-in verifier that never trusts the harness's words or its tree proves the Gateway, the owner and one deployed template app from the outside, a four-way decision table says pass, pass-with-intervention, fail-onboarding or fail-infra with a reason code, the account is wiped again, and a redacted record is written. Four candidates were drafted and reviewed adversarially from six angles each; local containers won on the one axis that binds before Sunday (it runs tonight on a substrate that is already installed, with nothing deployed anywhere), with Modal sandboxes as the drop-in replacement behind one small interface if Ben vetoes Docker Desktop. The clean-slate wipe is the `everyapp teardown` command already in this worktree, opened as a PR and held for Ben.

## 1. Goals and non-goals

**Goals.** Prove, from a fresh sandbox with no memory, no logins, no caches and no prior state, against a Cloudflare account wiped of every Every App resource, that the pasteable setup prompt takes a coding agent from `pnpm install` to a claimed Gateway, a deployed template app that opens, and optionally `access on`, on each of five harnesses: Claude Code, Codex CLI, OpenCode on OpenCode Zen, Cursor agent CLI, Hermes. Record per run the harness and model, duration, tool calls, where it hesitated or asked, every error with its code, whether a person would have had to intervene, and cost. Turn hesitations and errors into concrete CLI, prompt and docs fixes with an owner. Run end to end on Claude Code and Codex before Sunday 2026-10-26, on all five by Sunday evening with provisional labels where the adapter has no live sample yet, then on demand and on change; a schedule, if ever, is a T3 scheduled task or a cron on Ben's Mac, later.

**Non-goals and hard rules.** The loop never touches Ben's main account `23bc28f0b638fbfc1c7f838573c17ee3` (openseo.so, everyapp.team): every test account belongs to a separate Cloudflare user, every token is account-restricted, and the teardown refuses that id by constant whatever any list says. It tests the template app (`everyapp create`, today `templates/simple-todo`, `starter/` after the simplify thread; the loop never hard-codes the path), not the example apps, which are being deleted. Postiz is not launching and is not in scope. The landing page is never deployed by this work. Nothing of the loop is a GitHub workflow or CI. No secret goes through chat or into the repository; Ben writes two files in his terminal and the script reads them. It is Linux only: macOS and Windows specifics are out of scope. Permission prompts are bypassed on every harness and said so in the record; measuring them is a later variant.

## 2. The four candidates

The drafts are in `/tmp/ea-loop/design/candidates/` and the 24 adversarial reviews (six lenses per candidate: cost, driving, findings, flakiness, secrets, success) in `/tmp/ea-loop/design/reviews/<candidate>-<lens>.md` on Ben's machine, cited below as `a/driving` and so on. Every reviewer worked from the checkout, the installed binaries and the vendors' docs, not from the drafts' claims.

**(a) Local containers.** `packages/onboarding-loop` drives one Docker container per run on this Mac. FACTS and Ben's decision 5 said Docker is not installed; six reviewers verified it is: Docker Desktop 4.95.0, engine 29.8.2, linux/arm64, 18 CPUs, 7.75 GiB VM memory, `node:22` cached, only the CLI off PATH. Compute $0; nothing deployed anywhere; the container outlives a turn, so native resume, `docker exec tail -F` of a file inside, `docker diff` for tamper detection and `docker commit` for post-mortems are one call away. Build: the draft said 5.5 agent-days, which overstates it because the teardown already exists. What the reviews found: the stream-regex owner claim cannot fire in order on any harness and the Claude Code command line did not start as drawn (`a/driving`); no infra taxonomy, no per-account lock, laptop DNS negative caching for 30 minutes, the 7.75 GiB VM (`a/flakiness`); host-side `cf` one fallback from Ben's Keychain login, the WIP guard's vacuous `authenticated` check, the driver's own stdout outside the redactor (`a/secrets`); the verifier passing a harness that stopped after setup and failing a healthy app because the gateway root is always 200 and the app host 302s only with `Accept: text/html` (`a/success`); the record parsed from truncated tool output on three of five harnesses (`a/findings`); provider estimates 2 to 4x low, no dollar cap, Cursor a subscription (`a/cost`). All script-level or a 30-line CLI seam.

**(b) Modal sandboxes.** The same package driving a fresh gVisor microVM per run through a ~150-line Python shim over Modal (configured, smoke-tested in 36 s). Lowest blast radius: the sandbox cannot reach this Mac at all; it survives a driver crash and can be re-attached; two accounts give two lanes. Build 2.5 to 3 agent-days plus about 1.5 of fixes. What the reviews found: the launch path is broken three ways as drafted (`runuser` not on the image PATH, `bash -lc` resets PATH so the pnpm tap vanishes, Cursor and Hermes installed as root and run as `dev`: `b/driving`, `b/flakiness`, `b/secrets`, each verified live in a sandbox); the pnpm tap misses `pnpm run deploy`, `pnpm exec everyapp` and `npx everyapp`, so the record is not exact (`b/findings`); unredacted harness output transits Modal, whose logs are retained 1 to 30 days in a workspace shared with Carter (`b/secrets`); every image change is a minutes-long rebuild and a Python shim lands in a TypeScript repo; `fixes == []` fails honest runs (`b/success`). Strong fallback; its best ideas are grafted below.

**(c) Cloudflare Sandbox.** A Worker in Ben's main account owning a Durable Object per run, a container from the managed image, a 10-second alarm as the scripted user, artifacts in D1 and R2. Infra under $4 a week; the test account holds no loop machinery. Build 5.25 agent-days, about 2 of them Worker, DO, alarm, SSE and snapshot plumbing that a local or Modal sandbox replaces with a quarter day; no local dev (`wrangler dev` needs Docker, which the draft believed absent), so every bug is a redeploy into Ben's account; stacked public betas; no runtime guarantee (a host restart loses a 45-minute run with no resume); Claude Code refuses `--dangerously-skip-permissions` as root in the managed image (`c/driving`, `c/flakiness`); a new internet-facing bearer-protected Worker plus transcripts and a test token in Ben's main account during launch week, and the executing side never re-checks the account it installs into (`c/secrets`); the parser in a DO cannot be re-run on saved artifacts (`c/findings`). Its own odds: three harnesses by Sunday 80%, five 55%. Its reviewers produced the best verifier, decision-table, control-run and findings-ledger designs, grafted below.

**(d) Background agents (Open-Inspect).** Reuse agents.everyapp.team: webhook automations start sessions on Modal, the loop plays the user through `sessionKey` follow-ups and reads the trace export. Zero sandbox infrastructure and a live multiplayer view of a stalled run. But it measures Open-Inspect's wrapped agents, not the CLIs a visitor types: the Claude lane is the Agent SDK with bundled CLI 2.1.284, backgrounding disabled, `AskUserQuestion` removed and `dontAsk`; OpenCode is 1.18.29 with plugins and `opencode/glm-5.3` silently swapped for the catalog default; Cursor and Hermes never run (`d/driving`, `d/success`). There is no unattended transcript export (the Day-1 fallback is Ben's Owner cookie), the memory layer primes run N+1 by default, every global secret lands in every sandbox, and the one real build item is a production auth change on agents.everyapp.team in launch week (`d/secrets`, `d/findings`, `d/flakiness`). Not viable as the loop; kept as a later "watch a stall live and type the answer" mode.

## 3. The decision

**(a), local containers, with the substrate behind one interface so (b) can replace it without touching anything else.** The one argument for (b) over (a) is blast radius; otherwise (b) is the same design on a substrate that is slower to iterate on. The sandbox is `src/sandbox.ts` with seven operations (create, copy in, exec with a streamed stdout, tail a file, copy out, diff, destroy); `src/docker.ts` implements it today, `src/modal.ts` can tomorrow. Adapters, scripted user, verifier, teardown, record and report never change. Why (a): the only candidate whose first real run is a Friday event rather than a substrate project; no new vendor, language or deploy; `$0` and seconds per iteration; the container outlives a turn so every resume and every post-mortem is one local call. The deductions are real and each has a fix below: the laptop is the substrate (caffeinate, auto-updates off, VM memory to 16 GiB), host-side `cf` can reach Ben's Keychain login (so every token-bearing `cf` call runs in a sibling container), and the first draft of the teardown's token gate was too weak (tightened in PR #444, section 5). **If Ben vetoes Docker Desktop**, swap only `src/docker.ts` for the Modal shim with the three verified fixes from `b/flakiness` (image PATH with `/sbin`, `/sbin/runuser -u dev -- bash -c` never `-l`, installers run as `dev`), move redaction inside the sandbox, and feed the sandbox its secrets from the per-account Modal secret `everyapp-loop-<n>` (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `EVERYAPP_LOOP_ZONE`) plus `everyapp-loop-providers` (Ben's decision 2, runbook section 6) in place of the 600 temp env file; `accounts.json` stays on the Mac for the driver's own calls (section 6).

### What was grafted from the other candidates

- From (b) and its reviewers: **the CLI is the source of truth for the record**, as a dormant env-gated tee, `EVERYAPP_EVENT_LOG=<path>` (section 4.5), not a pnpm PATH shim. First-class `fixtures{}` and `deviations[]` on every record; `run_key = (harness, resolved model, prompt sha256, checkout commit, image tag)` and comparisons only within a key; one lane per account; one committed file per run, never an appended ndjson two worktrees would conflict on.
- From (c)/flakiness: **harness #0 `script`**, a bash adapter that follows the prompt literally, run on each account after every wipe and every CLI commit as the plumbing smoke test and the per-account baseline (install, build, certificate and deploy durations), and the reference that classifies infra vs defect at n=1.
- From (c)/success and the three other success reviews: **the precise verifier** with gateway fingerprints a parking page cannot fake, the owner proved by signing in, severity-aware `status`, the two app-host signatures, and the four-way verdict evaluated in order with first-blocking-event precedence and a `phaseReached` ladder.
- From (c)/secrets and (c)/findings: reuse `everyapp teardown` as the one destructive path; token-bearing `cf` calls in a sibling container; the per-harness `signal{}` disclosure; parsers as pure functions over saved artifacts with one redacted real transcript per harness as a vitest fixture and `pnpm loop reparse`; findings keyed `route|signature|step` with harness as a dimension and a computed status.
- From (d)'s reviewers: the **D1-side owner claim** as fallback and control mode; D1-derived comparable metrics (claim rows = setup runs that reached the owner step; registry apps deployed by the token before the verifier phase); `answeredBy` derived from facts; the `falseDone` flag; `pnpm loop replay`; a whitelist, never a denylist, for anything committed to the soon-public repository.

## 4. The architecture

### 4.1 Components

`packages/onboarding-loop` (root script `pnpm loop`, `tsx` entry), TypeScript, its own package with **no imports from `packages/cli`'s source** (`/tmp/ea-loop/design/LOOP_BUILD_SPEC.md`, decision 1, which wins over this doc where they disagree): it shells out to the CLI (`pnpm everyapp … --json` from a checkout inside a container) and to `docker`, talks to Cloudflare through small typed `fetch` calls against `https://api.cloudflare.com/client/v4` with the account token (`src/cf.ts`: D1 query, D1 list, the workers.dev subdomain PUT), never runs `cf` on the host (it can fall back to Ben's Keychain login), resolves hostnames with `node:dns/promises` pointed at the zone's NS records (`src/dns.ts`), and parses the teardown's `--json` NDJSON with its own zod schema. The CLI's `lib/cf`, `lib/domains/*` and the FakeCf fixtures stay the house pattern to copy, not to import.

### 4.2 A run, step by step

1. **Preflight.** `pnpm loop run --harness codex --account loop-1 [--model <id>] [--ref <commit>] [--mode defaults|raised] [--with-access] [--claim-after immediate|turn-end] [--no-event-log] [--checkout bundle|clone] [--prompt-variant checkout-present|public] [--repeat-on-infra 1] [--keep] [--parallel 2]`. The driver re-executes itself under `caffeinate -i`; refuses if `EVERYAPP_TEST_ACCOUNTS`, `CLOUDFLARE_API_TOKEN` or `EVERYAPP_GATEWAY_URL` is set in its own environment; reads `accounts.json` (must be mode 600) and `providers.env`; takes the O_EXCL lock `locks/<accountId>.json` (pid, runId, startedAt, host; stale after 3 h); enforces a 30-minute gap since that account's `lastTeardownAt` (Cloudflare's SOA negative TTL is 1800 s) and prefers the other account; `docker info` must answer (memory recorded; `--parallel` refused under 14 GiB), `docker rm -f` of stale `loop-*` containers, host and container clocks within 60 s, `lsof -nP -iTCP -sTCP:LISTEN` recorded (an all-interfaces listener is reachable from the container through `host.docker.internal`; loopback-only ones are not, tested). In a sibling container with exactly `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`: `cf auth whoami` must show `tokenValid: true`, `authSource` the env token, accounts exactly `[accountId]`, none forbidden; `cf accounts subscriptions get` recorded (Workers Paid, or the Free-plan live check); `cf zones list` shows the zone active; `GET /accounts/{id}/workers/subdomain` recorded; `https://everyapp.com/llms.txt` probed into `fixtures.docs_url`. A bad token is a fixture error: nothing runs.
2. **Wipe.** `everyapp teardown --account-id <id> --dry-run --json` in the sibling container (the plan is `fixture.preRunInventory`, `preRunPlanTotal` must end at 0), then `--confirm <id> --json` with the id typed at `/dev/tty` or read from the confirm file; the inventory is re-polled up to 3 minutes; then `cf dns records list -z` must show nothing at or under `apps.<zone>`. An in-account marker younger than 2 hours (KV `every-loop-run-<runId>`) makes the teardown refuse unless `--force`.
3. **Sandbox.** `docker create --name loop-<runId> --platform linux/arm64 --cpus 4 --memory 6g --pids-limit 4096 --init -u dev -w /work/every-app --env-file <600 temp file, deleted after create> everyapp-loop:<tag> sleep infinity`, then `docker start`. The env file holds exactly `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, the one provider variable and `EVERYAPP_EVENT_LOG=/loop/everyapp-events.ndjson`; `CI` is never set (with it, `setup` hides the owner link). No socket, no mounts, no GitHub token.
4. **Checkout in** (section 4.6): `git bundle create` of `--ref` on the host, `docker cp`, `git clone /loop/launch.bundle /work/every-app` inside. The prompt (section 7) is written to `/loop/prompt.txt`. `docker stats` sampling starts (every 30 s).
5. **Harness, turn 1.** `docker exec -i -u dev -w /work/every-app loop-<runId> <command line from 4.4>` with stdin at EOF (the prompt comes from a file or stdin, never `sh -c "$(cat …)"`), stdout and stderr streamed line by line through the adapter into `events.jsonl` (every line parsed as JSON; `receivedAt` stamped) and teed to the run directory as they arrive, so a dead driver still leaves a record. In parallel, `docker exec tail -n +1 -F /loop/everyapp-events.ndjson` feeds the scripted user. Once, while `setup` runs, `/proc/<pid>/environ` of the running `everyapp` is read for `CI`, `TERM`, `SHELL` into `toolEnv`.
6. **Scripted user** (section 4.5): the domain answer, the owner claim within seconds of `action_required claim_owner`, the subdomain PUT if `register_workers_subdomain` appears, `--team` under `--with-access`, resume with a universal reply when the harness ends a turn without `DONE`, caps. A `setup` start with no end in the event log means wait, not reply.
7. **Turn 2, planned.** After `setup` reaches `done`, if the harness has not already created and deployed an app: "Now create an app called hello and deploy it: `pnpm everyapp create hello --json`, then from its folder `pnpm everyapp deploy --json`; tell me its URL." Recorded as an expected hand-off (`create_app`), not an intervention.
8. **Verifier** (section 4.7) from the host and from a sibling container with a pristine clone of the same commit, never the harness's tree or words.
9. **Collect.** `docker cp` of `/loop/*`, the harness's session store through an allowlist per harness (Claude `~/.claude/projects/**/*.jsonl` and `tool-results/`, Codex `~/.codex/sessions/**`, OpenCode `opencode session export`, Hermes the stream only, Cursor the stream only), `docker diff`, `docker logs`; everything through the redactor; `UPDATE owner_setup_tokens SET expires_at = 0 WHERE consumed_at IS NULL` through the D1 query API (`src/cf.ts`); `docker rm -f` (or, with `--keep`, `docker cp` of a redacted copy; never `docker commit` of a container that held secrets).
10. **Teardown again** in a `finally`; `postRunFootprint` recorded; the lock released; `run.json` written; `pnpm loop report` renders the committed files; `pnpm loop findings` prints the hand-off text for the thread.

### 4.3 The sandbox image

`Dockerfile`, `FROM node:22-bookworm`, native arm64 (amd64 under emulation as a fallback, verified for node): `git curl ca-certificates unzip procps build-essential`; `npm i -g pnpm@10.34.5` (not corepack: its per-user cache is empty for `dev`); `useradd -m dev`; `npm i -g @anthropic-ai/claude-code@2.1.309 @openai/codex@0.163.0 opencode-ai@2.1.3` as root (global, on PATH for everyone); then `USER dev` and the per-user installers as `dev` so their binaries land in `/home/dev`: `curl https://cursor.com/install -fsS | bash` (writes `~/.local/share/cursor-agent` and `~/.local/bin/agent`; linux-arm64 supported), `curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash -s -- --non-interactive --skip-browser --skip-computer-use` (writes `~/.hermes`, `~/.local/bin/hermes`, pins its own uv and Python); `/etc/profile.d/loop.sh` prepends `/home/dev/.local/bin` for any login shell a harness opens; `ENV PATH` includes `/usr/sbin:/sbin`. A build-time assertion runs `command -v pnpm claude codex opencode agent hermes` as `dev` and fails the build if one is missing. Seeded as deviations: `~/.claude/settings.json` `{"skipDangerousModePermissionPrompt": true}` and `~/.claude.json` `{"hasCompletedOnboarding": true}` (`claude_consent_seeded`). "No prior state" means no sessions, memories, logins or caches, not an empty `$HOME`. The tag is a hash of the Dockerfile and pins; `ls -la $HOME` and every `--version` are recorded per run; a pin bump is a deliberate edit and shows in the report.

### 4.5 The scripted user and the owner claim

**The claim, settled.** The scripted user never claims from the harness stream, because every harness returns tool output only when the tool call ends while `setup` blocks in `waitForSetupLink` for up to 15 minutes after printing the link (verified by three reviewers against `setup-link.ts`); Claude Code backgrounds the command, Hermes caps tool results at 5000 characters, Claude cuts a failing result to a 10 KB excerpt and a large one to a 2 KB preview, OpenCode streams the last 2000 lines, Cursor's shell result is undocumented; and every rerun's `mintSetupLink` expires the link just seen, so a stream-timed claim races the agent and manufactures loop-induced stalls.

- **Primary: the CLI event log.** `packages/cli` gains a dormant seam, about 30 lines around `createNdjsonSink` and `createHumanSink` in `lib/output/events.ts` plus the launcher: when `EVERYAPP_EVENT_LOG=<path>` is set, every invocation appends `{type:"invocation", pid, argv, cwd, json, isatty:{stdin,stdout,stderr}, ci, ts}`, every event verbatim regardless of `--json` (honouring `maySetupLinkBeShown`, so the link is absent exactly when a person would not see it), and `{type:"exit", code, ms}` from `process.on("exit")`. Tested with the existing sink tests; auto-merge class; invisible to the agent. The driver tails it and, within seconds of `action_required claim_owner`, POSTs `https://apps.<zone>/api/setup/claim` with `Content-Type: application/json`, `Origin: https://apps.<zone>` and `{token, name: "Loop Owner", email: <accounts.json email>, password: <random, memory only>}`, resolving at the zone's authoritative nameservers (`src/dns.ts`, a `node:dns/promises` `Resolver` on the zone's NS records, the same idea as the CLI's `lib/domains/authoritativeDns.ts` without importing it), retrying with backoff up to 10 minutes on dns, tls, 5xx and `ECONNRESET`, never on 4xx except expired or consumed (then re-claim on the newest link). `setup`'s own 5-second poll then finishes the step identically on every harness. The seam also makes `everyappCommands[]`, every error and warning, each `setup` rerun, `OWNER_NOT_CLAIMED` with its cause (`dropped_json_flag` vs `ci_set_by_harness`) and every timing come from the CLI's own `ts`, independent of truncation. `pnpm run deploy`, `pnpm exec everyapp`, `node_modules/.bin/everyapp` and `npx everyapp` are all covered.
- **Fallback and control mode (`--no-event-log`): the D1-side claim.** From harness start the driver polls, every 5 s with the account token, `SELECT id FROM owner_setup_tokens WHERE kind='claim' AND consumed_at IS NULL AND expires_at > <now>`; on a new row it mints `est_<32 random bytes base64url>`, `UPDATE owner_setup_tokens SET token_hash = <sha256> WHERE id = ? AND consumed_at IS NULL`, and POSTs the claim as above. `findClaimLink` matches any active row by hash and `consume(id)` flips exactly the row `setup` is polling, so `setup` prints "Owner account created" as if a person had clicked. `403 INVALID_OR_EXPIRED_SETUP_LINK` means `setup` reran: poll again. `409 ALREADY_CLAIMED`, or `status.owner.email` differing from the loop's email, is `harness_self_claimed`. No CLI change; identical on all five harnesses; the D1 row count is also the number of setup runs that reached the owner step.
- **Telemetry only:** whether the `est_` URL or an "open this link" sentence appeared in assistant text (`linkSurfacedToPerson`), `linkEmittedAt` from the CLI's `ts`, `claimedAt`, `claim.how: event-log|d1|none`.
- **Never:** pre-creating the owner (it destroys the first-time experience), or a test-only claim flag in the product. `OWNER_NOT_CLAIMED` stays a named verdict, `fail-onboarding:owner_link_not_shown`, with `cli` and `prompt` as owners.
- `--claim-after immediate|turn-end`: immediate is the Sunday default (the hand-off is then invisible in a pass, and the record says so); turn-end measures the hand-off itself (does the agent relay the link and wait) and is a labelled variant.

**Replies.** A fixed table, every reply logged in `scriptedUserTurns[{at, trigger, reply, expected}]`: the domain question gets "My domain is <zone>" (never "use apps.<zone>", which invites `apps.apps.<zone>`; the recorded argv must contain `--domain apps.<zone>`); `register_workers_subdomain` gets the REST `PUT /accounts/{id}/workers/subdomain {subdomain: "everyapp-loop<n>"}` with the token, a 10-second wait, then "Done, continue"; `ACCESS_TEAM_REQUIRED` under `--with-access` gets `--team everyapp-loop<n>`; `cloudflare_login`, `choose_account`, `upgrade_workers_paid`, `add_domain` and `DOMAIN_REQUIRED` after the domain was given are fixture errors, never answered. A turn that ends without `DONE` or `BLOCKED` and without an expected hand-off gets one universal reply carrying every known answer ("My domain is <zone>. The Cloudflare token is in CLOUDFLARE_API_TOKEN. The owner account exists. Continue; if blocked say BLOCKED: <why>."), counted as an intervention; a `setup` start without an end in the event log means wait up to 15 minutes before any reply, whatever the harness process did. Caps: 3 nudges (expected hand-offs unlimited), 90 minutes per run with per-phase budgets, 2 resumes after a harness exit without a result event (`resumes[]`). `expectedHandoffs = {domain question, claim_owner, register_workers_subdomain, create_app, ACCESS_TEAM_REQUIRED}`; everything else a person would have typed is `interventions[]`. `pnpm loop answer <runId> "<text>"` lets a person watching `docker logs -f` unstick a run through the native resume, recorded `interventions[] {source: person}`.

### 4.6 The checkout before the public repository exists

`git bundle create /tmp/launch.bundle <ref>` on the host from any local commit (no push, no credentials), `docker cp`, `git clone /loop/launch.bundle /work/every-app` inside the container: a real clone with the real HEAD. Not a `git archive`: without `.git`, `hashCheckoutTree` returns null, the install row carries no tree hash, the release cache is off, `status.upToDate` is null (the free tamper check is lost) and `pnpm install --frozen-lockfile` fails with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` (verified; pre-registered as a product finding, since agents add that flag and `CI=1` implies it). The prompt is the section-7 draft with step 1 replaced; that draft is not yet what a visitor sees (section 7, "Where it lives"), so until `setup-prompt.txt` lands the loop measures a text nobody can paste yet, and the prompt sha256 in `run_key` is what keeps that honest. The record carries `checkout: {commit, how: "bundle"}`, `cli: {commit, version}`, `prompt: {variant: "checkout-present", sha256, text in the run dir}`, `deviations: ["checkout_preplaced", "api_token_auth", "event_log", "claude_consent_seeded", …]`, `agentDocs: {present, commit}` (the agent docs are on main since #420, so this is the checkout's commit, recorded so a docs change shows up as a new key, not a deviation) and `fixtures.docs_url`. The day `every-app/every-app` is public, `--checkout clone --prompt-variant public` runs the verbatim prompt and the clone becomes part of what is measured; reports compare only within a `run_key` that includes the prompt sha and commit, so week-1 and launch-day runs are never silently mixed.

### 4.7 The outside-in verifier

A plain TypeScript module, `src/verify.ts`, run by the driver: HTTP probes from the host with `redirect: "manual"` and authoritative DNS, and `everyapp status --json` from a sibling container (`docker run --rm` of the same image, a pristine clone of the same commit, the pnpm store volume mounted only here, exactly the token and account id in its env), never the harness's tree (`pnpm everyapp` rebuilds dist from src, so a verifier in that tree would grade the agent's own patch) and never the harness's words. Every probe's raw evidence goes to `verify.json` so `pnpm loop replay <runId>` recomputes the verdict after a rule change. The harness must have: completed `setup` to `done` with the owner claimed through the loop's claim, run `create <name> --json` then `deploy --json` from the app folder, and printed `DONE` with the Gateway URL. ### 4.8 The decision table

Four verdicts, evaluated in order, first match wins, each with a `reasonCode`; `verifier.version` and `decisionTable.version` in every record.

| Verdict | Rule |
| --- | --- |
| `fail-infra` | preflight or the whoami gate failed; a fixture `action_required` (`cloudflare_login`, `choose_account`, `upgrade_workers_paid`, `add_domain`, `CLOUDFLARE_TOKEN_REJECTED`) or a non-empty pre-run plan (`reasonCode: fixture_*`); exit 137 or a `docker stats` peak within 5% of the limit; the harness exited on a provider 401/429/529/overloaded with no later turn; an everyapp error carrying a Cloudflare 5xx or `CfTimeoutError`; `CERT_PENDING` past 15 min; authoritative DNS answers but the system resolver says NXDOMAIN (`dns_negative_cache`); npm `ECONNRESET|ETIMEDOUT|503`; the 90-minute cap without an idle loop; the Access team name taken; `waiting for the deploy lease` after a harness kill; the verifier's own container or `pnpm install` failed (`inconclusive`); a budget kill (`budget`) |
| `fail-onboarding` | a non-infra everyapp exit-1 code; `BLOCKED`; an unknown hand-off; caps exceeded; `OWNER_NOT_CLAIMED` (`owner_link_not_shown`, with `toolEnv` saying whether `--json` was dropped or `CI` was set); `app.by === "verifier"`; `tainted` or `shortcut`; any verifier row red; `falseDone` (the harness printed `DONE` while a check was red: a first-class finding, never "partial") |
| `pass-with-intervention` | verifier green, but `interventions[]` is non-empty: a nudge, a repeated answer, a resume after a harness exit, a person's answer, no `DONE` printed, `harness_self_claimed` (plus a finding) |
| `pass` | verifier green; every scripted turn an expected hand-off; `DONE` with `reportedUrl === https://apps.<zone>`; not tainted, no shortcut |

`interventionNeeded = interventions.length > 0`. `--repeat-on-infra 1` reruns a fail-infra once with a new runId and `retryOf`. A finding reaches TODO.md or a sibling thread only when it is an everyapp exit-1 code or an `action_required` the prompt and docs do not cover, or when it recurs in two or more runs or two or more harnesses; infra never routes. `gap_over_60s` counts only between a tool result and the next tool call with no tool in flight. Same `run_key` with mixed verdicts is `flaky`.

## 5. The clean-slate guarantee

**The command.** `everyapp teardown --account-id <id> [--confirm <id>] [--dry-run] [--json] [--verbose]`, those five flags and no other, already built in this worktree (`packages/cli/src/commands/teardown/{command,index}.ts`, `lib/teardown/{guards,inventory,plan,delete}.ts`, `lib/cf/r2.ts`, 2,275 lines with FakeCloudflare end-to-end tests), documented in `SKILL.md` and the runbook. It is the one destructive path; the loop does not grow a second wipe (two allowlists and two forbidden constants would drift, and the plan has no 0.75 agent-day for it). `pnpm loop` calls it in a sibling container with `EVERYAPP_TEST_ACCOUNTS` and `CLOUDFLARE_API_TOKEN` set for that child only (a Linux container has no macOS Keychain, so Ben's OAuth login, which host-side `cf` still reads while an env token is set, is structurally unreachable). Its PR, #444, is open against main and **held for Ben**; the loop runs it from this branch until then. This doc asks nothing more of that PR: no new flag, no retry logic (both would be new work and are not in section 9).

**Guards, in order, all before any read but `cf auth whoami` and before any write.** `TEARDOWN_INVALID_ACCOUNT_ID` (not 32 hex); `TEARDOWN_ACCOUNT_FORBIDDEN` (`FORBIDDEN_ACCOUNTS = ["23bc28f0b638fbfc1c7f838573c17ee3"]`, refused before any list is read); `TEARDOWN_NOT_ALLOWLISTED` (the union of `EVERYAPP_TEST_ACCOUNTS` and `~/.config/everyapp/test-accounts`; ids only, no secrets; the driver derives the variable from `accounts.json` for the child and refuses to start if it is already set in its own environment); `TEARDOWN_NEEDS_TOKEN`; then whoami. **The whoami gate, as built in `lib/teardown/guards.ts` `checkTokenScope`** (the first draft rejected only on `!authenticated`, which a bogus env token satisfies: `authenticated: true, tokenValid: false, accounts: []`, verified live): `!authenticated || tokenValid === false` is `CLOUDFLARE_TOKEN_REJECTED`; an `authSource` that does not name `CLOUDFLARE_API_TOKEN` (a person's OAuth login) is `TEARDOWN_NEEDS_TOKEN`; every account the token lists must be on the allowlist and none forbidden, else `TEARDOWN_TOKEN_TOO_BROAD`; the target must be among them, else `TEARDOWN_ACCOUNT_NOT_VISIBLE`. So a token that sees both test accounts is accepted, by design: the allowlist, not a one-account rule, is the boundary, and the runbook still asks for one account per token. `CfWhoamiOutput` already carries `tokenValid` and `authSource`; `guards.test.ts` and `commands/teardown/index.test.ts` cover the bogus-token shape, the OAuth `authSource`, an account outside the list and the forbidden id. The loop's `withTestAccount()` applies the same checks on the same whoami JSON before every `cf` or `everyapp` call it makes, plus one stricter rule of its own (4.2 step 1): the token must list exactly the target account, because the runbook mints one token per account and a loop token that sees both lanes is a mistake worth stopping on.

**Dry run and confirmation.** `--dry-run` is what the loop runs first and what a person should run first: it prints the inventory grouped by kind with ids as `data.plan` and exits 0 with nothing written. Without `--dry-run`, at a terminal the account id is typed (never y/N); under `--json` or without a terminal the id is passed again as `--confirm <id>`, else the run stops with `TEARDOWN_CONFIRMATION_REQUIRED` whose `data.rerun` carries `--confirm <id>` and `data.authorize: true`. There is no `--yes`. The loop forwards `--confirm` from the id typed at `/dev/tty` when attended, or from `~/.config/everyapp/onboarding-loop/confirm-<accountId>` (mode 600, written once by Ben by hand, content `delete everything in <accountId>`) when unattended; the second confirmation is thus outside the allowlist mechanism, and honest about unattended runs: there, the rings that protect Ben's account are the separate Cloudflare user, the account-scoped token, the allowlist, the forbidden constant and the exact whoami.

**Deletion order and the calls per kind** (each kind its own `step`; a failure is a `TEARDOWN_DELETE_FAILED` warning and the item goes to `kept`; the command itself does not retry, there is no backoff in `lib/teardown/*.ts` or `lib/cf/*.ts`, and it declares leftovers from one pass. Retrying is the loop's job, section 4.2 step 2: it re-runs `--dry-run` for up to 3 minutes and calls the teardown again while the plan is not empty; how Cloudflare lists a certificate pack mid-deletion is a first-live-run observation, not a rule written here):

| # | Kind | Inventory | Delete |
| --- | --- | --- | --- |
| 1 | Access applications on the gateway host and `*.<base>`, then the policy "Every App gateway members" | `cf zero-trust access applications list`, `… policies list` | `cf zero-trust access applications delete <id>`, `… policies delete <id> --force`; the OTP identity provider and the team are listed as kept |

| 3 | Workflows whose script is `every-*` | `cf workflows list` | `cf workflows delete <name>` |
| 4 | Workers: apps, their helpers `every-<org>-<app>--<name>`, the gateway `every-app-gateway` last, each with references | `cf workers list` (with their Custom Domains) | `cf workers delete <name> --force`; the Custom Domains go with each (live check on run 1: no `references.domains` left) |
| 5 | Certificate packs on the gateway host, each app host, each live domain (never the zone's universal pack) | `cf ssl certificate-packs list -z` | `cf ssl certificate-packs delete <id> -z`, **every planned pack, unconditionally** (`delete.ts` step 5; the runbook says the same). | 9 | Hyperdrive `every-*--*` | `cf hyperdrive list` | `cf hyperdrive delete <id>` |

Then `done` with `removed[]`, `kept[]` and the plan; a second run on a clean account says nothing is left and exits 0. **Never deleted:** the zone, the Workers Paid subscription, the Zero Trust team and its identity providers (no delete API; permanent), the workers.dev subdomain, the API token, the user, any DNS record not under the gateway host, any resource not named `every-*` and not recorded in the gateway D1, anything in any other account (the token sees none, by construction). The loop adds, around the command: the in-account run marker it refuses on, the post-wipe DNS check, `inventory-before` and `inventory-after` on every record, and `UPDATE owner_setup_tokens SET expires_at = 0 WHERE consumed_at IS NULL` before the D1 goes on any abnormal exit.
