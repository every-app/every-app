# Events: what they are, how general they are, and a simpler design

Written 2026-11-02 for Ben, from main at `673bed8c8`. Design only: nothing here is built yet.
It answers Ben's question of 2026-11-02: "What are the pushes into apps? Is this events system generalized? It would be sweet to support arbitrary webhooks. What do you think a better design is?"

It replaces the events part (I9) of `docs/design/2026-11-simplify-audit.md`. Ben's 2026-11-02 ruling keeps every events feature: the audit log, webhooks, the email sink, pushes into apps, and `emit()`. So this doc cuts complexity *inside* events. It doesn't cut the feature.

## 0. The short answer

- **Is it general?** The middle is: one bus, one table of subscriptions, one delivery loop with retries and a log. The edges aren't. Every event type is hand-written in about six places. Every destination has its own special rules. Every payload has one fixed shape.
- **Arbitrary webhooks?** Any HTTPS URL works today, but only if it accepts our JSON. A plain Slack incoming webhook or a Discord webhook refuses it (our own docs say "won't work directly"). That's the real gap.
- **The fix:** each subscription gets a **format**: Every App JSON (the default), Slack or Discord. Signing moves to **Standard Webhooks**, so receivers use an off-the-shelf library instead of our snippet.
- **One catalogue:** one entry per type holds its name, summary, who may receive it and its email link. Apps declare their own events in the manifest, so they appear in the same picker and docs as the Gateway's.
- **Fewer types:** 60 → about 33. One `<thing>.changed` type, with a `changes` map, replaces a new type per admin action.
- **Delete the special cases:** the `ping` type, the built-in Cap alerts flag, `apps.setup_state`, `tool.error`, `connection.used`, `subscription.redelivered`, read-time summaries and the CLI's second copy of every event (the outbox).
- **Keep the engine:** D1 rows, a first attempt under `waitUntil`, the per-minute retry sweep, the delivery log, redeliver, the URL rules and the no-secrets rule. That part works and is small.
- **Pushes into apps** stay a destination like the others. The app's manifest asks for event types, the way it asks for scopes.
- **Rough size:** ~5–6k lines out and ~1.5k in. About 2.5k of the "out" is the CLI outbox, which the cli-admin-api lane removes anyway. Six PRs after the cli-admin-api prerequisite, effort M.

## 1. In plain English

### What an event is

An event is one line in a diary the Gateway keeps: "this happened, at this time, because of this person". Examples from today's catalogue:

- `member.joined`: "jo@acme.com joined as member".
- `cap.warning`: "crm is at 80% of its monthly cap ($40 of $50)".
- `tool.blocked`: "Claude's call to crm_delete_contact was blocked: destructive".
- `app.workout.workout.finished`: an app's own event, sent by Workout with `emit()`.

Each one is a row in D1's `events` table: type, time, actor, `data` (ids, names and counts, never a secret) and the organization. A receiver gets this JSON:

```json
{ "id": "evt_01M5…", "type": "member.joined", "version": 1,
  "summary": "jo@acme.com joined as member", "time": "2026-11-02T09:15:03Z",
  "gateway": "https://apps.acme.com", "organization": { "id": "org_…", "slug": "acme", "name": "Acme" },
  "actor": { "kind": "user", "email": "ada@acme.com" }, "data": { "user": { … }, "role": "member" } }
```

### Where events go

| Destination | What it does | Example |
|---|---|---|
| **Audit log** | Every event row *is* the audit log. Admin → Activity → Audit, `everyapp workspace audit`, `everyapp_workspace_audit`. 90 days. | "Who removed Jo, and when?" |
| **Webhook** | A signed JSON POST to any public HTTPS URL. Retried 6 times over ~35 h, then **Dead**. 30-day delivery log, Redeliver. | Zapier Catch Hook → open a Linear issue on `tool.blocked`. |
| **Email** | One mail per owner (or owner and admin), through the Gateway's sender. Never to an outside address. | "Cap alerts": at 80% and 100% of a cap. It's made automatically on the first cap. |
| **App** | The Gateway POSTs the event to an app's own Worker. See below. | Birds hears `member.removed`. |

Subscriptions pick types by pattern: `member.joined`, `member.*`, `app.crm.*`, `*`. Admins manage them in Admin → Events, with `everyapp events …`, or with the `everyapp_workspace_events*` tools.

### What "pushes into apps" means

An app can ask the Gateway to tell it when something happens in the workspace. Birds' `everyapp.config.ts` says:

```ts
events: { subscribe: ["member.*", "connection.*"],
          why: "Suspend the Agents a departing member sponsors, and refresh credentials when connections change." }
```

The deploy turns that into a subscription whose destination is "the Birds Worker". When Ada is removed, the Gateway sends `member.removed` to `POST /__everyapp/events` on Birds' Worker. It goes over the service binding, not the internet. A 60-second Gateway token bound to the exact body authenticates it. The SDK checks the token and calls `everyApp(handler, { events: { on } })`, and Birds suspends Ada's agents. It's built in #901, on main, and only Birds uses it.

It works in the other direction too. An app *sends* its own events with `emit({ env, event: "workout.finished", data })`. They become `app.workout.workout.finished` and can go to any webhook, email or app. Workout and the starter call it (#643).

### What it is today, by the numbers

- 60 event types in `packages/sdk/src/internal/events.ts` (63 at the audit).
- About 30 Gateway files emit events, and 13 CLI files write them straight into D1 (the outbox).
- `apps/every-app-gateway/src/server/events/`: 4.5k lines of code, plus 3.6k of tests. `catalogue.ts` alone is 1,644 lines.
- Tables: `events`, `event_subscriptions`, `event_deliveries`, plus `apps.setup_state`.
- Surfaces: Admin → Events (about 2k lines of UI), 9 CLI subcommands, 7 event tools plus the audit tool, `emit()`, `events.on`, and `verifyWebhook`.
- Live use on everyapp.team: 0 webhook or email subscriptions. Birds uses the app destination on its own branch.

## 2. How general it really is

### What is already general (keep)

- **One bus.** Every emitter calls `emit()` (`server/events/bus.ts`). One batch writes the event row and one delivery row per matching subscription.
- **One delivery loop.** `deliver.ts` claims a row, builds the envelope, calls one of three senders, then marks the row delivered, retrying or dead. Retries, the dead state, the log and redeliver are the same for every destination.
- **Sensible webhook hygiene.** HMAC with a timestamp (Stripe's scheme), no redirects, a 10 s timeout, a 1 KB read of the answer, SSRF rules (`target.ts`), and a key name that looks like a credential is refused.
- **Pattern subscriptions**, at-least-once delivery, and event ids that sort by time. Receivers dedupe on `id`.

### Where it isn't general

1. **One fixed payload.** Every webhook gets the envelope above. Slack incoming webhooks need `{ "text": … }` and Discord needs `{ "content": … }`, so both answer 400. `docs/events.mdx` tells people to put Zapier or Workflow Builder in between. That's the "arbitrary webhooks" gap. Svix calls the fix "transformations" and Stripe calls it "event destinations".
2. **Six places per event type.** Adding a type touches:
   - `EVENT_TYPES` (the name);
   - a builder in `catalogue.ts` (the `data`);
   - a case in `summarize()` (the line, rebuilt every time a row is read);
   - `adminPathFor()` and `eventEmailFields()` (the email);
   - `auditTypeLabel` and `auditSubjectOf` in `packages/sdk/src/internal/audit.ts`;
   - the docs table.

   The CLI adds a seventh, its own `data` literal, so the two writers can drift.
3. **A type per admin action.** `cap.raised` and `cap.changed`; `mcp_app.enabled`, `.disabled`, `.updated` and `.tool_changed`; `group.updated`, `.members_changed` and `.apps_changed`; `ai.default_changed` and `ai.model_changed`; `access.changed`; `signin_provider.added` and `.removed`. Each new setting has meant a new type, a builder, a summary and a docs row.
4. **Two kinds of event, told apart by a guess.** Gateway types live in the catalogue. App events are an undeclared pattern, `app.<id>.<name>`, and `isAppOwnEventType` tells them apart from the Gateway's own `app.*` by counting dots. App events can't be listed in the Add dialog or the docs, because nothing declares them.
5. **Each destination has its own rules.**
   - App: an allowlist of six families plus an exclusion list (`APP_SINK_EVENT_FAMILIES`, `APP_SINK_EXCLUDED_TYPES`), checked in three places. Apps never get their own events back. Admins can't edit an app's subscription, and removing it only pauses it.
   - Email: recipients by role, with "already mailed" markers kept in the rate-limit table.
   - Cap alerts: a `builtin` column, plus an "ensure it exists on the first cap" written twice (Gateway `ensureCapAlerts`, CLI `capAlertsStatement`). Removing it disables it instead, so it never comes back.
6. **The test ping is threaded everywhere.** `ping` is a catalogue type with an `only` route. Matching skips it, delivery lets it reach paused rows, the audit log hides it, and `*` excludes it.
7. **The bus logs itself.** `subscription.*` events are excluded from `*` so a catch-all doesn't hear about its own creation. `subscription.redelivered` repeats what the delivery log already shows.
8. **Events made by watching reads.** `apps.setup_state` exists only to notice ready ↔ needs-setup changes, and it's checked on *list* views with a per-isolate cache. Two Gateway paths feed it: list views (`services/listedAppSetup.ts`) and the perimeter's setup gate (`refuseUnreadyApp` in `server/app-needs-setup.ts`). The CLI also writes it after `configure`, `secret` and `deploy`. Nothing else reads the column. The gate itself (an app that needs setup refuses requests) stays; only its event side goes.
9. **Copies of the tool-call log.** `tool.blocked` and `tool.error` copy rows of `mcp_tool_calls`. The audit log then hides them by default because the Agent tab already lists every call. `connection.used` is a once-a-day ping in the same spirit.
10. **Two writers.** The CLI writes event and delivery rows itself (`queueEventFromCli`), probes for old schemas, and copies the Gateway's matching and allowlist logic. Everything the Gateway learns about events, the CLI has to learn again.
11. **Filtering is by type only.** "Cap alerts for crm only" can't be expressed, although every app event row already has `app_row_id`.
12. **Our own signature format.** It's fine, but it's ours. The docs carry verifiers in Node, Python and Go, and `verifyWebhook` has an `everyapp` mode for it. Standard Webhooks already has maintained libraries in a dozen languages.

## 3. The proposal: one catalogue, one subscription model, three destinations

```
something happens ──► emit(type, data, summary)          one writer: the Gateway
                         │
                         ├─► events row  ══ the audit log (90 days)
                         │
                         └─► for each subscription where  pattern matches type
                                                       and (no app filter, or the event's app is in it)
                                  └─► delivery row ──► webhook  (format: everyapp | slack | discord)
                                                   ──► email    (owners | admins)
                                                   ──► app      (its Worker, over the binding)
                             first attempt now · retries from the per-minute sweep · 30-day log · redeliver
```

### 3.1 One catalogue, one entry per type

One module holds the whole contract for a type: `apps/every-app-gateway/src/server/events/catalogue.ts`, with names re-exported to the SDK for the docs test.

```ts
memberRemoved: event("member.removed", {
  description: "A member was removed",
  apps: true,                       // may an app subscribe to it?
  page: "/admin/users",             // the email's button
  summary: (d) => `${d.user.email} was removed`,
}),
```

- **The summary is computed once, at emit, and stored** in a new `events.summary` column. The audit log, the email and the envelope all read the stored line. `summarize()` at read time, `eventEmailFields`, `adminPathFor`, and the label and subject tables in `sdk/internal/audit.ts` go away. The audit subject comes from the standard keys in `data` (`user`, `app`, `group`, `provider`).
- **Email shows the summary, so the summary carries the numbers.** Without `eventEmailFields`, cap emails lose their field table (Cap, Cost this month, Month) and become the summary line plus the button. That's a visible change to a kept feature, so cap summaries keep every number: "crm is at 80% of its monthly cap ($40 of $50 in November)". If Ben wants the table back, an optional `fields(d)` on the entry restores it, for email only.
- **`apps: true` replaces the family allowlist and the exclusion list.** It's still an allowlist, one flag per type, so a new type reaches no app until someone says so.
- **App events join the catalogue.** The manifest declares them:

  ```ts
  events: { emits: { "workout.finished": "A member finished a workout" },
            subscribe: ["member.*"], why: "…" }
  ```

  `emit()` refuses a name the manifest doesn't declare, with `event_not_declared`. It also accepts an optional `summary` line, and the default is "Workout: A member finished a workout". The Add dialog, `everyapp events types` and the docs list installed apps' events next to the Gateway's. A new `events.source` column (`gateway` or the app id) replaces the dot-counting guess. The wire type stays `app.<id>.<name>`, so `app.crm.*` still works.
- **Drop `version`.** Every type is version 1 and nothing has bumped one. With no outside users, a breaking change is just a change.

### 3.2 Fewer types: `<thing>.changed` with a `changes` map

The rule is that a new setting on something that already exists is a new key in `changes`, never a new type. That's Stripe's `customer.updated` + `previous_attributes` and GitHub's `action` field. `data.changes` looks like `{ "name": { "from": "Old CRM", "to": "CRM" }, "access": { "added": [...], "removed": [...] } }`.

`changes` keys are fixed field names from the catalogue entry (`name`, `access`, `settings`, `members`, …), never user-chosen names. The no-secrets rule (`checkEventData`) refuses any key, at any depth, that looks like a credential (`secret`, `token`, `api_key`, …). Keying `changes` by a setting name such as `OPENAI_API_KEY` would make `queueEvent` throw and lose the event. So setting names stay values in a list, as `app.settings_changed` does today: `"settings": { "changed": ["OPENAI_API_KEY"] }`.

| Family | Today (60) | Proposed (~33) |
|---|---|---|
| member | 8 | the same 8 (Birds uses joined, removed, deactivated and reactivated) |
| workspace | `organization.renamed`, `.linked_dev_changed`, `access.changed`, `signin_provider.added`/`.removed`, `ai.default_changed`, `ai.model_changed` | `workspace.changed` (name, linked dev, Access, sign-in, AI default and model) |
| app (incl. MCP apps) | 11 `app.*` + 6 `mcp_app.*` | `app.installed` (first time it goes live), `app.updated` (new version), `app.removed`, `app.changed` (name, settings, access, email, tools, on/off, risk); `data.app.kind` says app, builtin or remote |
| cap | 4 + `app.paused_cap` | `cap.warning`, `cap.reached` (the app is now Paused), `cap.changed` |
| group | 5 | `group.created`, `group.changed` (name, members, apps), `group.removed` |
| tool | 2 | `tool.blocked` |
| connection | 3 | `connection.created`, `connection.revoked` |
| token | 2 | the same 2 |
| provider | 6 | `provider.added`, `provider.changed`, `provider.removed`, `provider.connected`, `provider.disconnected`, `provider.connection_expired` |
| subscription | 4 + `ping` | `subscription.created`, `subscription.changed`, `subscription.removed` |

The trade-off: a webhook that wants only access changes now gets every `app.changed`. The `changes` keys tell it which. If that turns out to matter, a `changes`-key filter can come later.

### 3.3 One subscription model

A subscription is **patterns + an optional app filter → one destination**.

- **`events`**: patterns, as today. `*` really means everything, with no ping or `subscription.*` exceptions.
- **`apps`** (new, optional): a list of app ids. "`cap.*` for crm only" is `--events 'cap.*' --app crm`. It matches on `events.app_row_id`, which every app event row already has.
- **Destination: `webhook`.** It has a URL, a secret and a new **`format`**:
  - `everyapp` (the default): the envelope, signed with Standard Webhooks. Works with Zapier, n8n, Make, Pipedream and your own code.
  - `slack`: `{ "text": summary }`. Works with Slack incoming webhooks, and also Mattermost and Rocket.Chat.
  - `discord`: `{ "content": summary }`.

  Each format is a preset: a function from envelope to body, about 10 lines each. There's no user-written code to sandbox. Adding Teams or ntfy later is one more preset.

  Summaries carry strings that members and admins control (names, group and app names) and, under §3.1, an app's own `emit({ summary })`. So the presets escape them. `slack` escapes `&`, `<` and `>` (Slack's rule), which defuses `<!channel>` and `<https://evil|Open Usage>`. `discord` sends `allowed_mentions: { parse: [] }`, so `@everyone` and role pings don't fire.
- **Destination: `email`.** `owners` or `admins`, as today. Still members only, never an address.
- **Destination: `app`.** It names an app row. The deploy creates and updates it from the manifest's `events.subscribe`, and only for types with `apps: true`. Admins can pause, test and redeliver it. Its patterns belong to the manifest, the way scopes do. Everything else is the shared engine.
- **Cap alerts** becomes an ordinary email subscription, made when an organization is created (and by migration for existing ones). The `builtin` column, both "ensure" functions and remove-means-disable go. Deleting it deletes it, and nothing recreates it.
- **Send test** sends one sample event to that destination directly. It writes no rows and reports the status, latency and error. The `ping` type and the `only` route go. A test must still be unmistakable, or Zapier zaps fire and an app such as Birds acts on fake data. So it carries the reserved type `test`: only direct sends use it, no pattern (not even `*`) matches it, and `emit()` refuses it. It also carries `"test": true` in the envelope and an `x-everyapp-test: 1` header. Slack and Discord see "Test from Every App". An app's `events.on` gets type `test`, as it gets `ping` today, so it ignores it by type.

### 3.4 Signing: Standard Webhooks

Use the [Standard Webhooks](https://www.standardwebhooks.com) spec. It's what Svix and many providers send.

- Headers: `webhook-id` (the event id, the same on every retry, so receivers dedupe on it), `webhook-timestamp`, and `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">`. We keep one convenience header, `x-everyapp-event: <type>`.
- The secret is `whsec_` plus **standard** base64 of 32 random bytes (the spec allows 24–64). We already use the prefix, but today's generated secrets are base64url (`generateSecret` in `subscriptions.ts`), which `standardwebhooks` libraries don't decode, so generation switches alphabet. `everyapp events add --secret` (today any 16–128 characters) is validated as `whsec_` + base64 of 24–64 bytes and refused otherwise.
- Receivers run `npm i standardwebhooks` (or the Python, Go, Ruby, PHP, Rust, Java or C# equivalents), so the three hand-written verifiers leave the docs.
- The app destination sends the same headers. It keeps the body-bound Gateway token in place of the HMAC, so apps hold no secret.

### 3.5 Arbitrary webhooks *into* apps

Ben's "arbitrary webhooks" may also mean *receiving* them, say a Stripe or GitHub webhook reaching an app. That already works the simple way: the app declares a `public` route and checks the signature itself. Birds does this for GitHub with its own configurable verifier (header, prefix, hex or base64: `apps/server/src/scheduledTasks/webhookVerification.ts`). No app calls the SDK's `verifyWebhook()` yet. Birds' verifier is the prior art for two small SDK changes that would cover most of the world:

- **`verifyWebhook({ provider: "standard" })`** verifies anything Standard Webhooks signs: Clerk, Resend, Svix users, and our own events. It replaces the `everyapp` mode.
- **`verifyWebhook({ provider: "stripe" })`** uses today's `everyapp` algorithm (`t=…,v1=…`, Stripe's scheme), but reads the `Stripe-Signature` header instead of `X-EveryApp-Signature` and accepts any of several `v1=` entries (Stripe sends more than one while a secret rolls). So it's a small new mode, not a rename.

A Gateway-level inbox (`POST /hooks/<id>` → an event → any destination, so one GitHub hook fans out to several apps) is possible on this model. But it adds a public route and stored secrets. **Not proposed now.** See question 1.

### 3.6 What stays exactly as it is

- The D1 tables as the queue and the log. The first attempt under `waitUntil`, and the per-minute sweep (the cron stays anyway for the deploy sweep). Claims, the retry schedule (Svix's is nearly the same), Dead after 7 tries, 30-day deliveries, 90-day events, redeliver.
- The target rules (`target.ts`, `EVENTS_ALLOW_PRIVATE_TARGETS`), the no-secrets key rule, 8 KiB app data, 600 emits an hour, 25 subscriptions per organization.
- Admin → Events, the CLI and the tools, all three (UI = CLI = MCP). The Add dialog gains a Format select and an Apps filter, and loses Built-in and ping.
- `events.on` in the SDK, and the same `AppEvent` shape minus `version`.
- Hosted mode: everything stays organization-scoped. A shared app that needs every organization's events gets one app subscription per organization it's granted to (Birds' doc item 5). The model allows that without changes.

## 4. What goes, the migration, size and order

### Deleted or merged

- 27 fewer event types (§3.2): most fold into `*.changed`. `ping`, `subscription.redelivered`, `tool.error`, `connection.used`, `app.ready`, `app.needs_setup` and `app.live` go (`app.live` folds into `app.installed`).
- `apps.setup_state`, `server/events/setup-state.ts`, `packages/cli/src/lib/gateway/setupState.ts`, and their callers: `recordSetupState` in `server/app-needs-setup.ts` (the setup gate) and in `server/services/listedAppSetup.ts` (list views), and the CLI's `deploy`, `configure` and `secret`. The setup gate itself stays. The "Needs setup" chip already shows the state, and `app.changed` records the setting names that changed.
- `summarize()` at read time, `adminPathFor`, `eventEmailFields`, and most of `sdk/internal/audit.ts`. They become the stored `summary` and a generic subject.
- `isAppOwnEventType`, `APP_SINK_EVENT_FAMILIES` and `APP_SINK_EXCLUDED_TYPES`. They become the `source` column, the per-type `apps` flag and the declared app events. The two lists go in PR 1. `isAppOwnEventType` goes in PR 5: pattern validation (`eventPatternProblem`, e.g. `app.crm.invoice.paid`) and `appSinkMayReceive` still need it until app events are declared.
- The `builtin` column, `ensureCapAlerts`, `capAlertsStatement` and remove-means-disable.
- The `only` route and every ping and `subscription.*` exception, in `bus.ts`, `deliver.ts`, `audit.ts` and `eventPatternMatches`.
- Our signature format and its three verifiers in the docs. The `everyapp` mode of `verifyWebhook` goes. A `standard` mode and a `stripe` mode (its algorithm, Stripe's header, several `v1` values) are added.
- The CLI outbox (`queueEventFromCli`, the schema probes, the event literals in 13 files). The CLI calls the Gateway, and the Gateway emits. This depends on the cli-admin-api lane, which moves CLI admin onto the Gateway's tools. Whatever the CLI still writes itself (a deploy's `apps` row) is announced by the Gateway when it activates the app (`app.installed` / `app.updated`).

### Added

- `events.summary` and `events.source`. `event_subscriptions.format` and `event_subscriptions.app_filter`.
- Manifest `events.emits`. `emit({ summary? })` and the `event_not_declared` code.
- Three webhook format presets. The Standard Webhooks signer. `verifyWebhook` `standard` mode.
- Format and Apps fields in the Add dialog, on `everyapp events add` (`--format`, `--app`) and on the tool.

### Migration (D1, expand then contract, per `release-migrations.test.ts`)

1. **Expand.** Add `events.summary` (nullable) and `events.source` (default `gateway`), backfilling `source` for `type GLOB 'app.*.*'` rows. Add `event_subscriptions.format` (default `everyapp`) and `app_filter`. Insert a Cap alerts email row for each organization without one.
2. **Backfill summaries before any type folds.** PR 1 keeps today's `summarize()` just long enough for a one-off pass that writes `events.summary` on every existing row. It runs from the Gateway's cron in batches, because SQL can't run the builders. Only then does PR 1 delete read-time `summarize()`, and PRs 2–3 retire types. So for the 90 days old rows live, the audit log still shows "Ada removed jo@acme.com" for `group.members_changed`. A redeliver of an old delivery (30 days) sends its real summary, not blank Slack text. Old rows keep their old types; no mapping.
3. **Secrets.** Live has 0 webhook subscriptions, so there's nothing to convert. Any row made before the switch gets a fresh `whsec_` secret, shown once.
4. **Contract** one release later (`-- everyapp:contract`): drop `events.version`, `event_subscriptions.builtin` and `apps.setup_state`.

## 5. Questions for Ben

1. **A Gateway inbox for inbound webhooks?** (`POST /hooks/<id>` → event → apps or webhooks.) Lean: **not now**. Apps take webhooks on `public` routes with `verifyWebhook`, which gains `standard` and `stripe`. Build the inbox when one webhook needs to reach two apps.
