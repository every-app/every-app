# MCP provider apps

The research behind it is [2026-10-mcp-provider-apps-research.md](2026-10-mcp-provider-apps-research.md). Since the evening of 2026-10-24 the person-facing name is **MCP apps** and the CLI group `everyapp mcp` (alias `provider`): [2026-10-mcp-apps-ui.md](2026-10-mcp-apps-ui.md) has the name, the launcher section and dialog, and the curated-versus-pass-through verdict; "provider app" below is the code's name.

## 1. The ask

People find Monid, Treg and DataForSEO useful because having the data in Claude lets them automate work. Ben wants them available at the gateway level: supported natively, like apps, exposed through the gateway's one `/mcp` so a member connects one MCP and gets them all, governed by the gateway (who can use them, which key, attribution, metering, scopes). Today DataForSEO and Context.dev are capabilities an app's Worker calls over REST through the gateway; no AI client sees them as tools, and OpenSEO wraps DataForSEO in tools of its own.

## 2. Decisions (Ben, 2026-10-24, in the MCP provider apps thread)

| Question | Decision |
| --- | --- |
| How a provider shows up | An `apps` row of a new tier `provider`, no Worker: Admin → Apps, the library, access rules, usage counters and the audit trail treat it like any app. |
| First provider | DataForSEO, curated: the key is on everyapp.team already and the capability proxy exists. |
| Proxy the provider's MCP, or curate over REST | Both: a curated set now; a generic remote-MCP proxy kind (Treg, Monid) next, built against an in-process fake until Ben opens accounts. |
| Whose key | The operator's Gateway setting (`DATAFORSEO_API_KEY`), as every capability today; per-organization keys are a hosted-tier feature later. |
| Turning on | Everything through the CLI, MCP and the UI where possible; the UI isn't always necessary. Built: `everyapp provider on|off|list`. The MCP way (a write built-in) and a UI toggle are follow-ups. |
| Default access | Nobody until granted, like a deployed app: the person turning it on, the owners and the admins get it; an admin grants others. |
| Live check | Ben's DataForSEO key against the free sandbox only, in the gateway's local `.dev.vars`; tests use a fake upstream. |
| Treg and Monid accounts | Not now: PR 3 ships the proxy kind against fakes. |

## 3. Design

### The row

`provider on dataforseo` writes an `apps` row in the install organization: `app_slug` the provider id, `tier` `provider` (`PROVIDER_APP_TIER`, `packages/sdk/src/internal/providerApps.ts`), `hostname` and `worker_name` null, the generated manifest (`providerAppManifest(id)`: the capability listed with `access: "read"` and a `why`), `status` `active` at once, `deployed_by_actor` the Cloudflare login, `is_default` false, plus `user_app_access` rows for the actor, owners and admins. The rules are pure functions in `packages/perimeter/src/registry/providerApps.ts` beside `planRegistration`; the CLI runs them against D1 (ADR-0003) in `packages/cli/src/lib/gateway/providerApps.ts`. A deployed app's id is refused (`APP_TIER_MISMATCH`, tombstones included), and a deploy under a provider id likewise. `off` is a tombstone like `everyapp delete`'s (access, tokens, tools snapshot and connections go); `on` again revives it as new.

The perimeter never routes the row (no hostname; `DrizzleAppRegistry` leaves tier `provider` out as it leaves tombstones out) and `getAppFetcher` reaches no Worker for it. `everyapp delete` and `everyapp email` refuse it (`APP_NOT_FOUND`: it has no Worker), and `everyapp status` and `secret list` leave it out of their per-app reports; `provider list|off` are its commands.

### Serving it

The gateway serves a provider app as an SDK app (`everyApp(handler, { id }, { tools: defineTools(...), publicKeys: [JWT_PUBLIC_KEY], issuer: GATEWAY_URL })`) that runs inside the gateway Worker (`apps/every-app-gateway/src/server/provider-apps/`). One seam changes: `appFetcherFor` in `catalog-sync.ts` returns an in-process fetcher for tier `provider` instead of a service binding. Everything downstream is what every app gets: the catalog snapshot in D1 (synced on first use with the system token; re-synced when the gateway's provider catalog changes, by comparing the stored `version_id` with the code's catalog hash), `tools/list` from the snapshot, `tools/call` through `executeToolCall` with a fresh identity whose `aud` is `provider:<row id>` (never a Worker name, so one organization's row never answers another's), policy, the `mcp_tool_calls` row and the `mcp.tool_call` line.

A tool's handler calls the provider through `handleIntegrationProxyRequest`, the capability proxy's one path: the provider's hosts only, account-wide paths refused, the key put on the call, redirects refused, DataForSEO's `cost` read off the answer; `admit` attributes the call to the member whose client called (the identity in the tool context), and `onCall`/`onCost` count it in `usage_daily`/`usage_monthly` as `kind` `capability`, `target` `dataforseo`, against the provider row. The key never reaches the ToolBus, the client, or a result: the handler returns `{ cost, result }`, the call's cost in USD and `tasks[0].result` as DataForSEO shapes it (no `.ai` cropping, which would drop the `cost` the usage counters read; `limit` defaults to 20, `depth` to 10 on the SERP tools and 1 on related keywords), and the gateway's own refusals as `ToolError` messages. The organization's monthly cap on the row (Admin → Usage, #416) is checked before every call, as the AppGateway entrypoint checks it for an app's; a timed-out call is cancelled upstream through the ToolBus's abort signal.

### The DataForSEO set

Seventeen read tools over Live endpoints, every one `risk: "read"`, idempotent, open-world and titled, under `dataforseo_`: `serp_google` (organic, live advanced), `serp_google_maps`, `serp_google_autocomplete`, `keyword_search_volume` (Google Ads), `keyword_overview`, `keyword_suggestions`, `keyword_ideas`, `related_keywords`, `keyword_difficulty`, `search_intent`, `ranked_keywords`, `domain_rank_overview`, `competitors_domain`, `domain_intersection`, `backlinks_summary`, `backlinks`, `referring_domains`. Each takes `location_code` or `location_name` (default 2840, United States) and `language_code` (default `en`) where the endpoint does, passes `tag: "everyapp:<org id>"` on every task, and caps `limit`, `depth` and keyword lists so one answer stays well under the ToolBus's 1 MiB (the tool refuses an answer over 768 KB and asks for a smaller limit). No `locations` lookup: DataForSEO's location lists run to tens of thousands of rows; the tools take a `location_name` instead. While the key isn't set, the app needs setup like any app (#396: its tools are left out of `/mcp`, `everyapp_list_apps` names it with the command, the app lists show "Needs setup"); a refusal of the gateway's own reached in a call comes back as a tool error: `integration_not_configured` with the command (`everyapp secret set DATAFORSEO_API_KEY`), any other as `The gateway refused the call (<code>): <message>.`; the provider's own errors come back as `DataForSEO answered <code>: <message>.`

### Tool count

The gateway surface lists a provider app's tools in full like any app's, every name `<provider>_<tool>` with a `title` and `readOnlyHint`, so clients that search by prefix find them; the curated set stays small (17 tools). The code-mode research thread ([2026-10-code-mode-and-skills.md](2026-10-code-mode-and-skills.md); TODO.md "Code mode and skills (2026-10-24)") owns the tool-count side. Its first ruling (2026-10-24) still holds for provider apps: never an app collapsed behind `<app>_search` + `<app>_call` (a free-form call wrapper would sidestep the per-tool risk policy, the per-tool argument check, the `tc.name` claim and the audit row's tool column, and every harness shows the model only what `tools/list` returned), no `_meta["anthropic/alwaysLoad"]` on provider tools (Claude Code's own tool search handles the full list). Ben then ruled on 2026-10-24 ("why wouldn't we add the search? why would we want to enforce these arbitrary caps") that the gateway gets a search and loses the per-app cap: on that thread's branch `t3/compact-surface` (PR #567, merged 2026-10-25 after #559, @modelcontextprotocol/server 2.4.0) the ToolBus gains `everyapp_search_tools`, `everyapp_call_read` and `everyapp_call_write` (one inner call each through `executeToolCall`, the read ceiling on the read wrapper, one audit row naming the inner tool), a listing mode per view (`full` as today; `compact` lists the built-ins only, chosen with `X-EveryApp-Tools: compact|full` or `?tools=` on `/mcp`, or automatically once a full listing would pass 256 entries or 1 MiB), and `CATALOG_LIMITS.toolsPerApp` removed. Provider apps change nothing under those thresholds: they list in full, and their snapshots live in `app_tools` like any app's, so the search covers them for free. The bound that made the compact mode automatic: claude.ai and Cowork drop a connector's tools past 256 with no warning (claude-ai-mcp #587), and a read & write member of a gateway running the four launch apps sees 187 listed tools (207 with DataForSEO on; about 105k tokens of `tools/list`, 43% of it output schemas). A proxied upstream still gets an operator allowlist (Treg lists 10, Monid 13, DataForSEO v3 four; its deprecated v2 90). ChatGPT treats a tool without `readOnlyHint` as a write needing confirmation, one more reason every provider tool carries its hints.

### Remote-MCP proxy kind (PR 3)

A second provider kind, `remote_mcp`, honouring what the code-mode thread listed from the spec eras the ToolBus serves: snapshot the upstream catalog by following `nextCursor` to the end and trust it no longer than a 2026-07-28 `ttlMs` says; prefer a 2026-07-28 upstream (no sessions) and for a 2025-era one re-initialize per call or keep the `Mcp-Session-Id` beside the row and re-initialize on 404; never hold the upstream's `subscriptions/listen` from a stateless Worker, re-sync on the hourly cron and on drift instead (answer `unknown_tool` when the upstream does, so the ToolBus's own re-sync runs); normalize upstream names to the ToolBus pattern with a stored reverse map, refusing collisions and warning about what was dropped; map annotations to risk explicitly (`readOnlyHint` true is read, `destructiveHint` explicitly true is destructive, otherwise write; the spec's missing-means-true defaults would hide every unhinted tool), strip `x-mcp-header` at every depth, pass `outputSchema` through, declare no sampling, elicitation or roots and fail such requests as tool errors, leave 2025-11-25 tasks out, relay only MCP result fields, carry upstream instructions into the app's. An operator allowlist bounds a proxied upstream's list whatever the per-app cap (removed on `t3/compact-surface`). In short: the in-process app's tools are the upstream server's `tools/list` (cached in the D1 snapshot like any catalog, with an operator allowlist), each call forwarded over `@modelcontextprotocol/client` 2.x `StreamableHTTPClientTransport` with the operator's key (`authProvider: { token }` for bearer keys such as Treg's; `requestInit.headers` for Basic), `connect({ prior: { kind: "legacy" } })` per provider, no `elicitation`, `sampling`, `roots` or tasks declared, any `input_required`/task result turned into `isError: true`, the call given 25 of the ToolBus's 30 s, and only `com.everyapp/…` `_meta` keys forwarded. Never the downstream user's token (the spec forbids passthrough). Treg carries attribution upstream (`X-Treg-Meta` per call, usage by tag); Monid's MCP is OAuth-only today, so Monid's first kind is curated over REST with a `monid_live_…` key, pending Monid's written yes to server-side resale (its ToS §8 and its integration docs disagree).

## 4. Security boundaries touched

- B5 (AI client → `/mcp`, the ToolBus): a new app tier served in-process. `tools.per-call-identity` still holds (one app, one fresh identity, `aud` the row's own audience); the catalog is fetched with the system token in-process. New invariant: a provider tool never returns, logs or audits the provider key or the gateway's refusal bodies verbatim.
- B4 (app → gateway, capabilities): the same `handleIntegrationProxyRequest` rules apply to a provider tool's call as to an app's; the caller is the provider row (registered, active, lists the capability in its manifest).
- Not touched: mcp-auth (consent, OAuth, PATs), the perimeter's routing (provider rows are invisible to it).

Reviewed adversarially from three lenses (security boundary, correctness against DataForSEO's API and the sync logic, conventions and doc truthfulness) with two skeptics per finding; the confirmed findings (the cap bypass, the missing abort signal, an issuer mismatch, `search_intent`'s fields, the Google Ads keyword limit, `status` reading a provider row as an unbound Worker, and the doc mismatches) were fixed before merge.
