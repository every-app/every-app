(this repository) and `t3/every-app-mode` (OpenSEO), with every finding checked by three

Scope: the uncommitted work on `t3/port-openseo-to-gateway` (Every App) and `t3/every-app-mode` (OpenSEO), the `poc/github-integration` branch, and Ben's 2026-10-15 direction for Google at the gateway. Evidence is quoted from the working trees. Where a claim rests on something I did not read myself (Cloudflare `cf workers secrets bulk` behaviour, Google refresh-token semantics), it is marked.

## Now: before this branch is committed

These change wire contracts, manifest shapes or registry shapes that every later app and the Google work would otherwise have to migrate. Ben's no-backcompat rule makes them cheap today and expensive after the first live deploy.

### 1. One provider registry, one gateway route, one SDK fetch (folds AI providers into integrations)

**Case.** The gateway carries the same brokered-call pipeline twice on this branch and a third time in the PoC: identify caller → check manifest → look up a gateway-held credential → strip headers → forward → tap a number → log. The AI proxy keys it on a path prefix with an origin rewrite and its own table (`apps/every-app-gateway/src/server/ai-proxy.ts:32` `keyEnv: "OPENAI_API_KEY" | "OPENROUTER_API_KEY"`), the integration proxy on host-in-path with `INTEGRATIONS` (`packages/sdk/src/internal/integrations.ts`), and `packages/sdk/src/cloudflare/worker.ts:173-179` hand-copies both into `DEV_GATEWAY_KEYS`. The two SDK fetches disagree on URL model, which is why OpenSEO and Chef both invent `https://every-app-gateway.invalid/...` (OpenSEO `src/server/lib/openrouter.ts:22-23`). The AI proxy's own refusals carry no `x-everyapp-error` header (`ai-proxy.ts:134` `jsonResponse({ error: "Provider is not configured" }, 503)`), it does not set `redirect: "manual"` and passes `set-cookie` through, while the integration proxy does both. The manifest has three keys for one concept (`manifest.ts:245` `providers`, `:250` `integrations`, `:254` `ai`), and `ProvidersSchema` (`manifest.ts:125-130`) accepts any kebab name while `IntegrationsSchemaStrict` rejects unknown ids. TODO.md:49 already queues the fourth duplicate ("A status route for AI providers like `integrationStatus`"). Google is a fourth credential kind with five `*.googleapis.com` hosts; it has to land in one of these, and whichever it picks, the others keep diverging. This reverses the TODO.md:25 default ("OpenRouter is an AI provider ... rather than being an integration"); the stated reason is that every later feature (approval, status, spend caps, audit, dev story) would otherwise be built twice or land on one side only.

**New shape.**
- Registry, three layers keyed by one id set, with a test asserting the sets are equal: (a) `packages/sdk/src/internal/integrations.ts` keeps what apps and the dev fallback need (`id, label, hosts, readMethods | readRoutes, authorization(cred)`), with `credential: { kind: "api_key"; secret } | { kind: "oauth"; ... } | { kind: "github_app" }` and new `openai`/`openrouter` entries (`secret` stays: `everyapp gateway secret set`, the status probe and the operator default need the name); (b) `packages/perimeter/src/manifest/manifest.ts` owns per-provider entry schemas (`models`/`routes` for openai/openrouter, `scopes` for google, `permissions` for github) and validates `integrations` as `z.record(id, entrySchemaFor(id))`; (c) the gateway owns enforcement packs in `apps/every-app-gateway/src/server/integrations/<provider>.ts` with `prepare?(req, entry, env)` (store:false, model allowlist, `AI_PROXY_EXTRA_ROUTES` ceiling) and `meter?: { window: "head" | "tail"; bytes; extract }`. Do not put zod or enforcement hooks in `sdk/internal`: it ships in every app Worker.
- Manifest: one key. `integrations: { openrouter: { access: "read", models: [...] }, dataforseo: { access: "read", why }, context: {...}, google: { access: "read", scopes: [...] } }`. Delete `providers` and `ai`. (Also see #2 for `as`/`background`.)
- Route: `/api/integrations/<id>/<host>/<path>` for everything (`/api/integrations/openai/api.openai.com/v1/responses`); `/api/ai/*` and `routeFromPath`'s two branches (`app-gateway-entrypoint.ts:216-229`) are deleted.
- SDK: one `gatewayFetch({ env, provider, for, account? })` taking the provider's real URLs; `createGatewayFetch` and `integrationFetch` are removed. Chef passes `baseURL: "https://api.openai.com/v1"`, OpenSEO `"https://openrouter.ai/api/v1"`.
- Gateway: one `handleIntegrationRequest` built on the PoC's injected `deps` seam (`grant`, `credential`, `fetchUpstream`), with the strictest existing behaviour (`redirect: "manual"`, `set-cookie` stripped, streamed bodies); one `tapBody(body, { window, bytes }, extract, onDone)` in `src/server/integrations/meter.ts` replacing `tapCost` (`integration-proxy.ts:197-224`) and `tapUsage` (`ai-usage.ts:40-59`); `dataforseo: head/2048/costFromEnvelope`, `openai|openrouter: tail/16384/extractUsage`, no meter for context/github/google. Keep the DataForSEO meter: OpenSEO only bills in `AUTH_MODE=hosted`, so the gateway log is the only spend record in everyapp mode.
- One log event `gateway.provider.call { provider, host, path, method, status, attribution, userId?, toolCallId?, worker, meter? }`.
- Behaviour change to state: OpenSEO's SAM/workflows call OpenRouter with no request (`openrouter.ts:31`), so under one pipeline those calls are background-attributed (fine under #2).

**Effort.** Medium-large; the enforcement code moves nearly verbatim. Two stacked PRs: PR A defines the `ProviderPack` interface and moves `INTEGRATIONS` onto it (small; unblocks Google); PR B folds openai/openrouter, deletes `providers`/`ai`/`createGatewayFetch`/`DEV_AI_PROVIDERS`/`DEV_GATEWAY_KEYS.providers`/`/api/ai`, updates Chef, OpenSEO, `docs/integrations.md:14-15`, TODO.md:25/49.

**Files.** `packages/sdk/src/internal/{integrations,aiProviders,protocol}.ts`, `packages/sdk/src/server/{gatewayFetch,integrationFetch,index}.ts` (+tests), `packages/sdk/src/cloudflare/worker.ts` (DEV_GATEWAY_KEYS), `packages/perimeter/src/manifest/manifest.ts`, `apps/every-app-gateway/src/server/{ai-proxy,ai-usage,integration-proxy,app-gateway-entrypoint}.ts` → `src/server/integrations/*`, `apps/chef/everyapp.config.ts`, `apps/chef/src/routes/api/chat.ts`, OpenSEO `everyapp.config.ts`, `src/server/lib/{openrouter,provider-access}.ts`, `docs/integrations.md`, TODO.md.

### 2. Credential resolution seam, grant model and typed refusals (manifest entry loses `as`/`background`)

**Case.** Phase 0 resolves a credential as `const key = env[integration.secret]?.trim();` (`integration-proxy.ts:119`) with no organization in the lookup even though `caller.organizationId` is passed in and used only for the log, and it authorizes from the caller's own manifest (`:93` `const asked = integrations?.[route.id]`), so the requester is the grantor. The PoC authorizes from `app_integration_grants` via `deps.findGrant` → `effectiveGrant`. Ben's direction ("shared by the org's approved apps") and Google both need the grant; merging without one seam yields two authorization paths in one proxy. The manifest entry has a field that carries no information (`manifest.ts:139` `as: z.literal("org")`) and one Ben's direction makes constant for org connections (`:146` `background`; OpenSEO sets it on both entries, `everyapp.config.ts:54,60`), plus three silent disagreements with the PoC (`access` required vs optional, `why` 200 vs 300, no `permissions`). The status probe returns `configured` even when `requested` is false (`:74-81`), telling any app in any org whether the operator holds a key it never asked for, and the proxy forwards every GET/POST on `api.dataforseo.com`, including the account-wide `tasks_ready`/`id_list`/`errors` enumeration endpoints, the exact lesson `ai-proxy.ts:33-37` already documents for one shared key. Refusals are untyped strings (`refusal(status: number, code: string, ...)`), the header is exported only from the gateway app (`integration-proxy.ts:59`), OpenSEO re-declares it (`src/server/lib/dataforseo/core.ts:62`) and maps every code but one to `AUTH_CONFIG_MISSING` ("deploy it again") before the 5xx retry (`core.ts:70-73, :127-129`), so a provider outage renders as an auth-setup card. The PoC has a third vocabulary with no header (PoC `proxy.ts:71-90`).

**New shape.**
- `resolveCredential({ organizationId, provider }) → { source: "organization", accountId, credential } | { source: "operator_default", credential } | null`, with the Worker secret as the operator default in both deployment modes (Ben's phase-0 decision stands; org-held `kind: "api_key"` rows arrive with #8). Replaces `env[integration.secret]` and `env[aiProvider.keyEnv]`.
- Grants: take the PoC's `app_integration_grants`; `AppRegistrationService.markDeployed` records requests; `statusForRequest` auto-approves when the provider's `approval: "deploy"` (set for api_key + read, so OpenSEO's zero-click deploy is unchanged) and leaves `pending` for `approval: "admin"` (OAuth/GitHub App). The proxy's `deps.grant()` is the single authorization path; the PoC's vestigial manifest check goes.
- Manifest entry: `IntegrationRequestSchema = z.object({ access: z.enum(["read","write"]).default("read"), why: z.string().min(1).max(300).optional() })` plus the pack's own fields. Drop `as` (reintroduce `as: "user"` only if per-person accounts ship) and `background` (an approval is of the app; attribution still comes from the identity header). `integration_needs_user` disappears; attribution rules live in #5.
- Path policy now, independent of the seam: when the credential came from the operator default, deny `/v3/.*/tasks_ready`, `/v3/.*/id_list`, `/v3/.*/errors`; keep `task_get/<id>` (OpenSEO polls it in every async flow; ids are unguessable without `tasks_ready`).
- Status: `GET /api/integrations/<id>` → `{ ready: true, source, accounts? } | { ready: false, code, kind, message }`, with `configured`/`connected` reported only when the grant covers the provider.
- One refusal table in `packages/sdk/src/internal/integrations.ts`, `INTEGRATION_REFUSALS = { integration_not_requested: { status: 403, kind: "app_manifest" }, integration_not_approved: { 403, "approval" }, integration_method_not_allowed: { 405, "app_manifest" }, integration_not_configured: { 503, "gateway_setup" }, integration_not_connected: { 409, "connection" }, integration_needs_reauth: { 409, "connection" }, integration_needs_account: { 428, "connection" }, integration_upstream_failed: { 502, "transient" }, ... }` plus the entrypoint's `caller_*` codes and the AI pack's `model_not_allowed`/`route_not_allowed`; `GATEWAY_ERROR_HEADER`, `IntegrationErrorCode` and `readGatewayRefusal(response)` re-exported from `@every-app/sdk/server` (not `/internal`, which is declared not-for-apps). All gateway refusals, AI included, set the header.
- Vocabulary everywhere: operator (runs the gateway and the Cloudflare account, `everyapp gateway ...`) vs organization owner/admin (Admin UI). `integration-proxy.ts:124` "An admin sets it with: everyapp gateway secret set" becomes "the gateway's operator sets it with ..."; on hosted, the message names the admin integrations page instead. OpenSEO: `src/server/everyapp/tools.ts:30` "bills this organization's DataForSEO account" → "uses the gateway's shared DataForSEO key; calls cost real money"; `core.ts` maps `kind: "transient"` → `UPSTREAM_UNAVAILABLE` (retried), `integration_not_configured` → `DATAFORSEO_AUTH_FAILED`, other `app_manifest` → `AUTH_CONFIG_MISSING`; `selfhost-preflight.ts:144/229/254` and `docs/maintainers/every-app.md:43` say "operator".

**Effort.** Medium. Lands as the base of the same stack as #1 (PR A), since both reshape the registry and the entry schema.

**Files.** `apps/every-app-gateway/src/server/integration-proxy.ts` (→ `integrations/proxy.ts`), `app-gateway-entrypoint.ts`, `src/server/services/{AppRegistrationService,IntegrationService}.ts` (+ PoC `grants.ts`, `drizzle/0033` grants table only), `packages/sdk/src/internal/integrations.ts`, `packages/sdk/src/server/index.ts`, `packages/perimeter/src/manifest/manifest.ts`, OpenSEO `everyapp.config.ts`, `src/server/lib/dataforseo/core.ts`, `src/server/everyapp/tools.ts`, `src/lib/selfhost-preflight.ts`, `src/client/lib/error-messages.ts`, `docs/integrations.md`, TODO.md:24/50.

### 3. Pin the gateway binding's props in deploy policy; helpers present their own name

**Case.** Caller identity rests on service-binding `props`, but the policy that turns deploy access into "this Worker speaks for exactly this app" never reads them: `PolicyInputs = Pick<DeployInputs, "workerName" | "resources" | "deletedDurableObjects">` (`packages/cli/src/lib/app/policy.ts:84-90`, no `organizationId`), and the gateway binding is accepted on `name === "EVERY_APP_GATEWAY" && binding["worker"] === GATEWAY_WORKER_NAME && binding["exportName"] === "AppGateway"` (`:109-113`). No policy test mentions props. The gateway looks the app up *from* the props and compares them back (`app-gateway-entrypoint.ts:109-113`), so a hand-written binding carrying a sibling app's `{ organizationId, appId, workerName }` passes and inherits that app's manifest `integrations`, and soon its grants and the org's Google connection. Every helper also presents the app Worker's name (`worker.ts:472-474` "The app's identity: the gateway treats its helper Workers as the app"), so `caller = { organizationId, appId }` (`:120-123`) and the integration log can never say which Worker made a background Google call. This is a guardrail inside the policy's stated contract, not a trust boundary: `buildApp` runs the app's build with the deployer's Cloudflare credentials, so the real fix for the hosted tier is gateway-as-deployer. But the intra-org case needs nothing secret and the props shape is checked for every live app, so it should be right before the first live deploy.

**New shape.** `PolicyInputs` gains `organizationId` and the manifest id; `bindingProblems` accepts a `type: "worker"` binding to `every-app-gateway` only when `name === "EVERY_APP_GATEWAY"`, `exportName === "AppGateway"`, and `deepEqual(binding.props, { organizationId, appId: manifest.id, workerName: <this Worker> })` with no extra keys (app and each helper, each with its own name). Negative tests: props name another app, another org, extra keys. `everyAppAuxiliaryWorker` emits `props.workerName = helperWorkerName(appWorker, worker)`; the entrypoint accepts `props.workerName === app.workerName || app.manifest.workers.some(w => helperWorkerName(app.workerName, w.name) === props.workerName)` (derive from the stored manifest at `register`, or accept the union of previous and current until `activate`, because helpers upload first and the caller cache is 30 s), and puts `worker` into `caller` for every proxy event. Do not change `findByOrgApp` to `findByWorkerName`: `workerName` is `every-<orgKey>-<appId>`, no less guessable. Record "gateway verifies uploaded script bindings at activate / gateway-as-deployer" in TODO.md as the hosted-tier follow-up. On the hosted platform tier (research H17a) a first-party app's props are `{ appId, workerName, trust: "catalog" }` with no organization, and the entrypoint resolves the organization per call instead (Google design §6); the pin above is for self-host and the dispatch tier, where props do carry it.

**Effort.** Small.

**Files.** `packages/cli/src/lib/app/policy.ts` (+ `policy.test.ts`), `packages/cli/src/commands/app/deploy/deployApp.ts` (pass `inputs`), `packages/sdk/src/cloudflare/worker.ts` (`gatewayBinding`, `everyAppAuxiliaryWorker`), `apps/every-app-gateway/src/server/app-gateway-entrypoint.ts`, TODO.md.

### 4. Identity bound to the deployment: `aud = workerName`, org check in the SDK, one `OrgRole`

**Case.** Every token is minted with `audience: app.appId` (`packages/perimeter/src/gateway.ts:326`, `packages/toolbus/src/execute.ts:219`, `packages/perimeter/src/dev/devGateway.ts:138`) and the SDK verifies against `EVERYAPP_APP_ID` only (`packages/sdk/src/server/everyApp.ts:117-131`). `appSlug` is unique per organization (`apps.schema.ts:72` `apps_organization_app_slug_unique`) while `worker_name` is the globally unique column (`:32`), so two orgs' `openseo` installs share an audience, issuer and signing key. The deploy ships `EVERY_APP_ORG_ID` as a secret and nothing in `packages/` reads it; OpenSEO alone pins it by hand (`src/middleware/ensure-user/everyApp.ts:50`) and hand-declares the role vocabulary (`:14` `const ROLES = new Set(["owner", "admin", "member"])`, `:60` `"member"` fallback); Chef has no org check. Nothing is exploitable today (`hasAppAccess` refuses to mint across orgs, the perimeter strips inbound identity headers, props are cross-checked), so this is hosted-tier readiness and protocol hygiene, and it is the platform's own written plan: `docs/architecture-v2-overview.md:151` "Identity JWTs use `aud = t_<tenant>_<app>` so dispatch routing is not the only line between tenants". `aud = workerName` unifies both tiers because the hosted dispatch script name is exactly that string. Tokens live 120 s, so there is no migration.

**New shape.** Mint `audience: app.workerName` in perimeter identity and public markers, ToolBus `execute.ts` and `catalog.ts` (ToolBusApp gains `workerName`), and the dev gateway-lite (`every-<appId>`). `verifyIdentityJwt` options gain `organizationId?`. `everyAppWorker()`/`everyAppAuxiliaryWorker()` set `EVERYAPP_WORKER_NAME` and `EVERYAPP_ORG_ID` as text bindings (replacing the `EVERY_APP_ORG_ID` secret, `deployApp.ts:422`); `audienceFor` reads `EVERYAPP_WORKER_NAME`; `getEveryAppUser` refuses `org_id !== EVERYAPP_ORG_ID` when set (dev gateway mints a fixed dev org id). A shared platform-tier Worker has no single organization: there the SDK's pin is "the token's `org_id` has an install row for this app", which the gateway already enforced when it minted the token (research H2, H17a). The entrypoint's `resolveAttribution` verifies `{ audience: props.workerName, organizationId: props.organizationId }` and drops the hand-rolled compare. Export `type OrgRole = "owner" | "admin" | "member"` and `isOrgRole()` from `@every-app/sdk/server`; `EveryAppUser.orgRole: OrgRole`; the gateway's `org-roles.ts` imports it; OpenSEO deletes `ROLES`, the pin and the fallback. Delete the deprecated `everyApp(handler, manifest)` overload. Minimum PR if split: SDK org check + the two text bindings.

**Effort.** Medium; self-contained and parallelisable.

**Files.** `packages/perimeter/src/gateway.ts`, `packages/perimeter/src/dev/devGateway.ts`, `packages/toolbus/src/{execute,catalog,types}.ts`, `packages/sdk/src/internal/{identity,protocol}.ts`, `packages/sdk/src/server/everyApp.ts`, `packages/sdk/src/cloudflare/worker.ts`, `packages/cli/src/commands/app/deploy/deployApp.ts`, `apps/every-app-gateway/src/server/{app-gateway-entrypoint,org-roles}.ts`, OpenSEO `src/middleware/ensure-user/everyApp.ts`.

### 5. Explicit attribution (`for`), one request scope in OpenSEO, expired vs forged identities

**Case.** `integrationFetch({ env, provider, request? })` (`packages/sdk/src/server/integrationFetch.ts:15-30`) makes "forgot the person" indistinguishable from "background work". OpenSEO omits `request` on every provider call (`src/server/lib/provider-access.ts:19-21` "No request is passed", `:42`), including MCP tool calls where the handler has `{ user, request }` in hand (`src/server/everyapp/tools.ts:88`) but `toolContext` drops it; so the gateway logs `attribution: "app"` for every OpenSEO call and the PoC's agent read-only rule (`chan: "mcp"` without `mcp:write`) could never fire once a write-capable provider exists. The root cause is that OpenSEO's seams are `(headers) => EnsuredUserContext` and `() => fetch`; it even discards the user the SDK verified at the Worker entry (`src/server.ts:154-156` `everyApp<Env>((verified) => handleAppRequest(verified, env, ctx))` ignores the 4th `user` argument) and re-verifies the RS256 token from a synthetic `new Request("https://openseo.invalid/", { headers })` on every server function and SAM connect (`everyApp.ts:26-29`), which always misses the SDK's per-Request WeakMap. The refuted "fails open" findings were right that the gateway's `resolveAttribution` returning `null` on any failure (`app-gateway-entrypoint.ts:274-282`) is deliberate and that a hard 401 would break long calls (identity TTL is 120 s); the surviving correction is to distinguish expiry from forgery and to make the app side explicit.

**New shape.** SDK: `for: Request | { background: true; organizationId? }` required on `gatewayFetch` (never `EveryAppUser`: it carries no token); a platform-tier app names the organization for background work and the SDK sends it as `x-everyapp-org` (research H17a). Gateway: a present token that fails signature/audience/issuer/org → 401 `identity_invalid`; a well-formed but expired token → continue as background with `attribution: "expired"` (org connections always permit background per Ben, so nothing is lost but a label). Add `jti`/`toolCall.id` to the proxy's `logged` object so a DataForSEO spend can be joined to a ToolBus `call_id`. OpenSEO: `src/server/request-context.ts` with `const requestScope = new AsyncLocalStorage<{ request: Request; identity: EveryAppUser | null }>()`, seeded in `handleEveryAppRequest` from the SDK's verified `user` and in `everyAppTool`'s handler from `{ user, request }` (the same pattern as `pgClientStore`, `src/db/pg/client.ts:25`); `resolveEveryAppContext` reads `currentIdentity()` (no re-verification, no synthetic Request); `provider-access.ts`/`openrouter.ts` pass `for: currentRequest() ?? { background: true }`. Later `getGoogleFetch()` is one line.

**Effort.** Small.

**Files.** `packages/sdk/src/server/{gatewayFetch,integrationFetch}.ts`, `apps/every-app-gateway/src/server/{app-gateway-entrypoint,integration-proxy}.ts`, OpenSEO `src/server.ts`, `src/server/request-context.ts` (new), `src/middleware/ensure-user/{everyApp,resolve}.ts`, `src/server/everyapp/tools.ts`, `src/server/lib/{provider-access,openrouter}.ts`.

### 6. Model R2 as an owned resource; Workflows by derived name

**Case.** The manifest is "the single source of truth for an app's resources" and the ownership table exists because "a resource's name proves nothing", yet R2 sits outside both: `ResourcesSchema` has d1/kv/durableObjects/workflows and no `r2` (`manifest.ts:46-58`), `type ResourceKind = "worker" | "d1" | "kv"` (`ownership.ts:42`), `provisionAppResources` handles d1/kv only, `purgeApp` deletes worker/d1/kv only, `storageBindings` emits d1/kv only, and the policy's `case "r2"` (`policy.ts:221-229`) checks only `isOwnResourceName(bucket, workerName)` while d1/kv are compared to provisioned ids. Chef (`apps/chef/cloudflare.config.ts:20`) and OpenSEO (`cloudflare.config.ts:34`, threaded to the helper via `vite-plugin-every-app.ts:34`) hand-write the bucket; cf's deploy auto-provisioning creates it and silently adopts any existing bucket of that name; TODO.md:28 promises helpers "share the app's D1, KV and R2" but only OpenSEO's wrapper delivers it. Buckets hold user data (recipe images; Lighthouse payloads, exports) that survives `--purge` and is silently re-adopted on redeploy because the tombstone keeps the names. The collision vector is another gateway/project on the same Cloudflare account or a stale bucket, not another org on one gateway (`orgKey` is unique). Workflows do not need ownership rows: a `<worker>--x` Workflow can only have been created by that Worker's deploy, and cf rejects >64 chars and duplicate exports within a Worker; the uncaught case is a case-variant binding split across app and helper.

**New shape.** PR A (small, land next): `resources.r2: z.array(BindingNameSchema)` in strict and tolerant schemas; `EveryAppWorkerManifest.resources.r2`; `R2Binding { type: "r2"; name }` in the SDK union; `storageBindings` emits it for the app and every helper (`R2` → the Worker's name like `DB`/`KV`, others `resourceNameFor`); gateway `AppRegistrationService.resourcesFor` assigns r2 names and `assertDistinctResources` covers r2 and workflows (lowercase, ≤63 chars, case-collision check); policy `case "r2"` checks membership in `inputs.resources.r2`; Chef and OpenSEO move `R2` into `everyapp.config.ts` and delete the hand-written binding. PR B (medium, with TODO.md:51): `provisionAppResources` adds `kind: "r2"` via `cf r2 buckets list/create`, records `{ kind: "r2", binding, name, resource_id: name }` (name-only ownership, stated plainly in `ownership.ts`), refuses an existing unrecorded bucket like `claimAppWorker`, `purgeApp` deletes Workers, then `cf workflows delete` by derived name, then empties (paginated) and deletes recorded buckets; `unrecordedResources` reports buckets; `fakeCloudflare` gains buckets; `AppResources`/`DeployInputs.resources` gain `r2`. ## What we got right

- Host-in-path routing (`/api/integrations/<id>/<host>/<path>`): generalizes to Google's many hosts and to OpenAI/OpenRouter without a second channel.
- Caller identity from service-binding props cross-checked against the registry, plus a short-lived RS256 identity JWT per forwarded request: the right two layers; the fixes above tighten, not replace, them.
- Keys never in apps; the gateway holds every credential, and the AI proxy's inference-only allowlist already recorded the lesson about one shared account.
- OpenSEO as a mode, with `provider-access.ts` as a single seam that hands a `fetch` to callers: the same shape the Google port needs.
