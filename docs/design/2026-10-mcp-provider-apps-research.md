# MCP provider apps: research synthesis

Inputs: five research reports (Monid, Treg, DataForSEO REST, DataForSEO MCP, MCP-proxy feasibility) and their skeptics' corrections, all dated 2026-10-24. Every skeptic correction below is applied; where two skeptics disagree and the evidence does not settle it, that is said in place. Nothing was POSTed to any provider, no account was created, no CLI run; MCP `tools/list` outputs are therefore reconstructed from source code and vendor docs, not observed live.

## 2. Per provider

### Monid

What it offers. Monid is a pay-per-call broker in front of 93 third-party providers (2,900 endpoints on 2026-10-24 per https://api.monid.ai/public/v1/stats): web search/scrape (TinyFish, Context.dev, Firecrawl), people/company enrichment (PDL, Apollo, Hunter), SEO (DataForSEO, Ahrefs), finance, maps, generative media (Kling, MiniMax). The model is three verbs: `discover` (free natural-language search over the catalog), `inspect` (free schema + live price), `run` (billed). One prepaid USD wallet per workspace; "every account starts with free credit" ($1). Monid wraps DataForSEO itself with HTTP Basic and reads DataForSEO's top-level `cost` as the billed amount (`connectors/dataforseo/provider.ts` lines 27, 46, 103 in https://github.com/monid-ai/monid), so a DataForSEO call via Monid is the same blocking profile the gateway has today (`requestMs: 130_000`) with a 408 instead of a 50401 at the end.

Surfaces: REST at `https://api.monid.ai` (`/v1/auth/whoami`, `/v1/auth/workspaces`, `/v1/discover`, `/v1/inspect`, `/v1/run`, `/v1/runs`, `/v1/runs/:runId`, `/v1/runs/:runId/stop`, `/v1/wallet/balance`, `/v1/wallet/activities`; undocumented but present in the open CLI: `/v1/feedback`, `/v1/dispute`, `/v1/resources/*`, and `/v1/wallet/topup/sessions` in open PR #16). Remote MCP at `https://mcp.monid.ai/v1` (Streamable HTTP, OAuth only, closed source). `discover` `query` 1–1000 chars, `limit` default 5 max 40, `minScore` default 0.2 (values above 1 return nothing); `includeUnavailable` and `metrics` (`status` healthy/stable/degraded/outage/unknown, `runTimeMs.p50/p95`) exist in the CLI types and skill but not in the REST reference (https://monid.ai/docs/api/discover.md, https://raw.githubusercontent.com/monid-ai/cli/main/src/api/types.ts). Rankings for Oct 14–20, 2026 (weighted: "Free calls count as one fifth of a paid call"): #1 TinyFish Web Search 568K, #2 TinyFish Fetch 185K, #3 Context.dev Scrape Markdown 164K; all TinyFish endpoints except `/automation/run` ($0.016/step, `PER_UNIT`) are $0 `PER_CALL` (https://monid.ai/rankings, https://api.monid.ai/public/v1/endpoints?provider=tinyfish).

Identity model: an API key is bound to one workspace and one owning user; every run proxied through it is recorded as the same `USER#<userId>`; `GET /v1/runs/:runId` isolates per workspace (403 for another workspace's run) but not per user. Monid's direct-integration docs explicitly endorse one key for many end users ("All usage bills to your single Monid wallet with one invoice and no per-user setup. Charge your users however you like.", https://monid.ai/docs/integrations/direct/setup.md) and a proxy pattern ("Whitelist or blocklist endpoints", "cache results", https://monid.ai/docs/integrations/proxy.md). Both are REST patterns; no Monid document endorses forwarding `https://mcp.monid.ai/v1` with a shared OAuth token. OAuth per user (Clerk AS, DCR live despite the docs' "Email support@monid.ai") is the only per-user model. A working reseller precedent exists: Notis resells "a curated slice of Monid", "charges 20% over Monid's price", refuses any call quoted above $1.20, and advises "Do not build multi-tenant on it yet without your own per-user cap and your own allowlist" (https://www.notis.ai/blog/monid-review/, 2026-08-22).

Tool list (remote MCP `https://mcp.monid.ai/v1`, server 1.2.0; 13 tools, from https://raw.githubusercontent.com/monid-ai/plugins/main/plugins/monid/skills/monid/SKILL.md; not verified by a live `tools/list`):

- Catalog and execution: `monid_discover` (POST /v1/discover, free), `monid_inspect` (POST /v1/inspect, free), `monid_run` (POST /v1/run, paid), `monid_get_run` (GET /v1/runs/:runId), `monid_stop_run` (POST /v1/runs/:runId/stop), `monid_list_runs` (GET /v1/runs).
- Account: `monid_balance` (GET /v1/wallet/balance), `monid_list_workspaces` (GET /v1/auth/workspaces).
- Resources: `monid_list_resources`, `monid_get_resource`, `monid_get_resource_external`, `monid_list_resource_events`, `monid_release_resource` (irreversible, "may affect billing").

Curated first tools (REST, option b) and why:
1. `monid_discover` with `limit` ≤ 10, surfacing `price`, `tags` (`no-markup`, `verified`), health — members see cost before running.
2. `monid_inspect` — exact `pathParams/queryParams/body` schema; avoids wasted paid calls.
3. `monid_run` pinned to allowlisted `provider`/`endpoint` pairs; record `runId` + member.
4. `monid_get_run` restricted to runIds the member created — where `cost.value` becomes available; the metering hook lives here.
5. `monid_stop_run` — caps runaway spend (not for `METERED` prices, which bill accrued usage and settle `COMPLETED`).
6. Curated `tinyfish /search` and `/fetch` — $0, highest volume, cheapest live web context.
7. Curated `context-dev /web/scrape/markdown` — overlaps the Context.dev key Every App already holds; a price comparison point.
8. Curated `dataforseo /labs/keyword-ideas` ($0.012 + $0.00012/result), `/serp/*` ($0.002/call) — `no-markup`, for operators without their own DataForSEO account.
9. Curated `apollo`/`hunterio` enrichment — per-result pricing where a gateway cap matters.
10. Operator-only: `monid_balance`, `monid_list_runs` (would leak every member's inputs/outputs).

What breaks if proxied (option a, forwarding `https://mcp.monid.ai/v1`): the gateway must be an OAuth client of Clerk (DCR, `offline_access`, refresh) linked to the operator's account — a pattern Monid nowhere describes; all runs attribute to the operator; `monid_list_runs`, `monid_balance`, `monid_list_workspaces`, `monid_release_resource` are account-wide and must be hidden; one member's spend trips the shared `WORKSPACE_BUDGET` and `BLOCK`s everyone; tool names become `monid_monid_discover` unless the prefix is stripped; `Mcp-Session-Id`/listChanged/protocol version: not stated; whether MCP results carry `cost`/`billing`: not stated. Shared with option b: actual cost arrives asynchronously (202 → poll); sync runs can hold the connection up to the provider's `requestMs` (300 s for firecrawl/cloro) so a 30 s budget needs fire-and-poll or a menu restricted to ≤30 s connectors (exa, keenable, hunterio, ahrefs in the open repo); sync/async mode is not exposed by `discover`/`inspect`; media returns signed URLs on `sfs.monid.ai` with TTLs, large JSON inline; `hints` are server-generated text that can name shell commands (PR #16: `monid topup -a <amount>`) and must be treated as untrusted; terminal runs are `Cache-Control: private, max-age=60` and ToS §8 forbids compiling "a collection, compilation, database"; Monid rate limits are unknown; no auto-recharge so an empty wallet 402s every member; run inputs/outputs are stored with no retention statement (Notis pulled a full payload back an hour later). ## 3. MCP proxy feasibility in a Cloudflare Worker

### Client package

Use `@modelcontextprotocol/client` 2.x (2.4.0 on 2026-10-23; node ≥20; deps zod ^4.2.0, jose, cross-spawn, eventsource, pkce-challenge, eventsource-parser, `@modelcontextprotocol/core`). It is the v2 line "implementing the 2026-07-28 MCP spec"; the toolbus already pins `@modelcontextprotocol/server` 2.3.1 (`packages/toolbus/package.json`), so it is same-major. It is built for workerd: exports `./validators/cf-worker` and `./_shims` with a `workerd` condition → `dist/shimsWorkerd.mjs` (`CfWorkerJsonSchemaValidator`, `preloadSchemas()` at module scope); stdio isolated on `./stdio`. TypeScript 6 needs `"types": ["node"]` because the `.d.mts` references `Buffer`. Cloudflare's `agents` 0.30.1 runs it unmodified on Workers (peer `@modelcontextprotocol/client` 2.3.1; `StreamableHTTPEdgeClientTransport` is now a deprecated alias). The v1 `@modelcontextprotocol/sdk` is at 1.32.2. https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/package.json, https://github.com/cloudflare/agents/blob/main/packages/agents/src/mcp/client/transports.ts

Transport options that matter (`StreamableHTTPClientTransportOptions`): `authProvider: { token: async () => key }` — always emitted as `Authorization: Bearer ${token}` (caller `Authorization` is only sent while the provider has no token), 401 → `onUnauthorized()` then one retry; so for DataForSEO's Basic credential use no `authProvider` and put `Authorization: Basic <base64(login:password)>` in `requestInit.headers`; reserve `authProvider` for bearer keys (treg). `requestInit` headers lose to transport-managed `authorization`, `dpop`, `content-type`, `mcp-protocol-version`, `mcp-method`, `mcp-name`, `mcp-session-id`. `sessionId`/`protocolVersion` resume a persisted 2025-era session; `redirectPolicy` default `'same-origin'` (treg's `/mcp` → `/mcp/` 307 is same-origin but use the slash); reconnection defaults 1000 ms → 30000 ms, ×1.5, `maxRetries` 2; `onInsufficientScope` default `'reauthorize'`. https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/src/client/streamableHttp.ts

### Spec eras to handle

- 2025-03-26: Streamable HTTP, OAuth 2.1 framework, batching, tool annotations. 2025-06-18: batching removed, RFC 9728 protected resource metadata, RFC 8707 resource indicators, elicitation, `MCP-Protocol-Version` header required on later requests. 2025-11-25: OIDC discovery, CIMD, SEP-986 tool-name guidance, experimental tasks (`tasks/result` blocks until terminal), pollable SSE, `ttlMs`. https://modelcontextprotocol.io/specification/2025-11-25/changelog
- 2026-07-28: no sessions, no `initialize`; every request carries `_meta["io.modelcontextprotocol/protocolVersion"]` and `_meta["io.modelcontextprotocol/clientCapabilities"]` (missing → `-32602`, HTTP 400); `server/discover` MUST exist; headers `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` must match the body (`-32020 HeaderMismatch`); `Mcp-Param-*` from `x-mcp-header` must be forwarded by intermediaries; GET/DELETE → 405; closing the SSE stream is cancellation; `subscriptions/listen` replaces the GET stream and `resources/subscribe` (first message `notifications/subscriptions/acknowledged`); MRTR (`resultType: "input_required"`, byte-exact `requestState` echo; servers MUST NOT send `inputRequests` the client did not declare); tasks moved to extension `io.modelcontextprotocol/tasks` ("Never return a task to a client that did not declare support"); Roots/Sampling/Logging deprecated; DCR deprecated for CIMD; client credentials keyed by issuer (SEP-2352). "Servers MUST NOT rely on prior requests over the same connection to establish context" — the explicit licence for a stateless Worker. https://modelcontextprotocol.io/specification/2026-07-28/changelog, https://modelcontextprotocol.io/specification/2026-07-28/basic/index
- Compatibility: modern client ↔ legacy server fails; legacy client ↔ modern-only server fails; dual-era client probes `server/discover` and falls back to `initialize` only when the 400 body is not a recognized modern error; verdict cached per origin. In the SDK: `versionNegotiation.mode` default `'legacy'`; `'auto'` probes; `{ pin: '2026-07-28' }`; `connect({ prior: { kind: 'modern', discover } | { kind: 'legacy' } })` skips the probe. All three providers are legacy-era today: DataForSEO (`sdk ^1.30.0`, prints 2025-03-26), treg (Python `mcp>=2`; `subscriptions/listen` → METHOD_NOT_FOUND, so no 2026 path), Monid (not stated). So `connect({ prior: { kind: 'legacy' } })` per provider is the practical setting. https://modelcontextprotocol.io/specification/2026-07-28/basic/lifecycle

### Session and listChanged semantics

2025-era: server MAY return `Mcp-Session-Id`; client MUST echo it; missing → 400, expired → 404 → re-`initialize`; DELETE to end (405 allowed). None of the three issues one: DataForSEO hosted is `sessionIdGenerator: undefined`; treg is `stateless_http=True`; Monid not stated. A cold Worker invocation against a 2025-era upstream still costs `initialize` + `notifications/initialized` + `tools/call` (2–3 POSTs) unless the session and `protocolVersion` are persisted (KV/D1/DO) and replayed; against a stateless upstream the handshake is required but cheap. listChanged: treg `tools.listChanged=false`; DataForSEO v3 capabilities `{ logging: {} }` only; Monid not stated. Upstream list-change signals in 2026-era require holding a `subscriptions/listen` POST stream, which a plain Worker cannot do between invocations (Durable Object territory); the toolbus already serves its own clients with a tool-list hash in the minted `Mcp-Session-Id` (list_changed then 404 → re-init) and polls `LISTEN_POLL_MS` 30 s / `LISTEN_MAX_MS` 10 min / 8 streams per caller (`packages/toolbus/src/http.ts`), so proxied apps should ride that, with upstream `tools/list` cached (Cloudflare portals resync ~2 h; 2026 servers supply `ttlMs`/`cacheScope`). `_meta` passthrough: reserved prefixes `modelcontextprotocol`/`mcp`; vendor keys reverse-DNS (`com.everyapp/…`); `traceparent`/`tracestate`/`baggage` reserved for W3C propagation; `clientInfo`/`serverInfo` "self-reported … SHOULD NOT rely on them for security decisions"; no on-behalf-of field exists. Token passthrough is forbidden: "The MCP server MUST NOT pass through the token it received from the MCP client"; "MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client". https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations

### Pagination and tool naming

`params.cursor`/`result.nextCursor`; `listTools()` auto-walks up to `listMaxPages` 64, `listTools({ cursor })` one page. Moot for 13/10/4 tools. 2026 servers SHOULD return deterministic order; names 1–128 chars of `A-Z a-z 0-9 _ - .`; aggregating proxies SHOULD prefix with a server identifier and SHOULD NOT rely on `serverInfo.name`. Client-side name limits: Anthropic review 64 chars; Gemini CLI sanitizes to letters/digits/`_`/`-`/`.`/`:`, truncates >63 with "(...)", namespaces `mcp_{serverName}_{toolName}` and "the last registered tool overwrites the previous one" on collision; Cloudflare agents uses `tool_${id}_${tool}` matching `/^[A-Za-z0-9_]+$/`, server ids ≤64; Cloudflare portals `{server_id}_{original_name}`. https://modelcontextprotocol.io/specification/2026-07-28/server/tools, https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/tools/mcp-server.md

### What major clients do with large tool lists

- Claude API: `tool_search_tool_regex_20251119` / `tool_search_tool_bm25_20251119` with `defer_loading: true`; "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools"; a five-server example of "~55k tokens in definitions" cut "by over 85 percent"; default 5 results, up to 10,000 deferred tools; tip: "prefix by service or resource (for example, github_, slack_)"; deferred tools cannot carry `cache_control`; supported from Opus 4.5/Haiku 4.5 through the 5.x line (Sonnet 4.5 marked deprecated). https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool

### Latency and limits

Workers: subrequests 50 (Free) / 10,000 (Paid); 6 simultaneous connections waiting for headers; CPU 10 ms / 30 s default (to 5 min); "no hard limit on duration for HTTP-triggered Workers" and "no set time limit on individual subrequests" while the client stays connected; `waitUntil()` 30 s; 128 MB (https://developers.cloudflare.com/workers/platform/limits/). Network wait is not CPU. Unconfirmed: whether a Worker's `fetch()` to an upstream that itself sits behind Cloudflare's proxy inherits that zone's 125 s Proxy Read Timeout (error 524 page, updated Jul 23, 2026; 30 s Proxy Write Timeout "cannot be adjusted") — treg is behind Cloudflare. ToolBus budget: `DEFAULT_CALL_TIMEOUT_MS = 30_000`, `MAX_RESULT_BYTES` 1 MiB, request body 256 KiB (`packages/toolbus/src/execute.ts`). Against that: DataForSEO Live avg 6 s, p95 ~25 s (treg's sample), cutoff 120 s; treg MCP 120 s / routed 60 s poll; Monid sync up to 300 s. A proxied call is 1 POST (modern) or 2–3 POSTs (legacy, cold). Held `subscriptions/listen` streams or long polls need a Durable Object.

### Precedents

### Recommendation

Do (c): ship (b) first — curated gateway-side tool sets over each provider's REST API as provider apps, since the capability proxy with Basic injection, host allowlist and per-org/app/user attribution exists, DataForSEO's `tag` + `cost` and treg's `X-Treg-Meta` + `X-Treg-Cost-Micro` give real metering, and narrow read-only tools with `title`/`readOnlyHint` are what clients and reviews reward; keep the existing body `cost` tap (DataForSEO, non-`.ai`) and add one for the `X-Treg-Cost-Micro` header. Then add (a) as a narrower feature, "proxy a remote Streamable HTTP MCP server as an app", on `@modelcontextprotocol/client` 2.x: `StreamableHTTPClientTransport` with `requestInit.headers` for Basic (DataForSEO) or `authProvider: { token }` for bearer keys (treg), never the downstream user's token; `connect({ prior })` with the era verdict cached per provider; cache upstream `tools/list` (honor `ttlMs`/`cacheScope`, default 1–2 h) in D1/KV and serve `<app>_<tool>` filtered by an operator allowlist; declare no `elicitation`, `sampling`, `roots` or `io.modelcontextprotocol/tasks` upstream and convert any `input_required`/`task` result into `isError: true`; forward only `com.everyapp/…` `_meta` keys plus `traceparent`/`baggage`; give the proxied call ~25 s of the 30 s with an AbortSignal; keep list_changed on the existing hash-in-session polling. For DataForSEO specifically, the MCP route adds nothing over REST but a catch-all; prefer REST. For Monid, the MCP route needs an operator OAuth link Monid has not endorsed; prefer REST with written approval. For treg, either route works and MCP (`/mcp/`, bearer Agent key, `X-Treg-Meta` per POST) is the vendor-designed path.
