### Hosted build (2026-10-16)

Defaults the overnight build of the hosted platform shipped without Ben. Each item says what shipped; yes keeps it. [docs/hosted-platform-build.md](https://github.com/every-app/private-every-app/blob/5ef30882/docs/hosted-platform-build.md) §3 has the reason and the walk-back for each.

**Hosting shape**

- [ ] **First-party hosts share the control plane's cookie.** First-party apps live at `<app>.app.everyapp.com` on one session cookie for `app.everyapp.com`; third-party apps live on `everyapp.dev` with a session per host (#314).
- [ ] **The host never picks the organization.** One hostname per first-party app; a person works in their session's organization (their personal one, else the last active, else the first joined; the switcher changes it).
- [ ] **The install organization is the platform organization**, always named Every App whatever the claimant types; it owns every shared app, and first-party Workers' binding props name it.
- [ ] **The hosted gateway activates first-party apps on their first request**, as self-host does.
- [ ] **A missing or mistyped `GATEWAY_DEPLOYMENT_MODE` fails closed in both modes**: a self-hosted gateway that loses it refuses the setup claim, Access sign-in, dynamic registration, app activation and account actions until someone sets it.
- [ ] **The hosted gateway ignores and logs `CLOUDFLARE_ACCESS_*` and `EMAIL_PASSWORD_SIGN_IN`** rather than refusing to start.
- [ ] **The identity audience is the Worker name for every app**, first-party and self-hosted included, with no compatibility window: an app not built with `everyAppWorker()` answers 500 until it sets `EVERYAPP_AUDIENCE`, and apps refuse identities between a gateway upgrade and their own redeploy.
- [ ] **A browser carrying two session cookies is locked out until it clears cookies** (a 401 with a hint), rather than treated as signed out.
- [ ] **`APP_BASE_DOMAIN` stays the gateway's host on hosted**, so the mobile shell's copy of the session cookie matches the server's and it never holds two.
- [ ] **Redirect URIs on the platform's domains are refused at authorize, consent and the token endpoint**, not at dynamic client registration.
- [ ] **Deferred**: publishing the SDK and CLI, the agent, organization deletion and export, legal pages, and email bounce handling.

**Sign-up and organizations**

- [ ] **Open sign-up with verified email and daily mail budgets**, no Turnstile or social sign-in yet; invited sign-ups verify too, and verification links last 24 hours.
- [ ] **The preview launches invite-only** (`HOSTED_OPEN_SIGNUP=false`, as the hosted-install runbook says).
- [ ] **Exactly one personal organization per verified account**; growth by invitation; no self-serve creation or deletion.
- [ ] **A personal organization is named after the person** ("Ada Lovelace", else the email's local part), not "Ada's workspace".
- [ ] **An invitee whose invitation expired before they joined has an account and no organization**, and gets no personal one at the next sign-in.
- [ ] **Mail budgets**: hosted 5 per address per kind per day and 2,000 verification, 1,000 reset and 2,000 invitation emails per gateway; self-hosted 10 and 1,000.
- [ ] **Self-hosted people in several organizations start in their last active one**, not the organization picker.
- [ ] **On hosted, Delete removes a person from the organization and keeps their account**; admins can't deactivate accounts or reset passwords.
- [ ] **A member of two organizations keeps one MCP connection per organization** for the same AI client, rather than the newest replacing all.
- [ ] **A suspension applies to the organization acted under**: a member of a suspended organization still opens their other organizations' apps.
- [ ] **A suspension takes up to 30 seconds** to stop a shared app's background work (the caches' window).

**Shared apps and attribution**

- [ ] **No install rows**: every organization gets every shared app, and an organization can't hide or cap one.
- [ ] **Other organizations see shared apps read-only in Admin → Apps** rather than not at all.
- [ ] **An API token may deploy, register and delete shared apps** as the account's own authority (CI), alongside the platform organization's owners and admins. (CLI surface removed 2026-10-24; see docs/hosted-vision.md)
- [ ] **Externally deployed first-party Workers take the registry's names** (`every-everyapp-<app>`), not names of their own.
- [x] **Chef is in the day-one catalog.** Superseded on 2026-10-24: Chef was deleted in the simplify stage 1; the catalog is decided when the hosted build resumes.
- [ ] **Background work counts only for an active organization with at least one member who isn't banned.**
- [ ] **Pending and unverified members count as live** for background attribution.

### OAuth scopes (2026-10-24)

Can an app ask the gateway for only the OAuth scopes it needs, enforced at the gateway? Designed and built 2026-10-23/24 in [docs/design/2026-10-oauth-scopes.md](docs/design/2026-10-oauth-scopes.md) (its section 13 lists what was built and where it differs; PRs #398 merged, #414, #411, #412, #408 open, Slack's policy on `t3/oauth-scopes-slack`); its section 1 records that until this work the answer was no: the gateway completed token endpoints without reading scopes, and the app chose the consent's scopes and kept the tokens. Each bullet shipped with a default; confirm or change it.

- [ ] **Named scope sets in the manifest, not provider scope strings.** `capabilities: { "google-workspace": { access: "write", scopes: ["search-console.read", "analytics.read"], why } }`; the registry maps each set to the provider's strings and to the API hosts and paths it unlocks, and the status hands the app the strings for the authorize URL. Google's sets are `identity`, `gmail.read`, `calendar.read`, `search-console.read`, `analytics.read`; Microsoft's `identity`, `mail.read`, `calendar.read`. Alternative: raw provider strings validated against a flat list (more precise, unreadable in Admin → Apps and in `why`).
- [ ] **`scopes` is required for a client with a scope policy and refused for every other capability.** The strict validator refuses a missing or empty list, a duplicate, an unknown name, and `scopes` on Mastodon or DataForSEO; a stored row with a missing, empty or malformed value, or any unknown name, is refused at the token endpoint (`integration_scopes_undeclared`) and shows `ready: false`: an unknown name voids the whole grant rather than narrowing silently. Alternative: `scopes` optional meaning identity only, or unknown names dropped (a grant nobody declared).
- [ ] **The enforced boundary is the token endpoint, not API calls.** The gateway reads the token request and the provider's token response and refuses to forward a token whose granted scopes exceed the app's sets (`integration_scope_exceeded`); the app still holds the tokens and calls the provider itself, and the provider enforces the scopes on its API. The per-set host+path allowlist is built and tested but enforces nothing until the outbound Worker (dispatch tier) or gateway-held tokens (every tier) use it. Alternative: a minimal gateway-held-token mode before launch (3 to 4 more agent-days and Open CRM changes; the design's section 2 says why not now).
- [ ] **No write scope sets this week.** `gmail.send`, `calendar.events`, `mail.send`, `contacts.read` are not defined: no app asks, the deployed manifest is a self-declared grant with no approval step, and the Google design's "read-only by construction" holds; a registry invariant pins it. Alternative: define them now so authors have the vocabulary.
- [ ] **An over-scoped token the gateway refuses is dropped: never forwarded, stored, logged or revoked.** Google's `/revoke` removes every client's grant for that person across the Cloud project, and Slack's `auth.revoke` can kill an installation token another app shares. Alternative: revoke where it is safe (Slack per token; Google only on a client no other app shares), or forward with a warning header (the boundary would be advisory).
- [ ] **A 2xx token response that carries a token but names no scopes fails closed** (`integration_scope_unverified`, 502). All three providers document `scope` on every success response. Alternative: on Google, consult `oauth2.googleapis.com/tokeninfo` with the access token before deciding.
- [ ] **Microsoft is refused strictly, with no advisory flag.** On a shared Entra client a token may carry every scope the person consented to any app on it; the gateway refuses the narrower app's exchange, which is availability loss, not narrowing. Alternative: a registry flag that logs and forwards for Microsoft only (fail open inside a security boundary).
- [ ] **Grant types are per capability.** Google and Microsoft complete `authorization_code` and `refresh_token` only; `client_credentials` and token exchange are refused (`integration_grant_not_allowed`): an app never gets app-level tokens with the operator's client. Slack's policy, when it ships, takes a code exchange without `grant_type` (its `oauth.v2.access`) and `refresh_token`. Clients without a policy keep today's pass-through (Meta's exchanges). Alternative: a grant-type allowlist on every client.
- [ ] **The token request's `scope` is checked, then rewritten per provider.** Anything outside the allowed list is refused (`integration_scope_not_allowed`); then Microsoft's is replaced with the status's scopes on every token leg, Google's is dropped (Google documents none on either leg), Slack's is kept. `grant_type`, `scope` and `user_scope` in the query string are refused (`integration_body_invalid`) so the gateway decides on the body alone. Alternative: check only.
- [ ] **An explicit `identity` set plus a tolerated baseline.** Google: `openid email profile` as a set an app opts into; the two spellings Google echoes (`userinfo.email`, `userinfo.profile`) are tolerated and never refuse. Microsoft: `User.Read` as the set; `openid profile email offline_access User.Read` tolerated; `offline_access` always requested and never echoed. **Decide** (each shipped with a default; confirm it or change it)

- [ ] **Required by default.** A bare `providers`, `capabilities` or `secrets` entry is required: the app doesn't open until it is set. The author's rule: required = the app is useless without it; a setting only one feature needs is `optional: true`, and the feature says what is missing where it is used. Alternative: optional by default, with the app opening into features that fail one by one (design review, 2026-10-23).
- [ ] **`anyOf: "<group>"` names a group, and promises the app picks among the set members at run time.** The group is met once any member is set; while none is, every member blocks and the command names the first with the others in its note. The gateway refuses a call to a provider whose key isn't set whichever others are, so an app that chooses its provider at build time (agentic-inbox's `AI_PROVIDER`) declares that one required and the other optional instead. An entry can't be both optional and in a group; a group needs two or more members, counted across providers, capabilities and secrets. Alternative: `oneOf` with the gateway picking the provider (needs the provider status route below).
- [ ] **Each setting names its setup guide, `setup`: the registries' for a Gateway setting, the entry's for an app's own secret.** A provider's or a capability's guide is a registry default beside `docs` (`DEV_AI_PROVIDERS[id].setup`, a capability's `setup`: openai, openrouter, workers-ai, dataforseo, context, email, google-workspace, microsoft-365 and slack; the AI routes share `setup/openai.md`; `members` and the 16 social clients have none), written by the setup-skills thread under `packages/cli/skills/everyapp/setup` and copied into every app's `.claude/skills/everyapp/`; the strict schema refuses `setup` on a provider or capability entry and takes it on a secret entry as `setup/<name>.md`. Alternative: a manifest override for every kind; `docs` pointing at the guide instead of a page.
- [ ] **The model names `EMAIL_FROM` for email; the sender still needs a display name.** The registry's `settings` for `email` is `["EMAIL_FROM"]` with `EMAIL_FROM_NAME` under `optionalSettings`, and the gateway answers the capability by its own rule rather than by the names (`isEmailConfigured()`: a sender that parses, which needs a display name from `EMAIL_FROM_NAME` or `EMAIL_FROM="Name <address>"`, and a provider that is selectable). Open: the names only approximate the rule, so where values can't be read (the CLI's `secret list` and `status`) a bare address with no name shows `✓ set` while the gateway refuses to send (`EMAIL_SENDER_NOT_CONFIGURED`). Alternative: both names required, which would call the `Name <address>` form unset.
- [ ] **App secrets are recorded by the CLI (`apps.secret_names`, migration 0004), and unknown never blocks.** The gateway can't list an app Worker's secrets, so the CLI writes the names it sees (`deploy` after the upload in the same `markDeployed` update under the lease, `register`, `secret set|unset` after the targets are patched, `status` for every deployed app) with everyapp's reserved names left out; null (never recorded) reads `! not recorded` and never closes an app, so a pre-column row or an out-of-band change is a warning until the next `status`. The gateway reads the column like the email columns, with no PRAGMA guard: the schema is this checkout's, and `setup` migrates before it uploads. Alternative: the app Worker self-reporting (follow-up below).
- [ ] **`status` records names.** Every `pnpm everyapp status` re-reads each deployed app's Worker and writes `secret_names`, so it is also the repair ("Already set it another way? `pnpm everyapp status` re-reads the Worker."). A failed `secrets list` is one `SETTINGS_UNKNOWN` warning with the rows unknown; `pending` apps and missing Workers are skipped. Alternative: a read-only `status`.
- [ ] **One command per app, with `--app <id>`.** `pnpm everyapp secret set <gateway names> <app names> --app <id>` (`--app` only when an app-held name is in it; an unmet any-of group contributes its first member, the alternatives in the note), shown by the gateway's dialog, `status`'s `APP_NEEDS_SETUP` and `deploy`'s next steps, the same string everywhere (`setupCommand` in the SDK). `secret set|unset --app` reads the app's manifest from its registry row so the command runs from anywhere, since a release deploy has no checkout. No new verb. Alternative: `everyapp setup-app <id>` prompting through the unmet list.
- [ ] **A shared app seen from another organization gets no command.** Its `setup` says what is unmet with `command: null`; the platform operator fixes it. Admins of the app's own organization get the command; other members get the same names with "Ask an admin to run:".
- [ ] **Dispatch-tier apps aren't gated at run time.** Their providers and capabilities ride the platform's settings, which the platform checks at deploy (follow-up: the hosted deploy API refusing a manifest whose required platform settings are unset); `setup` is null for them.
- [ ] **Public routes close with the app.** The gate runs for every path after the status and activation checks, public routes included (a tracker's `/collect` goes dark with its dashboards), so authors weigh `required` against the public surface. Alternative: public routes stay open and the app's code checks its own secrets.
- [ ] **A closed app: 302 to the launcher for a browser, a nameless 503 for everything else.** A private HTML GET navigation goes to `${GATEWAY_URL}/?setup=<appId>`, which opens the dialog; a public route, an API call or a non-GET answers `503 { "error": "app_needs_setup", "app" }` with no `retry-after` and never a setting name. The gateway's evaluation is cached per row, version and recorded names (500 entries), with freshness bounded by the 30 s hostname cache. The gateway's `/mcp` leaves the app's tools out and says why in the instructions; `everyapp_list_apps` carries `needsSetup`.

- [ ] **The gate runs before authentication.** One hook point, no names in the body, app ids are hostnames, Access in front hides it from strangers; the cost is that a visitor to a private route of an unready app gets the nameless 503 with the app id where they used to get the sign-in redirect. Alternative from the threat model (docs/threat-model.md B1): run the hook after authentication for private routes and before it for public ones.

### MCP surface (2026-10-24)

The code-mode research's concrete fixes to the gateway's `/mcp` ("Code mode and skills (2026-10-24)" above, design doc section 6), built overnight 2026-10-24/25 under the overnight rule as #499 (the listen hold), #501 (the instructions head), #503 (alwaysLoad), #504 (the drift test), #505 (client_info) and #516 (polish from the reviews). Each bullet is the default taken; yes keeps it.

- [ ] **The listen hold is per surface: 30 minutes on the gateway's connector, 10 on an app host** (#499) (`GATEWAY_LISTEN_MAX_MS`, `APP_LISTEN_MAX_MS` in `packages/toolbus/src/http.ts`; `listenMaxMs` on `ToolBusDeps` overrides both). Why 30 and not the design's 15: Claude Code 2.1.309 (read from its binary) keeps the time of every reopen in a trailing one-hour window and parks re-listening for about six hours once five are in it, whatever ended the stream; a 10-minute hold parks it after fifty minutes (six closes an hour), 15 leaves room for one unscheduled close an hour, 30 for two (a deploy, an evicted isolate, a token expiry) with two scheduled. Proven with `claude -p` against a local ToolBus (`packages/toolbus/claude-code/listen-reopen.claude.ts`, docs/TESTING.md): with the hold scaled to 60 s Claude Code reopens five times and goes deaf at the sixth close; with 30 minutes it is still reopening and hearing changes past ninety minutes. The app host keeps 10 because it rechecks nothing between requests (a longer hold would let a stream outlive a revoked token longer). Alternatives: 15 minutes as designed; one hour (one scheduled close, bounded by the token anyway); have the app-host surface recheck its token each poll and hold 30 too.
- [ ] **A held stream never outlives its credential** (#499)**.** The gateway passes the OAuth access token's `expiresAt` (`ctx.auth` from the resource server) or the Access assertion's `exp` as `listenUntil` on the view; a personal token needs none, since each poll resolves it again, expiry included. Before, a stream could run up to ten minutes past an expired token.
- [ ] **A failed poll keeps the stream** (#499)**.** A re-read that throws anything but `ViewRefusedError` (the gateway's recheck throws that for a revoked, removed, deactivated or suspended caller) counts as a transient failure: the stream stays open and pushes nothing, and ends after three in a row (`LISTEN_REFRESH_FAILURES_BEFORE_END`). Before, any failure ended it, which spent a reopen, and three failed reopens in a row (Claude Code's `uc` loop: 1 s, 2 s, 4 s) stop its re-listening until the person reconnects, so a ten-second D1 blip could silence a session. Alternative: fail closed as before.
- [ ] **The gateway instructions' head stays inside Claude Code's 4,096-character read** (#501): header, app list and the "not available" lines first, tested on the five launch apps (openseo, crm, analytics, agentic-inbox, dataforseo); if that test ever fails, shorten those lines, not the apps' guidance. Codex reads 512 characters, so an app's own guidance may fall past a client's cut. Alternative: cap the head in code by dropping app names from the list when it would overflow.
- [ ] **`_meta["anthropic/alwaysLoad"]: true` on both built-ins** (#503), so Claude Code (2.1.285 and later) keeps `everyapp_list_apps` and `everyapp_whoami` loaded ahead of its tool search; other clients ignore it; a person's server-level `alwaysLoad: false` wins. Alternative: leave them deferred.
- [ ] **`mcp_tool_calls.client_info`** (#505, migration 0007): the client's self-description from the MCP handshake, `<name> <version>` cut to 200 characters, from the 2026-07-28 per-request `clientInfo` or, for 2025-era clients, from `initialize` carried in the session id's middle part (`<uuid>.<base64url client>.<hash>`); shown on Admin → Activity beside the credential. Self-asserted, never verified; it is what makes "which clients call us" answerable for Access and token callers (the trigger for the compact surface). Alternatives: record nothing for 2025-era clients (no session-id carrier); a filter on Activity.
- [ ] **The docs drift test derives the built-in names from `listBuiltinTools()`** (#504, tightened in #516) (the agent page, the skill's `mcp.md` and the invariant `toolbus.builtins-readonly-reserved` must name every built-in), and the toolbus checks that the gateway instructions only name built-ins that exist.
- [ ] Follow-ups: the agent page's listen identifiers (`GATEWAY_LISTEN_MAX_MS`, `APP_LISTEN_MAX_MS`, `listenUntil`, `ViewRefusedError`) added to the drift test's list once #499 and #516 are both on main; the head of the instructions is not clipped in code (#501's review: 20 apps needing setup put it past 4,096, 40 past 8 KiB), decide whether to cap it; the live check against everyapp.team after the deploy (connect Claude Code, wait an hour, redeploy an app, see the refetch); a counter of held streams per isolate in the maintenance log; the app-host surface's recheck.
